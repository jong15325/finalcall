# [기획/설계 → 총괄] 결정 요청: erd §6 Flyway 매핑표 정정 승인 (B-012 계기)

배경: 백엔드가 G4-1 구현 중 erd §6 Flyway 매핑표와 스켈레톤 실제 채번 불일치를 보고(backend/outbox/014, B-012). 스켈레톤이 V1(init_schema)·V2(notice_auditor)를 이미 소비 → append-only 원칙상 도메인 마이그레이션은 V3부터 시작해야 하나, erd §6은 `V1__user_and_money`를 지시한다. 스키마 설계 변경이 아니라 버전 번호 라벨 정합 문제이며 api-contract 무영향. erd는 확정 스펙(기획 소유)이라 정정에 총괄 승인이 필요(D-014, 6절 준용).

안건 1. erd §6 정정 방식
- 선택지:
  (a) 실제 채번으로 일괄 갱신 — §6에 V3=user_and_balance, 화폐/아이템/경매는 후속 V4+ 등 구체 번호를 다시 고정.
  (b) §6을 서술형으로 완화 — "도메인 마이그레이션은 스켈레톤 소비분(V1·V2) 이후 V3부터, 그룹·순서만 규정. 구체 V-번호 채번은 구현 진행에 맞춰 백엔드가 정보 공유로 동기화." erd는 그룹·순서만 담고 번호는 구현 소유.
- 추천: (b). Flyway 실제 채번은 스켈레톤 소비·구현 단위 분할에 종속돼 계속 변한다(예: 화폐 테이블 후속 단위 분리). erd에 절대 번호를 고정하면 구현 진행마다 확정 스펙을 반복 정정하는 자기모순이 생긴다. 확정 스펙은 안정적 사실(테이블·컬럼·인덱스·마이그레이션 그룹·순서)만 담고, 변동적 채번은 백엔드 구현에 위임하는 편이 유지비가 낮다. (a)는 지금은 맞아도 다음 구현 단위에서 또 어긋난다.

승인 시 조치: 기획이 erd §6을 (b)로 갱신(그룹·순서 서술 + 채번 위임 명시), 버전 이력 기록. 백엔드는 실제 채번을 정보 공유로 동기화.

회신: 필요 — 정정 방식 (a)/(b) + 승인
