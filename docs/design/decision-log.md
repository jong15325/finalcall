# 기획/설계 결정 로그 (P-xxx)

협업 가이드(docs/management/collaboration-guide.md) 4절 티켓 규약(D-009~D-011)을 따른다.
- ID: P-<3자리>, 접두어별 독립 증가, 불변, 재사용·재번호 금지. 1결정=1번호.
- P-003~P-007: void(규약 이전 임시 사용, 인덱스 미등록·재사용 금지). 정식 신규 발번은 P-008부터. 상세: outbox/006, notes/topic-5.md.
- 상태 라벨: PROPOSED / ACCEPTED / ON-HOLD / SUPERSEDED(대체 ID 명시).
- 필드: ID · 제목 · 상태 · 소유역할 · 결정 · 이유 · 기각된 대안 · 관련(참조 ID) · 날짜.
- 참조 키워드: depends-on / relates-to / supersedes / escalated-as.
- 에스컬레이션 4기준에 걸린 사안은 총괄 로그(D-xxx)가 정본. 여기서는 "escalated-as D-xxx (ACCEPTED)" 참조만 남긴다(내용 중복 기록 금지).
- 총괄로 보내는 모든 프롬프트 끝에 "신규 발번 ID: ..." 1줄 첨부 → 마스터 인덱스(management/decision-index.md) 동기화.
- 이 로그 + 총괄 D-로그가 domain-spec.md 초안의 근거가 된다.
- 기존 P-001~002는 규약 이전 발번분. D-011 지시에 따라 상태 라벨·참조만 추가하고 내용은 소급 재작성하지 않음.

논의 순서: 판매 방식 모델링 → 입찰 규칙 → 생명주기/상태 전이 → 즉시구매·낙찰 동시성 → 아이템 도메인 → 사용자·거래 범위 → 마감 처리 방식

## P-001. 판매 방식 모델링 구조 (C안)

상태: ACCEPTED · 소유: 기획 · 관련: relates-to D-004, D-005, D-008 · 2026-07-12

결정
- 경매(영국식 + 즉시구매)와 고정가를 별도 애그리거트로 분리.
  - `Auction`: 영국식 경매. 즉시구매는 `buyNowPrice` 선택 속성.
  - `FixedSale`: 고정가. 입찰 개념 없음.
  - `Bid`는 경매에만 존재.
- 통합 피드용 공통 부모 `Listing` 도입 여부는 ERD 단계에서 재판단(보류).

이유
- 타입 1·2는 입찰·마감·낙찰 메커니즘 동일, 차이는 `buyNowPrice` 존재 여부뿐 → 분리 시 입찰 서브시스템 중복.
- 고정가는 Bid·시간 기반 낙찰이 없는 "재고 1개 원자적 선점" → 경매 통합 시 무의미한 nullable·조건 분기로 FSM 오염.
- 동시성 이점: buyNow 종료 = 고정가 구매와 동일한 원자적 선점 패턴 → 공통 정책 재사용.

기각된 대안
- A안(단일 Listing + saleType enum): nullable 대량, FSM 조건 분기 폭증.
- B안(3개 독립): 타입 1·2 입찰 로직 전면 중복.

## P-008. 입찰 홀드 해제 규칙

상태: ACCEPTED · 소유: 기획 · 관련: relates-to D-052 · 2026-07-13

결정: 상위 입찰 발생 시 직전 최고입찰자의 게임머니 홀드를 즉시 해제한다(마감 일괄 해제 아님).

주: 홀드·해제·차감 경합은 동시성 필수 케이스로 등재(D-052).

## P-009. 회원가입 "비밀번호 확인" 필드 — 포함(클라 검증 전용·서버 미전송)

상태: ACCEPTED · 소유: 기획 · 관련: relates-to ux/outbox/008 안건1, api-contract §2, 068(비밀번호 변경 제외) · 2026-07-14

결정
- 회원가입 폼에 "비밀번호 확인" 필드를 포함한다. 클라이언트 일치 검증 전용이며 서버로 전송하지 않는다. 계약 §2 signup body `{loginId, password, nickname}`는 불변(계약 무영향).

이유
- 비밀번호 변경·재설정이 이번 범위에서 제외됐다(068 총괄 지정, B-016 보안게이트2 이월). 즉 가입 시 오타로 굳은 비밀번호를 사용자가 스스로 복구할 경로가 현재 존재하지 않는다.
- 확인 필드는 계약 비용 0으로 그 리스크를 막는 가장 값싼 방어다. 자금 시스템이라 계정 접근 상실 비용이 크다.

기각된 대안
- 미포함: 관례상 생략도 가능하나, 복구 경로가 없는 현 상태에선 리스크 대비 이득이 없다.

## P-010. 회원가입 성공 후 플로우 — 로그인 화면 이동(자동 로그인 미채택)

상태: ACCEPTED · 소유: 기획 · 관련: relates-to ux/outbox/008 안건2, api-contract §2(signup·SEC-005), screen-spec §3.1 · 2026-07-14

결정
- signup 201 후 로그인 화면(`/login`)으로 이동한다. 자동 로그인하지 않는다. 가입 성공 안내 + loginId prefill로 재입력 부담을 줄인다.

이유
- 계약 signup 201 응답은 `{userPublicId, nickname}`으로 토큰이 없다. 자동 로그인은 계약 변경(signup이 토큰 반환) 또는 클라의 login 재호출을 요구한다.
- 계약 변경은 6절 비용에 더해 "가입 = 즉시 인증 세션 부여"로 보안 성격을 바꾸는 결정이라 자금 시스템에서 과하다.
- login 재호출은 계약 무영향이나, login·signup 모두 엣지 rate limit 대상(SEC-005·§1.6)이라 연속 호출이 버스트로 `GATEWAY_429`를 유발할 수 있다. 가입 직후 자동 로그인이 429로 실패하면 UX가 오히려 악화된다.

기각된 대안
- 계약 변경으로 signup 토큰 반환: 6절 비용 + 보안 성격 변경.
- signup 직후 login 재호출: rate limit 버스트 위험 + 불필요한 라운드트립.

## P-012. 아이템 이미지 슬롯 데이터 출처 — 프론트 정적 자산 매핑 (계약 무변경)

상태: ACCEPTED · 소유: 기획 · 관련: relates-to ux/outbox/010 안건1·012 정정3, domain-spec [7]·[7.4], api-contract [3.3], D-067, U-012·U-016 · 2026-07-14

집행: `docs/frontend-planning/screen-spec.md` [3.5] item — 반영 완료. 계약·domain-spec 무변경(개정 불요가 이 결정의 요지).

결정
- 아이템 카드 이미지는 **프론트가 계약 필드로 정적 자산 경로를 파생**해 렌더한다. 서버는 이미지 필드를 갖지 않는다.
- 경로 = `gold_black/level{level}/{l|s}/{element}/{kind}.png`. `gold_black`은 **고정 세그먼트**이며 `mainCategory`는 경로에 쓰이지 않는다.
- 소비 계약 필드 = `level` · `element` · `kind` 3개. 전부 [3.3] item 블록에 이미 존재한다.

이유
- 디자인 실측(012)에서 `gold_black` = 648 = **9레벨 × 2크기 × 4속성 × 9종류**다. 이 산술에 `mainCategory` 차원이 없다. `gold_black`이 mainCategory 값이라면 다른 값의 아이템 세트가 있어야 하는데 실측은 `silver`(캐릭터·이벤트)·`white`(속성·구매)가 아이템이 아니라고 확인했다. 따라서 경로는 mainCategory 없이 결정되며, 012가 "확정돼야 경로가 결정된다"고 본 매핑 확인은 **불요**다.
- 경로가 계약 필드만으로 완전히 결정되므로 서버가 시각 자산을 질 이유가 없다. domain-spec [7]("시각 자산 관리는 범위 밖")을 개정하지 않고, 계약 6절 절차도 불요하다.
- 되돌리기가 싸다 — 후에 서버 관리로 승격하면 [3.3]에 필드를 추가하면 된다(6절).

기각된 대안
- 계약 item 블록에 `imageUrl` 추가: 서버가 자산을 지게 되어 domain-spec [7] 개정 + 6절 동반. 실측상 이득이 없다.
- 이미지 없이 텍스트·아이콘: U-016(원게임 UI 스킨 전면 차용)·U-012 전제와 충돌.

주(D-048 경계): 시드 단계에서 아이템 대분류 값 도메인이 확정될 때 `gold_black` 외 세트(pet·avatar 등)가 아이템으로 편입되면 경로 규칙을 재검토한다. 그 편입 여부는 아이템 세부라 총괄 안건이다.

## P-013. 레벨 시각 표기 — 아트 위임하되 목록 판독성은 도메인 요구

상태: ACCEPTED · 소유: 기획 · 관련: relates-to ux/outbox/012 정정2, D-044(시세 집계 단위), erd [5] 인덱스, accessibility.md · 2026-07-14

집행: `docs/frontend-planning/screen-spec.md` [3.5] item — 반영 완료. 표현 방식은 디자인 소관(U-012).

결정
- 레벨의 **시각 표기는 원칙적으로 아트에 위임**한다(아트에 배지가 구워져 있어 웹이 별도 배지를 그리면 중복 표기가 된다).
- 단 **목록에서 레벨이 판독 가능해야 한다는 것은 도메인 요구**다. 목록 자산(`s`, 26×28)의 구운 배지로 판독이 불충분하면 계약 `level`로 표기한다. 판독 충족 여부 판정과 표기 방식은 디자인 소관.
- 계약 `level`은 표시 여부와 무관하게 필터·정렬·시세 키·접근성 대체텍스트에 사용한다.

이유
- 레벨은 시세 집계 단위의 축이고(D-044 조건, erd 인덱스 `(template_id, level, skill1_id, skill2_id)`) 공통 목록 필터의 축(`minLevel/maxLevel`)이다. **거래 의사결정의 1급 정보**이므로 목록에서 매물 간 비교가 불가능해지면 도메인 요구가 깨진다.
- 아트 위임을 전면 적용하면 26×28 자산에서 레벨 식별이 사실상 불가능해질 수 있다. 크기별로 갈리는 문제라 일괄 위임이 성립하지 않는다.
- 아트의 구운 배지는 원게임 폰트·언어라 확대 시 열화되고 스크린리더가 읽지 못한다 — 대체텍스트에 `level` 포함이 필수인 이유다(012 지적 수용).

기각된 대안
- 전면 아트 위임(웹 표기 0): 목록 판독성 상실 위험. 시세 축 정보가 목록에서 사라진다.
- 전면 웹 표기: 상세(`l` 3x)에서 아트의 구운 배지와 중복.
