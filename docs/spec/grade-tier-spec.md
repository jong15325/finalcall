## 0. 이 문서의 지위와 편집 규칙

- **정본이 아니다.** 아래 정본 파일들을 **참조만** 하고 수정하지 않는다: `fee-policy-spec.md`(수수료 산식·구간·cap), `erd.md`(스키마), `api-contract.md`(계약), (예정) `search-spec.md`(검색 랭킹).
- 수수료 할인·스키마·계약 필드는 **제안 절**(§4·§8·§9)에 담고, 동결 해제 시 정본 파일로 **통합**한다(동시 편집 회피).
- 모든 수치(적립 배수·구간 경계·수수료 계수·부스트폭)는 **초기 제안값**이며 **게이트2에서 확정**한다. 본문에 "보수/표준/공격" 3안을 병기하고 **표준을 권장**한다.
- **전제 확인 필요(§1 플래그)**: CLAUDE.md member의 "보유 잔액/포인트"가 **소진형 적립금**을 의도한 것인지 사용자 확인이 선행돼야 §8 스키마가 확정된다.

## 1. 개념 — 경험치형 포인트(소진 없음)

두 종류의 "포인트"를 구분한다. 본 설계는 **경험치형**을 채택한다.

| 구분 | 경험치형 포인트(본 설계) | 소진형 적립금(대안) |
|---|---|---|
| 성격 | 등급 산정 전용 누적 경험치(XP). **소진되지 않는다.** | 결제·구매에 쓰는 현금성 잔액. 쓰면 준다. |
| 화폐성 | **비현금성**. 게임머니(G)·캐시와 별개 축. | 현금성(게임머니 유사). |
| 감소 사유 | 취소·환불 롤백, 사기 몰수(§7)뿐. 정상 사용으로 줄지 않는다. | 사용 시 차감. |
| 등급 연동 | 누적 경험치가 등급 경계를 넘으면 승급. | 등급과 무관(별개 설계). |
| 근거 | RuneScape XP·항공 마일 status(적립≠소비 분리). 등급의 "장기 신뢰 신호" 성격에 정합. | 무신사 적립금·PayPal 캐시백. |

- **채택 = 경험치형.** 등급은 "얼마나 오래·많이 거래했는가"의 누적 신뢰 신호이며, 소비로 등급이 깎이면 신호가 왜곡된다.
- **★ 확인 필요(사용자 상신, §11)**: CLAUDE.md §1 member 정의 "회원 계정, **보유 잔액/포인트**"의 "포인트"가 **소진형 적립금**(현금성)을 의도한 것이라면, 그것은 본 등급 경험치와 **별개 축**이며 별도 설계(적립·소진·정산)가 필요하다. 현행 erd `user_balance`에는 `cash_balance`·`game_money_balance`·`game_money_held`만 있고 **포인트 컬럼이 없다**(미실현). 본 설계는 "포인트=등급 경험치"로 전제하되, 소진형 적립금을 별도로 원하는지 확인해야 §8 스키마 방향이 갈린다.

## 2. 적립 — 판매·구매 양쪽, 거래액 비례, 비대칭

거래가 **SOLD로 성립할 때**(sale_order 생성 시점, domain-spec §5) 판매자·구매자 **양쪽**에 경험치를 적립한다.

- **적립 기준액 = `sale_order.final_price`**(최종 확정가, fee-policy-spec §1과 동일 기준). 경매 낙찰가·즉시구매가·고정가 공통.
- **비대칭 배수(권장 = 표준)**:

  | 주체 | 적립 배수 | 산식(제안) |
  |---|---|---|
  | 판매자(seller) | **1.0×** | `points += floor(final_price × 1.0)` |
  | 구매자(buyer) | **0.5×** | `points += floor(final_price × 0.5)` |

  - 상수 **1 G(거래액) = 1 point(판매자)**. 구매자는 0.5 point/G.
  - 3안: 보수(판매 1.0 / 구매 0.25 — 판매자 중심 강화) · **표준(1.0 / 0.5)** · 공격(1.0 / 1.0 대칭 — 구매 유인 강화).
- **근거**: 양쪽 적립은 표준이나 **거의 항상 비대칭**이다(Uber 라이더/드라이버·Etsy 구매/판매). 순수 대칭은 추천 보상 한정(PayPal). 우리 플랫폼의 가치 창출·수수료 원천이 **판매자 공급**이므로 판매자에 가중한다.
- **적립 시점·원자성**: 적립은 SOLD 정산 TX(EPIC-CLOSING) **동일 트랜잭션 내**에서 `point_ledger` 기록 + `user.total_points` 증분으로 수행한다(정산·소유이전과 원자적). 실패 롤백 시 적립도 함께 롤백.
- **취소·유찰·만료는 적립 없음**: sale_order 미생성이므로 경험치도 없다(fee-policy-spec §5와 대칭).

## 3. 등급 구간 — 5단계, 지수 간격

- **단계 수 = 5(권장)**. 실무 범위 3~5의 상단이며 StockX(L1~5)·KREAM(5단계)과 동형. 티어형 로열티 ROI 근거(≈1.8배). 수수료 4구간(fee-policy-spec §2)과도 정합(§4).
- **경계 = 누적 경험치, 지수 간격(약 ×4~5)**. RuneScape 지수 커브·StockX 승급 간격(판매액 $1.5K→5K→25K→100K, ≈×3.3~5) 참조.

| 등급 | 코드 | 누적 경험치 경계(제안, pt) | 배지 색 | 근거 간격 |
|---|---|---|---|---|
| 브론즈 | `BRONZE` | 0 이상 | 브론즈 | 기본(신규) |
| 실버 | `SILVER` | 500,000 이상 | 실버 | — |
| 골드 | `GOLD` | 2,500,000 이상 | 골드 | ×5 |
| 플래티넘 | `PLATINUM` | 12,500,000 이상 | 플래티넘 | ×5 |
| 다이아몬드 | `DIAMOND` | 50,000,000 이상 | 다이아 | ×4 |

- **경계값은 제안(게이트2 확정)**이다. 1 G≈1 pt(판매자)라 실버는 대략 "중소 거래 수 건" 누적, 다이아는 "장기 대량 판매자" 수준으로 설계했다. 실 데이터(sale_order 분포)로 재보정한다.
- 3안: 보수(간격 ×3, 승급 빠름 — 상위 인플레) · **표준(×4~5)** · 공격(×6~7, 승급 희소 — 상위 프리미엄 강화).
- **현재 등급 = 파생값.** `total_points`와 경계표로 결정한다(§8은 조회 성능을 위해 `current_grade`를 비정규화 컬럼으로 캐시하는 안을 제안).
- **다음 등급까지 진행률**: `GET /me`가 현재 등급·누적·다음 경계까지 남은 pt를 노출한다(§9).

## 4. 혜택 ① 판매 수수료 할인 (fee-policy-spec 결합 — 제안 절)

> **이 절은 `fee-policy-spec.md`를 수정하지 않는다.** 결합 방식을 제안으로 기술하며, 동결 해제 시 fee-policy-spec으로 통합(게이트2). fee 계수 확정은 게이트2 대상(§9).

- **베이스 = fee-policy-spec §2 판매자 누진 6/5/4/3%** + 최소 100 G / cap 300,000 G. 등급 할인은 그 위에 얹는다.
- **결합 방식 = 등급 계수(−%p)를 전 구간 요율에 평행 인하**(marginal 구조 보존). 구간별 요율에서 계수를 빼고, 그 뒤 fee-policy-spec §3의 **반올림 → cap → 최소** 순서를 그대로 적용한다.

| 등급 | 수수료 계수(제안, −%p) | 유효 구간 요율(6/5/4/3 → ) |
|---|---|---|
| 브론즈 | 0 | 6 / 5 / 4 / 3 |
| 실버 | −0.25 | 5.75 / 4.75 / 3.75 / 2.75 |
| 골드 | −0.50 | 5.50 / 4.50 / 3.50 / 2.50 |
| 플래티넘 | −0.75 | 5.25 / 4.25 / 3.25 / 2.25 |
| 다이아몬드 | −1.00 | 5.00 / 4.00 / 3.00 / 2.00 |

- **스프레드 최대 1.0%p**(브론즈↔다이아). StockX 2%p와 KREAM 0.5%p의 중도. 3안: 보수(0.5%p 총폭) · **표준(1.0%p)** · 공격(2.0%p, StockX급).
- **cap 300,000 G·최소 100 G 유지**(fee-policy-spec §2). 등급 할인은 raw 누진합을 낮출 뿐 cap·최소 클램프는 불변.
- **제안 산식**(등급 g, 계수 `d_g` %p; 각 구간 요율은 0 미만으로 내려가지 않음 — 현행 값에선 미저촉):

  ```
  raw_fee_g(P) =
      (0.06 − d_g/100) × min(P, 100_000)
    + (0.05 − d_g/100) × clamp(P − 100_000,   0, 900_000)
    + (0.04 − d_g/100) × clamp(P − 1_000_000, 0, 2_000_000)
    + (0.03 − d_g/100) × max(P − 3_000_000, 0)
  → round(raw_fee_g) → min(·, 300_000) → max(·, 100)     // fee-policy-spec §3 순서 그대로
  ```

- **워크드 예시** — `P = 2,480,000 G`(fee-policy-spec §4.1 대표 예시와 동일 P):

  | 등급 | 구간 부분합(6→ / 5→ / 4→) | raw_fee | fee_amount | vs 브론즈 절감 |
  |---|---|---|---|---|
  | 브론즈 | 6,000 / 45,000 / 59,200 | 110,200 | **110,200** | — |
  | 골드(−0.5) | 5,500 / 40,500 / 51,800 | 97,800 | **97,800** | 12,400 |
  | 다이아(−1.0) | 5,000 / 36,000 / 44,400 | 85,400 | **85,400** | 24,800 |

  (100k 구간 폭 100,000, 900k 구간 폭 900,000, 4% 구간 적용폭 1,480,000. fee-policy-spec §4.1 분해와 동일 구조.)
- **적용 지점 = EPIC-CLOSING**. 수수료 계산기 호출 시 판매자 `current_grade`의 계수를 주입한다. **어느 시점 등급을 쓸지**는 게이트2 결정 항목: (a) SOLD 성립 시각의 등급(권장 — 정산 시점 스냅샷, 감사 명확) vs (b) 리스팅 등록 시각. **권장 = (a)** — 정산 TX에서 등급을 읽어 `sale_order`에 적용 계수를 스냅샷 기록(§8).

## 5. 혜택 ② 배지

- **등급 배지 = 신뢰 신호(UI 표시)**. 프로필·목록/상세의 판매자 표기에 등급 배지를 노출한다(§9 계약 필드).
- **랭킹 직접 영향 아님(Etsy식 선긋기, 권장)**. 배지는 표시 신호일 뿐 검색 순위 승수와 분리한다. 순위 부스트는 §6이 담당한다(관심사 분리 — 배지=신뢰 표시, 부스트=노출 가중).
- eBay Top Rated seal·네이버 우수판매자 배지·KREAM 등급 배지 참조. 마스킹 정책(api-contract §3.3 소유자·최고입찰자 마스킹)과 **충돌하지 않는다** — 배지는 등급(집계 신호)만 노출하고 개인 식별정보를 늘리지 않는다.

## 6. 혜택 ③ 우선노출 (검색 랭킹 부스트 — EPIC-SEARCH 결합, 제안)

> **정량 승수는 비공개로 운영한다(어뷰징 방지).** 아래는 설계 의도이며 실승수는 코드·설정에만 두고 문서·API로 공개하지 않는다.

- **비공개 가중**: 판매자 등급을 검색 랭킹 스코어의 **한 신호로만** 소폭 반영한다(단독 결정 요인 아님). 전 플랫폼(eBay Best Match·네이버·당근)이 정량 승수를 비공개로 두는 관행을 따른다.
- **부스트폭(제안) = 상위 등급 스코어 +10~15% 내외**, 신규·저등급 매물의 노출 기회를 유지하도록 상한을 둔다(콜드스타트·신규 판매자 보호). 3안: 보수(+5%) · **표준(+10~15%)** · 공격(+25% 이상 — 상위 독식 리스크).
- **구현 = EPIC-SEARCH의 검색 랭킹**. Elasticsearch `function_score`의 `field_value_factor`(`modifier: ln1p`, `mode: multiply`)로 판매자 등급 가중을 곱 신호로 합성하는 방식을 **제안**한다 — 로그 완충(ln1p)으로 상위 등급 독식을 억제.
  - **★ 주의(포워드 레퍼런스)**: 현재 `docs/spec/search-spec.md`는 **아직 존재하지 않으며** `EPIC-SEARCH`도 미신설이다. 위 `function_score`·`field_value_factor` 서술은 **본 문서가 제안하는 방향**이지 기존 계약 인용이 아니다. 검색 에픽 착수 시 search-spec에 정본화하고 본 절과 상호 참조를 건다(그때까지는 참조 대상 파일 부재 — §11 플래그).
- **어뷰징 가드**: 등급은 취소·환불 롤백(§7)으로 자정되며, 자전거래(wash trade)는 이미 SEC-003(판매자 자기구매/자기입찰 금지)로 차단된다 — 등급 부스트가 자전거래 유인을 새로 만들지 않는지 EPIC-SEARCH에서 재점검한다.

## 7. 회수·강등·유지

### 7.1 회수(롤백)
- **취소·환불 시 해당 거래 적립분 롤백**. 카드 리워드 reversal 표준. 정산 후 환불(fee-policy-spec §5 비례 크레딧)이 발생하면, 그 거래로 적립된 판매자·구매자 경험치를 **비례 차감**하고 `point_ledger`에 음(−) 원장 행을 기록한다(감사·재계산 가능).
- 롤백으로 등급 경계 아래로 내려가면 **즉시 강등 반영**(파생 재계산). 단 상위 등급 특권(진행 중 부스트 등)은 §7.2 유예를 따른다.

### 7.2 강등 — Soft Landing
- **사기·제재 시 적립 몰수 + 강등**하되, **한 번에 최하위로 떨어뜨리지 않는다** — **한 단계씩·유예 기간**을 둔다(Marriott Soft Landing). 예: 제재 확정 시 1단계 강등 + N일 관찰, 재발 시 추가 강등.
- 몰수는 `point_ledger`에 사유 코드(FRAUD/SANCTION)와 함께 음 원장으로 남긴다(불투명 삭제 금지 — 재심·감사).

### 7.3 유지 — 이중 트랙
- **하위 등급 = 평생 누적 기본**. 한 번 쌓은 경험치는 정상적으로 유지된다(항공 마일 status 하한 개념).
- **상위 등급(예: 플래티넘·다이아몬드)은 최근 12개월 활동 조건 이중 트랙**. 평생 누적으로 진입하되 상위 특권 유지에는 최근 12개월 거래 활동을 요구한다(British Airways·무신사 12개월). 미충족 시 §7.2 Soft Landing으로 한 단계 하향.
- **적용 경계·유예 기간·활동 기준(건수/금액)은 게이트2 확정 항목**(초기 제안: 최근 12개월 판매 성립 ≥ K건 또는 ≥ M G — 값 미정).

## 8. 스키마 제안 (게이트2 — erd 미수정, 제안만)

> **erd.md를 수정하지 않는다.** 아래는 제안 컬럼/테이블이며 동결 해제 시 게이트2 승인 후 erd 통합·Flyway 채번한다.

### 8.1 `user` 확장(제안)
| 컬럼(제안) | 타입 | 널 | 설명 |
|---|---|---|---|
| `total_points` | BIGINT | N(기본 0) | 누적 경험치(소진 없음). 적립·롤백의 합. `point_ledger` 합계와 정합해야 함 |
| `current_grade` | ENUM | N(기본 BRONZE) | 파생값의 **비정규화 캐시**(조회 성능·§9 응답). `total_points` + 경계표로 재계산 가능 |
| `grade_since_at` | DATETIME(6) | Y | 현재 등급 진입 시각(상위 등급 12개월 활동 트랙 기준) |

- **대안(정규화)**: `current_grade`를 두지 않고 매 조회 시 파생. 목록/상세에서 판매자 등급 배지를 매번 계산하는 비용을 고려해 **비정규화 캐시 권장**. 정합은 적립 TX에서 재계산.
- **`user_balance`에는 넣지 않는다** — 경험치는 화폐(잔액)가 아니라 `user` 속성이다(§1 경험치형). 소진형 적립금을 별도로 도입한다면 그때 `user_balance`에 포인트 잔액 컬럼을 검토(§1 ★ 확인 필요와 연동).

### 8.2 `point_ledger` 신규 테이블(제안 — 이력 원장)
감사·재계산·롤백을 위한 **append-only 원장**. `total_points`는 이 원장의 합으로 검증 가능해야 한다.

| 컬럼(제안) | 타입 | 널 | 설명 |
|---|---|---|---|
| `id` | BIGINT PK | N | |
| `public_id` | ULID | N UK | 외부 식별자(B-004) |
| `user_id` | BIGINT | N FK→user | 대상 회원 |
| `delta` | BIGINT | N | 증감(적립 +, 롤백·몰수 −) |
| `balance_after` | BIGINT | N | 적용 후 누적(재계산 앵커) |
| `reason` | ENUM | N | EARN_SELL / EARN_BUY / ROLLBACK_REFUND / FORFEIT_FRAUD / FORFEIT_SANCTION / ADJUST |
| `sale_order_id` | BIGINT | Y FK→sale_order | 거래 적립·롤백일 때 연계(감사 추적) |
| `created_at` | DATETIME(6) | N | |

- 인덱스(제안): `(user_id, created_at)` 원장 조회, `(sale_order_id)` 거래 역참조.
- **정산 결합(EPIC-CLOSING)**: SOLD 정산 TX에서 (1) 수수료 계산에 판매자 등급 계수 주입(§4), (2) 판매자·구매자 `point_ledger` EARN 행 + `user.total_points` 증분 + `current_grade` 재계산을 **동일 TX**로 수행. 환불·크레딧 발생 시 ROLLBACK 행.
- **`sale_order` 확장(선택 제안)**: 적용 등급 계수를 스냅샷하려면 `applied_fee_grade`(ENUM)·`applied_fee_coefficient`(DECIMAL) 컬럼 추가 검토(§4 (a)안 감사 명확성). 게이트2 결정.

## 9. 계약 파급 (게이트2 — api-contract 미수정, 제안만)

> **api-contract.md를 수정하지 않는다.** 아래는 계약 변경 제안이며 게이트2 승인 후 반영.

- **`GET /api/v1/me` 응답 확장(§2.5)**: 현행 `{ userPublicId, nickname, isAdmin, createdAt }` →
  `{ ..., grade, totalPoints, nextGrade?, pointsToNextGrade? }` 추가.
  - `grade`(ENUM 문자열), `totalPoints`(integer), `nextGrade`(다음 등급 코드, 다이아면 null), `pointsToNextGrade`(다음 경계까지 남은 pt, 다이아면 null).
- **목록/상세 판매자 등급 배지 필드(§3.3)**: 경매·고정가 요약/상세 응답에 **판매자 등급 배지** 필드 추가(예: `sellerGrade`). 현행 응답은 소유자·판매자를 마스킹하므로(§3.3), **개인 식별정보를 늘리지 않는 집계 신호(등급 코드)만** 노출한다 — 마스킹 정책과 양립(§5).
  - ★ 현재 목록/상세 `item` 블록에는 판매자 필드가 없다(마스킹). `sellerGrade`는 요약 최상위 레벨에 두는 것을 제안(배지 UI용). 신규 노출면이므로 열거 리스크(SEC-007) 재점검 필요 — 등급은 이미 저·중 카디널리티라 개별 식별로 이어지지 않음.
- **회원 등급·포인트 조회는 `GET /me` 한정**. 타인 프로필/등급 직접 조회 엔드포인트는 도입하지 않는다(api-contract §2.5 타인 조회 미도입 원칙 유지). 목록/상세의 `sellerGrade`가 타 회원 등급 노출의 유일 경로다.
- **에러코드**: 등급 제도는 조회·자동 적립이라 신규 사용자 대면 에러코드는 없다(적립 실패는 정산 TX 롤백으로 흡수). 관리자 몰수/조정 API를 도입하면 별도 계약(게이트2).

## 10. 소유 에픽·연결

- **소유 에픽 = EPIC-GRADE**(member 확장, 미착수). 게이트1 방향 승인 완료, **게이트2(스키마·fee 계수·계약 필드) 대기**, **백엔드 동결이라 설계만**.
- **EPIC-CLOSING 연결**: 적립·수수료 할인의 **실행 지점**. SOLD 정산 TX에서 (§4 수수료 계수 주입) + (§8.2 point_ledger 적립·롤백). fee-policy-spec §7 구현 시 등급 계수 훅을 남긴다.
- **EPIC-SEARCH 연결(미신설)**: 우선노출(§6)의 실행 지점. search-spec 정본화 시 등급 부스트 신호를 `function_score`로 합성.
- **선행 의존**: EPIC-GRADE 구현은 EPIC-CLOSING(정산 TX 존재)과 **동시 또는 이후**여야 적립 훅을 걸 수 있다. 순수 조회·스키마(§8)는 선행 가능하나 적립 로직은 정산에 의존.

## 11. 요약 — 게이트2 항목·확인 필요·연결점

### 11.1 게이트2 상신 항목(값·구조 확정 대상)
1. **적립 배수**(§2): 판매 1.0 / 구매 0.5 및 1 G=1 pt 상수 — 확정.
2. **등급 단계 수·경계**(§3): 5단계, 지수 경계(500k/2.5M/12.5M/50M pt 제안) — 실데이터 재보정.
3. **수수료 계수**(§4): 실버 −0.25 / 골드 −0.5 / 플래 −0.75 / 다이아 −1.0 %p, 스프레드 1.0%p — fee-policy-spec 통합 대상.
4. **수수료 적용 등급 시점**(§4): (a) SOLD 시각 스냅샷 권장 vs (b) 리스팅 시각.
5. **우선노출 부스트폭**(§6): +10~15% 비공개 가중 — EPIC-SEARCH에서 확정.
6. **회수·강등·유지 파라미터**(§7): Soft Landing 유예 기간·상위 등급 12개월 활동 기준(건수/금액).
7. **스키마**(§8): `user`에 `total_points`·`current_grade`·`grade_since_at` + `point_ledger` 신규 테이블 (+ `sale_order` 등급 계수 스냅샷 선택) — erd 통합·Flyway 채번.
8. **계약 필드**(§9): `GET /me` 등급·누적·진행 필드 + 목록/상세 `sellerGrade` 배지 필드 — api-contract 통합.

### 11.2 사용자 확인 필요(설계 방향 전제)
- **★ 포인트 성격**(§1): CLAUDE.md member "보유 잔액/포인트"의 "포인트"가 **소진형 적립금**을 의도했는지 확인. 본 설계는 **경험치형(비현금성)** 전제. 소진형을 별도로 원하면 별개 축 설계가 추가된다(현행 `user_balance`에 포인트 잔액 컬럼 없음 — 미실현).

### 11.3 연결점
- **fee-policy-spec**: §4가 베이스 6/5/4/3%·cap 300,000·최소 100에 등급 계수를 얹는다. **fee-policy-spec은 이번에 무수정**, 동결 해제 시 §4를 통합.
- **EPIC-CLOSING**: 적립(point_ledger)·수수료 할인의 실행 지점. 정산 TX 동일 트랜잭션.
- **EPIC-SEARCH(미신설)·search-spec(부재)**: 우선노출(§6)의 실행 지점. **현재 파일·에픽이 없어** 포워드 레퍼런스로만 기술 — 검색 에픽 착수 시 상호 참조 확립.
