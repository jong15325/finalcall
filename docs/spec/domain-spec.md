## 1. 개요

FinalCall은 게임 아이템을 등록·거래하는 경매 플랫폼이다. 핵심 기술 도전은 마감 직전 입찰 폭주와 즉시구매·낙찰의 중복 처리 방지 등 동시성 제어다.

판매 방식은 3종이며 두 개의 애그리거트로 모델링한다(근거 P-001). 영국식 경매와 즉시구매는 하나의 경매(Auction)로 통합하고 즉시구매는 선택 속성으로 표현하며, 고정가 판매는 별도 애그리거트(FixedSale)로 분리한다. 설계의 이음새는 "판매 방식 3종"이 아니라 "입찰이 있는가(경매) / 없는가(고정가)"이다.

## 2. 용어 정의 (D-034)

이 스펙이 도메인 용어의 정본이며 별도 용어집을 두지 않는다.

- Auction(경매): 영국식 경매 애그리거트. 시작가에서 입찰 경쟁 후 마감 시 최고가 낙찰. 즉시구매가(buyNowPrice)가 설정되면 즉시구매 가능 경매가 된다.
- FixedSale(고정가): 입찰 없이 정가로 구매하는 판매 애그리거트.
- Bid(입찰): 경매에 대한 입찰 기록. 경매에만 존재한다.
- startPrice(시작가): 경매의 최초 입찰 하한.
- buyNowPrice(즉시구매가): 경매를 즉시 종료시키는 구매 가격. 선택 속성.
- 소프트 클로즈: 마감 직전 유효 입찰 시 마감 시각을 연장하는 anti-sniping 정책.
- 경매 상태(status): SCHEDULED / ACTIVE / SOLD / UNSOLD / CANCELLED.
- resultType: SOLD의 성립 사유 — BID(마감 낙찰) 또는 BUYNOW(즉시구매).
- 고정가 상태: ACTIVE / SOLD / EXPIRED / CANCELLED.
- Order(주문): 판매 성립(SOLD) 시 생성되는 거래 애그리거트. 결제·정산·전달의 후속 관심사를 담당한다.
- 캐시: 외부 결제(토스페이먼츠 테스트 API)로 충전하는 화폐. 충전 도메인이 관리한다.
- 게임머니: 캐시를 교환해 얻는 내부 화폐. 거래·입찰·정산은 전부 게임머니로 이뤄진다.
- 홀드(에스크로): 입찰 시 입찰자의 게임머니를 잠그는 것. 지불능력을 보장한다.
- item_template(아이템 정의 마스터): 표준화된 아이템 정의. 인스턴스가 참조하는 마스터. (상세 소절 7)
- 인스턴스: 매물이 보유하는 개별 아이템 상태(레벨·특수스킬 등). (상세 소절 7)
- 지연 인덱스: 시각 기반 상태 전이(마감·예약시작·만료)를 재예약 가능하게 관리하는 마감 처리 구조.
- CAS(조건부 원자 갱신): compare-and-set. 상태 전이의 단일 승자를 보장하는 조건부 UPDATE.

## 3. 판매 방식 (P-001, P-002)

경매(Auction)와 고정가(FixedSale)를 별도 애그리거트로 둔다. 영국식 경매와 즉시구매는 입찰·마감·낙찰 메커니즘이 동일하고 차이는 buyNowPrice의 존재 여부뿐이므로, 즉시구매를 경매의 선택 속성으로 흡수해 입찰 서브시스템의 중복을 없앤다. 고정가는 입찰이 없고 시간 기반 낙찰이 없는 "재고 1개의 원자적 선점" 구매이므로, 경매에 통합하면 무의미한 nullable과 조건 분기로 상태 머신이 오염된다.

Bid는 경매에만 존재한다. 통합 피드용 공통 부모(Listing)의 도입 여부는 ERD 단계에서 재판단한다(보류).

제약: 등록 시점에 `buyNowPrice > startPrice`. 같거나 낮으면 입찰할 이유가 없어 경매가 성립하지 않는다.

## 4. 입찰 규칙 (D-004, P-008)

최소 입찰 단위는 계단식(가격 구간별 증분)이다. 게임 아이템의 가격대가 넓어 단일 증분이 부적합하기 때문이다. 초기에는 설정(코드/구성) 기반으로 두고, 운영 중 실제 조정 요구가 생기면 DB 정책 테이블로 승격한다(ERD에는 정책 테이블을 넣지 않는다). 검증식은 `신규입찰 >= 현재 최고가 + 해당 구간 증분`이다.

판매자의 자기 경매 입찰과 최고가 보유자의 연속 입찰을 모두 금지한다(shill bidding 및 자기 가격 인상 방지). proxy(자동) 입찰은 이번 범위에서 제외한다.

소프트 클로즈를 도입한다. 마감 직전 트리거 윈도우(기본 T-30초) 내 유효 입찰이 발생하면 마감을 연장(기본 +30초)한다. 트리거 윈도우와 연장폭은 경매별 설정형이며, 총연장상한은 필수다(상한 없는 연장 금지 — 마감 자원이 무한히 고이는 것을 방지). 이 정책으로 마감 시각이 동적으로 변하며, 마감 처리(9절)는 재예약 가능한 구조여야 한다.

즉시구매가와 입찰의 상호작용은 "최고가 < buyNowPrice인 동안 즉시구매 유지" 방식이다. 입찰 상한을 buyNowPrice 미만으로 제약하여 입찰이 즉시구매가에 도달할 수 없게 하고, 즉시구매는 항상 유효하도록 한다. 즉시구매가는 그 경매의 상한선이라는 의미가 된다.

입찰 시 입찰자의 게임머니를 홀드(에스크로)한다(6절). 상위 입찰이 발생하면 직전 최고입찰자의 홀드를 즉시 해제한다(P-008). 마감 일괄 해제가 아니라 즉시 해제인 이유는, 밀린 입찰의 홀드가 누적돼 사용자 잔액이 장시간 묶이는 것을 막기 위함이다.

## 5. 경매·고정가 생명주기와 상태 전이 (D-005)

경매(Auction) 상태 머신:

```
SCHEDULED --(startAt 도달)--> ACTIVE
ACTIVE --(마감 & 유효 입찰 존재)--> SOLD (resultType=BID)
ACTIVE --(즉시구매 실행)---------> SOLD (resultType=BUYNOW)
ACTIVE --(마감 & 입찰 없음)------> UNSOLD (유찰)
SCHEDULED | ACTIVE --(취소)------> CANCELLED
SOLD / UNSOLD / CANCELLED = 종료(terminal)
```

예약 시작(SCHEDULED)을 지원한다. 소프트 클로즈용 지연 처리 인프라에 얹으므로 한계비용이 작다. 고정가(FixedSale)에는 SCHEDULED가 없다(비대칭 허용, 필요 시 확장).

종료 상태는 status(SOLD/UNSOLD/CANCELLED)와 resultType(BID/BUYNOW)을 분리해 표현한다. status는 상태 머신·쿼리의 축이고 낙찰 사유는 메타데이터이므로, enum 폭발을 피하고 FSM을 작게 유지한다.

취소 허용 조건: 판매자 취소는 **"입찰 0건 & (SCHEDULED | ACTIVE)"** 일 때만 가능하다. 입찰이 하나라도 있으면 판매자 취소는 불가하다(입찰자 신뢰 보호). 관리자 강제 취소는 상태와 무관한 별도 권한으로 정책 위반 등에 대응한다.

주(정정 2026-07-18, EPIC-AUCTION 게이트2 G6 · api-contract v1.7): 이 문단은 v0.5까지 "진행 중(ACTIVE)"으로만 적어 위 상태 머신의 `SCHEDULED | ACTIVE --(취소)--> CANCELLED`와 어긋났고, 예약 경매(SCHEDULED)의 에스크로 아이템이 startAt 도달 전까지 회수 불가한 문제가 있었다. 취소 대상 상태를 SCHEDULED|ACTIVE로 정밀화해 상태 머신과 계약에 정합시킨다. "입찰 0건" 판정 앵커는 `auction.highest_bidder_id IS NULL`이다(auction-domain-spec §9-e).

경매 FSM은 판매 성립 결정(SOLD)까지만 담당한다. 결제·정산·전달은 별도 Order 애그리거트로 핸드오프하며 SOLD 진입 시 Order를 생성한다. 결제·배송 상태를 경매에 섞으면 FSM이 비대해지고 관심사가 혼재하기 때문이다.

고정가(FixedSale) 상태 머신:

```
ACTIVE --(구매 성립)--> SOLD
ACTIVE --(기한 만료)--> EXPIRED   (endAt 설정 시)
ACTIVE --(취소)-------> CANCELLED
```

고정가는 선택적 판매 기한(endAt)을 가진다. 설정 시 만료하면 EXPIRED, 없으면 무기한 판매중이다. 고정가의 SOLD도 경매 SOLD와 동일하게 Order로 핸드오프한다(구매 경로 단일화).

고정가 판매자 취소는 구매 성립(SOLD) 전, 즉 ACTIVE 상태에서만 가능하다. 고정가는 입찰 개념이 없으므로 경매의 "입찰 0건" 제약에 대응하는 조건은 "아직 판매되지 않음"이다. 관리자 강제 취소는 경매와 동일하게 상태와 무관한 별도 권한이다.

유찰(UNSOLD) 후 재등록은 별도 플로우를 두지 않으며 신규 등록으로 처리한다(범위 절단).

## 6. 사용자와 거래 범위 (D-050~053)

사용자는 단일 User로 모델링한다. 한 사용자가 등록·입찰·구매를 모두 하는 C2C 거래소이므로 역할은 행위 기반(등록자=판매자, 입찰/구매자=구매자)이면 충분하고, 관리자는 권한 플래그로 구분한다. 판매자/구매자 역할 엔티티 분리는 과설계다. 사용자 식별은 JWT 스켈레톤이 보장한다.

화폐는 2단 모델이다.

- 캐시: 외부 결제(토스페이먼츠 테스트 결제 API)로 충전한다. 충전은 별도의 충전 도메인으로 다루며 콜백 검증과 멱등키를 갖춘다. 충전은 거래 트랜잭션과 분리되며, 거래 트랜잭션에 외부 연동을 엮지 않는다(D-053).
- 게임머니: 캐시를 교환해 얻는 내부 화폐다. 교환 비율은 파라미터화하고 추적 표에 등재한다. 거래·입찰·정산은 전부 게임머니로 이뤄진다.

역방향 환전(게임머니→캐시)과 환불은 범위 밖으로 절단한다.

충전/교환 플로우: 캐시 충전(외부 콜백·멱등) → 캐시↔게임머니 교환 → 게임머니로 거래.

입찰 시 게임머니를 홀드(에스크로)한다. 낙찰 시 최고입찰자의 홀드를 차감으로 확정하고 나머지 입찰자의 홀드를 해제한다. 상위 입찰 발생 시 직전 최고입찰자의 홀드는 즉시 해제한다(P-008, 4절).

### 6.1 회원 계정 관리 (D-080, 069)

계정 생애주기 중 가입·인증은 auth가 담당하고(api-contract 2절), 이 소절은 그 나머지 — 프로필·닉네임 변경·탈퇴의 **도메인 규칙**을 규정한다. 비밀번호 변경은 범위 밖이다(12절 — auth·보안 성격이라 별도 안건).

**프로필 조회**: 회원은 자신의 계정 정보(외부 식별자·표시명·가입 시각·관리자 여부)를 조회한다. **타인 프로필 조회는 두지 않는다.** 목록·상세에서 소유자·최고입찰자를 마스킹하는 정책과 정면으로 상충하기 때문이다 — 마스킹해 가려놓고 프로필 조회를 열면 마스킹이 무의미해지고, 회원 열거 노출면(SEC-007)만 넓어진다.

**닉네임 변경**: 허용하며 **변경 빈도를 제한하지 않는다**. 표시명은 목록·상세에서 마스킹되어 노출되므로 사칭·평판 세탁 리스크가 낮고, 빈도 제한은 변경 시각 보존(스키마 추가)을 요구해 이번 범위 대비 이득이 작다. 필요가 관측되면 후속 확장한다. 닉네임은 유일하며 중복 시 변경을 거부한다.

**가용성 조회(라이브 중복확인, EPIC-NICKNAME-UX)**: 회원가입 폼이 제출 전 닉네임 사용 가능 여부를 조회할 수 있다(계약 §2 `GET /api/v1/auth/nickname/availability`). 가용성 판정은 가입·변경의 유니크 검사와 **동일한 비교**(`existsByNicknameAndIsDeletedFalse`, `nickname_active` UK 기준)를 단일 경로로 사용해 조회 결과와 실제 가입 결과가 드리프트하지 않게 한다. 이 조회는 **예약이 아니라 스냅샷**이다 — 조회~제출 사이 선점(TOCTOU)이 가능하므로 유일성의 최종 권위는 제출 시 유니크 검사(가입 `AUTH_002`·변경 `MEMBER_001`)에 있다. 유니크 제약·검사 로직 자체는 무변경(FC-159 결정 B)이며 조회 경로만 추가한다.

**소셜 최초가입 닉네임 부여(EPIC-NICKNAME-UX)**: 카카오·네이버 최초가입 시(계약 §2 소셜 로그인) 닉네임을 **provider 표시명(스템) + 항상 무작위 꼬리표**로 자동 부여한다. 규칙:
- *스템*: provider 표시명을 정규화(trim, 비면 대체 기본값 `user`)하고, 꼬리표 폭(`_XXXX` = 5자)을 뺀 길이(≤ 25자)로 절단해 총 길이가 erd `nickname` VARCHAR(30) 이내가 되게 한다.
- *꼬리표*: 무작위 4자 영숫자를 **항상 부착**한다(순차 아님 — 열거·경합 회피). 종전 "UK 충돌 시에만 접미사"에서 **항상 부여**로 개정한다 — 소셜 표시명은 흔해 충돌·사칭 소지가 크므로 최초가입부터 유일 핸들을 부여해 가입 흐름을 단순화한다.
- *충돌 재시도*: 꼬리표 부착 후에도 `nickname_active` UK 충돌 시 새 꼬리표로 재시도한다(최대 N회, 관례상 10회). 무작위 공간(36^4 ≈ 168만)에서 연속 충돌은 사실상 불가하며, 초과 시 깨진 불변식으로 처리한다(재생성·기본값).
- *사후 변경*: 부여 후 회원이 `PATCH /me`로 자유롭게 변경할 수 있다(빈도 제한 없음, 위).
- 유니크 제약·검사 로직은 무변경(FC-159 결정 B) — 부여 방식만 손대며 소셜 로그인 응답 형상(`LoginResponse`)은 불변이다.

**탈퇴**: soft delete로 처리한다. 아래 규칙이 함께 적용된다.

- *잔액*: 잔존 캐시·게임머니가 있어도 **탈퇴를 허용**하되, 탈퇴 확인 단계에서 **소멸·복구 불가에 명시 동의**를 받는다(D-080). 환불·역방향 환전은 범위 밖(12절)이다. 이 결정은 토스 테스트 결제 전제에 종속하며, 실결제를 도입하면 재검토한다(캐시는 선불전자지급수단 성격상 환불 의무가 따른다).
- *진행 중 거래*: 진행 중 경매(판매자)·홀드를 보유한 입찰·미완료 주문이 **하나라도 있으면 탈퇴를 차단**한다. 사용자는 거래를 종료·정리한 뒤 탈퇴한다.
  - 잔액과 진행 중 거래에서 정책이 갈리는 이유는 **피해 귀속의 비대칭**이다. 잔액 소멸은 본인 손실이라 동의로 해소되지만, 진행 중 거래를 일방 탈퇴로 깨면 **거래 상대**가 피해를 입는다. 동의로 처분할 수 있는 것은 자기 몫뿐이다.
- *세션*: 탈퇴 시 refresh 세션을 전부 폐기한다(SEC-006 정합).
- *과거 거래 이력*: 보존한다. 상대방의 거래 이력이 타인의 탈퇴로 사라지면 안 된다. 탈퇴 회원의 표시명은 마스킹한다(3.3 마스킹 정책의 연장).
- *재가입*: login_id·nickname **재사용을 허용**한다. soft delete 테이블의 자연키 유니크가 삭제 식별 컬럼을 포함해(erd 1절 규약) 탈퇴행이 신규 가입을 막지 않으며, 이는 "삭제행-신규행 충돌 회피"라는 설계 의도 그대로다. 과거 이력은 별도 회원 행에 마스킹된 채 남아 데이터가 혼입되지 않는다.

## 7. 아이템 도메인 (D-044~047, D-062)

이 소절은 D-048(아이템 도메인 자율 예외)에 따라 목차·서술 방향을 총괄 안건으로 확정한 뒤 작성했다(outbox/012 → D-062). 서술 깊이는 개념·규칙 계층으로 한정한다. 구체 taxonomy 멤버(대분류·종류·속성의 실제 값), 특수스킬 목록, 명칭·수치는 ERD/시드 단계에서 확정한다(D-062 안건1). 시드는 원게임(SurvivalProject)의 실제 명칭·수치·코드를 사용한다(D-067 — IP 회피 조항 삭제).

### 7.1 개념

아이템 도메인은 표준 정의(item_template)와 개별 매물이 보유한 인스턴스 상태를 분리한다. 템플릿은 중앙에서 시드로 관리하는 유한한 마스터이고, 인스턴스는 그 템플릿을 참조하면서 레벨·특수스킬 같은 개별 변이를 정형 컬럼으로 보유한다. JSON 등 비정형 속성 계층은 두지 않는다. 템플릿 공간이 유한(수백 미만)하고 인스턴스 변이가 정형이라 비정형 계층이 불필요하며, 정형 컬럼이라야 검색·시세 집계가 전부 인덱스로 처리되기 때문이다(D-044).

이 도메인의 핵심 성질은 "동일 템플릿, 다른 가치"다. 같은 아이템 정의라도 레벨·특수스킬 조합에 따라 시세가 갈린다. 이를 검색 필터와 시세 집계 축으로 표현한다(7.7).

### 7.2 카테고리 계층

분류는 얕은 2단 계층(대분류 → 종류)이다(D-044). 유한한 템플릿 공간에 깊은 트리는 탐색·유지 비용만 키우므로 두지 않는다. 아이템의 정체성은 종류 × 속성의 조합으로 표현한다(D-073 — 등급 축은 제거. 원게임에 등급/희귀도 개념이 없고 아이템은 레벨+타입으로만 구분된다). 구체 분류 멤버(대분류·종류 목록, 속성 값 집합)는 ERD/시드에서 확정한다(D-062 안건1). 개념 수준의 규모는 종류·속성 조합에 특수 유형을 더해 수백 미만이며, 이 유한성이 마스터 시드로 채울 수 있다는 정형화 근거다.

예시(구조): 종류(검·도·활 등) × 속성(물·불·흙·바람) 조합에 마법·펫·아바타류 특수 유형. 실제 멤버·수치는 원게임 데이터로 시드 단계에서 확정한다.

### 7.3 인스턴스 속성

매물이 보유하는 개별 상태는 정형 컬럼으로 표현한다. 확정된 변이 축은 세 가지다(D-066). 첫째 레벨 — 인스턴스의 현재 상태 값이다. 둘째 특수스킬 2슬롯 — 각 슬롯은 스킬 정의를 참조하며, 스킬 자체의 발동확률(합성 결과로 정해지는 값)을 함께 가진다. 셋째 골드포스 — 아이템 자체 발동확률의 시간제 상태로, 만료 시각을 보유하며 활성 여부·잔여 시간은 현재 시각 대비 파생값이다. 골드포스의 발동확률은 스킬 발동확률과 별개다.

강화·합성 같은 상태 변경 "행위", 그리고 착용·세트 조합에 따른 발동확률 계산은 범위 밖이며(D-046, §7.6), 레벨·골드포스는 등록 시점에 주어진 현재 상태 값으로만 취급한다. 슬롯 수(2)와 슬롯 구조는 정형 고정이고, 구체 스킬 정의 목록·수치 범위·타입 체계는 ERD에서 확정한다(D-062, D-066).

초안(미확정, 확정은 ERD): 레벨 1~9, 특수스킬 슬롯1·슬롯2(각 스킬 정의 참조) + 스킬 발동확률, 골드포스 만료 시각.

### 7.4 매물-템플릿 관계·표시 스냅샷

매물(경매·고정가의 판매 대상)은 item_template을 FK로 참조하고, 7.3의 인스턴스 속성을 자신의 정형 컬럼으로 보유한다. 여기에 더해 등록 시점의 표시 필드(예: 표시명, 핵심 스펙 요약)를 스냅샷으로 보존한다(D-045). 스냅샷을 두는 이유는 이력 정합이다. 템플릿 시드가 이후 수정·개편돼도 과거 매물과 거래 이력의 표시는 등록 당시 상태로 고정돼야 한다. 즉 현재 값은 템플릿 참조로, 과거 표시는 스냅샷으로 이원화한다. 기존 P-007의 "스냅샷 단독" 초안은 void이며 마스터 참조 모델로 대체됐다.

### 7.5 시드 정책

item_template은 고정 시드 세트로 채우며 운영/마이그레이션(Flyway)으로 관리한다(D-047). 판매자가 새 템플릿을 제안·승인받는 플로우는 두지 않는다. 템플릿 공간이 유한해 사전 시드로 충분하고, 사용자 생성 템플릿은 정합·중복·검수 비용을 초래하기 때문이다. 시드는 원게임(SurvivalProject)의 실제 명칭·수치·데이터·코드를 사용한다(D-067). 구체 멤버·값의 확정은 ERD 시드(Flyway) 단계에서 한다(D-062·D-066).

예시(구조): 대분류 "무기" → 종류(검·도·활 등), 속성(물·불·흙·바람). 실제 템플릿 명칭·수치·타입코드는 원게임 데이터로 시드 단계에서 확정한다.

### 7.6 범위

강화·합성 행위는 도메인 범위 밖이다. 이 플랫폼은 거래를 다루지 게임 플레이를 다루지 않는다. 레벨·특수스킬은 매물 등록 시점에 주어진 인스턴스 상태로만 취급하고, 플랫폼 안에서 이를 변경하는 기능은 제공하지 않는다(D-046). 아이템 시각 자산(이미지 등) 관리와 감정·진위 검증도 이번 범위에서 다루지 않으며 필요 시 후속 확장한다.

### 7.7 검색·시세 축

"동일 템플릿, 다른 가치"를 다루기 위해 검색과 시세 집계를 정형 축으로 제공한다.

- 검색·필터 축: 카테고리(대분류/종류), 속성, 레벨, 특수스킬 조합, 골드포스(활성/잔여).
- 시세 집계 단위: (템플릿, 레벨, 특수스킬 조합). 같은 템플릿이라도 이 단위로 가치가 갈리므로 시세는 이 조합 키로 집계한다. 골드포스는 시간제 상태라 집계 키에서 제외하고 검색 필터로만 쓴다(집계 불안정 방지, D-066).

특수스킬 조합 필터와 이 시세 집계 단위는 ERD(G2) 검색·인덱스 설계의 필수 케이스다(D-044 조건). 구체 인덱스 구성은 ERD의 인덱스 표에서 이유 열과 함께 확정한다(D-036).

### 7.8 소유·이전

아이템 인스턴스는 항상 소유자(User)에 귀속된다. 상시 "인벤토리" 애그리거트를 별도로 둘지 여부는 ERD에서 판단하되, 이 스펙의 최소 요구는 "매물과 거래 이력이 소유자를 식별할 수 있어야 한다"이다. 낙찰·구매가 성립(SOLD)하면 해당 매물 인스턴스의 소유권이 판매자에서 구매자로 이전되며, 이전은 Order 핸드오프(5절)의 일부로 다룬다. 이전된 인스턴스는 구매자가 다시 매물로 등록해 재판매할 수 있고, 재판매는 신규 매물 등록으로 처리한다(유찰 재등록과 동일 원칙 — 별도 전용 플로우 없음, 5절·12절). 이 소유자 식별·이전 규칙이 ERD item_instance 소유자 FK 설계의 근거다(D-062 안건8).

## 8. 즉시구매·낙찰 동시성 정책 (D-008)

원칙: 정합성은 DB, 처리량은 락. 정합성의 최종 보증은 DB(조건부 원자 갱신 + 유니크 제약)가 맡고, 분산락(Redisson)은 경합 완화·처리량 최적화 수단이지 정확성 보장 수단이 아니다. 락만 의존하면 Redis 장애·락 만료·클럭 스큐 시 중복 판매가 발생할 수 있다(되돌리기 비용이 큰 리스크). 이 문장은 백엔드 구현이 인용하는 기준이다.

종료성 전이(SOLD/CANCELLED)는 조건부 CAS UPDATE로 처리한다(`... WHERE status='ACTIVE'`, 영향 행 수 0이면 이미 종료). 동시 요청 중 단일 승자만 성립하고 나머지는 "이미 종료됨"으로 응답한다. 즉시구매·마감 낙찰·취소가 이 단일 승자 패턴을 공유한다.

SOLD 확정과 Order 생성은 단일 트랜잭션으로 원자적으로 처리한다(D-053). 거래는 내부 게임머니로만 이뤄지므로 외부 연동을 트랜잭션에 엮지 않으며, 외부 연동은 충전 도메인에 한정한다.

입찰 유효성 검증·최고가 갱신은 경매 단위로 직렬화하되 최종 정합성은 DB가 보증한다. 소프트 클로즈의 마감 연장 판단은 입찰 수용과 동일한 직렬화 단위에 포함한다(입찰은 성공했는데 연장이 누락되는 틈 방지). Redis 완충 여부와 구체 직렬화 기법은 백엔드 자율이다.

## 9. 마감 처리 (D-056~058)

시각 기반 상태 전이(경매 마감, 예약 시작 활성화, 고정가 만료)는 재예약 가능한 지연 인덱스 + 짧은 주기 워커 + DB 재구축 안전망의 하이브리드로 처리한다. 소프트 클로즈로 마감 시각이 반복 갱신되므로 재예약 비용이 핵심이며, 지연 인덱스의 시각 갱신만으로 재예약되고 DB가 진실이라 인덱스 유실 시 재구축이 가능하다(8절 원칙과 정합). 구체 기술(예: Redis ZSET, DelayedQueue, 스케줄러 라이브러리)은 백엔드 자율이다.

세 종류의 트리거(마감/예약시작/만료)는 모두 "시각 도달 시 상태 전이"라는 동일 패턴이므로 단일 지연 인덱스로 통합 관리하고 트리거 종류만 구분한다.

마감 처리는 8절의 CAS로 멱등하다(이미 종료면 no-op). 워커가 다중화되어도 CAS가 단일 처리를 보장한다. 유실은 DB 재구축 스캔(status=ACTIVE이고 마감 시각 경과)으로 복구한다. 마감 시점의 최고입찰 차감과 나머지 홀드 해제는 종료 전이와 동일한 직렬화 단위에 묶는다.

트리거 정확도 목표는 비기능 요구로 명시하되 구체 수치는 백엔드와 조기 협의해 정한다.

## 10. 동시성 필수 케이스 (누적)

domain-spec이 요구하는 동시성 시나리오를 한곳에 모은다. ERD·구현·QA가 공통으로 참조한다.

- buyNow 근접 구간의 입찰 vs 즉시구매 경합.
- 취소 vs 첫 입찰 경합(취소 순간 입찰 유입).
- SOLD 확정과 Order 생성의 원자성.
- 마감 직전 입찰 폭주.
- 게임머니 홀드·해제·차감 경합.
- 마감 시점의 최고입찰 차감과 나머지 홀드 해제(종료 전이와 동일 직렬화 단위).

## 11. 비기능 요구

- 정합성 원칙: "정합성은 DB, 처리량은 락"(8절).
- 마감 트리거 정확도: 목표 수치는 백엔드 조기 협의로 확정(9절).

## 12. 범위 밖

- proxy(자동) 입찰.
- 아이템 강화·합성 행위(레벨은 상태 값으로만 취급).
- 역방향 환전(게임머니→캐시)·환불.
- 유찰 후 재등록 전용 플로우(신규 등록으로 처리).
