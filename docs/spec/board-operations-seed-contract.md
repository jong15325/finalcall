- 대상: 운영형 20인 시나리오의 공지사항·커뮤니티·이벤트 데이터 확장

  `operations-seed-spec.md`, `operations-seed-v2-impact.md`

## 1. 목적과 비범위

빈 게시판을 실제 서비스처럼 보이는 밀도의 창작 콘텐츠로 채운다. 한국에서 서비스된
`서바이벌 프로젝트`/`서프온라인`의 운영 방식과 이용자 문화는 **소재와 분위기만** 참고한다.
원문 공지·게시글·문장·이미지·로고·고유 캐릭터 설정을 복제하지 않으며 FinalCall의 경매·마켓
세계관에 맞게 새로 쓴다.

이번 작업은 기존 `board`, `post`, `comment`, `comment_reaction` 스키마와 API를 그대로 사용한다.
DB 마이그레이션, API 형상 변경, 이미지 첨부 및 관리자 화면 구현은 범위 밖이다.

## 2. 기존 게시판 매핑

| 용도 | slug | 정책 | 시드 작성자 |
|---|---|---|---|
| 운영 공지 | `notice` | `NOTICE`, `ADMIN_ONLY`, 댓글 불가 | `author_id=NULL`, 표시명 `FinalCall 운영팀` |
| 자유 커뮤니티 | `community` | `GENERAL`, `AUTHENTICATED`, 댓글 허용 | `test01`~`test20` |
| 참여 이벤트 | `event` | `EVENT`, `ADMIN_ONLY`, 댓글 허용 | `author_id=NULL`, 표시명 `FinalCall 이벤트팀` |

운영자 계정을 새로 만들거나 기존 테스트 계정에 관리자 권한을 부여하지 않는다. 시스템 글의
nullable 작성자 모델은 `board-domain-spec.md` §4.2·§8의 기존 계약을 따른다. 커뮤니티 작성자는
DB의 `login_id=test01`~`test20`을 조회해 FK를 고정하며 nickname 문자열로 사용자를 재조회하지 않는다.

## 3. 정확한 데이터 규모

| 구분 | 게시글 | 고정 글 | 루트 댓글 | 답글 | 반응 |
|---|---:|---:|---:|---:|---:|
| 공지사항 | 12 | 3 | 0 | 0 | 0 |
| 커뮤니티 | 36 | 0 | 108 | 48 | 240 |
| 이벤트 | 12 | 2 | 36 | 12 | 72 |
| 합계 | **60** | **5** | **144** | **60** | **312** |

- `post.comment_count`는 활성 루트 댓글+답글 수와 정확히 일치한다.
- 루트 `comment.reply_count`는 해당 활성 답글 수와 정확히 일치한다.
- `comment.like_count`·`dislike_count`는 `comment_reaction` 집계와 정확히 일치한다.
- 한 사용자는 같은 댓글에 한 반응만 갖고 자기 댓글에는 반응하지 않는다.
- 삭제 글·삭제 댓글·tombstone은 만들지 않는다. 운영형 기본 화면의 밀도 확인이 목적이기 때문이다.

## 5. 작성자와 상호작용 분포

- 커뮤니티 글: `test01`~`test16` 각 2개, `test17`~`test20` 각 1개.
- 커뮤니티 댓글·답글: 20명 모두 최소 루트 댓글 5개, 답글 2개 이상 작성한다.
- 이벤트 댓글·답글: 20명 모두 최소 1회 참여하되 동일 이벤트에 같은 사용자의 루트 댓글은 최대 1개다.
- 반응: 20명 모두 LIKE와 DISLIKE를 각각 1회 이상 갖되 LIKE 260, DISLIKE 52로 구성한다.
- 작성자 본인 반응 금지, 사용자별 총 반응 수 편차는 8건 이내로 제한한다.
- 공지와 이벤트 본문 작성자 FK는 NULL이므로 테스트 사용자의 관리자 권한·인가 모델에 영향을 주지 않는다.

## 6. 시간·조회수 분포

기준시각 `T`는 시드 트랜잭션 시작 시 DB `NOW(6)` 한 번으로 고정한다.

- 공지: `T-120일`~`T-1일`; 고정 3개는 최근 30일 안에 배치한다.
- 커뮤니티: `T-45일`~`T-10분`; 최근 7일 18개, 최근 24시간 8개를 포함한다.
- 이벤트: 종료 분위기 4개(`T-90`~`T-30일`), 진행 분위기 6개(`T-14일`~`T-1시간`),
  예고 분위기 2개(`T-2일`~`T-6시간`). 현행 스키마에 시작/종료 컬럼이 없으므로 날짜는 본문 표현일 뿐
  서버가 보장하는 이벤트 상태가 아니다.
- 댓글은 항상 부모 글 이후, 답글은 루트 댓글 이후에 생성한다.
- 조회수: 공지 180~3,800, 커뮤니티 12~1,450, 이벤트 90~2,600의 결정적 분포를 사용한다.
- `updated_at=created_at`; 수정 이력은 연출하지 않는다.

## 7. 멱등성·namespace·cleanup

별도 시나리오 `board-surf-20-v1`을 사용하며 기존 `ops-20-v2`의 완료 판정과 삭제 범위를 변경하지 않는다.

| 리소스 | 결정적 식별자 |
|---|---|
| post | `BSP01` + 21자리 zero-pad 순번 = CHAR(26) |
| comment | `BSC01` + 21자리 zero-pad 순번 = CHAR(26) |

`comment_reaction`은 public ID가 없으므로 namespace 댓글과 user FK의 조합으로 식별한다. 상태 판정은
게시글 60, 댓글 204, 반응 312개가 모두 맞으면 `COMPLETE`, 전부 0이면 `EMPTY`, 그 외 `PARTIAL`이다.
`PARTIAL`에서 apply와 cleanup은 모두 거부하고 조사 대상으로 남긴다.

Apply 순서는 post → 루트 comment → reply → reaction → 비정규화 카운터 검증이며 하나의 JDBC
트랜잭션으로 처리한다. Cleanup은 외부 참조를 먼저 검사한 후 reaction → reply/comment → post 순서로
삭제한다. 다음 중 하나라도 있으면 cleanup을 거부한다.

- namespace 글에 namespace 밖 댓글이 존재
- namespace 댓글에 `test01`~`test20` 밖 사용자의 반응이 존재
- 시드 글·댓글의 제목, 본문, 작성자, 삭제 여부 또는 FK가 결정적 fixture와 달라짐

Board 3행과 `test01`~`test20` 사용자는 선행 마스터이며 생성·수정·삭제하지 않는다. cleanup 후 기존
`ops-20-v2` 데이터는 그대로 남아야 한다.

## 8. 실행 안전장치와 검증

- 운영 부팅·Flyway에서 자동 실행하지 않는 명시적 one-shot CLI로 구현한다.
- 기존 `SeedGuard`와 동일하게 target fingerprint, `SEED_ALLOW_PROD=true`, apply/cleanup 확인 문자열을
  요구하되 scenario allowlist에는 `board-surf-20-v1`을 가법 추가한다.
- dry-run → DB 백업 → apply → verify 순서를 강제한다.
- verify는 §3 건수, 게시판별 귀속, FK, 시간 순서, 자기반응 없음, UK, 세 카운터 정합성,
  20명 참여 분포와 금칙 문구를 검사한다.
- API 확인: 세 게시판 목록/상세 200, 고정 우선 정렬, 댓글/답글 페이지, 로그인 사용자의 `myReaction`.

## 9. 저작권·표시 원칙

- 참고 범위: 온라인 포인트 적립, 계정/IP 중복 방지, 오프라인 보상·인벤토리 안내 같은 운영 소재;
  토너먼트·팀플레이·사커·노카드·길드·서버 선택·옛날 아이템전 같은 커뮤니티 화제;
  PvP·PvE·미니게임, 바람 계열, 장비 슬롯과 단계 성장 같은 장르적 소재.
- 금지: 원문 전재·근접 번역, 게시자 닉네임 복제, 공식 로고/스크린샷 사용, 실제 운영 공지인 듯한 날짜·보상,
  원작 제작사·운영사와의 제휴 또는 공식성을 암시하는 표현.
- 모든 본문은 FinalCall 거래 서비스 문맥에 맞춰 창작한다. 이벤트에는 테스트 이벤트 고지를 넣고,
  게시판 하단 또는 첫 고정 공지에 `FinalCall은 해당 게임의 공식 운영 서비스가 아니며, 게시글은
  테스트를 위한 창작 데이터입니다.`를 표시한다.

## 11. 게이트2 상신

다음 결정은 운영 DB 쓰기·시드 계약 및 되돌리기 안전성에 영향을 주므로 사용자 승인이 필요하다.

1. **권고 A — 독립 시나리오**: `ops-20-v2`에 합치지 않고 `board-surf-20-v1`로 분리한다.
   기존 거래 시드의 COMPLETE/cleanup 의미를 보존하고 게시판만 재실행할 수 있다.
2. **권고 A — 시스템 작성자 NULL**: 공지·이벤트는 기존 계약대로 nullable author와 운영팀 표시명을 사용한다.
   테스트 계정 승격이나 가짜 관리자 계정 생성을 피한다.
3. **권고 A — 이미지 없음**: 저작권·오브젝트 저장소 cleanup 부담을 피하고 텍스트 게시글만 생성한다.
4. **권고 A — 운영 DB 직접 적용**: dry-run, 백업, reviewer 통과 후 현재 단일 Docker DB에 apply한다.
5. **권고 A — 60글/204댓글/312반응**: 현재 20명 규모에서 목록·상세·댓글·반응 UI를 충분히 검증하되
   과도한 fixture 유지 비용을 만들지 않는 상한으로 고정한다.

승인 전에는 앱 코드와 DB를 변경하지 않는다.
