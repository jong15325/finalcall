# FinalCall 플랫폼 중계 수수료 정책 (fee-policy-spec)

상태: v1.0 — 게이트2 승인 확정(2026-07-20, 사용자). 이 문서가 수수료 정책의 **정본**이다.
소유 에픽: **EPIC-CLOSING**(정산). 백엔드 동결 중 — 이 문서는 계약(문서)만 확정하고 **구현은 EPIC-CLOSING 동결 해제 후**다.

---

## 1. 부담 주체와 적용 범위

- **부담 주체 = 판매자 단독.** 구매자 부담 0%. 경매(auction)·고정가(shop) **공통** 적용한다.
- **경매 구매수수료(buyer's premium) 미도입.** 구매자에게 별도 수수료를 얹지 않는다(후속 실험 여지만 기록 — §8).
- 수수료 기준액 = **판매가(final_price)** = 최종 확정가.
  - 경매: 낙찰가(`resultType=BID`) 또는 즉시구매가(`resultType=BUYNOW`).
  - 고정가: 판매가(`shop.price`).
  - 정본은 `sale_order.final_price`(erd §4.2). 경매·고정가가 한 컬럼으로 수렴한다.
- 화폐: **게임머니(G) 기준.** 거래·정산은 전부 게임머니로 이뤄진다(domain-spec §6).
- **부가세 과세 생략.** 내부 화폐라 스켈레톤 범위 밖이다(향후 실화폐 정산 도입 시 재검토).

---

## 2. 구간별 누진 요율 (marginal — 구간 부분 적용)

판매가를 구간으로 쪼개 **각 구간에 속하는 부분에만** 해당 요율을 적용한다(전체 금액 일괄율이 **아니다**).
이는 구간 경계에서 수수료가 역전(cliff)되는 것을 방지한다.

| 구간(판매가 G) | 요율 |
|---|---|
| ~ 100,000 | 6% |
| 100,001 ~ 1,000,000 | 5% |
| 1,000,001 ~ 3,000,000 | 4% |
| 3,000,001 ~ | 3% |

- **최소 수수료 = 100 G**
- **상한(cap) = 300,000 G** — 누진 합계에 적용한다(요율에 적용하는 것이 아니다).

---

## 3. 계산식 (누진 → 반올림 → 최소/상한)

`final_price = P`(게임머니, 정수)일 때 원시 누진 합계:

```
raw_fee(P) =
    0.06 × min(P, 100_000)
  + 0.05 × clamp(P − 100_000,   0, 900_000)      // 100,001 ~ 1,000,000 구간(폭 900,000)
  + 0.04 × clamp(P − 1_000_000, 0, 2_000_000)    // 1,000,001 ~ 3,000,000 구간(폭 2,000,000)
  + 0.03 × max(P − 3_000_000, 0)                 // 3,000,001 ~
```

`clamp(x, lo, hi) = max(lo, min(x, hi))`.

**적용 순서(중요 — 이 순서로 인코딩):**

1. **누진 합계** `raw_fee(P)` 계산(구간 부분 적용).
2. **반올림** — 원(=G) 단위 사사오입(round half up). `rounded = round(raw_fee)`.
3. **상한 적용** — `capped = min(rounded, 300_000)`.
4. **최소 적용** — `fee_amount = max(capped, 100)`.

최소(100)와 상한(300,000)은 값이 겹치지 않아 3·4 순서를 바꿔도 결과는 동일하다. 명세는 위 순서를 정본으로 한다.

정산:

```
settle_amount = final_price − fee_amount
```

`fee_amount`은 **사업자(플랫폼) 귀속**, `settle_amount`은 판매자 귀속이다.

---

## 4. 워크드 예시

### 4.1 대표 예시 — P = 2,480,000 G

| 구간 | 적용 폭 | 요율 | 부분 수수료 |
|---|---|---|---|
| ~ 100,000 | 100,000 | 6% | 6,000 |
| 100,001 ~ 1,000,000 | 900,000 | 5% | 45,000 |
| 1,000,001 ~ 3,000,000 | 1,480,000 | 4% | 59,200 |
| 3,000,001 ~ | 0 | 3% | 0 |
| **합계** | | | **110,200** |

- `fee_amount = 110,200 G`(반올림 무영향, cap·최소 미저촉)
- `settle_amount = 2,480,000 − 110,200 = 2,369,800 G`
- 실효 요율 = 110,200 / 2,480,000 = **4.44%**

### 4.2 경계·클램프 예시

| P (G) | raw_fee 계산 | fee_amount | 저촉 |
|---|---|---|---|
| 1,000 | 0.06 × 1,000 = 60 | **100** | 최소 100 floor |
| 100,000 | 0.06 × 100,000 = 6,000 | 6,000 | — |
| 1,000,000 | 6,000 + 45,000 = 51,000 | 51,000 | — |
| 3,000,000 | 6,000 + 45,000 + 80,000 = 131,000 | 131,000 | — |
| 8,633,333 | 131,000 + 0.03 × 5,633,333 ≈ 300,000 | 300,000 | cap 근처 |
| 20,000,000 | 131,000 + 0.03 × 17,000,000 = 641,000 | **300,000** | cap 300,000 |

- **cap 바인딩 지점** ≈ 판매가 8,633,333 G. 그 이상은 수수료가 300,000 G로 고정된다(실효 요율은 판매가가 클수록 하락).
- **최소 바인딩 구간** ≈ 판매가 1,666 G 이하(6% < 100). 이 이하는 100 G로 상향된다.

주(엣지, EPIC-CLOSING 유의): 판매가가 극소(예: P < 100)면 `settle_amount = P − 100`이 음수가 될 수 있다.
실무상 리스팅 최소 시작가/판매가가 이 대역을 배제하므로 현재는 비저촉이나, 구현 시 하한 검증으로 방어할지 판단한다(정책 미결 — 상신 대상 아님, 구현 티켓 관찰 항목).

## 5. 취소·유찰·환불 처리

- **수수료는 SOLD 성립 시에만 확정**된다. `sale_order`는 SOLD에서만 생성되므로(domain-spec §5), 미성립 거래에는 수수료가 없다.
  - 경매 **취소(CANCELLED)**·**유찰(UNSOLD)** → 수수료 **0**(sale_order 미생성).
  - 고정가 **취소(CANCELLED)**·**만료(EXPIRED)** → 수수료 **0**.
- **정산 후 환불** — 이미 정산된 거래를 되돌릴 때는 **비례 크레딧**으로 처리한다(원 수수료를 판매자에게 되돌릴 때 부분 환불 비율만큼 크레딧).
- **플랫폼 개입 분쟁 종결** — 플랫폼이 개입해 종결한 분쟁은 **크레딧 예외**로 처리한다(eBay 모델 — 플랫폼 귀책·정책 위반 종결 시 수수료 크레딧 취급을 사업자 재량으로).
- 환불·크레딧의 회계 처리 세부(크레딧 화폐·귀속·상계 순서)는 **EPIC-CLOSING 구현 범위**다. 이 문서는 원칙만 고정한다.

---

## 6. 반올림

- **원(=G) 단위 사사오입(round half up).** 게임머니는 정수라 소수 수수료를 정수로 반올림한다.
- 반올림은 누진 합계 산출 **직후**(§3 순서 2)에 한 번만 적용한다. 이후 cap·최소 클램프는 정수 대 정수 연산이라 추가 반올림이 없다.

---

## 7. 구현 에픽 = EPIC-CLOSING

- 이 정책의 구현(수수료 계산기·정산 TX 반영·환불 크레딧)은 **EPIC-CLOSING**(정산) 소유다.
- 현재 백엔드 동결 중이며, **동결 해제 후** 이 문서를 계약 근거로 구현한다.
- 스키마 접점: `sale_order.final_price` / `fee_amount` / `settle_amount`(erd §4.2). **스키마 변경 없음**(자리는 이미 존재).
- 구현 시 유의(§계산 위치·순서):
  - 누진 계산은 **SOLD 핸드오프의 정산 TX 안**에서 `final_price` 확정 직후 1회 수행한다(경매·고정가 공통 경로).
  - **cap·최소는 계산기 내부**에서 클램프한다(§3 순서). 호출부가 아니라 계산기가 단일 책임을 진다.
  - `money_hold` **CAPTURED**(홀드 차감 확정)와의 순서 — 홀드 차감(구매자 지불 확정)과 판매자 정산(`settle_amount` 지급)이 **동일 TX**에서 일어나되, `fee_amount`은 그 사이 사업자 귀속 몫으로 분리된다. 즉 `구매자 홀드 CAPTURED = final_price` → 그중 `settle_amount`가 판매자 게임머니로, `fee_amount`이 플랫폼 계정으로 귀속. 계산 → 분개 순서를 TX 내에서 고정한다.

---

## 8. 후속 실험 여지 (미도입, 기록만)

- **경매 구매수수료(buyer's premium)** — 현행 미도입(판매자 단독). 향후 A/B로 구매자 소액 프리미엄을 실험할 여지만 남긴다. 도입 시 게이트2 + 계약 변경 선행.
- **부가세 반영** — 실화폐 정산 전환 시 재검토.

---

## 9. 근거 (출처 요지)

- **국내 게임아이템 거래소 판매자 요율 앵커(≈5%)** — 국내 대형 게임아이템 중개소의 판매자 중개 수수료가 대체로 5% 안팎이다. 본 정책의 중위 구간(100,001~1,000,000 G = 5%)을 이 시장 앵커에 정렬했다.
- **경매하우스 구간별 누진 요율제** — 전통 경매하우스(판매자 커미션)가 낙찰가 구간이 커질수록 요율을 낮추는 누진(sliding scale) 구조를 쓴다. 고액 거래의 실효 부담을 낮춰 대형 매물 이탈을 막는 설계를 차용했다(cap 300,000 G 포함).
- **eBay 취소·분쟁 크레딧 모델** — SOLD 미성립·취소 시 수수료 0, 정산 후 되돌림은 비례 크레딧, 플랫폼 개입 분쟁 종결은 크레딧 예외로 처리하는 관행(§5)을 참조했다.

주: 위는 정책 설계의 벤치마크 요지이며 특정 사업자 요율의 축자 인용이 아니다. 정확한 값·구간·cap은 FinalCall이 게이트2에서 확정한 자체 파라미터다.
