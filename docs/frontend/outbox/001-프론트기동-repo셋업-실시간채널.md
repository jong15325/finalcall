배경: G3 전파(039) 수신 후 프론트 기동 완료. 폴더 세팅(decision-log·inbox-log·outbox·notes), 수신함 처리(039·025·011), 계약 v1.1 기준 초기 설계(화면·라우트 맵, feature 구조, 계약 타입 대응, 폴링/구독 전략 F-001)까지 마쳤다. 산출물: docs/frontend/notes/screen-route-map.md, decision-log.md(F-001). 다음 진행에 아래 2건의 결정이 필요하다.

안건 1. 프론트 저장소 스켈레톤 생성 시점·방식
- 배경: 프론트 repo 미생성 상태. 계약 복사본(원본 경로·버전·해시 헤더, D-030)은 repo 셋업 시 생성 예정이라, 셋업 전까지는 설계·계획만 가능하고 코드 착수(Claude Code 핸드오프)가 막혀 있다.
- 선택지: (a) 지금 프론트 repo 생성(Vite+React+TS 스켈레톤) 후 계약 복사본·CLAUDE.md 이관 → 코드 착수 개방 (b) 백엔드 auth 구현 진척까지 대기, 설계만 선행
- 추천: (a) — 스켈레톤·계약 복사본·타입 골격은 백엔드 응답과 독립(의존 없음, D-028 pull 우선순위). 지금 열어두면 auth 화면부터 병렬 착수 가능. repo 생성·초기 커밋 실행은 사용자 단일(D-061·D-030).

안건 2. 실시간 최고가 갱신 — 푸시 채널(SSE/WebSocket) 도입 여부
- 배경: 계약 v1.1은 REST 전용으로 실시간 푸시 채널이 없다. 현행 범위에서 실시간성은 GET /auctions/{id} 폴링이 유일(F-001로 확정). 다만 domain-spec §4·§10이 마감 직전 입찰 폭주를 핵심 도전으로 명시해, 푸시 채널이 UX상 필요할 수 있다.
- 선택지: (a) MVP는 폴링(F-001) 유지, 푸시는 G4 경매 도메인에서 재평가 (b) 지금 푸시 채널을 범위에 넣고 계약 확장(6절)으로 SSE/WS 엔드포인트 추가 요청
- 추천: (a) — 푸시는 계약 확장·백엔드 인프라(경계·아키텍처) 사안이라 선도입은 비용이 크다. 폴링으로 MVP 성립 후, 경매 상세 부하·체감 지연 측정 결과를 근거로 재평가가 합리적. (b) 채택 시 계약 변경 요청(templates 15)으로 재격상.
