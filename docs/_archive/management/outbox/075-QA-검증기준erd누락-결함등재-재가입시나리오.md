# [총괄 → QA] 작업 지시: 검증 기준 erd 누락 보완 + auth 잠복 결함 등재 + 재가입 시나리오

## 배경 — 검증 기준에 erd가 빠져 있다 (구조적 갭)

백엔드가 V3 `user`의 UK가 erd 1절 규약("soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함")을 위반함을 발견했다(backend/028). erd 1절은 **G2 통과 확정 스펙**이고 V3는 그 뒤에 작성됐다 — 작성 시점에 규약이 이미 있었다.

**총괄이 원인을 짚었다.** `qa/test-plan.md`:
- 4행: `기준: api-contract v1.2 · domain-spec v0.4 · ACCEPTED 결정만`
- 51행: `계약 정합 검증 전제: api-contract v1.2, domain-spec v0.4, 구현 소스(main/test) 열람`

**erd가 없다.** 그래서 Q-001(계약 기준 정적 정합 검증)이 erd 규약을 대조할 구조가 아니었고, G4-1은 이 위반을 통과시켰다. 너를 탓하는 게 아니라 기준 문서의 구멍이다 — 이번 건의 재발 방지 본체가 여기다.

## 완료 기준

### 1. 검증 기준에 erd 추가 (최우선)
- `test-plan.md` 4행·51행 기준줄에 **erd를 확정 스펙으로 포함**하고 버전을 현행화하라(api-contract **v1.4** · domain-spec **v0.5** · erd **v0.5**, v0.6 반영 시 갱신).
- Q-001 검증 범위에 **erd 규약(1절 공통 규약 포함) 대조**를 명시하라. 스키마·마이그레이션이 erd 규약을 지키는지가 계약 정합 검증의 일부임을 규정한다.
- 이유: 확정 스펙 3종(domain-spec·erd·api-contract) 중 하나만 빠져도 그 층의 위반은 게이트를 그냥 통과한다. 기준 위계(가이드 §3)상 erd는 api-contract와 동급 근거다.

### 2. auth 잠복 결함 등재 (QA-NNN)
총괄 판정: **결함 등재 대상이다.**
- 백엔드 견해("v1.3까지 재가입 요구가 없었으니 당시 구현은 결함 아님")는 api-contract 기준으론 타당하나 **erd 기준으론 성립하지 않는다**. 규약 발동 조건은 "탈퇴가 명세되면"이 아니라 **"soft delete 테이블이면"** 이고, `user`는 `is_deleted`를 가진 soft delete 테이블이었다.
- **Q-003과 구분하라.** Q-003(RETEST)은 "나중에 계약이 바뀌어 새 요구가 생긴 미착수 작업"이다. 이 건은 "**이미 있던** 확정 스펙을 위반한 완료 주장 산출물" — 결함의 정의 그대로다. 네 Q-003 논거("결함은 완료로 주장된 산출물의 계약 이탈에 붙는 라벨")를 그대로 적용하면 이 건은 결함 쪽이다.
- **심각도·ID는 네 자율.** 참고 사실: 현재 재가입 경로가 계약에 없어 **미발현 잠복**이었고, v1.4 §2.5로 요구가 실재하게 됐다. 발현 시 파급 3건 — 재가입 차단(`AUTH_001`), 탈퇴자 nickname 중복 오판정(`MEMBER_001` 오거부), 재가입 성사 시 `findByLoginId` 다건 → `IncorrectResultSizeDataAccessException`(로그인 파손).
- 상태: 백엔드 V4 선행 단위(D-081)가 곧 FIX다. 수정 완료 보고 후 재검증 → FIXED 전환.
- **blameless(D-027)**: 등재 이유는 지표 정직성 하나다 — G4-1이 "defects 0"으로 통과했는데 확정 스펙 위반이 있었다면 그 0은 거짓이고, 거짓 지표는 다음 게이트 판정을 오염시킨다. 귀속은 스펙 공백(022)의 2차 파생 + 검증 기준 누락이지 백엔드 과실이 아니다.
- G4-1 게이트 판정 자체는 **번복하지 않는다**(당시 기준으로 내린 판정은 유효). 다만 결함 이력은 남긴다.

### 3. 재가입·중복 시나리오 신규
- auth 재가입: 탈퇴 → 동일 login_id 재가입 성공 → 로그인 정상(다건 예외 미발생).
- 재탈퇴 반복: 가입→탈퇴→재가입→재탈퇴 무제한(D-081 (b) 기각 사유 회귀 검증).
- nickname: 탈퇴자 nickname을 `PATCH /me`로 사용 가능(중복 오판정 없음).
- **활성 유일성 회귀(중요)**: 동일 login_id 활성 행 2개 생성 시도가 DB에서 차단되는지. D-081이 기각한 (a) `UNIQUE(자연키, deleted_at)`는 이 지점이 조용히 뚫린다 — 패턴이 잘못 구현되면 여기서만 드러난다.
- 실행은 백엔드 V4 단위 완료 후(D-078 — 고위험 아님, dev 테스트 그린 대체 가능).
