# [총괄 → 프론트, QA, 백엔드] 작업 지시(전파): api-contract v1.3 — 게이트웨이 엣지 오류 명세

## 배경
계약 6절 변경 절차로 api-contract가 v1.3으로 확정됐다(총괄 057 승인 → 기획 반영 → 총괄 검수 통과, design/outbox/023).
변경점: 게이트웨이 엣지 오류(rate limit 429·직접접근 403)를 서비스 ErrorResponse envelope로 통일.
- 정본: docs/api-contract.md v1.3 (§1.6 신설, §5 GATEWAY_429·GATEWAY_403 등재, 버전 이력 v1.3)
- 근거: D-068(SCG 엣지 게이트웨이), 총괄 056(안건1 A) / 057.
- envelope: `{ success:false, code:"GATEWAY_NNN", message, timestamp }` (errors 미포함). `GATEWAY_` 프리픽스는 도메인 ErrorCode enum과 1:1 예외(엣지 발생, 게이트웨이가 직접 세팅).

기준 게이트 = G3(api-contract v1) 동기화분 + 이번 델타(v1.2→v1.3)만 아래에 발췌. 전문은 정본 경로 참조.

## 프론트(F)
- 목표: 계약 복사본 v1.3 동기화 + 429 처리 확인.
- 완료 기준: (1) 프론트 저장소 api-contract 복사본 v1.3 갱신(헤더 원본 경로·버전 표기). (2) GATEWAY_429 수신 시 백오프 — `Retry-After` 헤더 존중(있으면 그 값, 없으면 기본 백오프). code/message/timestamp는 기존 envelope 소비 로직 재사용(신규 파서 불요).
- 범위 제한: GATEWAY_403은 정상 경유 클라이언트 미해당 → 프론트 별도 처리 불요(음성 테스트 전용). 새 화면·상태 추가 금지.
- 관련: docs/api-contract.md §1.6·§5, 복사본 갱신은 계약 변경 전파 체크리스트.

## QA(Q)
- 목표: 게이트웨이 엣지 재검증 CLOSE(060에서 v1.3 후속으로 유보한 항목).
- 완료 기준: 게이트웨이 시나리오의 (1) 429 응답 본문이 GATEWAY_429 envelope·`Retry-After` 동반, (2) 직접접근 403 응답 code=GATEWAY_403 임을 재검증. defects/CQ 상태 갱신.
- 의존: 백엔드 게이트웨이 커스텀 에러 핸들러 구현(아래 B). 핸들러 미구현이면 D-078 손(Claude Code) 실행 시점은 총괄 순서 지정 대기 — 그 전 설계 시나리오만 확정.
- 범위 제한: auth·gateway 기능 시나리오는 이미 G4-1 PASS, 재실행 불요. 엣지 포맷 델타만.
- 관련: docs/api-contract.md §1.6·§5, qa/scenarios, 회신 management/outbox/060.

## 백엔드(B)
- 목표: 게이트웨이 커스텀 에러 핸들러를 v1.3 코드·필드에 맞춰 구현(429·403 envelope).
- 완료 기준: 게이트웨이 429/403 응답이 §1.6 envelope(GATEWAY_429·Retry-After / GATEWAY_403) 준수. 도메인 ErrorCode enum·서비스 envelope 포맷은 무변경.
- 의존/순서: 착수 시점은 총괄 도메인 시퀀싱(D-074)에 종속. 현 우선순위는 사용자 확정 대기(ON-HOLD 3종 → 도메인 재개) — 임의 선행 착수 금지. 대기 중이면 완료 보고에 "대기: 도메인 순서 확정" 명시.
- 범위 제한: 라우팅·rate limit 정책 변경 금지(구현은 포맷 정합만).
- 관련: docs/api-contract.md §1.6·§5, gateway/ 모듈, B-026·B-027.
