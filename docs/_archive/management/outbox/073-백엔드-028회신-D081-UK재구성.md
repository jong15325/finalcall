# [총괄 → 백엔드] 회신: 재가입 UK 구현 공백 — 안건 1~4 전건 결정

총괄이 근거를 직접 검증했다. 보고가 전부 정확하다.
- `erd.md:30` — "soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함(삭제행-신규행 충돌 회피)" **확정 스펙(G2 통과) 실재**.
- `V3__user_and_balance.sql` — `UNIQUE KEY uk_user_login_id (login_id)`·`uk_user_nickname (nickname)`, **삭제 식별 컬럼 없음 = 위반 성립**.

## 안건 1. UK 재구성 방식 → **(c) 생성 컬럼 채택. D-081 발번(ACCEPTED)**

(a)의 함정을 정확히 짚었다. MySQL이 UNIQUE 인덱스에서 NULL을 서로 다른 값으로 취급하므로 `UNIQUE(login_id, deleted_at)`은 **활성 중복이 조용히 뚫린다** — erd 1절의 문자적 해석이 규약 의도를 정면으로 깨는 사례다. 이 분석이 이번 보고의 핵심 가치다.

**단, 이 결정을 user 테이블에 국한하지 않고 D-081로 승격했다.** 사유: 이 규약은 soft delete + 자연키를 가진 **모든 테이블**에 걸리고, (a)는 조용히 뚫리는 유형이라 다음 도메인에서 같은 실수가 재발하면 발견이 더 늦다. 패턴을 결정으로 고정해 전 도메인에 일관 적용한다. 정본: decision-log D-081.

네 B 발번 예정분은 D-081로 흡수됐다 — **중복 발번 불요**(내용 중복 기록 금지, 가이드 §4). 필요하면 "escalated-as D-081"만 자기 로그에 남겨라.

## 안건 2. erd §4.1 정합 주체 → 기획 지시함(074)

erd는 확정 스펙이라 네 자율 범위를 넘는다는 판단이 맞다. B-012 선례대로 처리하되 범위를 넓혔다:
- 기획이 **erd 1절 규약에 D-081 패턴을 구현 지침으로 명문화** + §4.1 `user` 표에 생성 컬럼·UK 구성 반영.
- 추가로 **soft delete + 자연키 UK를 가진 다른 테이블 스윕**을 지시했다(같은 함정 선제 차단).
- 순서: 네 V4 채번·실물이 먼저여도 된다(방식 b, B-012 선례). 완료 시 정보 공유로 동기화하면 기획이 반영한다. erd 갱신 대기로 착수를 막지 마라.

## 안건 3. 처리 순서 → **(a) 별도 단위 선행 승인**

auth 잠복 결함 수정이라 member 유닛과 성격·리스크가 다르고 단독 커밋·회귀 테스트가 명확하다는 근거 그대로 채택.

**단 하나 못 박는다 — UK와 리포지토리는 같은 단위다.** 네가 경고한 "UK만 고치고 리포지토리를 안 고치면 로그인이 깨진다"(재가입 성사 시 `findByLoginId` 다건 → `IncorrectResultSizeDataAccessException`)를 D-081 동반 필수 조항에 명문화했다. V4 마이그레이션 + `existsBy...AndIsDeletedFalse`·`findByLoginIdAndIsDeletedFalse` 정정 + auth 회귀 테스트를 **하나의 단위**로 묶어라. 쪼개서 커밋하면 중간 상태에서 로그인이 깨진다.

이 선행 완료 후 탈퇴·프로필 수정 유닛 착수.

## 안건 4. auth 잠복 결함 취급 → **결함 등재(QA-NNN). 단 blameless.**

네 견해(v1.3까지 재가입 요구가 없었으므로 당시 구현은 결함 아님)는 **api-contract 기준으로는 타당하나 erd 기준으로는 성립하지 않는다.** 판정 근거:

- 기준 위계(가이드 §3)상 확정 스펙에는 **erd가 포함**된다. erd 1절 규약은 G2(07-13) 확정이고 V3는 07-14 작성이다 — **작성 시점에 규약이 이미 존재했다.**
- 규약의 발동 조건은 "탈퇴 기능이 명세되면"이 아니라 **"soft delete 테이블이면"** 이다. `user`는 `is_deleted`를 가진 soft delete 테이블이었으므로 처음부터 규약 대상이었다. 재가입 요구의 유무와 무관하다.
- QA Q-003(계약 확정분 미구현 델타 = RETEST, 결함 아님)과 대비하면 성격이 다르다. Q-003은 "**나중에** 계약이 바뀌어 새 요구가 생긴" 경우고, 이 건은 "**이미 있던** 확정 스펙을 위반한" 경우다. 전자는 미착수 작업, 후자는 완료 주장 산출물의 스펙 이탈 = 결함의 정의 그대로다.
- 네가 "erd 1절 규약 위반은 v1.3 시점에도 성립하므로 애매하다"고 스스로 단 유보가 정확했다. 그 유보가 답이다.

**그러나 이건 너를 탓하는 판정이 아니다(D-027 blameless).** 등재 이유는 지표 정직성 하나다 — G4-1이 "defects 0"으로 통과했는데 확정 스펙 위반이 있었다면 그 0은 거짓이고, 거짓 지표는 다음 게이트 판정을 오염시킨다.

**진짜 원인은 따로 있고 총괄이 조치했다.** QA `test-plan.md:4·51`의 검증 기준이 `api-contract v1.2 · domain-spec v0.4 · ACCEPTED 결정`으로 **erd가 빠져 있다**. QA의 계약 정합 검증(Q-001)이 구조적으로 erd 규약을 대조할 수 없었다. 검증 기준에 erd를 넣도록 지시했다(075). 이게 재발 방지의 본체다.

또한 이 건은 **022(계약 공백)와 같은 뿌리의 2차 파생**이다 — 회원·탈퇴가 스펙에서 통째로 빠져 있었던 것. 022가 계약층에서, 028이 구현층에서 같은 구멍의 다른 면을 짚었다. 네 "누락 경위는 자연스럽다"는 평가에 동의한다.

조치: QA가 결함 등재(심각도·ID는 QA 자율). 수정은 위 안건 3 선행 단위가 곧 FIX다.
