# [총괄 → 기획] 작업 지시: erd 1절 D-081 패턴 명문화 + soft delete 자연키 스윕

## 배경
백엔드가 V3 `user`의 UK가 erd 1절 규약을 위반함을 발견했다(backend/028). 계약 v1.4 §2.5 "재가입 허용"이 현재 구현에서 동작하지 않는다 — **계약은 옳고 구현이 규약을 못 지킨** 경우다(계약 변경 불요).

총괄이 구현 해석을 **D-081**로 확정했다(정본: decision-log D-081).

## 확정 패턴 (D-081, 재논의 불요)
```sql
<자연키>_active <TYPE> GENERATED ALWAYS AS (IF(is_deleted, NULL, <자연키>)) STORED,
UNIQUE KEY uk_<table>_<자연키>_active (<자연키>_active)
```
활성 행만 값 → 활성 유일성 보존 / 탈퇴행 NULL → MySQL 다중 NULL 허용으로 재탈퇴 무제한.

기각된 해석(erd 1절에 함께 남길 것):
- `UNIQUE(자연키, deleted_at)` — **활성 중복이 조용히 뚫린다**. MySQL이 UNIQUE에서 NULL을 서로 다른 값으로 취급하므로 `deleted_at=NULL` 활성 행이 동일 자연키로 N개 허용된다. **erd 1절의 문자적 해석이 규약 의도를 정면으로 깨는 함정** — 이게 이번 건의 핵심이라 반드시 명문화하라.
- `UNIQUE(자연키, is_deleted)` — 탈퇴행이 자연키당 1개로 제한, 재탈퇴 충돌. §6.1 이력 보존과 상충.

## 완료 기준

### 1. erd 1절 규약 — 구현 지침 명문화
현행 "soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함(삭제행-신규행 충돌 회피)"은 **의도는 옳으나 구현 해석이 열려 있어** 위 함정을 허용했다. D-081 패턴과 기각된 해석 2종을 규약에 못 박아 다음 도메인에서 재발을 막아라.

### 2. §4.1 `user` 표 갱신
`login_id_active`·`nickname_active` 생성 컬럼 + UK 구성 반영. 원본 `login_id`·`nickname` 컬럼은 존치(UK만 생성 컬럼에 건다). `deleted_at` 널 허용 유지.

### 3. soft delete 자연키 스윕 (선제 차단)
**`is_deleted` + 자연키 UK 조합을 가진 다른 테이블을 전수 점검하라.** user만의 문제가 아니다. 해당 테이블이 있으면 D-081 패턴을 동일 적용하고, 없으면 "없음"을 완료 보고에 명시하라. 미구현 도메인이라도 erd 표에 미리 반영해 두면 구현 시 함정을 안 밟는다.

### 4. 버전·이력
erd v0.5 → v0.6 + 변경 이력(사유: D-081, backend/028 발견).

## 순서 (착수 대기 금지)
백엔드가 V4 마이그레이션을 **먼저 채번·실행**한다(B-012 선례 = 방식 b, 구현 동기화). 네 erd 갱신을 기다리지 않는다. 백엔드 실물 정보 공유가 오면 그에 맞춰 반영하되, **1·3번(규약 명문화·스윕)은 지금 착수 가능**하다.
