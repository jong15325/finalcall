# [총괄 → 백엔드] 회신: member/잔액 구현 계획 검수 통과 — B-028 승인 + 실행 지시

## 검수 결과: 통과

작업 분해(023 재배치 → 024 잔액조회, 025 핸들러 병행)와 프롬프트 세트 3종 실재 확인. 착수 가능분에 한정하고 프로필·수정·탈퇴 3유닛을 계약 대기로 남긴 판단이 D-074 선행 게이팅에 정합하다.

## B-028 (계정·잔액 엔티티 auth → member 이동): 승인

068의 "구현 기법 = 백엔드 자율" 범위가 맞다. 논거도 타당하다:
- **역방향 의존 차단** — 존치 시 `domain/member → domain/auth` 역방향이 생기고, 화폐·bid·settlement가 전부 `auth.UserBalance`를 참조하게 되어 왜곡이 전 도메인에 전파된다는 지적은 정확하다. CLAUDE.md §4 단방향 원칙의 도메인 내부 적용으로 읽는다.
- **시점 판단** — 참조자가 `api/auth` 4파일 + 통합테스트 1파일뿐이라는 실측을 근거로 "지금이 마지막 two-way door 구간"이라 본 것도 옳다. member가 화폐·bid의 선행(D-074)이라 뒤로 갈수록 비용이 커진다.
- 기능 무변경 순수 리팩터 + 단독 커밋 방침 유지하라.

## 066 대비 범위 조정: 전부 수용
- "balance 신규 생성" → 기실재·재배치로 정정(068 승인분).
- "홀드/차감 구조적 골격" → `getGameMoneyAvailable()`(balance − held) 파생 + 증감 시그니처로 **이미 충족**, 신규 작업 없음. 원자적 갱신(D-008)은 화폐 도메인 후속. 수용.
- `money_hold`는 bid 소관. 확정.

066은 계약 미확인 상태로 쓴 지시라 범위 서술이 실물과 어긋났다(068에서 정정). 실측으로 바로잡아 보고한 게 맞다.

## 계약 정합 리스크(MEMBER_001): 조치함

`MemberErrorCode.MEMBER_001`(잔액 행 부재) 잠정 사용을 사전 통지한 판단이 정확하다. 총괄이 기획에 채번 조율을 지시했다(070).

- **채번 권한은 기획(계약 §5 정본)에 있다.** 네 잠정 번호에 기획이 맞출 의무는 없다 — 어긋나면 계약 기준으로 코드를 맞춘다는 네 방침(D-028)이 정답이다.
- **주의**: "방어적 내부 코드"라도 **클라이언트 응답에 실리면 계약 대상**이다. 응답에 노출되지 않는 내부 예외라면 그렇게 유지하고, 노출된다면 §5 등재 대상이니 기획 확정 전까지 번호 고정에 의존하는 코드를 쓰지 마라(상수 참조로 격리 권장).
- 069 확정 시 총괄이 정합 지시를 붙여 전파한다.

## 실행 지시
1. **023 → 024 순차, 025 병행**으로 Claude Code 실행 진행하라(총괄 승인 — 사용자 지시 시점은 사용자 재량).
2. **025 완료 시 "QA RETEST-1·2 트리거" 통지 의무**(067) 유지. 총괄이 그 시점에 QA 재검증을 지시한다. 추적표 등재분이다.
3. 069 계약 확정·전파 시 프로필·수정·탈퇴 분해 착수. 전파는 총괄이 한다 — 임의 선행 금지.

## 참고 통지 (계약 확정 예고)
탈퇴 잔액 처리가 **D-080(소멸 동의)** 으로 확정됐다. 탈퇴는 **잔액 잔존과 무관하게 허용**되고, 잔액 조건 차단 분기는 없다. 탈퇴 유닛 설계 시 참고하라(정본: decision-log D-080, 계약 반영은 v1.4 대기).
