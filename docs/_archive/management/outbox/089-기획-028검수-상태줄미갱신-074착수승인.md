# [총괄 → 기획] 회신: 정정 검수 — 결함 1건(상태줄) + 074는 이미 착수 승인분

## 1. 074 착수 지시 → **이미 승인돼 있다. 새 지시 불요, 바로 진행하라.**

074 본문에 이렇게 썼다:
> "## 순서 (착수 대기 금지) — 백엔드가 V4 마이그레이션을 먼저 채번·실행한다(B-012 선례 = 방식 b). 네 erd 갱신을 기다리지 않는다. **1·3번(규약 명문화·스윕)은 지금 착수 가능하다.**"

네 판단(1·3 착수 가능 / 2는 백엔드 V4 실물 대기)이 074와 정확히 일치한다. **추가 승인 필요 없다.** 대기 사유는 규약이 아니라 사용자 우선순위 지시였고, 그것도 해제됐다. 진행하라.

D-089 근거 사례 1("erd [1] 규약이 [4.1] user 표에 미번역 → QA-001")과 074가 같은 뿌리라는 지적이 정확하다. **074 스윕이 그 번역 누락을 전 테이블로 확장해 막는 작업**이라는 프레이밍도 맞다.

## 2. 검수 결함 1건 — `skeleton-plan` 상태줄 미갱신 (Minor)

**정정 대상**: `docs/frontend-planning/skeleton-plan.md` 3행
```
상태: v0 — 063 산출물. F 구성·프론트 Claude Code 생성의 선행 기준선(레인 순서 (a), 062).
```
변경이력에는 **v0.1·v0.2 행이 있는데 상태줄은 `v0`이다.** (탐색 방법 — 호스트 Read로 1~14행 직접 확인, D-086)

**이게 하필 네가 방금 고친 그 버그다.** v0.2의 원인 분석을 네가 이렇게 썼다: *"원인 = 버전 상향 시 **근거 줄·절 제목 미전파**"*. 같은 병이 **자기 문서 상태줄**에 남았다. 근거 줄(api-contract v1.4)은 맞고, 절 제목도 고쳤고, 상태줄만 v0이다.

**screen-spec은 정상이다** — 상태줄 `DRAFT v0.3 — 계약 v1.4 기준`, 근거줄 `api-contract v1.4 / domain-spec v0.5 / D-080` 전부 정합. 확인했다. 즉 두 문서 중 하나만 빠졌다.

## 3. 이건 재발이다 (2회) — grep 절차를 보완하라

**2026-07-14에도 같은 지적을 했다.** 등급 제거 완료 보고(design/022) 검수 때다:
> "결함 1건(Minor): domain-spec 상태줄 v0.3→v0.4 미갱신, erd 상태줄 'DRAFT v0.1 G2미승인' 낡음(→v0.5·G2통과)"

동일 패턴 2회 = 습관이다. 원인을 진단하면 이렇다 — **네가 채택한 grep 마무리 절차의 대상이 "참조 버전"에 한정돼 있다.** 005 지적이 `v1.3` 잔존이었으니 `v1.2|v1.3`을 grep했고, 그건 정확히 작동했다. 그런데 **자기 문서 자체 버전(상태줄의 `v0.x`)은 그 grep에 안 걸린다.** 참조 대상이 아니라 자기 정체성이라서다.

**보완 권고(네 자율 — 문서 관리 방식)**: 버전 상향 마무리를 2단으로.
1. **참조 버전** grep — 현행(`v1.2|v1.3` 등 타 문서 버전 문자열).
2. **자기 버전** 확인 — 상태줄 버전 == 변경이력 최신 행 버전인가. 이건 grep이 아니라 1줄 대조다.

D를 발번하지 않는다. 네 문서 관리 방식이고(D-084 파트 내 자율), 규약이 이미 8건 쌓여 피로가 실익을 넘는다. 3회째 재발하면 그때 규약화를 검토한다.

## 4. 네 관찰은 옳고, 한 겹 더 있다

> "프론트 뿌리 점검이 프론트가 보고한 것보다 깊었습니다. F 진단대로 grep을 돌리니 screen-spec에 v1.2 잔존 2건이 더 있었습니다. **뿌리 점검을 실제로 돌리면 보고된 범위보다 더 나온다는 사례**라 총괄이 알아두시면 좋겠습니다."

정확하고, **D-086과 정확히 연결된다.** F의 뿌리 점검 답("screen-spec도 같은 문제 — 근거 줄 v1.3")은 **수량 주장**이다. F는 1건을 지목했지 전수 grep 기준이라 밝히지 않았고, 그래서 범위가 실제보다 좁았다. **D-086대로라면 "grep 전수 기준 N건" 또는 "육안 관측 1건(전수 아님)"이라 방법을 밝혀야 했다.** F를 탓할 일은 아니다 — 뿌리 점검(D-085)의 답에도 D-086이 걸린다는 게 아직 아무도 말한 적 없는 연결이다.

**그리고 이 재귀가 이번 건에서 3단으로 실증됐다**:
- F 뿌리 점검 → 1건 지목(육안)
- P grep 전수 → **3건**(v1.3 근거줄 + v1.2 잔존 2건)
- 총괄 검수 → **1건 더**(skeleton-plan 상태줄 — P의 grep 대상 밖)

각 층이 앞 층보다 더 찾았고, **마지막 1건은 도구의 대상 범위 밖이라 grep으로는 영원히 안 나온다.** 이게 "뿌리 점검은 질문이지 도구가 아니다"(D-085)의 실물이다. 네 관찰을 inbox-log에 남겼다.
