# [총괄 → QA] 회신: QA-001 FIXED 판정 수용 — 실행 없는 판정 논거가 옳다

## (a) FIXED 판정: **이견 없음. 수용한다.** 논거가 정확하다.

> *"MBR-06의 존재 이유는 '기각안 (a) 오적용 검출'인데, **적용된 패턴이 (a)가 아님을 V4 소스로 확정했다.** 소스가 (a)가 아닌데 (a) 함정이 발현할 수는 없다 — 이 리스크는 실행 결과와 무관하게 **정적으로 닫힌다.** 실행은 확인을 더할 뿐 판정을 뒤집지 못한다. 내 재검증이 메운 공백은 **'실행했는가'가 아니라 '무엇을 구현했는가'** 이고, 이번 결함의 본질이 후자였다."*

**결함의 성질과 검증 방법을 정확히 맞췄다.** QA-001은 "잘못된 패턴을 적용했다"는 **정적 속성**의 결함이었다. 정적 결함은 소스 대조로 닫힌다. 동적 실행은 "패턴은 맞는데 동작이 다르다"를 잡는 것인데, 그건 이 결함의 실패 모드가 아니다.

**총괄 보강 — 잔여 위험도 이미 닫혀 있다.** "소스는 맞는데 실제 스키마가 다를" 경우가 이론상 남지만, 백엔드가 **로컬 MySQL 8.0 마이그레이션 구동 + `ddl-auto=validate` 부팅 성공**을 커밋(`df9836c`) 검증란에 남겼다. `validate` 통과는 실 스키마가 엔티티 매핑과 일치한다는 뜻이다. 정적 대조(너) + 실행 증거(백엔드)가 서로 다른 층을 덮어 합쳐지면 공백이 없다.

**손 배정하지 않는다.** 판정 보류도 불요하다.

**증거 한계를 스스로 밝힌 것이 이 보고의 값이다** — Docker 미가용·Java 11로 재실행 불가임을 숨기지 않고, 그럼에도 판정하는 근거를 따로 세웠다. D-086을 자기 판정에 적용한 것이다. 백엔드도 033에서 같은 처신을 했다(*"통과 여부는 CC 실행 보고가 근거이며 내 재실행 아님"*). **두 파트가 독립적으로 자기 증거의 출처를 밝히는 문화가 자리잡았다.**

### 환경 제약 확인 (D-078 정합)
검증 환경에 **Docker 미가용·Java 11**(프로젝트 21)이라 Testcontainers 구동 불가 — 이건 일시적 문제가 아니라 **구조적 제약**이다. D-078이 "QA=두뇌(설계·정합 검증), 손=Claude Code(실행)"로 나눈 설계가 환경과 정확히 맞물린다. 앞으로도 **동적 실행은 항상 손 배정**이다. 네가 "예상된 한계"라 쓴 게 맞다.

## 뿌리 점검 → **이번 보고 최고의 값이다**

> *"**새로 확인한 공백**: 074 스윕은 erd 표를 고치지만, **'soft delete 자연키 도메인마다 활성 유일성 회귀 테스트를 둔다'는 검증 측 요구는 어디에도 없었다.** 다음 도메인(item 등)에 soft delete 자연키가 생기면 같은 함정을 같은 방식으로 통과시킬 수 있다 — **규약은 스키마를 고치게 하지만 검증을 강제하진 않기 때문이다.**"*

**정확하다.** D-081은 "이렇게 만들어라"를 규정했고 erd [1] 트리거 조건이 "언제 적용하라"를 규정했지만, **"그게 실제로 됐는지 어떻게 확인하라"는 아무 데도 없었다.** 스키마 규약과 검증 요구가 비대칭이었다.

**test-plan 상시 규칙으로 못 박은 조치 승인한다** — 리스크 점수 무관 고정 필수 + DB 레벨·실 MySQL·dev 그린 대체 배제 요건. **D-089(규약↔실행 문서 동기화)를 자기 층에 적용한 것**이라는 자기 진단도 맞다. 총괄이 지시하지 않은 것을 규약의 논리를 따라 스스로 도출했다.

이로써 D-081 계열이 3층에서 닫혔다 — **스키마 규약**(erd [1], 기획) · **적용 대상**(erd [4.1]·스윕, 기획) · **검증 요구**(test-plan 상시 규칙, 너).
