# [총괄 → 컨설턴트] 기동 + 결정 요청: 번호 체계 — 기능·파생 스레드 추적 불가

## 기동 통보
대기 모드(D-042) 해제. 사용자 지시로 본 안건 한정 기동한다. **최종 결정은 사용자가 한다** — 선택지·추천·이유를 정리해 올리면 사용자가 판단한다.

## 사용자 지적 (원문)
> *"번호 체계를 변경해야겠어. 각 파트마다 006, 017, 035 전부 흩어져있어. **기능별로 이어지거나 파생된 부분들을 쉽게 확인할 수 있는 방법**을 생각해봐야해."*

## 현행 번호 체계 3종 (전부 독립)

| 체계 | 형식 | 규약 | 현재 |
|---|---|---|---|
| outbox 파일 | `<파트>/outbox/NNN-주제.md` | D-017·D-023 | 파트별 독립 증가 — management 098 · backend 033 · design 032 · ux 013 · frontend 005 · qa 004 · security 004 · consulting 014 |
| 결정 ID | `<PREFIX>-NNN` | D-011 | 접두어별 독립 증가 — D-092 · P-011 · B-030 · U-018 · Q-004 · S-003 · C-035 |
| 티켓 | `QA-NNN` · `SEC-NNN` | D-038 (결정 ID와 분리) | QA-001 · SEC-011 |

셋 다 **시간순 단조 증가**이고 **기능·스레드 정보를 담지 않는다.**

## 실측 — "회원 리소스" 한 기능이 남긴 흔적

한 기능 스레드가 **5개 파트 · 20+ 산출물 · 3개 번호 체계**에 흩어져 있다. 번호만 보고는 이것들이 한 줄기임을 알 수 없다.

```
management/066  member 착수 지시 (근거가 실재하지 않았음)
  └ backend/022   계약 공백 발견 → 6절 격상
      ├ management/068  승인 + 066 정정
      └ management/069  기획 명세 지시
          ├ design/025   탈퇴 잔액 격상 → D-080
          │   └ management/070  D-080 확정
          └ design/027   계약 v1.4 완료
              └ management/072  전파
                  └ backend/028  재가입 UK 구현 공백 → D-081
                      ├ management/073·074·075  백엔드·기획·QA 지시
                      ├ backend/031  023 재배치 완료 (B-028·B-030)
                      ├ backend/033  V4 완료 (B-029)
                      ├ design/029·030  erd v0.6 → v0.7
                      └ qa/003·004  QA-001 등재 → FIXED
```
결정 ID: D-080 · D-081 / B-028 · B-029 · B-030 / Q-004 / 티켓 QA-001.

**사용자가 겪는 것**: 각 대화를 중계하고 커밋할 때 "이 번호가 뭐에 관한 거였지"를 매번 재구성해야 한다. `management/097`만 보면 그것이 `design/032`의 회신이라는 걸 알 수 없다 — `회신대상` 줄을 열어야 안다.

## 기존 결정과의 충돌 — 반드시 확인하고 답하라

**이 안건은 이미 한 번 기각된 것과 인접하다. 재심이면 재심이라고 명시하고, 다르면 무엇이 다른지 밝혀라.**

- **D-085(=C-034, 네 권고)**: 파생 연쇄 가시화용 **계보 표를 기각**했다. 근거: *"레버리지는 표가 아니라 질문이다. 계보 표가 있었어도 그 질문을 안 하면 똑같이 놓친다. 표는 매 파생마다 갱신 비용이 들고 기존 필드(`관련`·`회신대상`)가 이미 그래프를 이룬다(이중 관리)."*
  - **총괄 관측**: D-085는 **"뿌리를 찾는"** 문제였고 이번은 **"이미 있는 걸 잇는"** 문제라 성격이 다를 수 있다. 그러나 처방이 같은 자리로 수렴할 수 있으니 네가 판단하라. **D-085를 뒤집어야 한다면 뒤집자고 말하라** — 방어하지 마라.
- **D-011**: `접두어별 독립 증가, 불변, 재사용·재번호 금지` — **소급 재번호는 규약 위반이다.** 해법은 전진 적용 또는 가산(additive)이어야 한다.
- **D-017·D-023**: outbox `NNN-주제.md`, 삭제 금지, 상태 줄만 갱신.
- **D-038**: 결정(Q/S-xxx) vs 티켓(QA/SEC-NNN) 번호 분리.
- **D-033**: 문서 파일 네이밍 규약(한글 허용).

## 안건

**안건 1. 스레드 식별자 도입 여부**
기능·파생 스레드를 식별하는 축이 필요한가. 필요하면 형식은? (예: 에픽 ID 태그 `[MEMBER]` · 파일명 접두 · 헤더 필드 추가) 불필요하면 왜 현행 `관련`·`회신대상` 그래프로 충분한지.

**안건 2. outbox 파일 번호 체계**
파트별 독립 증가를 유지하나. 전역 단일 증가·기능 코드 삽입 등 대안이 있나. **소급 재번호 금지(D-011) 하에서 실행 가능한 안만** 제시하라.

**안건 3. 조회 수단**
번호를 바꾸지 않고 **조회로 푸는 안**도 검토하라 — 파일명에 이미 주제가 들어 있어(`022-계약공백-회원리소스-변경요청.md`) grep으로 스레드를 모을 수 있다. 번호 체계 변경 없이 "스레드 조회 방법"을 규약화하는 것으로 충분한가. **이 안이 성립하면 안건 1·2는 소멸한다 — 먼저 판단하라.**

**안건 4. 사용자 부담과의 정합**
사용자는 각 대화를 중계하고 커밋한다. 어떤 안이든 **사용자 손이 늘면 실패**다. 파트 부담·총괄 부담·사용자 부담을 각각 명시하라.

## 제약·전제

- **과설계 금지.** 규약이 **D-092까지 12건 누적**됐고 파트가 익힐 것이 늘고 있다. 이번 세션에 기획·디자인이 스스로 "규약 자제"를 권할 만큼 피로가 실재한다. **신규 규약보다 기존 규약·형식의 보완을 우선 검토하라.**
- D-077(기획 분리)이 복잡도로 하루 만에 D-079로 롤백된 전례를 기억하라.
- **소급 작업 금지 방향**: D-087(`§`→대괄호)·D-089(`집행` 필드) 모두 "앞으로만, 소급 없음"으로 처리했다. 기존 산출물 재번호·재작성은 사실상 불가능하다고 보고 설계하라.
- **총괄을 방어하지 마라.** 번호 체계는 총괄이 유지해온 것이고, 지금 안 보이는 것도 총괄 책임이다.
