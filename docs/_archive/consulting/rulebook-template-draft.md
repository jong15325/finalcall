# 공통 규약 문서 템플릿 (초안)

성격: 미확정 초안 — 타 역할 근거 인용 금지 (D-014 유형 4)
소유: 컨설턴트 · 2026-07-15 · 관련: 사용자 지시(docs 전면 개편), 099 안건 B·D

---

## 0. 이 템플릿이 푸는 문제

**증상**: 파트가 "지금 유효한 규약이 뭔가"를 알려고 `decision-log.md` 1,377줄을 읽는다.
그 안에 `grade 축 제거`·`골드포스 아트 확정`·`탈퇴 잔액 소멸` 같은 **이미 끝난 작업의 결정**이
규약과 같은 무게로 섞여 있다. 매 대화가 매번 이걸 다시 읽는다.

**원인**: `decision-log`는 유형 3(이력·불변)인데 유형 2(지침·현행)로도 쓰이고 있다.
한 문서가 **"무슨 일이 있었나"**와 **"지금 뭘 해야 하나"**를 겸한다.

**처방**: 두 축을 분리한다.

| | 규약 문서 (신설) | 결정 로그 (현행 유지) |
|---|---|---|
| 답하는 질문 | 지금 뭘 해야 하나 | 왜 그렇게 정해졌나 |
| 내용 | 행동 규칙만 | 이유·기각 대안·사례·이력 |
| 시제 | 현재·명령형 | 과거·서술형 |
| 갱신 | 덮어쓴다 (현행만 남음) | 불변 (append만) |
| 분량 | 얇게 — 부팅 필독 | 두껍게 — 필요 시 조회 |
| 특정 작업 내용 | **금지** | 허용 (그게 이력이니까) |

**규약 문서는 "왜"를 쓰지 않는다.** 이유는 로그에 있고 `근거:` 줄로 링크만 건다.
이유를 규약에 쓰면 규약이 로그를 닮아가고, 두 번째 decision-log가 생긴다.

## 1. 편입 판정 — 3문 테스트

**세 문항 전부 "예"여야 공통 규약에 넣는다. 하나라도 "아니오"면 결정 로그에만 남긴다.**

| # | 질문 | 아니오면 |
|---|---|---|
| **Q1 재사용** | 이 규칙이 **앞으로 새로 시작할** 작업에도 적용되나? | 작업 결정 — 로그행 |
| **Q2 고유명사** | 도메인명·파일명·ID·버전·날짜를 **지워도 규칙이 성립**하나? | 작업 결정 — 로그행 |
| **Q3 행동** | 누군가 이걸 읽고 **다르게 행동**하나? | 이력·설명 — 로그행 |

이런 건 "공통 규약"이 아니라 **파트 지침**으로 간다. 규약과 지침은 다른 층이다.

## 2. 규약 항목 형식

```markdown
### R-NNN. <규칙 한 문장 — 명령형, 무엇을 하라/하지 마라>

적용: <누가 · 언제>
규칙:
- <행동 1 — 검증 가능하게>
- <행동 2>
예외: <없으면 이 줄 삭제>
근거: D-xxx<, D-yyy>
```

**작성 규칙**
- **명령형 현재.** "~한다 / ~하지 않는다". 과거·경위 서술 금지.
- **이유 금지.** "왜냐하면"이 나오면 그건 로그로 간다. `근거:` 줄의 D 번호가 이유를 대신한다.
- **고유명사 금지.** 도메인명·파일명·특정 ID·버전·날짜가 규칙 문장에 들어가면 Q2 탈락이다.
  (단 규약 자신이 가리키는 문서 경로는 예외 — 예 "정본은 api-contract.md")
- **한 항목 = 한 규칙.** 묶지 않는다.
- **예외는 세어라.** 예외가 2개를 넘으면 규칙 자체가 틀린 것이다. 다시 설계한다.

### 예시 (D-023 → 규약 항목으로 변환)

```markdown
### R-012. 역할 간 전달은 발신자 outbox에 파일로 남긴다

적용: 전 역할 · 모든 발신(결정 요청·회신·보고·공유)
규칙:
- 주제당 1파일 `<역할>/outbox/NNN-주제.md` 로 쓴다. 삭제하지 않는다.
- 머리에 상태 1줄을 둔다: `상태: SENT | ANSWERED → <결정 ID 또는 회신 경로>`
- 회신도 발신이다. 자기 outbox에 쓰고 `회신대상: <경로>` 를 명기한다.
- "수신함 확인" 지시를 받으면 전 역할 outbox에서 `[X → 자기역할]` 을 스캔하고,
  자기 inbox-log.md 에 없는 파일만 처리한 뒤 1줄 추가한다.
근거: D-023, D-017
```

원본 D-023 로그 항목의 이유·기각 대안·레퍼런스(액터 모델 메일박스 패턴 등)는 **가져오지 않는다.**
로그에 있고, 링크가 걸려 있다.

## 3. 규약 문서 전체 골격

```markdown
# FinalCall 공통 규약

이 문서 하나로 "지금 뭘 해야 하나"가 끝난다. 이유가 궁금하면 `근거:` 의 D 번호를 로그에서 찾는다.
개정: 소유 역할 제안 → 총괄 승인 → 이 문서를 덮어쓴다(이력은 git).
최종 갱신: <날짜> · 반영 최신 결정: D-<NNN>

## 1. 역할과 권한
## 2. 결정 권한 (에스컬레이션 기준)
## 3. 문서 구조와 소유권
## 4. 결정 로그 규칙
## 5. 메시지 프로토콜
## 6. 확정 스펙 변경 절차
## 7. 게이트와 리추얼
## 8. 도구
```

**절 번호는 고정한다.** 항목이 추가돼도 절을 새로 만들지 않고 해당 절 안에 R 번호로 붙인다.
절 번호가 흔들리면 전 문서의 `[N.M]` 참조가 깨진다(D-087).

## 5. 개정 규칙

- **규약 문서는 덮어쓴다.** 결정 로그와 달리 불변이 아니다. 현행만 남는다.
  이력은 git이 갖는다 — 그래서 부분 SUPERSEDE 주석이 필요 없다.
- **D가 채택되면 같은 커밋에서 규약 문서에 반영한다.** 반영 없이 D만 채택하는 것을 금지한다.
  (D-089 `집행` 필드가 이걸 강제하려던 것 — 규약 문서가 생기면 `집행:` 은 "규약 [N] 갱신"으로 단순해진다.)
- **부분 SUPERSEDE가 사라진다.** 현행 D-043·D-069·D-072의 "본문은 살아 있고 일부 조항만 대체"
  문제는, 규약 문서를 덮어쓰면 자동 해소된다. 로그는 이력이므로 그대로 두면 된다.

## 6. 이 설계가 풀지 못하는 것 (한계 자진 명시)

1. **분류 오판은 못 막는다.** 3문 테스트는 판정을 **명시적으로 만들 뿐** 정확하게 만들지 않는다.
   경계 사례(D-081 같은)는 여전히 사람이 판단하고 틀릴 수 있다. 효과는 "틀렸을 때 드러남"이다.
2. **이중 관리 위험이 새로 생긴다.** 규약 문서와 로그가 어긋날 수 있다. 5절의 "같은 커밋 반영"이
   유일한 방어이고, 이건 규율이지 장치가 아니다.
3. **문서가 1개 늘어난다.** 과설계 금지에 정면으로 걸린다. 상쇄 논거는
   "guide(293) + decision-log(1,377) 필독 = 1,670줄" 이 "규약 1장(추정 250줄) 필독"으로 바뀌어
   **부팅이 약 85% 줄고**, decision-log가 필독에서 빠진다는 것이다. 순증이 아니라 순감이어야 정당하다.
   → **대안: 신규 문서를 만들지 않고 `collaboration-guide.md` 를 이 골격으로 개편한다.**
      이미 규약 정본이고 절 구조도 유사하다. 문서 수 순증 0. 이쪽이 낫다고 본다.
