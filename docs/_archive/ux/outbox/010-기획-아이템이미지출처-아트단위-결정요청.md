# [디자인 → 기획] 결정 요청: 아이템 이미지 슬롯의 데이터 출처 · 아트 단위 (계약·스펙 공백)

배경: 사용자가 게임 카드창 구조를 제공했고 비주얼 방향을 원게임 UI 스킨 전면 차용으로 확정했다(U-016). 상거래 카드 설계에 착수하려 계약을 대조했더니, U-012가 전제한 "게임 카드 이미지 슬롯"의 **데이터 출처가 계약·스펙 어디에도 없다.** 임의 가정 금지 원칙에 따라 올린다.

탐색 방법(D-086): `docs/*.md` 전체에 `image|imageUrl|이미지|asset|sprite|thumbnail` 대소문자 무시 grep. 계약 [3.3] item 블록 직접 확인.

## 확인된 사실

계약 [3.3] item 블록 = `{ typeCode, mainCategory, subGroup, element, kind, level, skill1?, skill2?, skillPercent, goldforceExpireAt?, nameSnapshot, specSnapshot }` — **이미지 참조 필드 없음.**

domain-spec [7] 인용: "아이템 시각 자산(이미지 등) 관리와 감정·진위 검증도 이번 범위에서 다루지 않으며 필요 시 후속 확장한다."

즉 스펙이 이미지 관리를 명시적으로 범위 밖에 뒀다. 이건 결함이 아니라 의도된 절단으로 읽히는데, 그렇다면 카드에 아이템 그림을 어떻게 띄우는지가 비어 있다.

## 안건 1. 이미지 슬롯의 데이터 출처

- 선택지:
  (a) **프론트가 `typeCode` → 정적 자산으로 매핑**(이미지는 프론트 번들, 서버 무관). 계약 변경 0, domain-spec [7] "서버가 시각 자산을 관리하지 않는다"와 정합 유지.
  (b) 계약 item 블록에 `imageUrl` 등 필드 추가 → 6절 계약 변경 + 서버가 자산 관리 → domain-spec [7] 개정 동반.
  (c) 이미지 없이 텍스트·아이콘만으로 카드 구성 → 게임 스킨 차용(U-016)·U-012 전제와 충돌.
- 추천: **(a)** — `typeCode`는 "고정 시드·유일 조합"이고 이미 외부 식별자로 확정돼 있어(035, 계약 [4.1] 비고) 정적 매핑 키로 그대로 쓸 수 있다. 서버가 자산을 지지 않으므로 domain-spec [7]을 건드리지 않고, 6절 절차도 불요다. 되돌리기도 싸다(후에 서버 관리로 승격 시 필드 추가).

## 안건 2. 아트 단위 — `typeCode` 1개당 이미지 1개인가

- 선택지:
  (a) **`typeCode` 단위** — [대분류][중분류/슬롯군][속성][종류] 조합마다 아트 1개. 레벨·골드포스·스킬은 계약 데이터로 아트 위에 오버레이(게임 카드창의 `Level 9` 배지와 동일 구조).
  (b) `typeCode` × 레벨 단위 — 레벨마다 다른 아트. 자산 수가 배수로 늘고 프론트 번들·자산 제공 부담이 커진다.
- 추천: **(a)** — 게임 카드창 스크린샷에서 레벨이 아트 위 배지로 얹혀 있어 아트와 레벨이 분리된 층으로 보인다. 다만 이건 스크린샷 1장에서 온 추정이라 원게임 실제 구조 확인이 필요하다(사용자는 "잘 모르겠다"로 기획 확인 요청).
- 사용자 입력이 필요하면 그 경로로 확인해 달라 — 원게임 데이터 전면 사용(D-067)이라 실물 근거가 있을 것이다.

## 안건 3. 계약에 데이터가 없는 카드창 필드 3종 — 웹 카드에서 제외 확인

게임 카드창에는 있으나 계약 item 블록에 없는 것: `채널링대`(고수채널이상) · `합성조건` · `능력수치`.

- 내 판정(확인만 요청): 셋 다 웹 상거래 카드에서 **제외**한다.
  - `합성조건` — domain-spec [7] 인용: "강화·합성 행위는 도메인 범위 밖이다. 이 플랫폼은 거래를 다루지 게임 플레이를 다루지 않는다"(D-046). 명시적 범위 밖.
  - `채널링대` — design/outbox/024 부수 회신 판정("등급 표기는 장식 계층 허용, 필터·정렬 축 승격 금지")과 정합. 데이터 필드가 없으므로 아트에 그려진 장식으로만 존재.
  - `능력수치` — 계약에 대응 필드 없음. `specSnapshot`이 이를 담는 자리인지 불명(아래 안건 4).
- 회신: 이 판정이 맞는지 확인만 필요. 이견 없으면 회신 불요.

## 안건 4. `specSnapshot`의 내용 정의

- 계약 [3.3] 주에 "item.nameSnapshot/specSnapshot은 등록 시점 스냅샷(D-045)"만 있고 **specSnapshot의 구조·내용이 정의돼 있지 않다.**
- 게임 카드창의 `기본특징` 탭 내용("1. 공격 시간 27% 감소 / 2. 부스터 불가 7초(23%)")이 여기 해당하는지, 아니면 자유 텍스트인지에 따라 카드·상세의 표현이 달라진다.
- 회신: 필요 — 구조(자유 텍스트 / 키-값 / 배열)만 알려주면 표현은 디자인이 정한다.

뿌리 점검 (D-085): 같은 원인이 다른 층에도 공백을 만들었나 — **그렇다.** 이미지 출처 공백의 뿌리는 "domain-spec이 시각 자산을 범위 밖으로 절단했는데, 그 절단이 화면 층(screen-spec·design-system)에 번역되지 않아 디자인이 이미지 슬롯을 전제로 U-012를 발번한 것"이다. 같은 계열로 `specSnapshot`(안건 4)도 계약에 이름만 있고 내용이 화면 층에 번역되지 않았다. 두 건 모두 스펙 자체는 옳고 하위 실행 문서와의 비동기화 — D-089가 겨냥한 유형이다.
