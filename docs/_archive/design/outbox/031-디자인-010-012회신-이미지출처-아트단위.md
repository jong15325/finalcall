# [기획 → 디자인] 결정 회신: 아이템 이미지 출처 · 아트 단위 (010+012)

**5안건 중 4건 확정, 1건(골드포스 아트)만 총괄 격상.** 상거래 카드 블로킹은 이 회신으로 해소된다.

자산을 실측해 자기 추천을 스스로 뒤집은 정정(012)이 정확한 판단이었다. 스크린샷 추정으로 (a)가 확정됐으면 아트 단위를 잘못 잡아 자산 체계 전체를 다시 짜야 했다.

## 정정 3 관련 — **`mainCategory` 매핑 확인은 불요하다. 네 경로 템플릿에 오류가 있다.**

012가 "이 매핑이 확정돼야 경로가 결정된다"며 남긴 마지막 확인 사항인데, **확인할 필요가 없다.** 네 실측 수치가 이미 답을 담고 있다.

`gold_black` = **648 = 9레벨 × 2크기 × 4속성 × 9종류**. 이 산술에 **`mainCategory` 차원이 없다.** 648이 네 개 축으로 정확히 나누어떨어지고 남는 자리가 없다.

그리고 `gold_black`이 `mainCategory` 값이라면 다른 mainCategory 값에 해당하는 아이템 세트가 있어야 하는데, **네 실측이 `silver`(캐릭터·이벤트)·`white`(속성·구매)는 아이템이 아니라고 확인했다.** 즉 `gold_black`은 mainCategory 값이 아니라 **고정 세그먼트**다.

→ 경로 = **`gold_black/level{level}/{l|s}/{element}/{kind}.png`**. 소비 필드 = `level`·`element`·`kind` **3개**(네가 4개로 본 것에서 mainCategory 제외).

## 안건 1 — 이미지 출처 → **(a) 채택** (P-012)

서버는 이미지 필드를 갖지 않는다. 프론트가 계약 필드로 정적 경로를 파생한다.
- 경로가 계약 필드만으로 완전히 결정되므로 **계약 변경 0 · domain-spec [7] 개정 불요 · 6절 절차 불요.** 네 (a) 추천이 실측으로 강화됐다는 판단 그대로다.
- 되돌리기 싸다 — 후에 서버 자산 관리로 승격하면 [3.3]에 필드 추가(6절).
- 반영: `screen-spec [3.5-b]`에 명시했다. **이게 010 뿌리 점검("스펙의 절단이 화면 층에 번역되지 않았다")에 대한 대응이다** — domain-spec의 범위 밖 절단을 화면 층 기준선으로 번역해 뒀으니 다음에 같은 질문이 반복되지 않는다.

## 안건 2 — 아트 단위 → **(b) `typeCode` × 레벨 확정** (실측 수용)

`l` 324개 md5 전수 → 고유 324·중복 0, 파일 크기가 레벨과 함께 증가. 반증이 명확하다. 010의 (a)는 폐기.

## 정정 2 — 레벨 배지 → **조건부 동의** (P-013). 전면 위임은 안 된다.

"레벨 시각 표기를 아트에 위임하고 웹은 배지를 그리지 않는다" — **원칙은 동의**한다(중복 표기 방지). 대체텍스트에 `level` 필수라는 판단도 맞다.

**다만 전면 적용은 도메인 요구를 깬다.** 레벨은 시세 집계 단위의 축이고(D-044 조건, erd 인덱스 `(template_id, level, skill1_id, skill2_id)`) 공통 목록 필터의 축(`minLevel/maxLevel`)이다. **거래 의사결정의 1급 정보**다. 그런데 네 설계는 `s`(26×28)를 목록 카드로 쓴다 — **26×28에 구워진 원게임 폰트 배지가 목록에서 판독 가능한가?** 판독이 안 되면 사용자가 목록에서 레벨로 매물을 비교하지 못한다.

→ 도메인 요구: **목록에서 레벨은 판독 가능해야 한다.** `s` 자산의 구운 배지로 그게 충족되는지 판정은 **네 소관**이고(U-012 — 표현), 불충분하면 계약 `level`로 표기하라. 상세(`l` 3x 확대)는 아트 위임으로 충분해 보인다.

즉 "위임 여부"가 크기별로 갈린다. 일괄 규칙이 성립하지 않는 게 이 건의 실질이다.

## 안건 3 — 계약 미보유 3필드 → **확인. 2건 확정, 1건 보정.**

- `합성조건` — 제외 확정. D-046 명시적 범위 밖.
- `채널링대` — 제외 확정. design/024 판정(장식 계층 허용·필터/정렬 축 승격 금지)과 정합. 네 판정 그대로다.
- `능력수치` — **"제외"보다 정확히는 "별도 필드가 없다"**. 아래 안건 4대로 `specSnapshot` 요약 문자열에 포함될 여지가 있다. 독립 필드로 표현하지 마라.

## 안건 4 — `specSnapshot` 구조 → **단일 문자열(자유 텍스트). 이미 확정돼 있었다.**

새로 정할 것이 없다. 아래 두 곳에 이미 결정돼 있다.
- `erd`: `item_spec_snapshot **VARCHAR**` — "등록 시점 핵심 스펙 요약 스냅샷"(auction·shop 양쪽).
- `domain-spec [7.4]`: "등록 시점의 표시 필드(예: 표시명, **핵심 스펙 요약**)를 스냅샷으로 보존(D-045). 이유는 이력 정합 — 템플릿 시드가 수정·개편돼도 과거 매물·거래 이력의 표시는 등록 당시 상태로 고정."

→ **키-값도 배열도 아니다. 임의 길이 문자열 1개.** 네 요청("구조만 알려주면 표현은 디자인이 정한다")에 대한 답이다.

**주의**: 문자열의 **내용 구성**(무엇을 요약하는가 — 게임 카드창 `기본특징` 탭이 여기 해당하는지 등)은 아직 미확정이며 시드 단계 확정분이다(D-048 아이템 세부). 그러니 **내용에 의존하지 않는 표현**으로 설계하라 — 길이 가변 전제, 줄바꿈·말줄임 처리. 내용이 확정돼도 표현을 다시 짜지 않아도 된다.

이것도 010 뿌리 점검의 두 번째 사례("계약에 이름만 있고 내용이 화면 층에 번역되지 않았다")다 — 구조는 확정돼 있었는데 화면 층에서 보이지 않았을 뿐이다. `screen-spec [3.5-b]`에 번역해 뒀다.

## 안건 5 — 골드포스 아트 교체 → **총괄 격상.** 도메인 제약은 아래대로 전달했다.

네 발견이 정확하다 — `gold_force` 18개 = 2크기 × 9종류로 **레벨·속성 분기가 없다.** 아트가 통째로 교체되는 구조라면 골드포스 활성 아이템은 **레벨·속성 시각 정보를 잃는다.**

**도메인 제약(내가 총괄에 전달한 것)**: 레벨·속성은 시세 집계 축·필터 축이다. 골드포스 활성 매물만 이 정보를 시각적으로 잃으면 **그 매물만 거래 판단이 불가능**해진다. 골드포스는 D-066상 시세 키에서 제외된 부차 속성인데, 부차 속성 때문에 1급 축이 가려지는 건 도메인상 성립하지 않는다.

다만 **원게임 충실도(U-016 전면 차용)와 충돌**할 수 있고 비주얼 최종은 총괄+사용자다(D-072). 그래서 내가 단독 확정하지 않고 격상했다(design/outbox/032). 원게임 실제 동작 확인도 사용자 경로가 필요하다.

**네 D-066 질문에 대한 내 해석**(참고): D-066은 골드포스를 "**검색 필터만·시세 키 제외**"로 뒀다. 이건 **검색·집계 축**에서의 배제이지 **표시 금지가 아니다.** 계약 [3.3]이 `goldforceExpireAt`을 노출하고 있는 것이 그 증거다 — 표시하라고 준 필드다. 따라서 "D-066이 표시까지 배제했나"의 답은 **아니다**. 문제는 표시 여부가 아니라 아트 교체 시 다른 정보가 소실되는 것이다.

## 네가 자체 처리한다고 통지한 것 — 이견 없음

`image-rendering: pixelated`·정수배 확대·`s`/`l` 용도 배분 전부 표현 소관(U-012)이다. 다만 `l`(50×93) 3x = 150×279가 상세 주인공으로 작다는 관측에 동의한다 — 필요하면 4x 이상도 네 판단이다. 원본 도트 보존 판단은 픽셀 아트 전제상 맞다.

## 진행 가능 여부

- **상거래 카드 설계 착수 가능.** 블로커였던 이미지 출처·아트 단위·경로·specSnapshot 구조가 전부 확정됐다.
- **골드포스 아트만 대기.** 골드포스 활성 카드의 아트 처리만 총괄 회신 후 확정하면 된다 — 나머지는 막지 않는다.
