# [기획 → 디자인] 결정 회신: auth 폼 미확정 2건 (008)

수신처 정정 확인 — D-079로 PF가 기획(P)에 흡수돼 회신 주체는 기획(P)다. 임의 확정하지 않고 넘긴 판단이 규약 정합이다(계약·스펙 소유는 P).

두 안건 모두 계약 §2 대조 결과 **계약 무영향**이라 6절 격상 없이 기획 자율로 확정했다(P-009·P-010·P-011).

## 안건 1. 회원가입 "비밀번호 확인" 필드 → 포함 (P-009)

- 결정: 폼에 포함한다. **클라이언트 일치 검증 전용, 서버 미전송**. 계약 signup body `{loginId, password, nickname}`는 불변.
- 이유: 비밀번호 변경·재설정이 이번 범위에서 제외됐다(068, B-016 보안게이트2 이월). 가입 시 오타로 굳은 비밀번호를 사용자가 스스로 복구할 경로가 **현재 없다**. 확인 필드는 계약 비용 0으로 그 리스크를 막는 가장 값싼 방어다.
- 와이어프레임 반영: loginId · password · password 확인 · nickname 4필드. 확인 필드 불일치는 클라 검증 에러(서버 400 아님).

## 안건 2. 인증 성공 후 이동 플로우

### 2-1. 회원가입 성공(201) 후 → 로그인 화면 이동 (P-010)

- 결정: `/login`으로 이동. **자동 로그인하지 않는다.** 가입 성공 안내 + loginId prefill로 재입력 부담 완화.
- 이유: 계약 signup 201 응답이 `{userPublicId, nickname}`으로 **토큰이 없다**. 자동 로그인은 계약 변경(signup 토큰 반환) 또는 클라의 login 재호출을 요구하는데,
  - 계약 변경은 6절 비용 + "가입=즉시 세션 부여"로 보안 성격을 바꿔 자금 시스템에서 과하다.
  - login 재호출은 login·signup 모두 엣지 rate limit 대상(SEC-005·§1.6)이라 연속 호출이 버스트로 `GATEWAY_429`를 유발할 수 있다. 가입 직후 자동 로그인이 429로 실패하면 UX가 오히려 나빠진다.
- 와이어프레임 반영: 가입 성공 → 성공 안내 → 로그인 화면(loginId 채워진 상태).

### 2-2. 로그인 성공(200) 후 → 홈 `/` 기본 + returnUrl 복귀 (P-011)

- 결정: 기본 목적지는 홈 `/`. 단 **인증 필요 라우트에서 튕겨 로그인에 유입된 경우 원래 목적지로 복귀**(returnUrl 보존). 복귀 대상은 앱 내부 라우트로 한정(외부 URL 금지 — 오픈 리다이렉트 방지).
- 이유: 마이페이지·판매등록·인벤토리 등에서 유입된 사용자를 홈으로 보내면 목적을 잃는다. 이 규칙은 IA 셸의 인증 가드와 묶이므로 스켈레톤 기획(063)에도 반영한다.
- 와이어프레임 반영: 로그인 화면 자체엔 분기 표현 불요(라우팅 동작). "가입하기" 상호 링크만 유지.

## 반영 결과

- screen-spec §3.1 auth에 위 폼 구성·플로우를 확정 기재했다(기준 계약도 v1.2 → v1.3 갱신).
- 디자인은 wireframe-auth.html에 안건1의 4필드 + 안건2-1의 가입 성공 후 로그인 이동을 반영하면 된다.

## 부수 회신 — ux/006 등급 표기 관찰 (회신 불요 건이나 판정 통지)

차용 게임 카드 아트에 등급(S)·채널링등급 표기가 포함되는 건이다. **도메인 표현상 문제 없다**고 판정한다. D-073이 제거한 것은 **기능적 등급 축**(필터·정렬·시세 키·응답 필드)이고, 이미지 내 장식 표기는 계약 §3.3 스키마에 등급 필드가 없는 이상 도메인과 충돌하지 않는다. 다만 사용자가 "등급으로 거를 수 있다"고 오인할 여지는 있으므로, **등급 표기를 필터·정렬 UI의 축으로 승격하지 말 것**을 조건으로 둔다(장식 계층에 머무르는 한 허용).
