# [기획/설계 → 총괄] 완료 보고: api-contract v1.3 — 게이트웨이 엣지 오류 응답 명세

결과: 게이트웨이 엣지 오류(rate limit 429·직접접근 403)를 서비스 ErrorResponse envelope로 통일하는 계약 명세를 v1.3으로 반영했다(6절 계약 변경, 057 지시=총괄 승인).

산출물: docs/api-contract.md v1.3
- §1.6 게이트웨이 엣지 오류 신설: envelope `{success:false, code:"GATEWAY_NNN", message, timestamp}`(errors 미포함), code는 GATEWAY_ 프리픽스 엣지 발생 코드(도메인 ErrorCode enum 1:1 예외).
- 엣지 코드 2종: `GATEWAY_429` rate limit 초과(→429, Retry-After 동반), `GATEWAY_403` 직접접근 차단(→403).
- §5 에러코드 표에 GATEWAY_429·GATEWAY_403 등재 + 1:1 규칙 예외 주석.
- 버전 이력 v1.3 기록(사유: D-068 엣지 429 포맷 통일, 056 안건1 A).

완료 기준 대비:
- 공통 오류 절 엣지 응답 스키마 추가(429·게이트웨이 계열, 서비스 동일 포맷): 충족(§1.6).
- 직접접근 403 명세 판단·반영: 충족 — 반영하되 "정상 경유 클라이언트 미해당·QA/보안 음성 테스트용, 프론트 별도 처리 불요"로 분류. envelope 일관성은 확보하되 프론트 소비 부담을 주지 않는 선택.
- v1.3 변경 이력 기록: 충족.
- 하지 말 것(도메인 에러코드·envelope 포맷 변경) 준수: 서비스 코드 무변경, envelope 포맷 동일.

설계 판단(회신 불요, 이견 시에만):
- 429에 Retry-After 헤더 동반을 명세했다(프론트 백오프 DX). 게이트웨이 커스텀 에러 핸들러 구현 시 반영 대상.
- GATEWAY_ 프리픽스는 도메인 enum과 분리(게이트웨이는 도메인 ErrorCode 미보유 WebFlux 모듈). 백엔드 구현이 이 코드·필드에 맞춰 핸들러 확정.

다음 단계 제안: 확정 시 프론트·QA·백엔드 전파(백엔드는 게이트웨이 커스텀 에러 핸들러를 v1.3 코드에 맞춰 구현). 프론트 복사본 갱신 체크리스트 반영.
