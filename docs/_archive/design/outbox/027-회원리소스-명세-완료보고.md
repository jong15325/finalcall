## 완료 기준 대비 (069)

### 1. domain-spec §6.1 — 충족
- **프로필**: 본인 조회만. **타인 프로필 조회 미도입** — 목록·상세의 소유자·최고입찰자 마스킹(§3.3)과 정면 상충하기 때문이다(마스킹해 가려놓고 프로필을 열면 마스킹이 무의미). SEC-007 열거 노출면도 넓어진다.
- **닉네임 변경**: 허용, **빈도 제한 없음**. 표시명이 마스킹되어 노출되므로 사칭·평판 세탁 리스크가 낮고, 빈도 제한은 변경 시각 보존(스키마 추가)을 요구해 이번 범위 대비 이득이 작다. 필요 관측 시 후속 확장.
- **탈퇴 정책** (핵심):
  - 잔액 — 잔존해도 허용 + 명시 동의 필수(D-080). 실결제 도입 시 재검토 조건 명문화.
  - 진행 중 거래 — 경매(판매자)·홀드 보유 입찰·미완료 주문 중 하나라도 있으면 **차단**.
  - 세션 — refresh 전부 폐기(SEC-006).
  - 이력 — 보존 + 표시명 마스킹(상대방 이력이 타인 탈퇴로 사라지면 안 됨).
  - 재가입 — login_id·nickname **재사용 허용**(erd 1절 "soft delete 자연키 유니크는 삭제 식별 포함 — 삭제행-신규행 충돌 회피"의 설계 의도 그대로. 앱 레벨로 되돌리면 컨벤션과 싸우는 꼴).
- **잔액과 진행 중 거래에서 정책이 갈리는 근거**를 "피해 귀속의 비대칭"으로 명문화했다 — 잔액 소멸은 본인 손실이라 동의로 해소되지만, 진행 중 거래를 일방 탈퇴로 깨면 **거래 상대**가 피해를 입는다. 동의로 처분할 수 있는 건 자기 몫뿐이다.

### 2. api-contract §2.5 — 충족
- **절 위치 판단**: §2.5(인증 뒤) 채택, §2 제목을 "인증·회원"으로 확장. 이유 — (a) `:96` 전방 참조가 **§2 말미**에서 가리키던 대상이 바로 이것이라 참조 이행이 자연스럽고, (b) 계정 생애주기(가입→로그인→프로필→탈퇴)가 한 곳에 모이며, (c) **최상위 절 신설은 §3·§4·§5 renumbering을 유발**해 백엔드·QA·프론트의 기존 인용(§3.3·§5 등)을 전부 깨뜨린다. 이 파괴를 피하는 게 결정적이었다.
- `GET /me` → `{userPublicId, nickname, isAdmin, createdAt}`. loginId·passwordHash 미노출(열거 리스크). isAdmin은 UI 노출 제어용이며 **인가는 서버 권위**임을 명시.
- `PATCH /me` → nickname 한정. `MEMBER_001` 중복 409.
- `DELETE /me` → 204. **body `{balanceForfeitAcknowledged: true}` 필수** — 잔액 0이어도 필수로 뒀다(클라 분기 제거 + 동의 감사 추적 일관성). refresh 세션 전부 폐기 명시(B-018 이월분과 모순 없음 — 폐기 방향이라 더 강한 쪽).
- `:96` 전방 참조 정정 완료: "3절(후속)" → 프로필·수정·탈퇴 §2.5 / 잔액 §4.4. 정정 사실을 절 안에 주로 남겨 이력 추적 가능하게 했다.
- **잔액 조회는 §4.4 유지**(중복 명세 안 함) — 잔액은 화폐 관심사.

## MEMBER_ 채번 결과 (070 요청 — 백엔드 정합 지시 필요)

| 코드 | 의미 | HTTP |
|---|---|---|
| `MEMBER_001` | 닉네임 중복(프로필 수정) | 409 |
| `MEMBER_002` | 진행 중 거래 보유로 탈퇴 불가 | 409 |

**`MEMBER_001` 처리 — 백엔드 잠정 사용과 충돌한다. 재배치가 필요하다.**
- 백엔드는 `MEMBER_001`을 "잔액 행 부재"로 잠정 사용 중이다(backend/026). 나는 같은 번호를 **닉네임 중복**에 배정했다.
- **"잔액 행 부재"에는 MEMBER_ 코드를 부여하지 않았다.** 잔액 행은 가입 시 함께 생성되는 불변식(erd `user_balance` 1:1, V3)이므로 그 부재는 **도메인 규칙 위반이 아니라 데이터 무결성 위반**이다. 사용자가 취할 행동이 없어 클라이언트가 분기할 의미가 없고, §5에 등재하면 "정상적으로 발생 가능한 상태"라는 잘못된 신호를 프론트·QA에 준다. **500 내부 오류(COMMON 계열)로 다루는 게 맞다** — §5가 COMMON_004만 등재하고 나머지 공통 코드를 싣지 않는 현행과도 정합한다.
- 070의 "응답에 실리면 계약 대상" 기준에는 동의한다. 다만 이 코드는 **응답에 실려서는 안 되는 코드**라는 것이 내 판단이다(실린다면 그 자체가 버그 신호).
- 요청: 백엔드에 `MEMBER_001` → COMMON 계열 500 재배치 + `MemberErrorCode`를 v1.4 §5 기준으로 정합 지시 바람. D-028대로 계약이 기준이다.
