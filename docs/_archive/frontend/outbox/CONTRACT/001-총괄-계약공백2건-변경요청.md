## 안건 1. item `element` enum의 **wire 값이 계약에 열거돼 있지 않다**

**실물 — 지금 이 상태로 코드에 서 있다** (`frontend/src/types/schema.ts:12-25`):

```ts
export interface ItemBlock {
  typeCode: string;
  mainCategory: string;
  subGroup: string;
  element: string; // 공백: 계약에 enum 값 미열거 → string 유지
  ...
}
```

**탐색 방법**(`[5.34]`): 호스트 Read로 `spec/api-contract.md` `[3.3]` item 블록 + `frontend/src/types/schema.ts`
대조. **bash 미사용**(`_broadcast/001` 경고 — `api-contract.md`가 마운트에서 34줄 절단된 이력이 있다).

- 계약 `[3.3]`이 `element` **필드**는 정의하나 **값 목록**이 없다.
- `design-system`·`erd`는 **water/fire/earth/wind 4종**을 안다. 다만 **색 매핑으로만** 안다
  (`tailwind.config.js:36-41`의 `element.water/fire/earth/wind`가 그걸 그대로 받았다).
- **`[1.3]` 표기 규약이 enum은 대문자라고 말한다.** 그러면 wire는 `'WATER'`일 것 같은데
  **「같은데」로 타입을 좁히는 게 정확히 D-028이 금지한 것이다.** CC가 안 좁혔고 옳았다.

- **선택지**: (a) 계약 `[3.3]`에 `element` 값 4종을 대문자로 열거 (b) 지금 `string` 유지, item 도메인 착수 시 확정
- **추천: (a).** 이유 2개.
  1. **소문자 4종은 이미 3문서(`design-system`·`erd`·코드)가 안다. 모르는 건 wire 표기뿐이다** —
     **결정할 게 사실상 없고 받아 적는 것에 가깝다.** 비용이 거의 0이다.
  2. **`string`으로 두면 실패 신호가 없다.** 백엔드가 `WATER`를 보내고 프론트가 `water`로 분기하면
     **타입 체크를 통과하고 런타임에 조용히 아무 색도 안 칠한다.** 유니온으로 좁혀 두면 컴파일에서 잡힌다.
     **먼저 구현한 쪽이 기준이 되는 것을 D-028이 막고 있는데, `string`은 그 방어를 무력화한다.**
- **영향 범위**(네 판단 재료): 계약 `[3.3]` 1개 필드에 값 목록 1줄. **백엔드는 아직 item 미구현이라
  기존 코드 영향 0.** 프론트는 `schema.ts:16` 1줄을 유니온으로 좁힌다. **erd·design-system 무변경**(이미 안다).

## 안건 2. 상태 enum이 `[3.3]` 응답 스키마에 값 목록으로 없다 — **경미**

**실물** (`frontend/src/types/schema.ts:27-34`):

```ts
export type AuctionStatus = 'SCHEDULED' | 'ACTIVE' | 'SOLD' | 'UNSOLD' | 'CANCELLED';
export type ShopStatus = 'ACTIVE' | 'SOLD' | 'EXPIRED' | 'CANCELLED';
export type ResultType = 'BID' | 'BUYNOW';
```

- **값 자체는 공백이 아니다.** 계약 `[3.1]` 산문 + `screen-spec [3.2][3.4]` + `design-system [5.8]`에
  열거돼 있고 **CC가 문서화된 값만 썼다. 추측 0.**
- **문제는 위치다.** 값이 **산문과 타 역할 문서 3곳에 흩어져** 있고 `[3.3]` 응답 스키마에는 없다.
  `[3.3]`이 *"프론트·QA·디자인 단일 진실"*(코드 주석 `schema.ts:2`)인데 **상태 값만 거기 없다.**

- **선택지**: (a) `[3.3]`에 세 enum의 값 목록 명시 (b) 현행 유지 — 산문·타 문서로 충분
- **추천: (a). 단 안건 1보다 약하다.**
  이유: **산문은 조용히 갈린다.** `[3.1]` 산문에서 상태 하나가 늘면 `[3.3]`을 보는 사람은 모른다.
  QA가 `[3.3]`으로 시나리오를 짜면 그 상태가 시나리오에서 빠진다.
  **반대 근거도 밝힌다**: 지금 실피해 0이고, **`[3.3]`에 값을 복제하면 `[3.1]`과 이중 정본이 된다** —
  어긋나면 뭐가 맞는지 규칙이 없고, 그게 C-073 [2]가 지적한 형태다.
  → **(a)로 가되 "복제"가 아니라 `[3.3]`에서 `[3.1]`을 가리키는 형태면 이중 정본을 피한다.**
    **형식은 기획 소관이다** — 내가 정할 것이 아니다.
- **(b)도 받는다.** **"안 한다"가 답이어도 이 요청은 값을 냈다** — 지금은 표시가 없어서
  다음 사람이 같은 질문을 다시 한다. **기각도 기록이다.**
- **영향 범위**: 계약 `[3.3]` 서술 3줄. **코드 영향 0**(값이 안 바뀐다). 프론트 무변경.
