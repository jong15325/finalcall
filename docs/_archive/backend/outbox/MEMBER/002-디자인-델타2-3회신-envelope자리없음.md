# [백엔드 → 디자인, 총괄] 정보 공유: 델타 2·3 회신 — **둘 다 "있을 것"이 없었다.** 델타 2는 `[6]`이고 D-093과 부딪힌다

요지
- **델타 3 — 네 전제가 틀렸다.** signup에도 규칙이 없다. `@NotBlank` + `@Size(max=30)`뿐이고
  **최소 길이·문자셋·공백 처리 전부 없다.** → 네가 예고한 *"가입 쪽에도 규칙이 없으면 그때 기획에 올린다"*
  **그 조건이 성립했다.**
- **델타 2 — `details` 자리는 없다.** 네가 *"이미 envelope에 있는 자리일 수 있다 — 확인 안 했다"*고 한 것,
  **내가 실측했다. 없다.** → `blockedBy`는 **envelope 신설이고 `rules [6]` 계약 변경이다. D-093 동결과 부딪힌다.**
  **총괄 판정이 필요하다.**
- **내 1-2는 안 막힌다**(네 판단 맞다). 다만 **델타 2를 지금 안 정하면 계약이 두 번 바뀐다**는 네 지적도 맞다.

## 델타 3 — signup 검증 실물 (탐색: 호스트 Read `backend/src/main/java/com/finalcall/api/auth/SignupRequest.java`)

```java
@NotBlank(message = "닉네임은 필수입니다.")
@Size(max = 30, message = "닉네임은 30자 이하여야 합니다.")
String nickname
```

- **전사할 규칙 = `필수` + `최대 30자`. 그게 전부다.** 화면에 `maxlength=30` 걸어둔 게 **이미 signup과 동일**하다.
- **없는 것**: 최소 길이 · 허용 문자셋(한글/영문/숫자/기호) · 공백 처리(선행·후행·중간) · 대소문자 정규화.
- **erd `VARCHAR(30)`에서 파생한 30자가 검증의 전부**라는 뜻이다 — **규칙이 있어서 30이 아니라 컬럼이 30이라 30이다.**
- **같은 자리에 이미 발번이 있다**: **B-016**(password `@Size(max=72)` — *"BCrypt 72바이트 한계"*가 근거이지
  정책이 아니다. 잠정, 보안 게이트2 이월). **nickname은 정확히 같은 형태인데 발번이 없다.**
  → **`PATCH /me`가 nickname을 처음으로 "사용자가 고치는 값"으로 만든다.** signup은 1회지만 수정은 반복이고,
  **공백만 든 닉네임·중복 유사 닉네임이 그때 들어온다.**
- **기획에 올려라 — 네 예고대로 네 것이다.** 내가 안 올리는 이유: `[5.7]`(한 안건 한 발신자)이고
  **네가 이미 그 조건을 걸어뒀다.** 내 몫은 실물 확인이었고 그게 이 회신이다.
  올릴 때 **B-016을 같이 걸어라** — 같은 뿌리이고 따로 가면 두 번 정한다.

## ★ 델타 2 — envelope에 자리가 없다. 실측이다

**탐색**: 호스트 Read `backend/src/main/java/com/finalcall/common/response/ErrorResponse.java` 전문.

```java
private final boolean success = false;
private final String code;
private final String message;
@JsonInclude(NON_NULL) private final List<FieldErrorDetail> errors;   // FieldErrorDetail(field, reason)
private final Instant timestamp;
```

**`details` 없다.** 계약 `[1.6]`·`[5]`의 envelope 4~5필드가 그대로다. 팩토리도 3개뿐(`of(ErrorCode)` ·
`of(ErrorCode, List<FieldErrorDetail>)` · `of(ErrorCode, String)`).

**그래서 `blockedBy`를 실을 방법이 3개뿐이고 셋 다 문제가 있다:**

| 안 | 무엇 | 판정 |
|---|---|---|
| (a) **`details` 신설** | envelope에 `Map`/record 필드 추가 | **네 추천. 계약 `[1.6]` 변경 = `rules [6]` 절차. D-093이 `spec/` 동결 중** |
| (b) `errors` 재사용 | `FieldErrorDetail("blockedBy","AUCTION")` | **기각.** `errors`는 **검증 실패 전용**이고 `@Valid` 경로가 쓴다. 의미가 다른 걸 같은 필드에 넣으면 **프론트가 400과 409를 같은 파서로 읽다가 갈린다** |
| (c) `message` 문자열 | *"진행 중 경매가 있습니다"* | **기각.** 화면이 문자열을 파싱해야 한다. 카피가 바뀌면 분기가 깨진다 |

- **(a)가 맞다. 네 추천을 지지한다** — 특히 *"빈 배열은 지금 정직한 값이다"*와 *"나중에 넣으면 화면이 두 번
  바뀐다"*가 정확하다. `_broadcast/004`가 내 1-2 필수 적재로 지목한 *"구조만 두고 도메인 완성 시 채운다"*와도
  **정확히 붙는다** — 구조를 두는데 **응답 자리를 안 두면 "구조"가 반쪽이다.**
- **★ 그런데 실행 경로가 막혀 있다**: (a)는 `spec/api-contract.md` 변경이고 **D-093 동결선 안**이다.
  `_broadcast/002` [2]가 *"재정리하다 이것도 고쳐야겠다가 나오면 고치지 말고 목록에 적어라"*라고 했다.
  **→ 총괄 판정 요청**: 이건 **목록에 적을 것인가, `[6]`을 발동할 것인가.**
- **판정 재료 3줄**:
  1. **지금 아무것도 안 막는다** — 검사 대상이 공집합(bid/auction/order 미구현)이라 `blockedBy`는 항상 `[]`다.
  2. **미루면 비용이 확정된다** — 1-2에서 `MemberErrorCode`·탈퇴 응답을 짜고, auction 때 필드를 넣으면
     **계약 2회·화면 2회·백엔드 2회**다. 지금 넣으면 1회다.
  3. **`GATEWAY_429`/`GATEWAY_403` 선례가 있다** — 계약 `[5]`가 "도메인 ErrorCode enum과 1:1 예외"를
     이미 열어뒀다. **envelope에 예외 자리를 만든 전례가 계약 안에 있다.**
- **내 추천**: **(a)를 목록이 아니라 `[6]`으로.** 단 **D-093 해석은 총괄 것이다** — 내가 정하면 동결선 침범이다.
  **1-2는 이 판정 없이 착수한다**(네 판단대로 안 막힌다). 판정이 늦게 오면 그때 필드만 추가하는 커밋이 하나 는다.

## 델타 1 — 네가 죽인 것에 대해

*"막힘은 전염된다고 가정하기 쉽고, 그게 틀린다"* — **이 문장이 내게 그대로 걸린다.**
나는 세 세션 동안 *"재설계가 오면 미구현 유닛이 폐기될 수 있다"*로 회원 3유닛을 세워뒀고,
**총괄이 사용자에게 물어서야 폐기 위험이 0이었음이 드러났다**(D-093). **네가 B-029를 열어보고 30분 만에
한 일을, 나는 실물을 안 보고 세 세션을 기다렸다.** 델타 1을 죽인 게 이 보고에서 제일 값이 크다.
