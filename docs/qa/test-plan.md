# FinalCall 테스트 플랜 (QA, D-040·qa-guide §2)

성격: 전체 테스트 전략 1~2페이지. 리스크 기반 우선순위(qa-guide §3). 무거운 IEEE 829식 미채택.

기준(확정 스펙 **3종 전부** + ACCEPTED 결정만): **api-contract v1.4 · domain-spec v0.5 · erd v0.7**
(2026-07-15 갱신 — erd v0.5→v0.7 델타 검토·반영 완료, D-092 3단). 갱신은 게이트 진행에 따라 누적.
- 확정 스펙 3종은 기준 위계(`common/rules.md [3.9]`)상 **동급 근거**다. 하나라도 빠지면 그 층의 위반은
  게이트를 그대로 통과한다 — 실제로 erd 누락이 V3 자연키 UK 위반을 G4-1에서 통과시켰다(QA-001, Q-004).
  검증 기준에서 erd를 빼지 말 것.

## 1. 범위

- 대상(현): G4-1 도메인 = auth(signup·login·refresh·logout) + SCG 엣지 게이트웨이(D-068).
  검증 대상 산출물 backend/outbox/019·021.
- 후속(누적 예정): 경매·고정가·입찰·즉시구매·취소·주문·화폐(충전·교환)·인벤토리. 도메인 구현
  완료(G4-n) 시마다 시나리오 추가.
- 비대상: 공격자 관점 보안(인증 우회·부정입찰·결제 변조 등)은 보안 파트(findings.md). 성능 부하
  튜닝 수치는 백엔드 비기능 협의 소관(domain-spec §11).

## 2. 테스트 레벨·방법

| 레벨 | 담당 | 비고 |
|---|---|---|
| 단위 | 백엔드(구현 DoD) | AuthServiceUnitTest 등. QA는 커버리지 갭만 시나리오로 보강 |
| 슬라이스·통합 | 백엔드(구현 DoD) | Testcontainers(MySQL 8/Redis 7). GatewayAccessIntegrationTest 등 |
| 스펙 정합 검증 | QA | 확정 스펙 3종 대비 정적 대조. Q-001 + **Q-004(erd 포함)** |
| 시나리오(재실행) | QA 설계 → 백엔드/CI 실행 | 기능·동시성·경계값. scenarios/NNN |

스펙 정합 검증의 대조 범위(Q-004 — 3종 전부, 층별로 빠짐없이):
- **api-contract**: 경로·요청/응답 스키마·상태코드·에러코드·envelope.
- **domain-spec**: 도메인 규칙·상태 전이·동시성 필수 케이스(§10).
- **erd**: 스키마·마이그레이션이 erd를 지키는지. **§1 공통 규약(네이밍·PK/FK·public_id·시간·soft
  delete 자연키 UK·상태 enum) 대조를 포함**한다. 테이블 정의표(§4)만 보고 §1 규약을 건너뛰지 말 것 —
  §4 표가 §1 규약을 반영하지 못한 경우가 실재한다(erd §4.1 user, 074로 정정 중).

QA는 확정 스펙을 기대치의 단일 근거로 삼고(qa-guide §1), 동적 재실행은 백엔드 Testcontainers
하네스에 위임한다(Q-001). 스펙 공백은 결함이 아니라 계약 질의로 격상(qa-guide §4).

## 3. 리스크 기반 우선순위 (영향 × 발생가능성, 각 1~3)

고정 고위험(총괄 지정 동시성 4건, D-008/qa-guide §3)은 점수 무관 시나리오 필수. 현 G4-1 범위는
경매·거래 도메인 이전이라 4건 중 직접 대상은 없으나, 인증 동시성(회전·중복가입)이 자금 시스템의
전제라 최우선으로 다룬다.

| 기능 | 영향 | 발생 | 점수 | 시나리오 |
|---|---|---|---|---|
| 활성 유일성(soft delete 자연키 UK) — 패턴 오구현 시 조용히 뚫림 | 3 | 3 | 9 | QA-S-MBR-06(회귀) |
| 재가입·재탈퇴 생애주기(D-081 패턴) | 3 | 2 | 6 | QA-S-MBR-04·05 |
| refresh 토큰 회전·재사용 탐지 | 3 | 2 | 6 | QA-S-AUTH-05·06(동시성) |
| 중복 signup 경쟁(UK 안전망) | 3 | 2 | 6 | QA-S-AUTH-02(동시성) |
| 게이트웨이 직접접근 차단(우회 시 인증 관문 무력화) | 3 | 2 | 6 | QA-S-GW-03·04 |
| 로그인 자격 검증·열거 완화 | 2 | 2 | 4 | QA-S-AUTH-03 |
| rate limit 429(무차별 대입 억제) | 2 | 2 | 4 | QA-S-GW-02 |
| logout 세션 폐기(멱등·소유자 한정) | 2 | 2 | 4 | QA-S-AUTH-07 |
| 라우팅 정합(경로 프록시) | 2 | 1 | 2 | QA-S-GW-01 |
| 입력 검증 400(경계값) | 1 | 2 | 2 | QA-S-AUTH-08 |

고정 고위험 4건(마감 입찰 폭주 / buyNow vs 입찰 / 취소 vs 첫 입찰 / SOLD-Order 원자성)은
해당 도메인 구현(G4-n) 시 필수 등재 — 현 플랜에 예약 표기, 시나리오는 도메인 착수 시 작성.

상시 규칙 — soft delete 자연키 도메인은 활성 유일성 회귀 필수 (QA-001 재발 방지, QA 층):
- **발동 시점 = erd [1] 트리거 조건과 동일**: *"자연키 UK를 가진 테이블에 soft delete를 **새로
  도입하는 순간**"*(erd v0.6 명문화). 그 순간 D-081 패턴이 의무가 되고, **동시에 QA-S-MBR-06 형
  (활성 유일성 회귀) 시나리오 등재가 의무**가 된다. 리스크 점수와 무관한 고정 필수다.
- **감시 대상(erd [4] 말미 주 스윕 결과, v0.6 신설)**: 현재 soft delete 보유 = `user` 1건뿐(처리 완료).
  **조건부 리스크 = 자연키 UK 보유·soft delete 미보유 테이블**(`charge.pg_tx_id` 등) — 지금은 무관하나
  **soft delete가 도입되는 순간 본 규칙이 발동**한다. 해당 도메인 착수 시 erd [4] 말미 주를 대조해
  트리거 여부를 판정한다(목록 정본 = erd, 여기 복제하지 않는다 — 전사본 stale 회피, D-092).
- 이유: D-081이 기각한 `UNIQUE(자연키, deleted_at)`를 잘못 넣으면 **재가입·재탈퇴 등 다른 케이스는
  전부 통과하고 활성 중복만 조용히 열린다**. 유일한 검출 지점이 이 시나리오다.
- 요건: (a) **DB 레벨 단언**(애플리케이션 선검사를 우회해 제약을 직접 때릴 것 — API 경유는 선검사가
  먼저 409를 던져 UK를 타지 않아 무력하다), (b) **실 MySQL**(H2 대체 차단 — 생성 컬럼·NULL UK 의미가
  다름), (c) dev 그린 대체 배제(실행 증거 개별 명시).
- 근거: erd [1] soft delete 규약 · D-081 · QA-001 · 총괄 083 조건 · backend/033(API 경유 무력함 실측).
- 074 스윕은 erd 표를 고치지만 **검증 측 요구는 QA 소관**이라 여기 둔다(규약↔실행 문서 동기화, D-089).

## 4. 환경·전제

- 동적 재실행 전제: 로컬 Docker 데몬 up + Testcontainers(MySQL 8.0/Redis 7). `./gradlew clean build`
  (021 기준 61 테스트 그린). 게이트웨이 차단 검증은 `gateway.internal.enforced=true` 오버라이드.
- 스펙 정합 검증 전제: 확정 스펙 3종 **api-contract v1.4 · domain-spec v0.5 · erd v0.7([1] 규약 포함)**
  + 구현 소스(main/test)·**마이그레이션(db/migration)** 열람(D-016 pull).
- **도구**: 저장소 파일의 목록·내용·부재·수량 판단은 **호스트 도구(Read·Grep)가 정본**(D-090).
  bash 마운트 뷰 조회 결과를 판단 근거로 쓰지 않는다(stale 서빙, 실패 신호 없음). bash는 테스트·빌드·
  git 오브젝트 조회 등 마운트 뷰와 무관한 작업에만. 부재·수량 주장은 탐색 방법 1구 명시(D-086).

## 5. 완료 기준 (G4-1 QA 파트)

- auth 4종·게이트웨이 시나리오 스위트 작성 완료(scenarios/001·002).
- 계약 §2·§1 조항 대비 정합 검증 수행, 위반은 defects.md(QA-NNN)·계약 공백은 계약 질의로 격상.
- Critical(돈·정합성) 0건 확인. OPEN Major 0건.
- 결과를 [QA → 총괄] 완료 보고로 발신(게이트 통과 판정 권고 포함).
