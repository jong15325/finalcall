## 근거 확인 (D-082 정신 — 지시 수용 전 직접 대조)

- erd §1 line 30 원문: "soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함(삭제행-신규행
  충돌 회피)". erd v0.5 = **G2 통과 확정 스펙(2026-07-13)**.
- V3 작성 2026-07-14(그 이후). `user`는 `is_deleted`·`deleted_at` 보유 = soft delete 테이블이고
  `uk_user_login_id (login_id)`·`uk_user_nickname (nickname)`은 삭제 식별 컬럼 미포함 → **위반 확정**.
- 결론: 총괄 판정이 사실과 부합. Q-003(RETEST)이 아니라 결함이 맞다 — 규약 발동 조건은 "soft delete
  테이블이면"이고 V3 작성 시점에 규약이 이미 존재했다. 이의 사유 없음.

## 뿌리 점검 (D-085)

**같은 원인이 다른 층에도 공백을 만들었다 — 5개 층 중 4개는 이미 처리 중, QA 층이 이번 건이다.**
원인은 "규약(erd §1)은 있었으나 각 층이 그것을 대조할 구조가 없었던 것".
- 계약층: v1.4 §2.5 재가입 조항 — 옳음(변경 불요).
- erd 규약층(§1): 의도는 옳으나 해석이 열려 함정 허용 → 074 §1이 D-081 패턴 명문화 중.
- **erd 테이블층(§4.1)**: `user` 표가 login_id·nickname을 단순 `UK`로만 표기해 §1 규약 미반영 —
  **§4.1만 보고 구현하면 정확히 V3가 나온다**. → 074 §2가 커버(신규 격상 불요, 중복 회피).
- 구현층(V3): 위반 → V4/D-081이 FIX.
- **검증층(QA test-plan·Q-001): erd 누락** ← 이번 건. Q-004로 보완.
- 스윕 범위 확인: erd 테이블 정의 중 `is_deleted` 보유는 **`user` 단독**(현 시점). 074 §3 스윕 대상은
  user뿐일 것으로 관측된다(기획 전수 점검 결과가 정본).

## 백엔드 참고 (결함 아님 — 패턴 과적용 주의)

D-081 패턴은 **자연키(login_id·nickname)에만** 적용한다. `uk_user_public_id`는 대상이 아니다 —
public_id는 ULID 대리키라 재사용되지 않아 삭제행-신규행 충돌이 구조적으로 없다(erd §1 "외부 노출
식별자" 항). 일괄 적용 시 불필요한 생성 컬럼이 는다.
