# QA 결정 로그 (Q-xxx, D-040·D-038)

QA 파트의 결정 로그. 1항목=1원자적 결정, 항목 불변·상태 라벨만 갱신(collaboration-guide 4절).
번호 분리(D-038): Q-xxx는 결정(전략·케이스 설계), 결함 티켓은 defects.md(QA-NNN).

## Q-001. G4-1 검증 방법 — 계약 기준 정적 정합 검증 + 실행 가능한 시나리오 스위트

상태: ACCEPTED · 소유: QA · 관련: relates-to D-019(G4 게이트), qa-guide §1·§4 · 2026-07-14

결정
- G4-1 auth·게이트웨이 검증은 (a) 확정 계약(api-contract v1.2)·domain-spec v0.4 기준 시나리오를
  설계하고, (b) 구현 산출물(019·021 범위)을 계약 조항 대비 정적 정합 검증(코드·마이그레이션·기존
  테스트 대조)으로 판정한다. 시나리오는 백엔드 테스트 하네스(Testcontainers)에서 동적 재실행 가능한
  형태로 명세한다.

이유
- QA 기준 문서는 확정 스펙·계약뿐(D-016·qa-guide §1). 구현 코드는 기대 결과의 근거가 아니라
  "계약 대비 어긋남(결함)"을 찾는 대상으로만 본다.
- 동적 실행에는 MySQL 8/Redis 7 Testcontainers(로컬 Docker 데몬)가 필요하다(021 전제). 이 환경은
  백엔드 DoD에서 이미 그린(019·021). QA의 독립 검증은 계약 정합 정적 검증 + 재실행 가능한 시나리오
  스위트 인계로 수행하고, 동적 재실행은 CI/백엔드 하네스에 위임한다.

기각된 대안
- QA가 전체 스택을 직접 기동해 동적 실행만으로 판정: 재현 환경(Docker) 의존·중복 투자. 스켈레톤
  게이트 단계에서 과하다. 시나리오 스위트로 재실행성을 확보하는 편이 비용 대비 낫다.

## Q-002. 게이트웨이 엣지 오류 응답(429 본문·직접접근 403 코드)은 결함 아닌 계약 질의로 처리

상태: ACCEPTED · 소유: QA · 관련: relates-to D-068, 057(계약 v1.3 진행), qa-guide §1·§4 · 2026-07-14

결정
- 게이트웨이 rate limit 429 응답 본문 포맷과 직접접근 차단 403의 오류 코드(구현 관측 COMMON_006)는
  현행 계약 v1.2에 명세가 없다. 근거 조항을 인용할 수 없으므로 결함(QA-NNN)이 아니라 스펙 공백으로
  보고, 계약 질의로 총괄에 격상한다(이미 v1.3 진행 중, 057 → 재실행 대기).

이유
- qa-guide §4: 기대 결과에 계약 조항·에러 코드를 인용할 수 없으면 스펙 공백 → 결함이 아니라 계약 질의.
- 057(총괄 승인분)이 v1.3에서 엣지 오류 envelope·429 코드·직접접근 403 코드를 명세 중. 확정 시
  해당 시나리오(GW-S-02, GW-S-04) 기대 결과를 v1.3 기준으로 확정하고 재실행한다.

기각된 대안
- 429 본문 부재/COMMON_006을 결함으로 등재: 계약 근거 없는 기대치를 QA가 임의 설정하는 것 →
  qa-guide §1(추측 금지) 위반. 격상 처리가 규약 정합.

## Q-003. 계약 확정분 미구현 델타는 결함(QA-NNN)이 아니라 재검증 대기(RETEST)로 관리

상태: ACCEPTED · 소유: QA · 관련: relates-to Q-002(해소), 065(v1.3 전파·백엔드 할당), D-028 · 2026-07-14

결정
- 계약 변경으로 새 기대치가 확정됐으나 구현이 아직 그 계약을 반영하지 않은 델타는, 해당 구현이
  이미 특정 역할에 할당된 미착수 작업인 한 결함으로 등재하지 않고 defects.md의 재검증 대기
  (RETEST-N)로 관리한다. 구현 완료 보고 수신 후 재검증해 불일치가 잔존하면 그때 QA-NNN 발번한다.
- 첫 적용: RETEST-1(429 → GATEWAY_429 envelope + Retry-After), RETEST-2(403 COMMON_006 →
  GATEWAY_403). 트리거 = 백엔드 게이트웨이 커스텀 에러 핸들러 완료(065 B).

이유
- 결함은 "완료로 주장된 산출물의 계약 이탈"에 붙는 라벨이다. v1.3는 021 완료 보고 이후에 확정됐고
  (v1.2 시점 구현은 당시 계약에 정합), 포맷 반영은 065가 백엔드에 신규 할당한 미착수 작업이다.
  이를 결함으로 등재하면 "아직 하지 않은 일"과 "잘못한 일"이 한 통계에 섞여 결함 지표가 왜곡된다.
- 추적 누락 위험은 RETEST 표 + 트리거 명시로 방어한다(D-028 "대기 중" 명시 원칙과 정합).

기각된 대안
- 즉시 QA-NNN 발번(Major): 백엔드가 착수도 하기 전에 결함이 열려 결함 지표·재작업 귀속이 왜곡.
  버그 트래커를 작업 지시 채널로 오용하는 셈.
- 아무 데도 기록하지 않고 구현 후 검증: 계약 확정과 재검증 사이 추적 공백 → 누락 위험.

## Q-004. 검증 기준 = 확정 스펙 3종 전부(erd 포함) — Q-001 기준 열거 보정

상태: ACCEPTED · 소유: QA · 관련: relates-to Q-001(방법론 유효, 기준 열거만 보정)·QA-001, 지시 075 · 2026-07-15

결정
- QA 스펙 정합 검증의 기준을 확정 스펙 **3종 전부**(api-contract·domain-spec·**erd**)로 명시한다.
  erd 대조에는 **§1 공통 규약**(네이밍·PK/FK·public_id·시간·soft delete 자연키 UK·상태 enum)을
  포함하며, 스키마·마이그레이션이 이를 지키는지가 정합 검증의 일부다. test-plan 기준줄·검증 전제·
  레벨 표에 반영한다.
- Q-001의 검증 *방법*(정적 정합 검증 + 재실행 가능 스위트)은 유효하다. 보정 대상은 기준 문서 열거뿐이다.

이유
- 기준 위계(collaboration-guide §3)상 확정 스펙 3종은 동급 근거인데 test-plan이 api-contract·
  domain-spec만 열거해 erd 층이 검증 구조에서 빠졌다. 그 결과 V3 `user`의 자연키 UK가 erd §1 규약을
  위반한 채 G4-1을 통과했다(QA-001). 하나가 빠지면 그 층의 위반은 게이트를 그냥 통과한다.
- 실측 근거: erd §1(line 30) "soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함"은 G2
  통과분이고 V3는 그 이후 작성됐다 — 대조할 기준만 있었으면 잡혔다.
- 추가 교훈(erd 대조 시 §4만 보지 말 것): erd §4.1 `user` 표는 login_id·nickname을 단순 `UK`로만
  표기해 §1 규약을 반영하지 않는다. §4만 대조하면 위반을 못 잡는다(074로 정정 중).

기각된 대안
- Q-001을 SUPERSEDED 처리: 방법론 자체는 유효하고 기준 열거만 불완전했다. 전체 대체는 과잉이고
  결정 이력의 신호를 흐린다(항목 불변 원칙, 가이드 §4).
- test-plan만 고치고 결정 로그 미기재: 같은 누락이 재발해도 왜 3종인지 근거가 남지 않는다.
