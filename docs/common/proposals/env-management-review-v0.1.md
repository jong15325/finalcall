# 환경변수·시크릿 관리 전략 검토 (v0.1)

- **상태: 분석·권고 (DRAFT) — 채택은 게이트2 상신 대상(§5)**
- 작성: architect (FC-141)
- 축: **프로젝트 축**(빌드 의존성·설정 로딩 방식). 실제 도입은 이 문서 범위 밖(별건 게이트2).
- 트리거: 사용자 질문(2026-07-28) — SMTP 실발송(FC-140, `MAIL_USERNAME`/`MAIL_PASSWORD`/`MAIL_SENDER_ENABLED` env 주입) 착수 맥락.
  원문: "원래는 `.env`로 환경변수값을 모두 관리했는데 현재 프로젝트는 그렇게 진행 안 하고 있음 — 추후에 이 환경변수를 어떻게 관리해야 할까. 개발자 입장에선 env에서 한 번에 관리하는 게 편했는데 그렇게 개발되지 않은 이유와 앞으로 어떻게 하면 되는지."

## 0. 요약 (총괄용 — 평이한 언어)

- **왜 `.env` 한 파일이 아니었나**: 이 프로젝트는 값을 "환경(로컬/개발/운영)별로 파일을 나눠" 관리하도록 처음부터 설계됐다(`application-local.yml`, `application-dev.yml`, `application-prod.yml`). 핵심 안전장치 두 가지 때문이다 — (1) **비밀번호 같은 민감값은 코드에 절대 안 넣는다**(커밋 금지), (2) **운영에서 민감값이 빠지면 앱이 아예 안 켜진다**(fail-fast, 조용히 잘못된 기본값으로 뜨는 사고 방지). `.env` 한 파일로 다 몰면 실수로 비밀번호를 커밋할 위험이 커지고, 환경별 경계가 흐려지며, 운영 배포가 실제로 값을 넣는 방식(컨테이너 환경변수)과 이원화된다.
- **개발자 편의는 이미 상당 부분 확보돼 있다**: 로컬은 모든 값에 기본값이 박혀 있어(`${ENV:기본값}`) **환경변수를 하나도 안 넣어도 앱이 그냥 뜬다**. "한 곳에서 관리하는 편함"이 필요한 지점은 사실상 **로컬에서 실제 비밀번호를 넣어 테스트할 때**(지금은 SMTP 실발송)로 좁다.
- **권장안**: 로컬 한정으로 `.env` 파일을 읽어 주입하는 방식(옵션 A, `spring-dotenv` 로더 + `.env.gitignore` + `.env.example`)을 도입하되, **운영은 현행 fail-fast를 그대로 유지**한다. 이렇게 하면 "로컬에서 한 파일로 관리하는 편함"을 살리면서 운영 안전장치는 손대지 않는다.
- **지금 즉시 필요한 최소 조치 1건(안전 결함)**: 현재 `.gitignore`에 `.env`가 **없다**. 어떤 방식을 택하든, 또는 아무것도 안 하더라도, `.env`(및 변형)를 `.gitignore`에 추가해 실수 커밋을 원천 차단해야 한다. 이건 편의 문제가 아니라 시크릿 유출 예방이다.
- **게이트2 필요 여부**: 권장안(빌드 의존성 추가 + 설정 로딩 방식 변경)은 **전역 컨벤션 변경이라 게이트2 상신 대상**이다. `.gitignore`에 `.env` 추가만 하는 최소 조치는 로딩 방식 변경이 아니라 논쟁 여지가 작다(그래도 사용자 확인 후 별건 티켓 권장).

## 1. 현황 서술 — 지금 방식은 무엇인가

### 1.1 전체 골격: 프로파일별 yml + OS 환경변수 주입, `.env` 로더 없음

값은 세 층으로 나뉜다.

1. **공통 설정** `backend/src/main/resources/application.yml` — 프로파일 무관 값(포트, JPA, Flyway, 비즈니스 정책값 등). 활성 프로파일은 yml에 하드코딩하지 않고 `SPRING_PROFILES_ACTIVE` 환경변수로만 정한다(미지정 시 `spring.profiles.default: local`, 1~12행).
2. **프로파일별 오버레이** `application-local.yml` / `application-dev.yml` / `application-prod.yml` — 환경종속·시크릿 값을 프로파일마다 다르게 주입.
3. **OS 환경변수 주입** — 시크릿과 환경종속 값은 `${ENV}` placeholder로 실행 환경(셸/컨테이너)의 OS 환경변수에서 읽는다.

**`.env` 파일이나 dotenv 라이브러리(`spring-dotenv` 등)는 쓰지 않는다.** 빌드 의존성에 dotenv 로더가 없고, 소스에 `.env`를 로드하는 코드도 없다. 즉 "값이 자동으로 파일에서 프로세스로 흘러드는" 경로가 없고, 값은 **yml 기본값** 또는 **셸/컨테이너가 넣어준 OS 환경변수**에서만 온다.

### 1.2 로컬: 기본값 내장 → 환경변수 없이 부팅

`application-local.yml`은 모든 환경종속 값에 `${ENV:기본값}` 형태로 로컬 전용 더미 기본값을 둔다. 예:

- JWT: `jwt.secret: ${JWT_SECRET:finalcall-local-dev-secret-key-...}` (10~11행)
- 게이트웨이 공유비밀: `gateway.internal.secret: ${GATEWAY_INTERNAL_SECRET:...}` (15~17행)
- DB: `${DB_URL:jdbc:mysql://localhost:3306/finalcall}` / `${DB_USERNAME:finalcall}` / `${DB_PASSWORD:finalcall}` (20~24행)
- Redis: `${REDIS_HOST:localhost}` / `${REDIS_PORT:6379}` (34~37행)
- 메일 발송 스위치: `email.verify.sender-enabled: ${MAIL_SENDER_ENABLED:false}` (58~60행)

로컬 기본은 발송 스킵(`LoggingEmailSender`, 코드만 로그에 출력)이라 **크리덴셜 없이도 부팅·인증 흐름 테스트가 가능**하다. 실발송은 `MAIL_SENDER_ENABLED=true` + `MAIL_USERNAME`/`MAIL_PASSWORD`(네이버 앱 비밀번호)를 env로 넣을 때만 활성(`application-local.yml` 54~60행).

### 1.3 개발/운영: 기본값 없는 `${ENV}` → 누락 시 부팅 실패(fail-fast)

`application-dev.yml`·`application-prod.yml`은 시크릿·환경종속 값에 **기본값을 두지 않는다**. 미주입 시 부팅이 중단된다.

- DB: `url: ${DB_URL}` / `username: ${DB_USERNAME}` / `password: ${DB_PASSWORD}`(dev 11~15, prod 22~26행)
- Redis: `${REDIS_HOST}` / `${REDIS_PORT}`(dev 17~20, prod 28~31행)
- JWT secret·게이트웨이 secret: yml에 placeholder조차 두지 않고 **relaxed binding**으로 주입(dev 22~26, prod 33~37행). 이유는 주석에 명시 — `jwt.secret: ${JWT_SECRET}`처럼 placeholder를 쓰면 미해결 시 `${JWT_SECRET}` 리터럴이 그대로 남아 `@NotBlank`를 통과, **fail-fast가 무력화**되기 때문. 그래서 검증 대상 문자열은 placeholder 대신 환경변수명(`JWT_SECRET` → `jwt.secret`)의 relaxed binding으로만 주입한다.
- 메일: 공통 `application.yml`이 `mail.username: ${MAIL_USERNAME}` / `mail.password: ${MAIL_PASSWORD}`를 **기본값 없이** 둔다(41~42행). 주석 명시 — "공통 yml에 기본값을 두면 prod fail-fast가 무력화된다".

### 1.4 시크릿 취급 규약

- CLAUDE.md 섹션 2: "시크릿·`.env`·자격증명을 코드나 커밋에 넣지 않는다. 민감값은 환경변수(`${ENV_VAR}`)로."
- CLAUDE.md 섹션 4: "시크릿 fail-fast — 로컬은 `${ENV:기본값}`, 운영은 `${ENV}`(기본값 없음 → 누락 시 부팅 실패)."
- 시크릿 목록(커밋 금지·env only): `JWT_SECRET`, `GATEWAY_INTERNAL_SECRET`, `DB_PASSWORD`(및 DB_URL/USERNAME), `MAIL_USERNAME`/`MAIL_PASSWORD`.

### 1.5 발견된 결함 — `.gitignore`에 `.env` 미등재

현재 `.gitignore`(전체 확인)에는 IDE·빌드 산출물·로그·Codex 로컬 설정 등은 있으나 **`.env` 관련 항목이 없다.** 지금은 `.env`를 안 쓰니 당장 유출은 없지만, 누군가(사람이든 에이전트든) 로컬에서 `.env`를 만들면 `git add .` 한 번에 시크릿이 커밋될 수 있다. CLAUDE.md 섹션 2의 "`.env`를 커밋에 넣지 않는다"는 **정책은 있으나 기계적 가드레일이 없다.** (아래 §4 권장안·§5 게이트2와 별개로, 이 항목은 방식 선택과 무관하게 메꿀 것을 권한다.)

## 2. 왜 `.env` 단일 통합이 아니었나 (판단 아님 — 근거)

"왜 이렇게 설계됐나"의 근거를 정리한다. 어느 쪽이 옳다는 판단이 아니라, 현 구조가 따르는 원칙과 `.env` 단일 통합이 그 원칙과 어디서 부딪히는지를 서술한다.

### 2.1 CLAUDE.md 섹션 2·4의 설계 의도

- 섹션 2는 "`.env`를 커밋에 넣지 않는다"를 명시 규약으로 못박았다. `.env`를 프로젝트의 1차 관리 수단으로 삼으면, 그 파일이 항상 워킹트리에 존재하며 실수 커밋 표면(surface)이 상시 노출된다. 규약은 이 표면 자체를 줄이는 방향(env는 프로세스에 주입, 파일로 상주시키지 않음)을 택했다.
- 섹션 4의 fail-fast는 "운영에서 시크릿이 빠졌는데 조용히 뜨는 것"을 사고로 본다. `${ENV}`(기본값 없음)는 값이 없으면 부팅을 세운다. `.env` 단일 파일 방식은 통상 "파일이 있으면 로드, 없으면 무시"라 **누락을 침묵**시키기 쉬워 fail-fast와 정면으로 어긋난다(운영에서 `.env`가 안 실리면 값이 없는 채로 진행 시도).

### 2.2 12-factor config 원칙

12-factor(III. Config)는 "설정을 **환경변수**에 저장하고, 코드베이스와 엄격히 분리하라"고 권한다. 핵심은 **환경변수 자체**이지 `.env` 파일이 아니다. 오히려 12-factor는 "설정을 그룹화한 config 파일을 리포에 체크인하지 말라"고 경고한다 — 파일이 늘수록 실수 체크인 위험이 커지기 때문. 현 방식(값을 프로세스 환경변수로 주입, 파일로 상주 안 함)은 이 권고의 직역이다. `.env`는 어디까지나 "로컬에서 환경변수를 편하게 채우는 개발 보조 도구"로 쓰일 때 정당하고, "설정의 정본 저장소"가 되면 12-factor 취지에서 벗어난다.

### 2.3 Spring 프로파일 관례

Spring Boot는 `application-{profile}.yml` + `SPRING_PROFILES_ACTIVE`로 **환경별 값 분리**를 1급으로 지원한다. 이 프로젝트는 그 관례를 그대로 따른다 — 로컬/개발/운영의 값 정책(기본값 유무·fail-fast 여부)이 파일 경계로 명확히 갈린다. `.env` 단일 파일은 이 프로파일 경계를 하나로 뭉갠다(어느 값이 어느 환경 것인지 파일만 봐선 모름). 또한 Spring은 표준으로 `.env`를 로드하지 않는다 — dotenv를 쓰려면 별도 라이브러리를 얹어야 하고, 그 순간 "Spring 표준 프로퍼티 소스 순서"와 "dotenv 로더 주입 시점"이라는 두 메커니즘을 함께 이해해야 한다.

### 2.4 `.env` 단일 통합의 구체적 리스크

1. **실수 커밋**: 워킹트리에 시크릿 파일이 상주 → `.gitignore` 누락(현재 실제로 누락, §1.5)·강제 add·서브모듈 등으로 유출 표면 상시 존재.
2. **프로파일 경계 소실**: 한 파일에 로컬·운영 값이 섞이면 "이 값이 운영용인가 로컬용인가"를 파일이 답하지 못한다. 지금은 파일명이 답한다.
3. **운영 주입 경로와 이원화**: 운영은 통상 컨테이너 오케스트레이터(ECS task def·k8s Secret·SSM 등)가 OS 환경변수로 시크릿을 주입한다. 개발이 `.env` 파일에 의존하면 "로컬은 파일, 운영은 환경변수"라는 **두 경로**가 생겨, 로컬에서 되던 게 운영에서 안 되는(또는 그 반대) 이유를 진단하기 어려워진다. 현 방식은 로컬 기본값도 결국 `${ENV:...}`라 "환경변수로 덮어쓴다"는 **단일 멘탈 모델**을 유지한다.
4. **fail-fast 침묵**: §2.1 후단.

## 3. 개발자 편의 vs 현 방식 트레이드오프

### 3.1 "한 곳 관리"의 실익

- 값 하나 바꾸려고 yml 어느 파일·어느 위치인지 찾을 필요 없이 `.env` 한 파일만 연다.
- 새 팀원이 `.env.example`을 복사해 값만 채우면 로컬 구동 준비 끝(온보딩 단축).
- IDE·CLI·도커 컴포즈가 같은 `.env`를 공유하면 "실행 방법마다 env를 따로 세팅"하는 중복이 준다.

### 3.2 현 방식이 이미 편의를 확보한 지점

- **로컬은 env 없이 뜬다.** `application-local.yml`이 전 항목에 기본값을 박아둬서, 아무 환경변수도 안 넣고 `bootRun`하면 그대로 구동된다(§1.2). 즉 "한 곳에서 관리하는 편함"이 실제로 아쉬운 상황은 **로컬에서 진짜 크리덴셜을 넣어야 할 때**로 좁다 — 지금은 SMTP 실발송(`MAIL_USERNAME`/`MAIL_PASSWORD`/`MAIL_SENDER_ENABLED`)이 유일하게 그 지점이다.
- 그 좁은 지점조차 "안 넣으면 로깅 발송으로 폴백"이라 막히지 않는다. **편의 필요는 실재하나 범위가 작다**는 게 핵심이다.

### 3.3 운영 fail-fast의 안전 가치

- 운영에서 `DB_PASSWORD`나 `JWT_SECRET`이 빠지면 **부팅이 즉시 실패**한다. 잘못된/빈 시크릿으로 서비스가 떠서 인증이 뚫리거나 엉뚱한 DB에 붙는 사고를 배포 시점에 차단한다.
- 이 가치는 로컬 편의와 **트레이드 대상이 아니다.** 로컬 편의를 어떻게 개선하든 운영 fail-fast는 유지 전제로 둔다(아래 옵션 전부 이 전제를 지킨다).

### 3.4 요약 저울

| | 한 곳(.env) 통합 | 현행(프로파일 yml + OS env) |
|---|---|---|
| 로컬 값 편집 편의 | 높음 | 중(로컬은 기본값이라 편집 자체가 드묾) |
| 온보딩 속도 | 높음(example 복사) | 중(문서로 env 안내 필요) |
| 시크릿 유출 표면 | 큼(파일 상주) | 작음(파일 없음) |
| 프로파일 경계 명확성 | 낮음 | 높음(파일명이 환경) |
| 운영 주입 경로 일치 | 이원화 우려 | 단일(env 주입) |
| 운영 fail-fast | 침묵 위험 | 보장 |

핵심: **현 방식의 약점은 "로컬에서 실크리덴셜을 넣을 때의 편의"라는 좁은 영역**이고, 그 영역만 겨냥해 로컬 한정으로 `.env`를 보조 도입하면 표의 오른쪽 장점을 유지한 채 왼쪽 상단(로컬 편의)을 회수할 수 있다.

## 4. 앞으로의 옵션·권장안

**공통 전제**: 운영(dev/prod)은 현행 fail-fast(`${ENV}` 기본값 없음)를 **손대지 않는다.** 아래 옵션은 전부 **로컬 편의 개선**만 겨냥한다. 평가 축 4개 — **보안**(시크릿 유출 표면), **이식성**(OS·팀원 환경 독립성), **프로파일 정합**(Spring 프로파일·프로퍼티 소스와의 정합), **운영 경로 일치**(운영의 env 주입과 같은 멘탈 모델인가).

### 옵션 A — `spring-dotenv`(me.paulschwarz) 류 로더로 로컬 `.env` 로드

빌드 의존성으로 dotenv 로더를 추가하면 앱 시작 시 프로젝트 루트 `.env`를 읽어 **Spring `Environment`의 프로퍼티 소스로 등록**한다. 그러면 `application-local.yml`의 `${DB_PASSWORD:...}`, `${MAIL_PASSWORD}` 등 **기존 `${ENV}` placeholder가 그대로** `.env` 값을 집어간다(배선 수정 거의 불필요).

- **현 배선과의 공존**: `.env` → `${ENV}` placeholder는 완전히 호환. `.env`에 `MAIL_PASSWORD=...`만 적으면 공통 yml의 `${MAIL_PASSWORD}`가 해결된다. 기본값 있는 로컬 항목은 `.env`가 있으면 덮고 없으면 기본값. **relaxed binding 시크릿(`JWT_SECRET` → `jwt.secret`)과의 상호작용은 검증 필요** — 로더가 등록한 프로퍼티 소스가 relaxed binding 대상으로 잡히는지 스모크로 확인해야 한다(FC-140 배선 특성상 이 점이 유일한 실무 함정).
- **보안**: `.env`는 로컬만·gitignore 필수. 로더 라이브러리는 dev/prod에서도 클래스패스에 있으므로, **운영에서 `.env`를 실수로 두면 로드될 위험**을 차단해야 한다(운영엔 `.env` 미배포 원칙 + 로더를 local 프로파일에서만 활성/또는 운영 이미지에서 파일 부재 보장). 잘 배선하면 보안 중립, 잘못 배선하면 새 표면 생성.
- **이식성**: 높음(OS 무관, 파일 한 개).
- **프로파일 정합**: 중~높음. `.env`엔 프로파일 개념이 없어 "로컬용"이라는 규율은 문서·gitignore로만 강제. 로더 활성 자체를 local로 한정하면 정합 개선.
- **운영 경로 일치**: 높음. `.env`도 결국 "환경변수를 채우는" 도구라 `${ENV}` 단일 모델 유지. 운영은 여전히 OS env 주입.

### 옵션 B — IDE Run Configuration의 env (dotenv 라이브러리 없음)

IntelliJ Run/Debug Configuration의 Environment variables 칸(또는 EnvFile 플러그인으로 `.env` 지정)에 값을 넣는다.

- **현 배선과의 공존**: 완벽(순수 OS env처럼 주입). 빌드 의존성 0.
- **보안**: 높음(값이 리포 파일이 아니라 IDE 로컬 설정에 저장, 커밋 안 됨). 단 `.idea/workspace.xml` 커밋 여부 주의(현 `.gitignore`는 `.idea` 제외 중 → 안전).
- **이식성**: 낮음. IDE 종속(CLI `bootRun`·도커에는 별도 재설정). 팀원이 같은 IDE 안 쓰면 공유 불가.
- **프로파일 정합**: 높음(런 구성별로 분리 가능).
- **운영 경로 일치**: 높음(OS env와 동일).
- 성격: **빌드·리포 무변경**이라 게이트2 없이 개인이 오늘 바로 쓸 수 있는 방법. 팀 표준으로 삼기엔 이식성이 약점.

### 옵션 C — direnv (`.envrc`, 셸 레벨)

디렉터리 진입 시 셸이 `.envrc`를 자동 로드해 OS 환경변수를 세팅. 앱은 순수 OS env로 받는다.

- **현 배선과의 공존**: 완벽(빌드 의존성 0, 순수 env).
- **보안**: 높음(`.envrc` gitignore, 셸 밖으로 안 샘).
- **이식성**: 낮음~중. direnv 설치 필요, **Windows 기본 환경에서 번거로움**(WSL/Git Bash 전제). 이 프로젝트는 Windows 11 호스트라 팀 표준으론 마찰.
- **프로파일 정합**: 중.
- **운영 경로 일치**: 높음.

### 옵션 D — `.env.example` + gitignore + (로더는 A 또는 수동)

`.env.example`(더미값·커밋함)로 "무슨 env가 필요한지" 문서화 + 실제 `.env`는 gitignore. 로드는 옵션 A 로더가 하거나, 로더 없이 옵션 B/C가 파일을 참조한다.

- 단독 옵션이 아니라 **A의 필수 동반 요소**로 보는 게 맞다. 어떤 로더를 쓰든 `.env.example`은 온보딩·명세 가치가 크다.
- **보안**: example엔 절대 실값 금지(더미만). gitignore에 `.env` 필수.

### 4.1 권장안 — 옵션 A(+ D 동반) · 단, 운영 fail-fast 불변

**권장: 옵션 A(`spring-dotenv` 로더) + 옵션 D(`.env.example` + `.gitignore` 등재)**, 운영은 현행 fail-fast 유지.

근거:
- 사용자가 원하는 "한 파일로 관리하는 편함"을 정확히 회복하면서(로컬 `.env` 한 곳), **현 `${ENV}` 배선을 거의 안 바꾼다**(placeholder가 그대로 `.env`를 흡수). 마이그레이션 비용이 옵션 중 가장 낮다.
- 이식성이 IDE·OS에 독립(옵션 B·C의 약점 해소) — Windows 호스트에서도 파일 하나면 된다.
- "env를 채우는 도구"라는 점에서 운영 주입과 **같은 멘탈 모델**을 유지(옵션 A만의 장점: `.env`↔OS env가 동형).

채택 시 필수 안전 조건(이걸 못 지키면 옵션 B로 후퇴 권장):
1. **로더는 local 프로파일 한정 활성** 또는 운영 이미지에 `.env` 파일 부재를 배포로 보장 — 운영에서 `.env`가 로드돼 fail-fast를 침묵시키는 일이 없어야 한다.
2. **`.gitignore`에 `.env`·`.env.*`(단 `!.env.example`) 등재** — 실수 커밋 원천 차단(§1.5 결함 동시 해소).
3. **`.env.example`은 더미값만**, 실크리덴셜 금지.
4. **relaxed binding 시크릿(`JWT_SECRET`/`GATEWAY_INTERNAL_SECRET`) 스모크 검증** — 로더 프로퍼티 소스가 relaxed binding으로 잡히는지 로컬에서 실제 확인(안 잡히면 그 두 값만 예외 처리 필요).

### 4.2 "아무것도 안 함"도 유효한 선택지

현 방식은 로컬이 이미 무-env 부팅이라, SMTP 실발송처럼 **가끔** 실크리덴셜이 필요한 정도면 옵션 B(IDE env)나 "셸에서 export 후 실행"으로 충분할 수 있다. 도입 비용(빌드 의존성·스모크·게이트2)을 감안하면, **필수 조치는 §1.5의 `.gitignore` 보강 1건**뿐이고 로더 도입은 편의 투자 여부의 문제다. 이 판단은 사용자 몫이다.

## 5. 게이트2 플래그

- **옵션 A 권장안 채택은 게이트2 상신 대상**이다. 이유: (1) **빌드 의존성 추가**(`me.paulschwarz:spring-dotenv` 등 — `backend/build.gradle` 변경), (2) **설정 로딩 방식 변경**(프로퍼티 소스에 dotenv 로더 개입 — 전 도메인 부팅 경로에 영향), (3) **CLAUDE.md 섹션 2·4 문구 보강**(`.env` 커밋 금지 → "로컬 `.env` 로더 허용·운영 미배포" 예외 명문화). 되돌리기·전역 파급이 있어 총괄 자율 범위를 넘는다.
- **이 문서의 범위는 분석·권고까지다.** 실제 도입(빌드 파일·로더 배선·gitignore·example·스모크)은 **별건 티켓**으로, 게이트2 승인 후 backend-impl에 위임한다.
- **예외**: §1.5의 `.gitignore`에 `.env` 추가만 하는 최소 조치는 로딩 방식·빌드 변경이 아니어서 파급이 작다. 다만 시크릿 정책 관련이라 사용자 확인 후 별건 티켓으로 처리할 것을 권한다(게이트2 정식 상신까지는 불요, 총괄이 사용자에 고지).

### 5.1 사용자 상신 문장(총괄이 평이하게 전달할 초안)

> "지금은 비밀번호 같은 민감값을 환경별(로컬/개발/운영) 파일로 나눠 관리하고, 로컬은 기본값이 박혀 있어 아무것도 안 넣어도 앱이 뜹니다. `.env` 한 파일로 몰지 않은 건 실수 커밋 위험·환경 경계 흐려짐·운영 배포 방식과의 어긋남을 피하려는 의도였습니다. 앞으로 **로컬에서만** `.env` 한 파일로 편하게 관리하고 싶다면, 그걸 읽어주는 작은 라이브러리를 붙이는 방법을 권합니다(운영은 지금의 안전장치 그대로 유지). 이건 빌드 설정과 규약을 바꾸는 일이라 도입 전에 승인을 받고 싶습니다. 그리고 승인과 별개로, 지금 `.gitignore`에 `.env`가 빠져 있어 실수로 비밀번호가 커밋될 틈이 있으니 이 한 줄은 먼저 막는 걸 권합니다. 도입할까요, 아니면 지금처럼 두고 필요할 때만 환경변수를 넣는 방식을 유지할까요?"
