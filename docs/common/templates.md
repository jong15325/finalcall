# FinalCall 표준 템플릿

모든 산출물의 **모양**을 정한다. 여기엔 규칙이 없다 — 무엇을 할지는 `rules.md`, 왜 그런지는 `<역할>/decision-log.md`.

- **부팅 필독**: `rules.md` + 이 문서 + `spec/` 3종.
- **소유·개정**: 컨설턴트.
- **원칙 3개**
  1. **최소 골격만.** 채울 것이 없는 섹션은 **지운다.** 빈 섹션·"해당 없음"을 남기지 않는다.
  2. **필수 필드는 비우지 않는다.** 비울 것 같으면 보내지 말고 격상한다.
  3. **템플릿은 상한이 아니라 하한이다.** 더 쓸 수 있으나 골격은 지킨다.

최종 갱신: 2026-07-16 · 반영: C-064 · C-065 · C-069 (작성 규칙 29 → 17) · C-072 ([15] 작업 리스트) ·
**C-073 ([10] status.md 형식 폐기 — 결번)** · **C-076 ([7] 브리핑 — 사용자에게 규약 용어로 말하지 않는다)** · **C-080 ([7] 브리핑 — 요점만, 상세는 요청 시)** ·
**C-085 ([1] 헤더 — 발신·수신 8종 · 유형 4종을 예시로 박음. 회신은 유형이 아니다)**

## [1] 메시지 공통 골격

모든 `outbox/` 파일의 머리는 고정이다. **상태 줄은 없다.**

```
회신대상: <경로>              # 회신일 때만. 신규 발신이면 이 줄 삭제
관련 스레드: <스레드명>        # 여러 스레드에 걸칠 때만. 아니면 삭제
# [<발신> → <수신>] <유형>: <제목>
```

**발신·수신은 `rules [1]` 역할 표의 이름만 쓴다.** 지금은 이렇다 —
`총괄` · `컨설턴트` · `기획` · `백엔드` · `프론트` · `QA` · `보안` · `디자인`
**역할은 늘거나 줄 수 있다. 어긋나면 표가 정본이고 이 줄이 낡은 것이다.**

**유형은 이 4개만 쓴다:**
`결정 요청` · `작업 지시` · `완료 보고` · `정보 공유`

### 예시 — 모양만 베낀다. 제목은 자기 것을 쓴다

```
# [총괄 → 백엔드] 작업 지시: <제목>
# [백엔드 → 총괄] 완료 보고: <제목>
# [백엔드 → 기획, 총괄] 정보 공유: <제목>        ← 여럿이면 쉼표
# [컨설턴트 → 전 역할] 정보 공유: <제목>         ← rules [1] 표 전부일 때만
# [백엔드 → Claude Code] 작업 지시: <제목>       ← 버스 밖
```

회신은 이렇게 쓴다:

```
회신대상: <경로>
# [총괄 → 컨설턴트] 정보 공유: <제목>
```

- **`전 역할`은 `rules [1]` 표 전부일 때만 쓴다.** 일부면 쉼표로 나열한다. **순서는 무관하다**
- **`Claude Code`는 버스 밖이다** — 부모 대화가 자기 손에 내리는 지시다(`rules [9.20]`)
- **회신은 유형이 아니다.** `회신대상:` 줄이 회신 표시고, 유형은 위 4개 중에서 고른다

### 쓰지 않는다

```
# [총괄 → 컨설턴트] 결정 회신: …               ← 「회신」은 유형이 아니다
# [총괄 → 컨설턴트] 회신(결정): …              ← 〃
# [총괄 → 전 역할] 정보 공유(긴급): …          ← 괄호를 붙이지 않는다
# [총괄 → QA] 완료 보고 검수 + 게이트 판정: …   ← 합성하지 않는다
# [기획/설계 → 총괄] …                        ← 옛 이름이다. 「기획」이다
```

경로: `<역할>/outbox/<스레드>/NNN-주제.md`
말미 필수: `회신: 필요 — <무엇을>` 또는 `회신: 불요`

## [6] 결정 로그 항목

**`결과`는 긍정·부정·중립을 한 섹션에 나란히 쓴다.** 좋은 것과 나쁜 것을 갈라 놓으면 나쁜 것이
각주가 되고, 비용이 없는 척하는 문서가 된다.

```
## <ID>. <제목 — 결정 내용이 드러나게>

상태: PROPOSED | ACCEPTED | ON-HOLD | SUPERSEDED (→ 대체 ID) · 소유: <역할> · 관련: <참조 키워드> · <날짜>

맥락
- <어떤 힘들이 충돌하나. 중립적으로. 실물 근거는 경로·수치로>

결정
- <"~한다". 원자적 1건. 능동태, 애매어 금지>

결과
- 좋아짐: <이 결정이 개선하는 것>
- 나빠짐: <이 결정이 치르는 비용·추가 부담·새로 생기는 위험>
- 못 푸는 것: <처방이 닿지 않는 범위. 효과를 과장하지 않는다>

기각된 대안
- <대안>: <기각 사유>

집행: <반영처 + 반영됐는지 확인하는 방법>

레퍼런스: <외부 근거. 없으면 이 줄 삭제>
```

- SUPERSEDED 시 본문을 지우지 않고 상태 줄 아래에 **대체 사유 주**를 단다
- 에스컬레이션 후엔 상태 줄에 `escalated-as <ID>`만 추가한다

## [7] 사용자 브리핑 (매 응답 끝, 채팅)

사용자가 **작업 전체를 한 번에 보는 수단**이다. 결론이 맨 앞, 근거가 뒤.

```
---
**브리핑**

> **<결론 1~2문장. 이번 응답에서 무엇이 결정·완료·발견됐나>**

**한 일**
- **<작업명>** ← <출처: 어느 지시·결정·스레드에서 나왔나 · 경로 또는 ID>
  <구체적으로 무엇을 했나 1줄> → `<산출물 경로>`
- **<작업명>** ← <출처>
  <1줄> → `<경로>`

**주고받음**
- **→ <파트>** `<경로>` — <요지 1줄> · 회신 필요 | 불요
- **← <파트>** `<경로>` — <요지 1줄>

**발번·상태** · <ID> <상태> · <ID> → <상태 변경>

**할 일**                          # 없으면 → **할 일** · 없음

| # | 무엇 | 발신/수신 |
|---|---|---|
| 1 | **<동사로 시작>** — <왜 / 안 하면 뭐가 막히나> | **→ <파트>** = 사용자가 그 파트에 전달 |
| 2 | **<동사로 시작>** — <이유> | **← <파트>** = 그 파트에서 받아올 것 |
| 3 | **<동사로 시작>** — <이유> | — = 사용자가 여기서 판단할 것 |

**프롬프트** · #<번호> → <파트>
```
<복붙할 문구>
```

**커밋**
```
git add <경로> && git commit -m "<제목>

<본문>"
```
---
```

**작성 규칙**

- **사용자에게는 규약 용어 없이 먼저 답한다.** 조항 번호(`[N.M]`)·유형 번호·역할 접두어는
  **파트끼리 쓰는 말이다.** 무슨 일이 일어났고 무엇이 필요한지를 **사람 말로 먼저** 쓰고,
  추적이 필요하면 괄호로 뒤에 붙인다. **사용자가 규약을 열게 만들면 그 브리핑은 실패다**
- **요점만 쓴다. 안 물은 건 안 쓴다.** 근거·검증·값·자기 관측·기각한 대안은 **요청받을 때** 낸다.
  **단 골격은 버리지 않는다** — `할 일`·`프롬프트`·`커밋`은 **사용자가 쓰는 것이라 안 물어도 낸다.**
  **줄일 것은 뒤(근거·검증)지 앞(결론·할 일)이 아니다.**
  **사용자가 「장황하다」고 하면 그 브리핑은 실패다. 「브리핑이 없다」고 해도 실패다**
- **`프롬프트` 블록은 복붙만 하면 되게 완성형으로 쓴다.** 사용자가 문구를 짓게 하지 않는다
- **`커밋` 블록은 그 응답에서 산출물을 냈을 때만 낸다.** `git add`부터 전체 명령을 완성형으로 쓴다
- 파일에 쓴 내용도 요지는 여기 노출한다

## [13] 규약 항목 (`rules.md` · 파트 지침)

### 문서 골격

```
# <제목>

<이 문서가 답하는 질문 1줄>

- **부팅 필독**: <해당하면>
- **소유·개정**: <역할>. 개정하면 **덮어쓴다**(불변 아님, 이력은 git).
- **편입 기준 — 1문이다**: **"이 조항을 지우면 뭐가 실제로 깨지나?"**
  답이 *"언젠가 누가 실수할 수도"* 면 이 문서에 없다. 답이 *"지금 A가 B를 못 찾는다"* 면 있다.
- **읽는 법**: 모든 규칙은 `[N.M]` 번호 + 명령형 한 문장이다. 표는 참조 데이터일 뿐 규칙이 아니다.
  **결번은 정상이다** — 삭제된 조항의 번호를 재사용하지 않는다.

최종 갱신: <날짜> · 반영: <최신 결정 ID>

---

## [N] <절 제목>

<표가 필요하면 여기. 표는 참조 데이터다>

**[N.1]** <명령형 한 문장>
**[N.2]** <명령형 한 문장>
근거: <결정 ID 목록>
```

### 작성 규칙

- **이유 금지.** "왜냐하면"이 나오면 그건 결정 로그로 간다. `근거:` 줄의 ID가 이유를 대신한다
- **고유명사 금지.** 도메인명·특정 ID·버전·날짜가 규칙 문장에 들어가면 **다음 사례에서 조항이
  거짓이 된다** (문서 경로는 예외)
- **한 항목 = 한 규칙.** 묶지 않는다
- **번호 없는 규칙을 두지 않는다.** 굵게 쓴 문장도 규칙이면 번호를 준다
- **절차는 예외다.** 순서가 본질인 규칙은 한 번호 아래 번호 목록으로 쓴다.
  쪼개면 `[N.M.1]`이 되어 과설계다
- **절 번호는 고정한다.** 항목이 늘어도 절을 새로 만들지 않는다
- **항목 번호는 append-only다.** 신설은 **그 절의 최대 번호 + 1**을 쓴다.
  **중간에 삽입해 뒤를 밀지 않는다** — 밀면 불변 문서(`outbox/`·`decision-log`)의 인용이 영구히 어긋난다
- **번호는 발번 순서, 배치는 논리 순서다.** 둘이 어긋나는 건 정상이다(`[9.25]`가 `[9.3]` 옆에 있어도 된다).
  **결번도 정상이다** — 조항이 빠지면 번호를 재사용하지 않는다
- **개정 후 `^\*\*\[N\.\d+\]` grep으로 중복·결번을 확인한다.** 조항이 아니라 작업 습관이다
- **개정 후 `git show <직전 해시>:<파일>`로 기존 조항의 번호가 이동했는지 대조한다.**
  **밀림은 grep으로 안 잡힌다** — 밀린 번호는 중복도 결번도 아니고, 전부 연속이고 전부 실재하는
  다른 조항을 가리켜서 **실패 신호가 없다**
- 마지막 절은 **"이 문서가 하지 않는 것"** — 내용별 정본 경로 표

## [14] 킥오프 프롬프트 (새 세션 첫 기동)

브리핑 `할 일`의 `프롬프트` 칸에 그대로 넣는다. **사용자가 복붙만 한다.**

```
너는 FinalCall 프로젝트의 <역할>이다.

필독: docs/common/rules.md · docs/common/templates.md · docs/spec/ 3종
자기 폴더: docs/<역할>/
저장소: D:\Java\finalcall

출근해라.
```

- **역할 설명을 여기 쓰지 않는다.** `rules.md [1]`에 있다. 킥오프가 규약을 복사하면 사본이 늘어난다
- 특정 안건 한정 기동이면 마지막 줄을 `출근하고 <안건>만 처리해라`로 바꾼다

## [15] 작업 리스트 (사용자 요청 시, 채팅)

사용자가 `작업 리스트 보여줘`라고 하면 낸다. 전 역할이 낸다.
**파일로 만들지 않는다** — 요청 시점에 산출하는 뷰다. 갱신 의무가 없다.

산출: 자기 `notes/handover.md` + 대기 큐(`[5.26]`) + 자기 outbox 미완 지시.
총괄은 여기에 전 역할분을 더한다(`[8.9]` 스캔).

```
<역할> 작업 리스트 · <날짜>

뿌리: <전체를 막고 있는 것 1줄. 없으면 이 줄 삭제>

<묶음명>   ← <이 묶음이 어디서 왔나>
├─ [완료] <작업> — <결과 1줄>
│   └─ [진행] <이 작업에서 파생된 것>
├─ [대기] <작업> — <무엇을 기다리나>        → <끝나면 누가 풀리나>
└─ [막힘] <작업> — <무엇에 막혔나>

독립
└─ [진행] <어느 묶음에도 안 속하는 것>
```

- **상태 4종만 쓴다**: `[완료]` · `[진행]` · `[대기]`(남을 기다림) · `[막힘]`(못 감)
- **들여쓰기가 파생이다.** 부모 아래에 자식을 넣는다. 파생이 없으면 평평하게 둔다
- `←` 는 **어디서 왔나**(뿌리·결정 ID·지시 경로), `→` 는 **끝나면 누가 풀리나**
- **줄마다 경로를 달지 않는다.** 사용자가 물으면 그때 낸다 — 읽는 뷰지 색인이 아니다
