## 목표
닉네임 유니크 제약(`nickname_active` UK, OAuth 이전 제약)을 유지할지, 표시용 이름으로 완화(유니크 해제)할지 결정한다. **핵심 질문 = 닉네임이 "유일 핸들"이냐 "표시용 이름"이냐.**

## DoD
- **1단계(분석)**: 닉네임 유니크에 **의존하는 코드**(조회·중복체크·소셜 접미사·멘션·판매자특정) 목록화. publicId·loginId의 유일성 역할 확인.
- **2단계(게이트2 상신)**: 분석 결과 + 총괄 추천(A=유니크 해제·표시용 / B=유니크 유지)을 평이한 언어로 사용자에게 상신. UK drop·signup·소셜 접미사 제거 파급 포함.
- **3단계(결정 후)**: 사용자 선택에 따라 architect가 erd/contract 갱신 → backend-impl 구현(UK drop 마이그레이션·중복체크/접미사 제거) → frontend-impl 회원가입 닉네임 검증 조정. **이 티켓은 결정까지가 DoD**, 구현은 파생 티켓으로 분리.

## 근거인용
erd V4 `nickname_active` UK. FC-153 소셜 find-or-create 접미사 로직. 사용자 피드백(HANDOVER 2026-07-30 B.2). 총괄 추천 = A(publicId·loginId가 이미 유일성 담당).

## 결정 (게이트2, 2026-07-30)
**최초 A(유니크 해제) 잠정 → 사용자 재검토로 철회 → 최종 B 채택: 유니크 유지.**
근거(사용자): 닉네임이 **아이템 판매자 이름 등 표시로 노출**되므로 동명이인은 혼란을 준다 → 유일 핸들이 맞다.
- **기존 `nickname_active` UK·중복검사 로직은 그대로 유지**(마이그레이션·코드 제거 없음). FC-159 자체는 "유지" 결정으로 종결.
- **B 방향에서 파생된 후속 개선 2건**(별도 티켓, 아래):
  - **닉네임 중복확인 활성화**: 회원가입 화면의 현 비활성 "중복확인" placeholder를 실동작으로(백엔드 가용성 조회 엔드포인트 + 프론트 배선). 서버 제출 검증(AUTH_002)은 이미 존재 → 라이브 사전확인 UX 추가.
  - **소셜 랜덤 닉네임**: 카카오·네이버 최초가입 시 닉네임을 랜덤 부여(사용자 후 변경 가능, 기존 PATCH /me). 현 `SocialAccountRegistrar`(provider 표시명+충돌 접미사)를 랜덤 방식으로 조정. ※ 상세 정책(항상 랜덤 vs 표시명 기반)은 착수 전 확인 필요.
