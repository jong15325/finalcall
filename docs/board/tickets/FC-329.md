## 목표 / DoD / 검증
- production-like 멀티노드에서 20k socket, 300/s 지속, 1,000/s burst와 실제 장애 matrix를 재검증한다.
- 목표 미달이면 출시 차단 상태와 병목 근거를 명시한다.
- 150/s는 0 drop, p95 198ms·p99 305ms를 통과했다.
- 300/s는 실효 182.9/s·2,152 drop·p95 8.59초, pool 30/node 조정 후에도 실효 201.4/s·2,023 drop·p95 8.16초로 실패했다.
- 유력 병목은 local recipient 확인 전에 시작되는 `ChatRedisFanoutListener` 트랜잭션과 DB pool 경합이다.
- fan-out listener 경계와 retention 인덱스 보정 후 잔여 병목은 `afterCommit()`의 동기 Redis publish로 좁혀졌으며, FC-334·FC-335에서 비동기 fast-path 계약·구현을 보정한 뒤 동일 topology로 재측정한다.
- 20k socket·300/s 5분·1,000/s 60초와 최종 전체 build는 장기 실행을 중단해 미검증이며 출시 차단이다.
- FC-335 적용 후 실제 Linux host 기준 재검증이 필요하다. 현재 Windows native와 Docker Desktop Linux k6 모두 고율에서 response receiving tail이 왜곡되지만, 양 app access log는 평균 약 20ms·최대 60ms이고 Hikari pending·fast-path failure·Redis failure·Kafka lag은 0이었다.
- 차단 해소 조건: 실제 Linux host/CI runner에서 2-Gateway/2-app 클러스터 합산 keep-alive 50→150→300/s를 재검증한다. 기존 계약의 재검증이므로 게이트2는 필요 없다.
- 2026-08-20 사용자 지시에 따라 외부 Linux 환경 추가 전에 현재 Windows/Docker Desktop 경로의 앱 완료→Gateway flush→client body 수신 지연을 분리 진단한다.
- 통제 진단에서 backend 처리와 first-byte는 정상이고 Windows client body drain만 50/s부터 지연되는 최소 재현을 확보했다. 현재 gateway에 마지막 chunk flush timing 관측이 없어 SCG flush와 Windows TCP/Go transport 중 정확한 주체는 미확정이며, 코드·설정 변경 근거는 없다.
- 최종 self-hosted run `32503805495`에서 10→50→150→300/s와 300/s 5분은 모두 drop 0·HTTP 201 100%·SLO를 통과했다. 300/s 5분은 90,001건, p95 59ms·p99 84ms였다.
- 1,000/s 60초 burst는 완료 57,757건·drop 2,243건·HTTP 실패 1,479건·p95 3,799ms·p99 4,184ms로 실패했다. Hikari pending 최대 167/168, timeout 누적 646/705였고 socket 단계는 계약대로 미실행했다.
- 최종 reviewer 판정은 `changes-requested / release blocked`다. 추가 최적화·재진단 티켓은 자동 파생하지 않는다.
