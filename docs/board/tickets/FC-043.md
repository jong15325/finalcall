## 목표
- FC-041이 확정한 톤(v0.5 토큰·표면 층 분리·브랜드)을 **인증 화면**에 적용한다.
- 우선순위 변경(사용자 지시 2026-07-19): 홈 완료 후 **경매 목록·상세(FC-042)보다 인증을 먼저** 한다.

## 왜 이 화면인가
사용자가 이 프로젝트 디자인 부재를 처음 지적할 때 **직접 예로 든 화면**이다:
> "로그인도 흰 바탕에 버튼 입력칸밖에 없고?"

실제로 `LoginPage.tsx`는 `h1` + 필드 2개 + 버튼 + 링크가 흰 배경에 `max-w-sm`으로 가운데 정렬된 게 전부다. `AuthFormLayout`은 내비 없이 중앙 정렬 상자 하나뿐이다. **접근성·토큰은 정확한데 시각 디자인이 없다.**

## 만들 것 — 페이지 단위 분리
`docs/ux/mockups/` 아래 자체완결 정적 HTML. **파일 1개 = 페이지 1개**, 토글 금지.
1. **로그인**
2. **회원가입**

두 화면이 한 시스템으로 읽혀야 한다.

## DoD
- **인증 화면의 셸을 결정한다.** 현재 `AuthFormLayout`은 내비가 없다(의도된 것 — 폼 이탈 방지). 그 판단을 유지할지, 최소 셸(브랜드만)을 둘지 **결정하고 근거를 남겨라.** 유지한다면 브랜드가 어디에 어떻게 놓이는지는 여전히 설계 대상이다.
- **폼 시각 설계** — 필드 밀도·라벨 위치·에러 표현·포커스 상태·버튼 무게. `Field`·`Button` 컴포넌트 계약(§5.1·§5.2)은 지키되 **비주얼은 새로 만든다.**
- **상태 표현**: 에러(필드 단위 + 폼 단위) · 로딩 · rate limit 경고(§5.6 — `Retry-After` 카운트다운, "요청이 많습니다. N초 후…"). 실제 계약에 있는 상태다.
- **OAuth 자리** — `§5.11 SocialLoginButton`이 규정돼 있고 OAuth는 백로그(EPIC-OAUTH)다. **자리를 확보할지 지금은 비울지 결정하고 근거를 남겨라.** 나중에 넣으면 레이아웃이 흔들린다.
- **회원가입 고유 요소**: 약관 동의·중복 확인·비밀번호 규칙 안내 등이 계약(§2)에 있는지 확인하고 **있는 것만** 반영하라. 없는 필드를 창작하지 마라.
- **반응형** 최소 2폭.
- 가입 성공 → 자동 로그인하지 않는다(P-010, rate limit 회피). 가입 후 로그인 화면으로 돌아오며 성공 알림이 뜨는 흐름이 이미 구현돼 있다 — 그 상태도 보여라.

## 지켜야 할 제약 (design-system v0.5)
- **§1.2 색 3계층**: 조작=**블랙 CTA**, 퍼플은 **액센트만**(링크·포커스·선택). 퍼플을 CTA 채움으로 쓰지 마라.
- **표면 층**: `bg #F7F7F8` · `surface #FFFFFF` · `surface-band #EFEFF1` · `surface-sunken #E8E8EB`. 인증 화면은 콘텐츠가 적어 **층 구조를 어떻게 쓸지가 특히 중요하다** — 흰 카드가 오프화이트 위에 뜨는 구조를 살려라.
- **Game-Color Containment**: 인증 화면에는 **아이템이 없다.** element 색·글로우·골드포스를 여기 쓰면 명백한 위반이다.
- WCAG 2.1 AA. `text-subtle #67676E`·`border-strong #818187`(v0.5 보정값) 사용.
- 다크모드 만들지 마라.
