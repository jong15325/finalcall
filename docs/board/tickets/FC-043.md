## 목표
- FC-041이 확정한 톤(v0.5 토큰·표면 층 분리·브랜드)을 **인증 화면**에 적용한다.
- 우선순위 변경(사용자 지시 2026-07-19): 홈 완료 후 **경매 목록·상세(FC-042)보다 인증을 먼저** 한다.

## 왜 이 화면인가
사용자가 이 프로젝트 디자인 부재를 처음 지적할 때 **직접 예로 든 화면**이다:
> "로그인도 흰 바탕에 버튼 입력칸밖에 없고?"

실제로 `LoginPage.tsx`는 `h1` + 필드 2개 + 버튼 + 링크가 흰 배경에 `max-w-sm`으로 가운데 정렬된 게 전부다. `AuthFormLayout`은 내비 없이 중앙 정렬 상자 하나뿐이다. **접근성·토큰은 정확한데 시각 디자인이 없다.**

## 만들 것 — 페이지 단위 분리
`docs/ux/mockups/` 아래 자체완결 정적 HTML. **파일 1개 = 페이지 1개**, 토글 금지.
1. **로그인**
2. **회원가입**

두 화면이 한 시스템으로 읽혀야 한다.

## DoD
- **인증 화면의 셸을 결정한다.** 현재 `AuthFormLayout`은 내비가 없다(의도된 것 — 폼 이탈 방지). 그 판단을 유지할지, 최소 셸(브랜드만)을 둘지 **결정하고 근거를 남겨라.** 유지한다면 브랜드가 어디에 어떻게 놓이는지는 여전히 설계 대상이다.
- **폼 시각 설계** — 필드 밀도·라벨 위치·에러 표현·포커스 상태·버튼 무게. `Field`·`Button` 컴포넌트 계약(§5.1·§5.2)은 지키되 **비주얼은 새로 만든다.**
- **상태 표현**: 에러(필드 단위 + 폼 단위) · 로딩 · rate limit 경고(§5.6 — `Retry-After` 카운트다운, "요청이 많습니다. N초 후…"). 실제 계약에 있는 상태다.
- **OAuth 자리** — `§5.11 SocialLoginButton`이 규정돼 있고 OAuth는 백로그(EPIC-OAUTH)다. **자리를 확보할지 지금은 비울지 결정하고 근거를 남겨라.** 나중에 넣으면 레이아웃이 흔들린다.
- **회원가입 고유 요소**: 약관 동의·중복 확인·비밀번호 규칙 안내 등이 계약(§2)에 있는지 확인하고 **있는 것만** 반영하라. 없는 필드를 창작하지 마라.
- **반응형** 최소 2폭.
- 가입 성공 → 자동 로그인하지 않는다(P-010, rate limit 회피). 가입 후 로그인 화면으로 돌아오며 성공 알림이 뜨는 흐름이 이미 구현돼 있다 — 그 상태도 보여라.

## 지켜야 할 제약 (design-system v0.5)
- **§1.2 색 3계층**: 조작=**블랙 CTA**, 퍼플은 **액센트만**(링크·포커스·선택). 퍼플을 CTA 채움으로 쓰지 마라.
- **표면 층**: `bg #F7F7F8` · `surface #FFFFFF` · `surface-band #EFEFF1` · `surface-sunken #E8E8EB`. 인증 화면은 콘텐츠가 적어 **층 구조를 어떻게 쓸지가 특히 중요하다** — 흰 카드가 오프화이트 위에 뜨는 구조를 살려라.
- **Game-Color Containment**: 인증 화면에는 **아이템이 없다.** element 색·글로우·골드포스를 여기 쓰면 명백한 위반이다.
- WCAG 2.1 AA. `text-subtle #67676E`·`border-strong #818187`(v0.5 보정값) 사용.
- 다크모드 만들지 마라.

## 재점검 (2026-07-19, 사용자 지시) — FC-042 학습 소급 적용
이 목업들은 **2026-07-19 오전 산출물**이고, 그 뒤 FC-042 경매 상세가 **세 번 반려**되면서 확정된
원칙들이 **하나도 반영돼 있지 않다.** 사용자가 재점검을 지시했다.

### 소급 적용할 원칙 3가지
1. **★ 타이포 위계** — FC-042 1·2차 반려의 원인 진단은 **"12/13/14/15/16px이 촘촘히 깔려
   전부 비슷한 회색 글자로 뭉갰다"**였다(FF 픽셀 리마스터와 같은 증상). 3차에서 확립한 원리는
   **중간 크기를 없애 간극 자체를 위계로 삼는 것** — 라벨 11px/700/자간 +.12em(넓힘),
   주 값은 크게/800/자간 −.04em(좁힘). **반대 방향 자간이 대비를 만든다.**
   단 인증은 "큰 수치"가 없는 화면이라 **무엇이 주인공인지 먼저 정하고** 위계를 몰아준다.
   경매 상세의 44px을 기계적으로 복사하지 않는다.
2. **★ 반응형 별도 설계** — "좁아지면 1열로 접는다"는 설계로 인정하지 않는다. 데스크톱·모바일
   구조를 각각 도식으로 제시한다. 인증에서는 모바일 키보드가 CTA를 가리는지, OAuth 배치가
   엄지 도달 범위인지, 폼 좌측 배치가 모바일에서도 의미가 있는지 등이 쟁점이다.
3. **레퍼런스 기반 판단** — FC-042는 레퍼런스 없이 자체 논리로 설계해 두 번 실패했다.
   조사 문서에 인증 직접 자료는 없으므로 **"레퍼런스 부재"를 명시**하게 했다.
   **지어낸 근거보다 "근거 없음"이 낫다.**

### 유지(재검토 대상 아님)
최소 셸 · OAuth 자리 확보 · 에러 처리 두 화면 반대 · 창작하지 않은 것(약관 체크박스·비밀번호
규칙 힌트) 전부 유효하다.

### 판단 대기 4건은 여전히 사용자 결정 사항
약관 동의(문장 vs 체크박스) · 네이버 버튼 대비 · 가입 CTA 문구 · 폼 좌측 배치.
**타이포·반응형 개편이 이 4건에 영향을 주면 보고**하도록 지시했다.

### 재점검 결과 (2026-07-19)
**핵심 병증 확인** — 개편 전 **라벨 14px와 입력값 15px의 1px 차이**. 자간도 둘 다 음수라 라벨과
값이 사실상 같은 크기로 읽혀 폼 전체가 회색 문장 더미가 됐다. FC-042와 같은 증상이었다.
개편 후 자간이 **반대 방향**(+.12em ↔ −.01em)이라 크기 차이보다 큰 대비가 생긴다.
전수 감사 결과 14·15·16·20·22·30px 전멸(워드마크 22는 브랜드 자산이라 면제).

**주인공 = 폼 그 자체(입력값 + CTA).** 인증에는 "현재가" 같은 큰 수치가 없어 44px을 복사하지
않았다. 사용자가 하는 일은 **타이핑하고 누르는 것** 둘뿐이므로, 가장 굵은 활자를 제목이 아니라
① 방금 친 값(17px/600) ② 주 CTA(18px/800)에 몰았다. 화면의 무게 중심이 흰 카드 안에 있다.
부수 효과로 CTA 18px/800은 design-system §5.1 `lg` 스펙 **복귀**다(종전 16px는 스펙 미달).

**반응형 — 열 접기가 아닌 지점 4개**:
| 항목 | 데스크톱 | 모바일 | 근거 |
|---|---|---|---|
| CTA 도달 | 폼 아래 정위치 | **카드 내부 sticky bottom** | 가입 4필드는 360×640에서 키보드 뒤 잔여 ~300px이라 CTA가 절대 안 들어온다 |
| 보조 설명 | 병렬 열 | **접힌 아코디언** | 존재 이유가 "빈 우측 열을 정보로 채운다"였다 → 모바일엔 그 빈 열이 없다 |
| 첫 필드 포커스 | 자동 | **안 함** | 진입 즉시 키보드가 올라와 "여기가 어디인지" 확인 전에 입력을 강요 |
| 에러 전달 | `role=alert` 배너 | + **포커스 이동·스크롤** | `role=alert`는 낭독은 보장해도 시각 사용자의 시야는 보장하지 않는다 |

`fixed`가 아니라 `sticky`를 쓴 이유: fixed는 흐름 밖이라 하단 패딩을 따로 확보해야 하고
OAuth·푸터 위까지 떠다닌다. sticky는 `.form` 안에서만 붙고 폼을 지나면 자연히 풀린다.
**모바일 다단계 분할은 명시적 기각** — 계약에 없는 중간 상태(부분 제출)를 만들거나 비밀번호를
클라이언트에 오래 들고 있게 된다.

### 판단 대기 4건 갱신
- **폼 좌측 배치** — 영향 없음. 좌/우 어느 쪽이든 반응형 설계가 그대로 성립한다.
- **네이버 버튼 대비** — **수치 확정**: 흰 라벨 on `#03C75A` **2.25:1**, opacity .78 합성 후
  **1.94:1**. 결정 근거만 채웠고 결정은 하지 않았다.
- **약관 동의(문장 vs 체크박스)** — **약한 영향 발생.** 문장을 CTA 아래 둔 배치가 모바일 sticky
  CTA와 정합적이다. **체크박스로 전환하면** 체크박스가 CTA 위에 와야 하는데(미체크 시 disabled)
  sticky 바가 이를 가릴 수 있어 **sticky 영역에 체크박스를 함께 넣는 설계가 추가로 필요하다.**
- **가입 CTA 문구** — 영향 없음. 18px/800 슬롯은 어느 문구든 460px에서 한 줄에 들어간다.

### ★ 근거 없이 판단한 지점 (에이전트 자진 신고)
`auction-detail-references.md`에 **인증 화면 직접 자료가 하나도 없다**(조사 대상은 경매·거래소·
상품 상세·모달이었다). 레퍼런스 근거가 있는 것은 **타이포 원리**와 **디바이스별 상시 노출 수단**
둘뿐이고, 아래 4건은 **추론이다**:
1. "주인공 = 입력값 + CTA" — 인증 아이트래킹·전환율 자료를 찾지 않았다
2. 모바일 sticky CTA가 가입 이탈을 줄인다 — 커머스 PDP 스티키 바 자료를 **폼에 유추 적용**
3. 모바일 오토포커스 해제 — 관행이나 출처 미확인
4. 보조 설명 열을 모바일에서 접는 판단 — FC-042 논리를 옮긴 것

→ **인증 화면 레퍼런스 조사가 필요하면 별도 티켓**이 맞다(후속 후보).
