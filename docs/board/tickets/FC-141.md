## 목표
현 프로젝트의 환경변수/시크릿 관리 방식을 분석하고, 사용자 질문에 답하는 검토 문서를 작성한다. 사용자 질문 원문: "원래는 .env로 환경변수값을 모두 관리했는데 현재 프로젝트는 그렇게 진행 안 하고 있음 — 추후에 이 환경변수를 어떻게 관리해야 할까. 개발자 입장에선 env에서 한 번에 관리하는 게 편했는데 그렇게 개발되지 않은 이유와 앞으로 어떻게 하면 되는지."

## DoD
`docs/common/proposals/env-management-review-v0.1.md`(한국어)에 아래를 담는다:
1. **현황 서술**: 현재 방식 = 프로파일별 yml(`application-local.yml` 기본값 `${ENV:기본값}` / `application-dev.yml`·`prod.yml` 기본값 없는 `${ENV}` fail-fast) + OS 환경변수 주입. `.env` 파일·dotenv 로더 미사용. 시크릿(JWT/DB/게이트웨이/MAIL)은 커밋 금지·env only. 근거 코드·설정 위치 인용.
2. **왜 .env 단일 통합이 아니었나**: CLAUDE.md 섹션 2(시크릿 커밋 금지)·섹션 4(시크릿 fail-fast — 로컬 `${ENV:기본값}`, 운영 `${ENV}` 기본값 없음)의 설계 의도, 12-factor config, Spring 프로파일 관례, `.env` 통합의 리스크(실수 커밋·프로파일 경계 소실·운영 주입 경로와 이원화)를 설명. **판단 아님 — 왜 이렇게 됐는지 근거 위주.**
3. **개발자 편의 vs 현 방식 트레이드오프**: "한 곳 관리"의 실익과, 현 방식이 로컬은 이미 기본값으로 env 없이 부팅되는 점(로컬 편의는 이미 확보)·운영 fail-fast의 안전 가치를 대비.
4. **앞으로의 옵션·권장안**: 로컬 개발자 편의를 살리는 선택지들(예: `spring-dotenv`/`me.paulschwarz` 류 라이브러리로 로컬 `.env` 로드, IDE run configuration의 env, direnv, `.env.example` + gitignore + 로컬 로더)을 각각 **보안·이식성·프로파일 정합·운영 경로 일치** 축으로 트레이드오프 정리하고 **권장안 1개**를 제시. 운영은 현 fail-fast 유지 전제.
5. **게이트2 플래그**: 권장안이 프로젝트 전역 컨벤션 변경(빌드 의존성 추가·설정 로딩 방식 변경)이면 채택은 게이트2로 사용자 상신 대상임을 명시. 이 문서는 **분석·권고까지**이고 실제 도입은 별건.
