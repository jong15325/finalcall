## 목표
- **프로젝트 핵심 기술 도전을 증명하는 티켓.** "동시성 제어를 했다"가 아니라 "깨지지 않음을 테스트로 보였다"까지 간다.
- FC-032의 직렬화가 실제 경합에서 불변식을 지키는지 검증한다.

## DoD
- **마감 직전 폭주 시나리오**: N개 스레드가 동시 입찰. 검증 — 최고가 **단조 증가**, 최종 최고가 = 유효 입찰 중 최댓값, 최종 `highest_bidder_id`가 그 입찰자와 일치, 성공 입찰 수 + 거부 수 = 시도 수(유실·중복 없음).
- **홀드 합계 불변식**: 임의 시점에 `사용자 잔액 + 활성 홀드 합계 = 초기 잔액`(금전 총량 보존). 동시 입찰 후에도 성립. **활성 홀드는 경매당 최대 1건**(직전 입찰자 홀드가 반드시 해제됨 — P-008).
- **연장 경합**: 동시 입찰이 소프트클로즈 창에 몰릴 때 `extension_count`가 입찰 수만큼 무분별 증가하지 않고 규칙대로 증가. `end_at`이 `max_end_at`를 **절대 초과하지 않음**.
- **거부 경로 정합**: `BID_004`(연속 입찰)·`BID_005`(잔액 부족)가 동시 상황에서도 정확히 판정되고, 거부된 입찰이 홀드를 남기지 않음.
- **실패 시 롤백**: 홀드 생성 후 예외 발생 시 잔액·홀드·최고가가 모두 원복(중간 상태 없음).
- 기존 `AuctionRegisterConcurrencyIntegrationTest` 패턴 참조. 테스트가 flaky하지 않아야 한다(반복 실행 안정성).
- 스타일: `./gradlew :backend:spotlessApply` 후 checkstyle 통과.

## 유의
- 테스트가 통과하도록 프로덕션 코드를 느슨하게 만들지 말 것 — 불변식이 깨지면 **FC-032로 재작업**이 정답이다.
- 직렬화 방식(FC-030 게이트2 (a))에 따라 테스트 구성이 달라진다(분산락이면 Redis 필요, 비관락이면 DB 격리수준 유의).
