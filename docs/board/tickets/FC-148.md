## 목표
카드정보 구매 모달의 판매자 영역에 **판매자 완료 판매 건수(거래 횟수)** 를 실데이터로 표시하기 위한 **계약을 확정**한다. 사용자 결정: ⓐ 실제 만들기, 정의 = **완료된 판매 건수**(2026-07-29). ★ 계약 변경(게이트2)이나 사용자 직접 지시로 승인됨.

## architect가 확정할 것
1. **정의**: "완료 판매 건수" = 무엇을 세나. 후보 — 고정가 마켓 SOLD 리스팅(판매자=본인) + 경매 낙찰(판매자=본인) 합산? 아니면 마켓만? sale_order/order/settlement 도메인의 어느 상태(완료/정산완료)를 기준으로 셀지 정확히 정의. 취소·환불 건 제외 규칙.
2. **데이터 출처**: 실제 완료 판매 기록 테이블/컬럼 확인(sale_order 등). 위조 없이 집계 가능함을 입증.
3. **노출 방식·성능**: 목록(`ShopSummary`) 응답에 판매자 거래 횟수를 넣을지, 상세(`ShopDetail`)에만 넣을지, 별도 seller-stats 경로로 뺄지. **목록 N건 각각 카운트 쿼리 = N+1/성능 위험** → 집계 조인·서브쿼리·denormalized 카운터 중 권장안과 근거. 카드정보 모달은 목록(`ShopSummary`)에서 바로 열리므로 목록 응답 포함이 자연스러운지 검토.
4. **계약 형상**: 추가 필드명·타입(예: `sellerCompletedSales: long`)·위치. 기존 형상 보존 원칙(필드 추가만).
5. **파급**: 이 계약으로 나올 하위 티켓(backend 집계 구현 + frontend 표시). 파급 티켓 목록 제시.

## DoD
- api-contract(또는 shop-spec)에 판매자 완료 판매 건수 필드·정의·집계 규칙·성능 전략을 명시. 하위 티켓(backend/frontend) 분해안 제시. 코드 변경 없음(계약 문서만).
