## 목표
판매가가 최소수수료보다 작을 때 정산액이 음수가 되어 **판매자 잔액이 오히려 감소하고 원장 총량 보존(I-H)이 깨지는** 결함을 없앤다. 2026-08-03 거래 도메인 보안 감사 발견.

## 결함 (도달성 확인됨)
- `fee = max(rate·price 캡, minFee)`, `settle = price − fee`. `min-fee=100`(application.yml:183)인데 경매 `startPrice > 0`(1 허용, AuctionService.validatePrice:266)·상점 저가 리스팅이 가능 → 판매가 1에 낙찰/구매 시 `fee=100`, `settle = 1 − 100 = −99`.
- 음수 settle이 `increaseGameMoney(sellerId, settle)`로 흐르면 판매자 잔액 감소 + 플랫폼이 실이동보다 큰 fee 기록 → 게임머니 총량 보존(I-H) 위반.
- 자기손해형(공격자 이득 아님)이라 심각도 minor이나 **원장 정합성**이라 수정 가치 있음.
- 적용 지점: `CloseService.java:117`·`PurchaseService.java:104`·`ShopPurchaseService.java:91`(정산), `FeeCalculator.java:44`(계산).

## architect 산출 (2026-08-03) — 게이트2 상신용

### 1. 도달성 정밀 확인 (모든 판매 경로에서 재현)
- **경매 낙찰(BID, CloseService)**: `startPrice > 0`(AuctionService.validatePrice:266, 하한 1) + 첫 입찰 하한 = 시작가(BidService:164 "첫 입찰 하한은 시작가"). → 시작가 1 경매에 1코인 단일 입찰 → 낙찰가 `price=1`.
- **즉시구매(BUYNOW, PurchaseService)**: `buyNowPrice > startPrice`(:268) → 하한 2. → `price=2`.
- **상점 구매(SHOP, ShopPurchaseService)**: `ShopRegisterRequest.price @Positive`(하한 1) → `price=1`.
- **캐시↔게임머니 교환**: 화폐 충전 플로우일 뿐 수수료/정산 경로가 아니다(별도 판매경로 없음). 정산 소비자는 위 3경로 + 표시용 `MyShopListing.estimatedSettle`(읽기)뿐.
- **최소수수료 `minFee=100`**(application.yml:183, FeeCalculator:44). → 실제 음수 정산: `price=1` → `fee=100`, `settle=−99`. `fee>price`는 **오직 `price<100` 구간에서만** 발생(raw 6% < 100 ⟺ price < 1,667이나 minFee floor로 fee=100 고정; fee>price는 price<100일 때만). 즉 결함 대역 = **`final_price ∈ [1,99]`**.
- **잔액 손상 메커니즘**: `UserBalanceRepository.increaseGameMoney`(:46~48)는 `balance = balance + :amount` 순수 UPDATE로 **비음수 가드 없음**. 음수 amount가 들어오면 판매자 잔액을 감소시키고, 잔액 < (fee−price)면 **음수 잔액**이 된다.

### 2. 불변식 정의 (reviewer/테스트 정본 후보 — I-B 강화)
- **신규 하위 불변식(잠정명 I-B2 "수수료 상한 = 판매가")**: 모든 SOLD 정산에서 `0 ≤ fee_amount ≤ final_price`. 따라서 `settle_amount = final_price − fee_amount ≥ 0`. 결합하여 판매는 판매자 잔액을 **절대 감소시키지 않는다**(비음수 잔액 불변식과 정합).
- **I-H와의 관계(정정)**: 산술 항등 `Σ(잔액 델타) + Σ(원장 델타) = 0`은 **현행에서도 성립**한다(구매자 −price, 판매자 +settle, 원장 +fee, `−price+(price−fee)+fee=0`). 따라서 엄밀히는 "총량 산술 보존"이 깨지는 게 아니라 — (a) settle<0이 판매자 잔액을 매도에도 깎고, (b) 잔액을 음수로 만들 수 있고, (c) 원장이 판매가보다 큰 수익(미실현분)을 적립해 **I-H의 취지("플랫폼 수익 ≤ 실제 판매가")가 훼손**된다. 신 불변식 `fee ≤ price`가 이 셋을 한 번에 봉인한다. (티켓 본문·감사의 "I-H 위반" 표현은 이 취지 훼손을 가리킴 — 정확 표현은 `settle≥0`/`fee≤price` 불변식 부재.)

**추천 = B (수수료 클램프).** 근거:
1. **한 곳에서 모든 경로를 구조적으로 봉인** — 세 판매 경로(경매·즉시구매·상점)와 표시용 예상정산이 전부 `FeeCalculator.compute` 하나를 지나므로, 계산기에 클램프 한 줄이면 끝난다(fee-policy-spec §7 "cap·최소는 계산기 단일 책임"과 정합 — `price` 상한도 같은 자리).
2. **계약·마이그레이션·신규 오류코드 없음** — api-contract 무변경, 진행중 매물 자동 보호. 향후 새 판매경로가 생겨도 자동 적용.
3. **A의 빈틈 없음** — A는 등록 3경로에 각각 검증을 넣어야 하고, 이미 올라온 저가 매물은 마감 때 **여전히 버그**라 별도 마이그레이션이 필수다. B는 정산 수학 자체를 고쳐 이 빈틈이 없다.
4. **저가 매물 금지가 별개 제품 요구로 대두하면** 나중에 A를 B 위에 얹으면 된다(C) — 이 결함 티켓과 분리 가능.
- B의 유일한 트레이드오프: `price<100` 소액 매물에서 플랫폼이 "최소수수료 100"이 아니라 "판매가 전액"을 가져간다(예: 50코인 매물 → 수수료 50·정산 0). 자기손해가 아니라 수익 방향이라 무해하며, 소액대역이라 총수익 영향 무시 가능.
