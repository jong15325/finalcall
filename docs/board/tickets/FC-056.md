## ★★ 게이트2 상신 — 토큰 저장소 (확정 안 함)
**백엔드가 이미 선택지를 좁혀놨다.** 코드 확인 결과:
- `LoginResponse.java`·`RefreshResponse.java` — 토큰이 **응답 바디 JSON**. `Set-Cookie` 없음
- `AuthController.refresh` — refreshToken을 **요청 바디**로 받음
- `LogoutRequest.java` — 로그아웃도 refreshToken을 **바디로 요구**(`@NotBlank`)
- `SecurityConfig.java` — `csrf.disable()` + `STATELESS`, **CORS는 자리만 있고 비어 있음**

→ **httpOnly 쿠키는 백엔드 무변경으로 불가능하다.** JS가 refreshToken을 읽어 바디에 실어야 하므로
쿠키를 택해도 **`httpOnly` 없는 JS 가독 쿠키**다. 그러면 **XSS 노출면은 localStorage와 같은데
CSRF 표면만 새로 얻는다**(자동 전송 + CSRF 비활성 서버). **순수하게 나쁜 쪽.**

**XSS 관점에서 세 선택지가 등가**다 — "토큰이 JS 접근 가능해야 한다"는 제약이 그 축을 이미 결정했다.
**남는 실제 차이는 세션 수명뿐**: `localStorage`(탭·재시작 넘어 유지) vs `sessionStorage`(탭 닫으면 소멸).

CORS/SameSite 충돌 없음(dev는 프록시로 동일 오리진, 운영은 게이트웨이가 같은 경로).

**권고: `localStorage` 유지.** 단 근거는 "안전해서"가 아니라 **"제약상 셋 다 XSS 등가이고 UX가 가장
낫다"**이다. 진짜 개선은 저장소가 아니라 **백엔드 변경**(refresh를 httpOnly 쿠키 + CSRF 토큰)이며
**동결 해제 사안**이다. 자금 시스템이라 `sessionStorage`로 조이는 판단도 방어 가능하다.
→ 판정 시 `configs/app.config.ts` **한 줄**(`store/authStore.ts`가 그 값만 본다).
