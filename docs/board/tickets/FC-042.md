## 목표
- FC-041이 확정한 톤을 **데이터 밀집 화면**에 적용해 실전에서 버티는지 검증한다.
- 경매 목록·상세는 **이미 React로 구현돼 있다**(FC-036·037). 이 목업이 그 화면들을 어떻게 고칠지의 기준이 된다.

## 만들 것
`docs/ux/mockups/` 아래 자체완결 HTML 2면:
1. **경매 목록** — 카드 그리드(20장 규모로 리듬 확인)·필터 바·정렬·무한스크롤 말단
2. **경매 상세** — 아이템 아트·스탯·가격 블록·카운트다운·입찰 CTA·입찰 이력

## DoD
- **FC-041의 셸을 그대로 얹어라.** 톤이 이어지지 않으면 이 티켓은 실패다.
- **상태 다양성을 한 화면에 보여라** — 입찰 있음/없음, 마감 여유/임박(T-5분)/초임박(T-30초), 종료(딤), 즉시구매가 있음/없음. 실제 서비스에서 이 상태들이 **섞여 있을 때** 목록이 어떻게 보이는지가 핵심이다.
- **★ "입찰 없음 · 시작가 N" vs "현재가 · 입찰 N회"** 가 나란히 있을 때 혼동되지 않아야 한다. 이건 계약이 정직하게 설계한 지점이라 시각적으로도 정직해야 한다.
- **아이템 아트 슬롯** — `docs/game_ui/item_info/card_image/` 실물을 상대경로로 참조하라. 지금 React 구현은 플레이스홀더인데, **실제 아트가 들어갔을 때 카드가 어떻게 보이는지**가 이 목업의 큰 목적이다.
- **카운트다운 임박 색전이** 3구간이 실제로 눈에 띄게 다른지 시각적으로 확인 가능해야 한다.
- 상세의 **최고가·입찰수 영역**은 값이 있을 때/없을 때 **레이아웃이 흔들리지 않아야** 한다.
- 반응형 최소 2폭. 다크모드 만들지 마라.

## 지켜야 할 제약
- FC-041과 동일: §1.2 색 3계층(블랙 CTA·퍼플은 액센트만) · **Game-Color Containment**(element 색은 아이템 카드·속성 배지·필터 칩에만) · 등급 배지 없음(D-073) · WCAG 2.1 AA.
- **element 코드 1~4가 전부 확정됐다**(FC-044 게이트2 승인 2026-07-19): **1=물 · 2=불 · 3=흙 · 4=바람**. 원본 게임 DB 4경로 확증이라 **네 속성 모두 확정 표기해도 된다.** `design-system` element 4색 토큰이 이미 있으니 그대로 쓴다. 종전 "3·4 미확정" 제약은 해제됐다(FC-038 M-2의 FAIL 사유도 소멸).
- **`kind`는 `subGroup`에 의존한다**(FC-044). `kind=1`이 무기면 도끼, 방어구면 방패다. 필터 UI를 만들 때 **`kind`를 단독 축으로 그리지 마라** — `subGroup` 선택 후 종속 표시가 맞다. 마법은 `kind`가 2값뿐이다(다른 대분류는 4값).

## 산출 형식 — **페이지 단위 분리** (사용자 지시 2026-07-18)
- **파일 1개 = 페이지 1개.** 경매 목록과 상세는 **별도 파일**이다. 하나에 몰아넣지 않는다.
- **셸(헤더·푸터)은 각 페이지 파일에 포함**한다 — FC-041이 확정한 셸을 그대로 얹은 모습이어야 한다.
- 파일명은 무엇을 담은 페이지인지 **이름만 보고 알 수 있게** 짓는다.
- 반환 시 **파일별로** "이 페이지에서 결정한 것"을 한두 줄씩 붙인다.
- 단, **상태 다양성**(입찰 유무·마감 임박 3구간·종료 등)은 목록 페이지 **한 파일 안에서** 여러 카드로 보여준다 — 실제 서비스에서 섞여 있는 모습이 판단 대상이기 때문이다(상태별로 파일을 쪼개지 마라).

## 1차 디자인 게이트 결과 (2026-07-19) — 재작업
사용자가 브라우저로 확인. **목록은 지적 없음. 경매 상세만 재작업**한다.

1. **아이템 정보가 특정 사이즈에서 깨진다.** 폭은 특정되지 않아 frontend-impl이 전 구간을 훑는다.
   유력 후보는 전환점 3개(1040·1024·860) 사이 구간 — 스펙 2열과 400px 고정 아트의 상호작용.
2. **아트·정보·입찰 세 영역이 조화롭지 않다 → 전면 개편.** 부분 수선이 아니라 배치 재설계다.
   1차 안의 관찰(아트를 전폭으로 늘리면 검은 구멍)은 유효하나, **그 해법이 세 영역의 위계를
   만들어내지 못했다.**
3. **★ 카드 이미지 클릭 시 게임 UI를 차용한 카드 정보 모달**을 띄운다.
   참조: `docs/game_ui/ingame/카드 정보.png`(기본형) 외 탭 상태·카드 종류별 변형 4종.
   원본 구조 = 타이틀바 → 좌 아트 + 우 스펙표 → 탭 4개 → 본문 → 하단 액션.

### 재작업 시 못박은 제약
- **계약에 없는 데이터 창작 금지.** 원본 모달의 `공격 시간`·`데미지`·`채널제한`·`합성조건`은
  계약 v1.10 §3.3에 없다. 못 채우는 항목은 **보고**해 계약 확장 후보로 남긴다.
- **톤 충돌 명시 처리.** 원본은 남색 게임스킨인데 정본은 U-021 라이트 커머스이고
  게임스킨은 SUPERSEDED다. §1.2 Containment와의 관계를 **판단하고 근거를 대며**,
  대안안을 함께 보고한다(디자인 게이트에서 사용자가 판정).
- **모달 접근성 필수**: role=dialog·aria-modal·포커스 트랩·ESC·포커스 복귀·배경 스크롤 잠금.
  트리거는 button(이미지 onclick 금지).
- 수정 범위는 `template-auction-detail.html` **단일 파일**.

### 모달 방식 결정 (2026-07-19, 사용자) — **C 하이브리드**
원본 UI 소스가 `docs/game_ui/card_info/`에 슬라이스된 채 존재함을 확인(31개 + `card_info.xml`
레이아웃 정의, EUC-KR). 창 **211×307**, 탭 51×22, 액션 80×22, `IWS_CANMOVE|IWS_EXIT_ESC`.

**A안(자산 그대로)이 기각된 이유** — 크기보다 구조가 문제였다:
1. 배경이 단일 비트맵이라 **스펙 행 수가 고정**(점선이 이미지에 구워져 있음) → 계약 필드 수와 불일치
2. 텍스트 절대좌표 → 한글 줄바꿈·확대·반응형·고대비 전부 불가
3. 원본 탭 6개 중 계약으로 채울 수 있는 건 1~2개, 액션 버튼(상점에 팔기·포스충전·카드삭제·
   슬롯사용)은 **경매 맥락에 맞는 것이 하나도 없음**

**채택: C 하이브리드** — 레이아웃·색감·은유를 원본에서 정밀 계승하되 **CSS로 재현**한다.
§5.12가 `.spr`을 해독해 CSS로 재현한 선례와 같은 방식. 규격이 맞는 원본 자산만 선별 사용.

**계승 4요소(사용자가 전부 지정)**: 창 배경 색감·질감 / 타이틀바(카드정보 · CARD INFO) /
탭 은유(라디오형, 단 채울 수 있는 탭만) / 드래그 이동 · ESC 닫기.

**★ Containment 판정**: 배경 색감 계승으로 모달이 게임 톤(어두운 남색)이 된다.
→ **"카드 정보 모달은 아이템 표현의 연장이므로 §1.2 Containment 허용 범위"**로 판정한다
(아트 슬롯이 v0.5에서 §1.2에 추가된 것과 같은 논리). **모달 밖으로는 새지 않는다** —
트리거 버튼·페이지 배경·크롬은 라이트 커머스 그대로.
→ `design-system.md §1.2` 본문 개정은 **2차 게이트 통과 후 총괄이 수행**한다(미반영 상태).

**필수 동반 작업**: 어두운 배경이므로 모달 내부 전경색을 새로 도출하고 **AA를 수치로 재증명**해야
한다. 라이트 기준 토큰은 어두운 바탕에서 무효다. 원본 충실도보다 AA가 우선.

**원본 `.spr` 필요 시 사용자가 전달**한다(2026-07-19 사용자 제안). §5.12가 `.spr` 해독으로
정본을 만든 전례가 있으므로, 애니메이션·프레임 타이밍이 필요해지면 요청한다.
