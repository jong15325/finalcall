## 목표
인벤토리(96칸)·임시보관을 실구현한다. 현재 둘 다 `PagePlaceholder`다.
**`ItemArtSlot` 실아트가 가장 빛나는 화면**이다 — 격자에 아트가 깔린다.

## ★ 디자인 게이트 — 사후 판정
§10은 **새 화면은 디자인 방향을 승인받은 뒤 구현**하도록 규정한다. 이 티켓은 **목업이 없고**
사용자가 "진도 우선"으로 **선착수를 지시**해 그 순서를 뒤집었다.
→ **에이전트가 설계 근거와 도식을 반환에 제시**하고, **사용자가 산출물을 보고 판정**한다.
방향이 틀렸다면 재작업 대상이다(FC-042가 3차까지 간 전례가 있다).

## 쓸 수 있는 API (구현 확인됨)

**계약에 없는 엔드포인트를 전제하지 마라.** 슬롯 재배치(정규 내 이동)·아이템 삭제·정렬 저장
등은 **계약에 없다.** 필요하면 **보고**(게이트2).

## 참조 자산 (원게임)
`docs/game_ui/ingame/인벤토리 전체.png` — 원게임 인벤토리 화면.
**차용 판단은 FC-042의 교훈을 따르라**: 계승 대상은 **구조·은유**이지 **창(chrome)이 아니다.**
남색 게임스킨을 그대로 재현하면 2001년처럼 보인다(카드정보 모달이 그래서 폐기됐다).
**§1.2 Game-Color Containment 유지** — 게임색은 **아트 슬롯 안에만**.

## 설계 쟁점 — 판단하고 근거를 대라
1. **96칸을 어떻게 배치하나.** 데스크톱 열 수 / 모바일 열 수. 원게임은 격자였다.
   **빈 칸을 어떻게 표현**하나(칸을 다 그리나, 채운 것만 그리나).
2. **임시보관을 어디에 두나.** 별도 탭 / 같은 화면 하단 / 별도 페이지.
   임시보관은 **오버플로우**라 평소엔 비어 있다 — 비었을 때 자리를 차지할 이유가 있나.
3. **아이템 클릭 시** — 라이트박스(FC-049 패턴 재사용) / 상세 페이지 이동 / 인라인 패널.
4. **`relocate` 액션의 배치** — 임시보관 아이템을 정규 슬롯으로 옮기는 흐름. 목적 슬롯을
   사용자가 고르나, 서버가 자동 배정하나(계약 확인).
5. **★ 반응형 별도 설계** — 96칸 격자는 모바일에서 **접는다고 되지 않는다.**
   데스크톱·모바일 구조를 **각각 도식으로** 제시하라.

  처음 보는 화면이므로 초라하면 안 된다.

- `npm run test`·`typecheck`·`lint`·`build` 전건 통과.
