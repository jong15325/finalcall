## 목표
FC-171·FC-172 구현 전 메모/쪽지 도메인의 계약·스키마를 확정한다. 게임 `new_sp.user_memo`를 finalcall 컨벤션으로 재구성하되 클라 고정 계약은 boundary에서 흡수.

## DoD
1. **memo-domain-spec 작성**(`docs/spec/memo-domain-spec.md`): 도메인 개요·상태 전이(미열람↔열람·soft delete)·쓰기 소유자(웹=발신, 게임=읽기/상태)·불변식·수신자 검증(nickname=게임계정, char16 vs finalcall nickname 정합).
2. **스키마 확정**(Flyway V20 설계, erd 델타): finalcall 네이티브 memo 테이블. 컬럼 정리(필요/불필요), `memo_msg` 용량 보존(char(120) 상당), sender/receiver **닉네임 스냅샷 + user FK 정규화**(닉 변경 대비), `memo_type`/`memo_state`(0미열람/1열람)/soft delete 계승.
3. **게이트2 상신 3결정**(승인 후 확정):
   - (a) **레벨·성별 소스** — `memo_level_gender = 레벨×100+성별`. finalcall `user`엔 레벨/성별 없음 → user에 추가 vs 메모 스냅샷 vs 기본값. `usershop_box` 분리저장 선례 참고.
   - (b) **바이트 포맷 저장** — 안 A(깔끔 저장+전송 시 boundary 패딩·추천) vs 안 B(사전 패딩 저장). 저장은 분해·클라 응답 재합성 원칙(survey R6).
   - (c) **신규 테이블 스키마·채번**(V20).
4. **28바이트 재현 정책 결정**(survey §5 U2): 28바이트는 클라 입력폭이지 저장폭 아님. finalcall 유저 발신 메모에 이 규칙(다필드 고정폭)을 재현할지 = **정책/제품 결정**. 자유 단일 텍스트 vs 레거시 다필드 구조폼. 불명확 시 사용자 상신.
5. **api-contract 델타**: 받은함/보낸함 목록(커서 `CursorResponse<T>`)·열람(+읽음 처리)·발신·삭제. 반환 `ApiResponse<T>`. 도메인 ErrorCode(`MEMO_xxx`, `common.exception`).
6. FC-171·FC-172 구현 지시 한 줄씩.
