## 목표
- **이 프로젝트의 시각 톤을 확정하는 티켓.** 이후 모든 화면이 여기서 파생된다.
- 산출은 React 구현이 아니라 **정적 HTML 목업** — 브라우저로 바로 열어 판단할 수 있어야 한다.

## 만들 것
`docs/ux/mockups/` 아래 자체완결 HTML(인라인 CSS 또는 `<style>`, 빌드·서버 불요):
1. **공통 셸** — 헤더(브랜드·내비·인증 상태·검색 자리)·푸터. 로그인 전/후 두 상태.
2. **홈/랜딩** — 현재 `PagePlaceholder`다. 첫인상 전체를 설계한다. 경매 서비스임이 3초 안에 읽혀야 한다.

## DoD
- **브랜드 표현**: "FinalCall"이 지금은 그냥 `text-lg font-bold`다. 워드마크·타이포 위계·시각적 무게를 만든다. 로고 이미지가 없으면 타이포그래피로 해결하라(가짜 로고 파일을 만들지 마라).
- **헤더**: 지금은 얇은 선 하나에 텍스트 링크 3개다. 정보 위계(주 내비 vs 보조 액션)·밀도·상태 표현을 설계한다.
- **푸터**: 현재 없다. 커머스 신뢰감의 상당 부분이 푸터에서 온다.
- **홈**: 히어로·진행 중 경매·마감 임박·카테고리 진입 등 **무엇을 어떤 순서로 보여줄지**가 핵심 결정이다. 근거를 주석으로 남겨라.
- **반응형**: 모바일·데스크톱 최소 2폭. 목업이므로 미디어쿼리로 충분하다.
- **다크모드는 만들지 마라** — `index.css`가 "U-005 확정 시 얹는 미래 오버레이. 지금 다크값을 지어내지 않는다"고 규정했다. 그 규율을 지킨다.

## ★ 이 티켓의 성격 — 오해 금지
**규칙 준수가 아니라 시각 디자인이다.** 기존 화면들은 토큰을 정확히 썼고 접근성도 맞았지만 **디자인이 없었다.** `design-system.md` §5는 컴포넌트 *계약*(prop·상태·a11y)이지 *비주얼*이 아니다.

여기서 만들 것은 **여백 리듬 · 시각 위계 · 밀도 · 대비 · 타이포 스케일 · 이미지 사용**이다. 토큰을 지키되, 토큰만으로는 나오지 않는 것을 만들어라.

**`impeccable` 스킬을 반드시 로드해서 쓰라.** 이 티켓이 정확히 그 스킬의 대상이다.

## 산출 형식 — **페이지 단위 분리** (사용자 지시 2026-07-18)
- **파일 1개 = 페이지 1개.** 하나의 HTML에 여러 화면을 몰아넣지 않는다. 사용자가 페이지별로 열어보고 판단한다.
- **셸(헤더·푸터)은 각 페이지 파일에 포함**한다 — 실제 서비스에서 보이는 그대로여야 판단이 된다. 셸만 떼어낸 파일을 만들지 않는다(맥락 없이 헤더만 보면 평가가 불가능하다).
- 상태 변형(로그인 전/후 등)은 **각각 별도 파일**. 한 파일 안에서 토글·나란히 배치하지 않는다.
- 파일명은 무엇을 담은 페이지인지 **이름만 보고 알 수 있게** 짓는다.
- 반환 시 **파일별로** "이 페이지에서 결정한 것"을 한두 줄씩 붙이고, 여러 페이지에 걸치는 결정(브랜드·타이포 스케일·색 운용)은 따로 묶는다.
