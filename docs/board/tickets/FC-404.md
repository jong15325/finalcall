## 목표
- 메시지 전송 성공 뒤 상대 화면이 채팅방 재선택 또는 새로고침 전까지 갱신되지 않는 현상을 프론트 상태 반영, WebSocket 연결, 백엔드 fan-out으로 분리 진단한다.

## DoD
- 프론트 `MESSAGE_CREATED` 수신 후 상태 반영 경로와 테스트를 확인한다.
- 운영 Gateway·backend 로그에서 문제 시각의 WebSocket handshake와 STOMP 연결 결과를 확인한다.
- 프론트·백엔드·배포 인프라 중 1차 원인 계층과 후속 확인 지점을 판정한다.

## 검증
- 프론트는 `ChatRealtimeProvider → useChatController` 이벤트 병합 경로와 즉시 반영 회귀 테스트가 존재한다.
- 문제 시각 운영 Gateway 로그에서 `WebSocketClientHandshakeException: Invalid handshake response getStatus: 200`이 반복됐다.
- 같은 시각 backend `/ws/chat` 접근은 HTTP 200으로 기록됐고 WebSocket 통계는 CONNECTED 0건이었다. 따라서 메시지는 REST/DB에는 저장되지만 상대 STOMP 세션으로 전달되지 않아 재조회 때만 나타나는 증상과 일치한다.
- 이후 수동 Upgrade 요청은 HTTP 101로 성공해 상시 코드 결함보다 운영 연결 경로의 간헐적 handshake 실패로 판정한다. 브라우저 Network의 `101 → CONNECTED → SUBSCRIBE`와 Gateway/backend 로그를 동일 전송 시각에 대조하는 후속 재현이 필요하다.
- 2026-08-26 재현 시 최근 outbox의 `roomPublicId=OP2ROM00000000000000000013`이 listener의 ULID 검증에서 폐기되는 직접 원인을 확정했다. 일반 런타임 생성 방이 아니라 `ops-20-v2` fixture 공개 ID의 계약 위반이며 FC-405에서 교정한다.
