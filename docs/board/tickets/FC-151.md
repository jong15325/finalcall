## 목표
로컬 실행 중이던 백엔드(`FinalcallApplication`)가 **TCP 연결을 안 닫고 누수**해 Windows 소켓 리소스를 고갈시킨 사고의 **근본원인을 규명**하고 수정안을 제시한다. (조사·진단 우선. 수정은 원인 확정 후 범위 판단.)

## 사고 증거 (2026-07-29, push 차단 사고)
- 시스템 총 TCP 연결 **45,944개 중 백엔드 java 단일 프로세스가 45,760개** 점유 — Established 30,549 + Bound 15,304.
- 결과: Windows 소켓 버퍼·임시포트·비페이지풀(9.5GB) 고갈 → 신규 소켓 생성 전면 실패(`curl: getaddrinfo() thread failed to start`, 브라우저 `ERR_NO_BUFFER_SPACE`). 인터넷·DNS는 정상이었음.
- 프로세스 kill 즉시 총 연결 **45,944 → 278**로 회복, 네트워크 정상화.
- 백엔드 프로세스 시작 시각 이후 단일 세션에서 누적 → **연결을 재사용/반납하지 않고 계속 새로 여는 누수 패턴** 강력 시사.

## 조사 지침 (DoD)
- **누수 대상 특정**: 30,549 Established 연결의 목적지를 규명. 후보 = MySQL(3306, HikariCP)·Redis(6379, Lettuce/Jedis)·Elasticsearch(9200, RestClient)·Kafka(9092)·Kafka Connect(8083). 어느 클라이언트가 커넥션 풀을 안 쓰거나 반납/close 누락인지.
- **재현·계측(신중히)**: 재기동은 같은 누수로 머신 재고갈 위험 → **반드시 연결 수를 실시간 감시하며**(`Get-NetTCPConnection | Where RemotePort -in 3306,6379,9200,9092,8083 | Group RemotePort`) **짧게** 띄우고, 급증 시 즉시 kill. 급증하는 RemotePort로 범인 클라이언트 확정. 계측 후 반드시 종료.
- **원인 가설 검증**: (a) 커넥션 풀 미사용/매 호출 새 연결, (b) 의존성 DOWN(헤드리스에서 ES/redis/mail 등) 시 **재시도·헬스체크 폭주**로 연결 누적, (c) 스케줄러/시더/리스너(예: FC-144 경매 시더, Kafka consumer)에서 연결 누수, (d) `try-with-resources`/`close()` 누락. 코드·설정(application*.yml, 풀 크기·타임아웃) 정적 리뷰 병행.
- **산출물**: 근본원인 1건 확정(RemotePort 증거 포함) + 최소 수정안 제시(풀 설정·close 누락·재시도 백오프 중 무엇). 즉시 안전 수정이 명확하면 패치 제안(커밋 금지, 사용자 승인 대기). 광범위/설계 변경이면 게이트2로 상신 권고.
- `./gradlew :backend:spotlessApply :backend:checkstyleMain` 그린(수정 시).

## 조사 1차 결과 (backend-impl, 정적 분석)
**확정 배제(확신 HIGH)**: 도메인 코드에 매 호출 new 클라이언트·`close()`/try-with-resources 누락 **없음**. 모든 원격 클라이언트(MySQL HikariCP·Redis Lettuce·Redisson·ES ElasticsearchClient)는 공유·풀링 빈이고 원시 소켓/HttpURLConnection/RestTemplate 사용 0건. **풀 상한 합계 수백 규모 → 정상 경로로 30,549 Established 생성 구조적 불가.** 배경 @Scheduled 워커(Close 2s·ShopExpiry 60s·SearchReconciliation 300s)·시더도 전부 풀 자원만 사용. 앱 build.gradle에 Kafka/Debezium 클라이언트 없음(9092/8083 직접 연결 안 함).

**남은 가설**: 런타임 저수준 커넥션 스톰. `Bound 15,304`(로컬 bind 후 connect 미완)는 **아웃바운드 스톰** 특징. 앱에서 풀 없이 아웃바운드 여는 유일 경로 = **SMTP(JavaMailSenderImpl, 풀 없음·send마다 새 연결)** — 단 `email.verify.sender-enabled=true`(FC-140 도입, 로컬 기본 false) + 사용자 트리거 필요, 코드에 루프 트리거는 없음. 대안 가설 = **인바운드 스톰(LocalPort 8080 지배 = 프론트 폴링/재연결 루프, 백엔드는 피해자)**.

**미확정(확신 LOW)**: 정적으로 RemotePort 단정 불가. 프로세스 kill로 라이브 데이터 소멸.

## 확정 진단 (다음 수 — 라이브 재현 필요)
incident와 동일 env(IntelliJ EnvFile)로 백엔드 재기동 후, 연결 급증 시 아래로 인바운드/아웃바운드·포트 확정:
```powershell
$pid=(Get-Process java|Sort-Object StartTime|Select-Object -Last 1).Id
Get-NetTCPConnection -OwningProcess $pid | Group-Object State,LocalPort,RemotePort | Sort-Object Count -Descending | Select-Object -First 15 Count,Name
```
- LocalPort=8080 지배 → 인바운드(프론트 폴링/재연결 버그 → 별도 프론트 티켓), 백엔드는 Tomcat 캡 방어선.
- RemotePort=465 지배 → SMTP 누수 확정 → mail 타임아웃(`connectiontimeout/timeout/writetimeout=5000`) 최소 패치.
- RemotePort=3306/6379/9200 → 해당 재연결/풀 백오프 조정.

수정은 RemotePort 1건 확정 후 **단일 최소 config 패치**만(게이트2 불요·설계 변경 불요). 지금은 speculative 패치 미적용(coding-discipline).

## ⚠️ SMTP 가설 철회 (2026-07-29) — 원인 미확정
SMTP를 유력 원인으로 적었으나 **철회**한다. 근거:
- 사용자 증언: incident 백엔드(pid 54948) 기동 후 **인증받기를 누른 적 없음**.
- 코드 확인: 이메일 발송은 `EmailVerificationService`(verification-request/verify = 사용자 조작)에서만 호출. **어떤 @Scheduled/@EventListener/@KafkaListener도 이메일 미발송** → 사용자 트리거 없으면 SMTP 미개방. **∴ SMTP는 원인이 아니다.**
- incident 45k의 **실제 RemotePort/방향을 캡처한 적 없음**(push 언블록 위해 프로세스를 먼저 kill → 증거 소멸). "Bound=아웃바운드=SMTP" 는 추론이었을 뿐. **Established 30,549** 우세는 SMTP(지연=미완/Bound)와 오히려 불일치.
- 라이브 재현 2·3차: 현재 백엔드(pid 36320) same-code로 25분+ total 83 고정 → 현재 조건에선 무누수.

## 남은 가설 (미확정 — 재발 캡처 필요)
30k Established(완료·유지)는 (a) **인바운드 클라이언트 스톰**(브라우저 탭이 백엔드를 폴링/재연결 — 경매 "실시간 최고가" 페이지 등, LocalPort 8080 지배로 판별) 또는 (b) **아웃바운드 재연결 스톰**(incident 때 DOWN/플래핑이던 의존성 ES/kafka-connect 등에 대한 비백오프 재접속) 중 하나로 추정. **결정적 판별 = 재발 시 `Get-NetTCPConnection | Group State,LocalPort,RemotePort` 캡처**(현재 스크래치패드 감시 스크립트 재사용). 현재는 재현 불가라 파킹.
