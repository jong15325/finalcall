# FinalCall 협업 가이드

5개 역할(총괄 / 기획·설계 / 백엔드 / 프론트엔드 / QA)이 각각 별도 대화로 진행된다.
대화 간 직접 통신은 불가능하며, 모든 전달은 사용자가 프롬프트를 복사·붙여넣기로 중계한다.
이 문서는 역할 경계, 결정 권한, 문서 규약, 전달 프로토콜을 정의한다.
모든 대화는 시작 시 이 문서를 읽는다.

---

## 1. 역할과 권한

| 역할 | 책임 | 자율 결정 범위 |
|---|---|---|
| 총괄 | 범위·우선순위 판단, 에스컬레이션 결정, 산출물 검수, 계약 충돌 감시, 역할 간 프롬프트 조율 | 프로젝트 수준 결정만. 세부 설계·구현 결정은 하지 않는다 |
| 기획/설계 | domain-spec.md, erd.md, api-contract.md 작성 | 자기 문서 안에서 닫히는 도메인 규칙·모델링 세부 |
| 백엔드 | api-contract 기준 서버 구현 | 구현 기법 선택(락 구현, 쿼리 방식 등). 단 CLAUDE.md 컨벤션과 계약 준수 |
| 프론트엔드 | api-contract 기준 클라이언트 구현 | 화면 구성, 상태 관리 등 클라이언트 내부 결정 |
| QA | 테스트 계획·시나리오 작성, 결함 리포트 | 테스트 전략·케이스 설계 |
| 보안 | 설계·계약·구현의 보안 검토(인증/인가, 입찰 부정행위, 결제·정산, 시크릿, OWASP), 위협 모델링, 취약점 리포트 | 검토 기준·체크리스트 설계 |

최종 결정권자는 항상 사용자다. 총괄 대화는 선택지·추천·이유를 정리해 사용자의 결정을 돕는다.

---

## 2. 결정 권한: 에스컬레이션 4기준

기본 원칙: 결정은 해당 역할이 스스로 내리고 자기 결정 로그에 기록한다.
아래 4기준 중 하나라도 해당하면 총괄로 에스컬레이션한다. 애매하면 올린다.

1. 범위 변경 — 기능의 추가/삭제/연기
2. 경계 침범 — 확정 문서(스펙) 또는 다른 역할의 작업에 영향을 주는 결정
3. 아키텍처·기술 선택 — 구조나 기술 스택의 방향을 정하는 결정
4. One-way door — 되돌리기 비용이 큰 결정

역기준: 자기 문서·자기 코드 안에서 닫히고 나중에 바꿔도 싼 결정(two-way door)은
에스컬레이션하지 않는다. 예: 최소 입찰 단위 방식, DTO 필드명, 화면 레이아웃, 테스트 케이스 구성.

## 3. 문서 구조와 소유권 (D-014~D-018 개정)

### 문서 유형 6종 (D-014)

| 유형 | 위치 | 변경 규칙 | 기준(authority) |
|---|---|---|---|
| 1 확정 스펙 | docs 루트 | 계약 변경 절차(6절) | 최상위 — 전 역할의 작업 근거 |
| 2 지침 | management/, CLAUDE.md, 파트 지침 | 소유 역할 + 총괄 승인 | 행동 규약 |
| 3 결정 로그 | `<role>/decision-log.md` | 항목 불변, 상태 라벨만 갱신 | ACCEPTED만 근거 가능 |
| 4 작업 노트 | `<role>/notes/` | 자유 | 근거 인용 금지(참고만) |
| 5 전달 프롬프트 | `<role>/outbox/` | 발신 후 상태 줄만 갱신 | 이력(감사 추적) |
| 6 보고·트래킹 | decision-index.md, defects.md, findings.md 등 | 소유 역할 갱신 | 현황 공유 |

### 폴더 구조 (D-015: 역할 폴더 표준 내부 구조)

```
docs/
├── domain-spec.md · erd.md · api-contract.md   # 유형 1만. 그 외 파일 금지 (D-018)
├── management/                                  # [총괄]
│   ├── collaboration-guide.md  # 이 문서 (유형 2)
│   ├── decision-log.md         # D-xxx (유형 3)
│   ├── decision-index.md       # 마스터 인덱스 (유형 6)
│   ├── prompts/                # 킥오프 프롬프트 보관 (management 전용)
│   └── notes/ · outbox/
├── design/ backend/ frontend/ qa/ security/    # [각 역할] 표준 구조:
│   ├── decision-log.md         # P/B/F/Q/S-xxx
│   ├── notes/                  # 작업 노트
│   ├── outbox/                 # 발신 프롬프트 (NNN-주제.md, D-017)
│   └── (역할 고유 산출물: test-plan.md, findings.md 등 폴더 루트)
└── consulting/                                  # [컨설턴트, 한시] 동일 구조
```

- 프론트엔드 문서도 이 저장소 docs/frontend/ 로 일원화한다(문서 허브 단일화).
  프론트 저장소에는 api-contract 복사본 + 프론트 CLAUDE.md만 둔다(D-007 유지).

### 쓰기 규칙
- 각 역할은 자기 폴더에만 쓴다.
- docs 루트의 확정 스펙은 기획만 수정한다(총괄 승인 필요, 6절 변경 절차 참조).

### 읽기 규칙 (D-016 — 구 "참조 금지" 규칙 대체)
- 기본 열람: 필독 문서(확정 스펙, 총괄 D 로그, 이 가이드, 자기 폴더)만 상시 읽는다.
  타 역할 폴더를 상시 탐색하지 않는다. 백엔드는 CLAUDE.md도 필독.
- 필요 기반 열람(pull): 현재 작업에 타 역할 문서의 맥락이 필요하면 금지 없이 열람할 수 있다.
  열람 사유가 설명 가능해야 하고, 산출물에 출처를 남긴다.
- 기준 위계: 확정 스펙 > 총괄 D 로그(ACCEPTED) > 자기 결정 로그 > 타 역할 결정 로그(맥락 참고)
  > 작업 노트(근거 인용 금지).
- 타 역할 노트에서 얻은 맥락은 산출물에 "미확정 참고"로 표기한다.
  산출물의 근거는 반드시 확정 스펙 또는 ACCEPTED 결정이어야 한다.

## 4. 결정 로그 규칙 (티켓 규약, D-009~D-011)

- 각 역할은 자기 폴더에 결정 로그를 둔다.
- ID 형식: `<PREFIX>-<3자리 일련번호>` — D 총괄 / P 기획 / B 백엔드 / F 프론트 / Q QA /
  S 보안 / C 컨설턴트(한시).
  접두어별 독립 증가, 불변, 재사용·재번호 금지.
- 1 항목 = 1 원자적 결정. (D-009부터 적용. 기존 묶음 항목은 소급 재번호하지 않는다.)
- 상태 라벨: PROPOSED / ACCEPTED / ON-HOLD / SUPERSEDED(대체 ID 명시).
- 필드: ID · 제목 · 상태 · 소유역할 · 결정 · 이유 · 기각된 대안 · 관련(참조 ID) · 날짜.
- 참조 키워드: depends-on / relates-to / supersedes / escalated-as.
- 에스컬레이션 흐름: 역할이 자기 로그에 PROPOSED로 발번 → 총괄 확정 시 D-xxx 발번 →
  원 역할은 자기 항목을 "escalated-as D-xxx (ACCEPTED)"로 갱신. 내용 중복 기록 금지.
- ID 보고 규칙: 총괄로 보내는 모든 프롬프트 끝에 "신규 발번 ID: ..." 1줄을 첨부한다.
  자율 결정도 이 줄로 보고되어 마스터 인덱스에 반영된다.
- 마스터 인덱스: management/decision-index.md — 총괄이 유지하는 전체 ID 표
  (ID·제목·상태·소유역할). 내용의 단일 진실은 각 역할 로그이고 인덱스는 목차다.

## 5. 메시지 프로토콜 (D-017, D-020~024 개정)

### 파일 버스 (D-023)
- 역할 간 모든 전달(결정 요청·회신·보고·공유)은 발신자 outbox/에 파일로 남긴다.
  주제당 1파일(`NNN-주제.md`), 삭제 금지, 머리에 상태 1줄 `상태: SENT | ANSWERED → <결정 ID>`.
- 회신도 발신이다: 수신 역할이 자기 outbox에 회신 파일을 쓰고
  `회신대상: <역할>/outbox/NNN` 을 명기한다. 발신자는 회신 파일을 발견하면
  자기 상태 줄을 ANSWERED로 갱신한다.
- 사용자 중계는 "수신함 확인해" 한 줄. 지시받은 역할은 전 역할 outbox/에서
  `[X → 자기역할]` 헤더를 스캔하고, 자기 폴더의 inbox-log.md(처리한 메시지 경로 목록)에
  없는 파일을 신규로 처리한 뒤 1줄 추가한다.
- 저장소 폴더 접근이 불가한 대화가 있으면 그 대화에 한해 프롬프트 복붙 병행(하이브리드).

### 메시지 유형 4종 (D-020)
공통 헤더 `[발신 → 수신] <유형>: 제목` + 말미 `회신: 필요(무엇을) / 불요`.

| 유형 | 필수 요소 |
|---|---|
| 결정 요청 | 배경 1~3줄, 안건별 선택지+추천+이유, 신규 발번 ID |
| 작업 지시 | 목표, 완료 기준, 의존(확정 전이면 착수 금지, D-028), 범위 제한(하지 말 것), 관련 문서 경로 |
| 완료 보고 | 산출물 경로, 완료 기준 충족 여부, 신규 발번 ID, 다음 단계 제안 |
| 정보 공유 | 요지 3줄 이내 + 상세는 경로 참조, 회신 불요 명시 |

- 계약·스펙에 영향을 주는 내용은 정보 공유 유형으로 전달 금지 — 결정 요청으로 격상.
- 회신은 "결정 + 조건" 형식.

### 왕복 최소화 (D-021)
- 같은 수신자로 가는 독립 안건은 1메시지에 번호 매겨 묶는다(부분 회신 허용).
- 왕복 1회 완결: "이 회신만 오면 진행 가능한가" 자문 후 발신. 열린 질문·후속 질문 유발 문구 금지.
- 게이트 통과 = 프로젝트 지식 일괄 동기화 앵커. 동기화된 문서는 경로 참조,
  게이트 이후 변경분만 발췌 첨부(원본 경로·기준 게이트 병기).

### ID 소유자 통지 (D-024)
- 타 역할 소유 ID·산출물을 논의·변경·재해석하면 소유 역할 앞 정보 공유 파일을 남긴다(1~3줄).
- 각 역할은 세션 재개 시 자기 접두어(P-, B- 등)를 전 역할 outbox에서 grep하여
  inbox-log에 없는 언급을 점검한다.

## 6. 계약 변경 절차 (api-contract 확정 후)

api-contract.md는 백/프론트/QA가 병렬로 의존하는 단일 진실이다.
확정 후 변경은 반드시 다음 절차를 따른다.

1. 변경 필요를 발견한 역할이 변경 요청 프롬프트 작성 → 총괄
2. 총괄이 영향 범위 판단 후 승인/기각
3. 승인 시 기획이 api-contract.md 수정 + 문서 내 변경 이력(버전, 날짜, 내용, 사유) 기록
4. 총괄이 영향받는 모든 역할에 전파 프롬프트 생성

기획을 포함해 누구도 확정된 계약을 총괄 승인 없이 수정하지 않는다.

## 7. 단계 게이트와 리추얼 (D-019, D-022 개정)

### 게이트 (D-019)
진행은 게이트로 통제한다. 통과 기준(exit criteria)을 충족해야 다음 단계로 넘어가며,
통과는 총괄이 decision-index.md 게이트 표에 1줄 기록한다(D 발번 없음).

| 게이트 | 통과 기준 | 통과 시 후속 |
|---|---|---|
| G1 domain-spec 확정 | 기획 초안 + 총괄 검수 + 사용자 승인. 미해결 ON-HOLD는 인덱스 등재 | ERD 착수 |
| G2 erd 확정 | G1 기준 + domain-spec 정합 확인 | api-contract 착수 |
| G3 api-contract 확정 | 총괄 검수 + 보안 게이트 1(D-013) + 사용자 승인 | 백/프론트/QA/보안 동시 기동, 프론트 repo 복사본 생성 |
| G4-n 도메인 n 구현 | 구현 DoD(계약 준수+CLAUDE.md 컨벤션+테스트 통과) + QA 시나리오 실행 + defects 처리. 도메인 전체 완료 시 보안 게이트 2 | 다음 도메인 착수 |

- 보안: G3 직전 계약 보안 검토, G4 완료 후 구현 리뷰. 결과는 findings.md,
  계약 영향 시 6절 변경 절차.
- 결함 수정 전달은 5절 프로토콜, 계약 문제면 6절 변경 절차.

### 이벤트 기반 리추얼 3종 (D-022)
시간 기반 리추얼(데일리 등)은 두지 않는다.

1. 게이트 통과 → 총괄이 전 역할 전파 1메시지(변경점 + 역할별 할 일 + 지식 동기화 파일 목록)
2. 역할 작업 블록 종료 → 해당 역할이 총괄에 완료 보고
3. 사용자 세션 재개 → 총괄이 현황 브리핑(인덱스·보류 안건·SENT 대기 목록 기반, 신규 문서 없음)

### 병렬 구간 규칙 (D-028)
게이트 사이 병렬 작업의 완료 시점 비대칭에 적용한다.

- 착수 조건: 작업 지시의 "의존:" 대상이 확정(ACCEPTED 또는 게이트 통과) 전이면
  착수하지 않는다. 총괄이 추적 표에 블로커로 등재.
- 선완료 행동 우선순위: (a) 완료 보고에 "대기 중: <무엇>" 명시 → (b) 의존 없는 작업
  pull → (c) 가정 선언 진행 — 가정을 정보 공유로 발신하고 산출물 머리에 표기,
  가정이 깨지면 재작업은 진행한 쪽 부담(상대 전가 금지).
- 어긋남 해소: 기준 위계(3절)로 판정한다. 확정 스펙과 다른 쪽이 수정, 스펙 자체가
  문제면 6절 절차, 스펙 공백이면 결정 요청으로 격상. 먼저 구현한 쪽이 기준이 되지
  않는다(선착순 기준 금지).

## 8. 도구 구성 (D-007)

- 클로드 프로젝트 대화 5개(총괄/기획/백엔드/프론트/QA) + 보안·컨설턴트(한시) +
  Claude Code 2개(백엔드/프론트 코딩용).
- 대화 vs Claude Code 분업: 백엔드/프론트 대화는 구현 계획 수립, 작업 단위 분해,
  Claude Code 작업 프롬프트 생성, 설계 수준 리뷰를 맡는다.
