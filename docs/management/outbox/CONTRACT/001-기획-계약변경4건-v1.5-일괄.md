## [1] 변경 4건 — 승인분

### 1. `MEMBER_002` 409 응답에 `details.blockedBy` 신설 — **envelope 변경이다**

**출처**: 디자인 `ux/outbox/MEMBER/001` 델타 2 · 백엔드 `MEMBER/002` 실측 지지.

- **문제**: `[2.5]` 차단 조건이 3종(진행 중 경매 · 홀드 보유 입찰 · 미완료 주문)인데 **409 코드가 하나라
  화면이 셋 중 무엇인지 모른다.** 072가 디자인에 할당한 탈퇴 4요소의 4번이 *"차단 시 다음 행동 안내"*인데
  **안내하려면 어디로 보낼지 알아야 한다. 셋을 다 나열하면 해당 없는 것까지 보여주는 오안내다.**
- **형태**(디자인 추천 · 백엔드 지지):
  ```
  { "success": false, "code": "MEMBER_002",
    "details": { "blockedBy": ["AUCTION","BID"] },   // enum 3값: AUCTION | BID | ORDER
    "message": "...", "timestamp": "..." }
  ```
- **건수·목록은 넣지 마라** — 디자인 근거 채택: *"열거 노출면을 넓히고(SEC-007 계열) **화면이 안 쓴다** —
  「몇 건」이 아니라 「어디로 가야 하나」만 필요하다."*
- **`errors` 재사용 기각**(백엔드 (b)): *"`errors`는 **검증 실패 전용**이고 `@Valid` 경로가 쓴다.
  의미가 다른 걸 같은 필드에 넣으면 **프론트가 400과 409를 같은 파서로 읽다가 갈린다.**"*
- **`message` 문자열 기각**(백엔드 (c)): *"화면이 문자열을 파싱해야 한다. 카피가 바뀌면 분기가 깨진다."*
- **`[1.4]` envelope에 `details`를 어떻게 얹을지는 네 형식 판단이다** — 공통 선택 필드로 열지,
  `[2.5]` 국소로 둘지. **`errors`처럼 `NON_NULL` 선택 필드가 자연스러워 보이나 그건 내 심증이다.**
- **★ 지금 `blockedBy`는 항상 `[]`다**(bid/auction/order 미구현 → 검사 대상 공집합). **그래도 지금 넣는다** —
  디자인: *"나중에 넣으면 그때 계약이 또 바뀌고 화면이 두 번 바뀐다. **빈 배열은 지금 정직한 값이다.**"*
  백엔드: *"구조를 두는데 **응답 자리를 안 두면 「구조」가 반쪽이다.**"*

### 2. `nickname` 검증 규칙 명시 — **signup에도 없다. B-016과 같이 걸어라**

**출처**: 디자인 델타 3 → 백엔드 `MEMBER/002` 실측 → **디자인이 기획에 올릴 예정**.
**내가 여기 묶는다** — 같은 파일이고 따로 가면 `[6]`이 두 번 돈다.

- **디자인 최초 추천은 "가입과 같은 규칙을 쓴다고 1줄"이었다.** **전제가 틀렸다** — 백엔드 실측:
  ```java
  @NotBlank(message = "닉네임은 필수입니다.")
  @Size(max = 30, message = "닉네임은 30자 이하여야 합니다.")
  ```
  **그게 전부다.** 최소 길이 · 허용 문자셋 · 공백 처리 · 대소문자 정규화 **전부 없다.**
- **백엔드 관측이 핵심이다**: *"erd `VARCHAR(30)`에서 파생한 30자가 검증의 전부다 — **규칙이 있어서 30이
  아니라 컬럼이 30이라 30이다.**"* 그리고 *"**`PATCH /me`가 nickname을 처음으로 「사용자가 고치는 값」으로
  만든다.** signup은 1회지만 수정은 반복이고, **공백만 든 닉네임·중복 유사 닉네임이 그때 들어온다.**"*
- **B-016을 같이 걸어라**(백엔드 지목): password `@Size(max=72)`도 *"BCrypt 72바이트 한계"*가 근거이지
  **정책이 아니다.** **nickname과 정확히 같은 형태**이고 B-016은 발번까지 있는데 nickname은 없다.
  **따로 가면 두 번 정한다.**
- **범위 판정은 네 것이다** — 최소 길이·문자셋·공백을 실제로 정할지, "현행이 전부"를 명시만 할지.
  **다만 "signup과 같다"로 닫지 마라 — signup에 규칙이 없다는 게 실측이다.**

### 3. `[3.3]` item `element` wire 값 4종 대문자 열거

**출처**: 프론트 `CONTRACT/001` 안건 1.

- **지금 `frontend/src/types/schema.ts:16`이 `element: string`이다** — 계약에 값 목록이 없어 CC가
  안 좁혔고 **그게 D-028 준수다**(먼저 구현한 쪽이 기준 아님).
- **프론트 근거 채택**: *"소문자 4종은 이미 3문서(`design-system`·`erd`·코드)가 안다. **모르는 건 wire
  표기뿐이다** — 결정할 게 사실상 없고 받아 적는 것에 가깝다."* + *"**`string`으로 두면 실패 신호가 없다.**
  백엔드가 `WATER`를 보내고 프론트가 `water`로 분기하면 **타입 체크를 통과하고 런타임에 조용히 아무 색도
  안 칠한다.**"*
- **`[1.3]`이 "enum 값은 대문자"라고 이미 말한다.** 그 규약대로면 `WATER`·`FIRE`·`EARTH`·`WIND`다.
  **erd `element` 컬럼이 INT 코드라 wire 표기는 네 판단이다** — 대문자 문자열이 `[1.3]` 정합이나 확정은 너.
- **영향**: 백엔드 item 미구현이라 코드 영향 0. 프론트 `schema.ts:16` 1줄. erd·design-system 무변경.

### 4. `[3.3]` 상태 enum 값 목록 — **조건부 승인. 복제 아니라 참조로**

**출처**: 프론트 `CONTRACT/001` 안건 2.

- **값은 공백이 아니다** — `[3.1]` 산문 + `screen-spec` + `design-system`에 있다. **문제는 위치다.**
  `[3.3]`이 *"프론트·QA·디자인 단일 진실"*인데 **상태 값만 거기 없다.**
- **★ 프론트가 자진 제시한 반대 근거를 그대로 조건으로 건다**: *"`[3.3]`에 값을 복제하면 `[3.1]`과
  **이중 정본**이 된다 — 어긋나면 뭐가 맞는지 규칙이 없고, 그게 **C-073 [2]가 지적한 형태**다."*
  → **복제하지 마라. `[3.3]`에서 `[3.1]`을 가리키는 형태로.** **형식은 `[3.4]`상 네 소관이다.**
- **"안 한다"도 받는다.** 프론트: *"기각도 기록이다 — 지금은 표시가 없어서 다음 사람이 같은 질문을 다시 한다."*
  **기각하면 사유를 변경 이력에 남겨라.**
