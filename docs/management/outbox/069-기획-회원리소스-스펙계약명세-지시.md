# [총괄 → 기획] 작업 지시: 회원 리소스 공백 보완 — domain-spec + api-contract 명세 (6절 3단계)

## 배경
백엔드가 member 도메인 착수 중 계약 공백을 발견해 6절로 올렸다(backend/outbox/022). 총괄 검증·승인 완료(회신 068). 이 지시가 6절 3단계(기획 명세)다.

확인된 공백:
- `api-contract.md:96` §2 말미 "user 리소스 엔드포인트는 3절(후속)에서 기술" → §3은 경매·고정가·입찰. **전방 참조 미이행**.
- 프로필 조회·수정·탈퇴 계약 부재. `MEMBER_` 에러코드 0건. (잔액은 §4.4 `/me/balance`로 충족됨)
- **domain-spec에도 프로필·탈퇴·닉네임 0건**(§12 범위 밖에도 미등재) — 스펙 단계부터의 공백.
- 반면 erd `user`는 nickname UK·is_deleted·deleted_at 모델링 + V3 구현 완료 → **erd·구현은 탈퇴 전제, 스펙·계약은 침묵**하는 어긋남. 이번에 해소한다.

## 확정 범위 (총괄+사용자 결정 — 재논의 불요)
회원 리소스 = **조회 + 수정(nickname 한정) + 탈퇴**.
- 총괄 지정: **비밀번호 변경 제외**(auth·보안 성격, B-016과 함께 별도 안건·추적표 등재).
- 위 범위 자체는 확정이다. 기획은 범위를 넓히거나 줄이지 말고 **명세만** 작성한다.

## 완료 기준

### 1. domain-spec (§6 사용자와 거래 범위에 회원 계정 관리 소절 추가)
계약이 아니라 **도메인 규칙**이 필요한 항목이다. 아래를 규정하라:
- 닉네임 변경 정책: 허용 여부·빈도 제한·UK 충돌 처리 원칙(표시명이 거래 이력에 남는 점 고려).
- **탈퇴 정책 — 이번 작업의 핵심**:
  - 진행 중 경매(판매자)·입찰(홀드 보유)·미완료 주문이 있을 때 탈퇴 가능한가. 불가면 차단 조건, 가능이면 각 리소스 처리 규칙(D-052 홀드 해제 규칙과 정합).
  - 탈퇴 회원의 과거 거래 이력·닉네임 표시(마스킹 여부).
  - 재가입 시 login_id·nickname 재사용 가능 여부(UK 충돌).
- 버전 v0.5 + 변경 이력.

**격상 조건**: 탈퇴 시 잔액(캐시·게임머니) 잔존분 처리는 **결정 요청으로 격상하라**. 환불·역방향 환전은 범위 밖(§12)인데 잔액이 남은 채 탈퇴하면 돈이 소멸한다 — 돈 문제라 기획 자율 결정 대상이 아니다. 선택지·추천·이유를 정리해 총괄로 올려라(사용자 결정).

### 2. api-contract (회원 리소스 절 신설, v1.4)
- 절 위치는 기획 판단(§2.5 신설 vs §4.x 편입). 단 **`api-contract.md:96` 전방 참조 문구를 실제 절 번호로 정정**할 것(현재 "3절" 오기).
- `GET /api/v1/me` — 응답 필드 노출 범위 확정(publicId·nickname·createdAt·isAdmin 노출 여부 판단). 타인 프로필 조회(`/users/{publicId}`) 필요 여부도 판단해 명세하거나 명시적 범위 밖 처리.
- `PATCH /api/v1/me` — nickname 한정. 중복 409 코드.
- `DELETE /api/v1/me` — 204 예상. refresh 세션 폐기 동반 여부 명시(B-018 연계 — 보안게이트2 이월분과 모순 없게).
- `MEMBER_NNN` 에러코드 §5 표 등재.
- 버전 v1.4 + 변경 이력(사유: 6절, 022 발견, 068 승인).

### 3. 화면 정합 (D-079로 기획이 화면 기획 겸임)
- screen-spec 마이페이지 계열이 위 계약과 정합하는지 확인. 어긋나면 정정하고 완료 보고에 명시.

## 의존
- 확정 스펙 domain-spec v0.4 · erd v0.5(user 테이블 §4.1) · api-contract v1.3. 모두 확정 — **착수 가능**.
- erd는 이미 필드를 갖고 있어 **erd 변경은 원칙적으로 불요**. 필요하다고 판단되면 사유와 함께 보고하라.
