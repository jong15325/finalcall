# FinalCall 총괄 결정 로그

총괄(PM/아키텍트) 대화에서 내린 프로젝트 수준 결정을 기록한다.
도메인 세부 결정은 docs/design/decision-log.md 에, 확정 스펙은 docs/domain-spec.md · docs/erd.md · docs/api-contract.md 에 남긴다.
전체 ID 현황은 docs/management/decision-index.md 참조.
모든 대화(기획/백엔드/프론트)는 이 문서를 공유 기준으로 삼는다.

---

## D-001. 설계 문서 확정 순서 (2026-07-12, 확정)

### 결정
domain-spec.md → erd.md → api-contract.md 순서로만 확정한다.
앞 문서가 확정되기 전에 뒤 문서를 작성하지 않는다.

### 이유
ERD는 도메인 개념·상태 전이의 산출물이고, API 계약은 그 둘의 산출물이다.
순서를 어기면 계약서가 흔들려 병렬 진행 중인 백엔드/프론트가 재작업하게 된다.

---

## D-002. 도메인 설계를 인증(로그인) 설계보다 우선 (2026-07-12, 확정)

### 결정
경매 도메인 설계를 먼저 진행한다. 인증은 다음 두 지점에서 처리한다.
- 사용자 모델: domain-spec 논의 주제 6(사용자와 거래 범위)에서 도메인이 요구하는 만큼 정의
- auth API(회원가입/로그인/토큰 재발급): api-contract.md 작성 시 맨 앞 섹션으로 우선 확정하여 프론트에 먼저 전달

### 이유
- 의존 방향: 사용자 속성, 역할 구분, 인증 필수 API 목록은 전부 도메인 설계의 출력물이다. 역방향 의존은 "사용자가 식별 가능하다" 정도이며 JWT 스켈레톤이 이미 보장한다.
- 리스크: 로그인은 정형화된 문제라 언제 설계해도 결과가 비슷하지만, 판매 방식·상태 전이·동시성은 결정에 따라 테이블과 API가 통째로 달라지는 고위험 구간이다. 불확실성이 큰 쪽을 먼저 푼다.

### 기각된 대안
- 로그인 우선 설계: 도메인 요구를 모른 채 추측으로 결정하게 되어 재작업 위험. 소셜 로그인 등 과잉 설계 유인.

## D-004. 입찰 규칙 4건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 2)에 대한 총괄 결정. 4건 모두 기획 추천안 채택.

### 결정
1. 최소 입찰 단위: 계단식 테이블(가격 구간별 증분). 검증식 `신규입찰 >= 최고가 + 구간증분`.
   시작은 설정(코드/구성) 기반으로 하고, 운영 중 조정 요구가 실제로 생기면 DB 정책 테이블로 승격.
2. 판매자 자기 경매 입찰 금지, 최고가 보유자의 연속 입찰 금지. proxy(자동)입찰은 이번 범위 밖.
3. 소프트 클로즈 도입: 트리거윈도우 내 입찰 시 마감 연장(기본 T-30초 / +30초), 경매별 설정형.
   총연장상한은 필수 — 상한 없는 연장은 금지.
4. buyNow 상호작용: (b) 최고가 < buyNow인 동안 buyNow 유지. 입찰 상한을 buyNow 미만으로
   제약하여 즉시구매가 항상 유효하도록 한다.

### 이유·조건
- 1: 게임 아이템 가격대가 넓어 단일 증분 부적합. 단, 처음부터 DB 테이블화는 과잉 — 설정으로 시작.
- 3: 마감 시각이 동적이 되어 마감 처리(주제 7)가 "재예약 가능한 지연 처리" 구조여야 한다는
  제약이 생김. 프로젝트 핵심 도전(마감 직전 폭주)과 부합하므로 수용.
- 4: (a)는 buyNowPrice를 경매 속성으로 흡수한 D(주제 1) 결정의 의미를 약화시킴.
  buyNow 근접 구간에서의 입찰 vs 즉시구매 경합은 주제 4(동시성)에서 필수로 다룰 것.

## D-005. 경매 생명주기·상태 전이 5건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 3)에 대한 총괄 결정. 5건 모두 기획 추천안 채택 + 조건 3개.

### 결정
1. (3-1) 예약 시작 지원: Auction에 SCHEDULED 상태 도입. 소프트 클로즈용 지연 인프라에
   얹으므로 한계비용 작음. FixedSale은 SCHEDULED 없음(비대칭 허용, 필요 시 확장).
2. (3-2) 종료 상태: status(SOLD/UNSOLD/CANCELLED) + resultType(BID/BUYNOW) 분리. enum 폭발 방지.
3. (3-3) 취소: 판매자 취소는 "입찰 0건 & 진행 중"일 때만. 입찰 존재 시 불가.
   관리자 강제 취소는 상태 무관 별도 권한.
4. (3-4) 경매 FSM은 SOLD(판매 성립)까지. 결제/정산/배송은 별도 Order 애그리거트로
   핸드오프(SOLD 시 Order 생성). 상세 범위는 주제 6에서 확정.
5. (3-5) FixedSale 기한: 선택적 endAt(있으면 만료 시 EXPIRED, 없으면 무기한).

### 조건 (기획 대화에 부과)
- 취소 vs 첫 입찰 경합(취소 순간 입찰 유입)을 주제 4 동시성 필수 케이스에 추가.
- FixedSale의 SOLD도 동일한 Order 핸드오프로 통일(구매 경로 단일화).
- SOLD 확정과 Order 생성의 원자성(단일 트랜잭션 vs 이벤트 분리)은 주제 4 또는 6에서 명시 결정.

### 범위 절단
- 유찰(UNSOLD) 후 재등록은 별도 플로우 없음 — 신규 등록으로 처리.

## D-006. 협업 체계: 5역할 구성과 결정 위임 (2026-07-12, 확정)

### 결정
- 역할 5개: 총괄 / 기획·설계 / 백엔드 / 프론트엔드 / QA. 상세는 collaboration-guide.md.
- 결정 위임: 에스컬레이션 4기준(범위 변경 / 경계 침범 / 아키텍처·기술 선택 / one-way door)에
  해당하는 것만 총괄로. 나머지는 각 역할 자율 결정 + 자기 결정 로그 기록.
- 계약 변경: api-contract 확정 후 변경은 총괄 경유 필수 (요청 → 총괄 승인 → 기획 수정 → 전파).
- 문서 소유권: 역할별 폴더 분리(design/backend/frontend/qa), 확정 스펙은 docs 루트,
  다른 역할의 작업 폴더 참조 금지. (읽기 규칙은 D-016으로 대체됨)

### 이유
- 전건 승인 방식은 총괄이 병목이 되고 각 역할이 결정권 없는 작성자로 전락.
  위임 기준을 "되돌리기 비용 + 경계 침범"으로 정의하면 통제와 속도를 양립.
- 계약 변경만은 중앙 통제: 병렬 진행 중 한쪽만 아는 계약 변경이 가장 비싼 사고이기 때문.

### 기각된 대안
- 전건 총괄 승인(현행): 병목·피로 누적.
- 계약 변경의 기획 직접 처리: 빠르지만 백/프론트 간 비대칭 정보 위험.

## D-007. 도구 구성과 프론트엔드 저장소 (2026-07-12, 확정)

### 결정
- 도구 구성: 클로드 프로젝트 대화 5개(총괄/기획/백엔드/프론트/QA) + Claude Code 2개(백엔드/프론트 코딩용).
- 대화 vs Claude Code 분업: 대화는 구현 계획·작업 단위 분해·Claude Code 작업 프롬프트 생성·
  설계 수준 리뷰. Claude Code는 그 프롬프트를 받아 실제 코딩만 수행.
- 프론트엔드는 별도 저장소로 분리, 추후 프론트 스켈레톤을 독립 구성.
- api-contract.md 원본은 백엔드 저장소(finalcall)의 docs/. 프론트 저장소에는 복사본을 두고
  문서 헤더에 원본 경로와 버전을 표기. 계약 변경 전파 시(가이드 6절) 총괄이
  "프론트 저장소 복사본 갱신"을 전파 체크리스트에 포함한다.
- 문서 단일 진실은 저장소. 클로드 프로젝트 지식은 스냅샷 업로드(어긋나면 저장소가 우선).

### 이유
- 대화/Claude Code 분업: Claude Code 세션은 컨텍스트가 소진되지만 계획·이력은 대화에 남는다.
  경계 없이 두면 같은 일을 두 군데서 중복 수행.
- 별도 저장소: 이미 구축된 백엔드 스켈레톤(디렉토리 구조·CLAUDE.md·CI 경로)을 건드리지 않고
  프론트 스켈레톤을 독립 구성 가능. 계약서 동기화 비용은 복사본+버전 표기 규칙으로 수용.

### 기각된 대안
- 모노레포: 계약서 동기화 문제는 없으나 백엔드 스켈레톤 구조 재조정 필요, 스켈레톤 재사용성 저하.

## D-008. 동시성 정책 4건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 4)에 대한 총괄 결정. 4건 모두 기획 추천안 채택 + 조건 2개.
정책 수준 결정이며, 구현 기법(락 종류·Redis 완충 등)은 백엔드 자율.

### 결정
1. (4-A) 정합성 최종 보증은 DB(조건부 원자 갱신 + 유니크 제약). 분산락(Redisson)은
   처리량 최적화 수단이지 정확성 보장 수단이 아니다. 원칙: "정합성은 DB, 처리량은 락".
2. (4-B) 종료성 전이(SOLD/CANCELLED)는 조건부 CAS UPDATE(WHERE status='ACTIVE',
   affected=0이면 이미 종료). 즉시구매·마감낙찰·취소가 단일 승자 패턴 공유.
3. (4-C) SOLD 확정-Order 생성은 기본 단일 트랜잭션. 결제/외부연동이 범위에 들어오면
   outbox 이벤트 분리로 승격.
4. (4-D) 입찰 유효성 검증·최고가 갱신은 경매 단위 직렬화 + DB 최종 정합성.

### 조건
- 4-D: 소프트 클로즈 마감 연장 판단을 입찰 수용과 동일 직렬화 단위에 포함할 것.
  분리 시 "입찰 성공했으나 연장 누락" 틈 발생.
- 4-C: 최종 방식(단일 TX 유지 vs outbox 승격)은 주제 6 종료 직후 재확정 안건으로 자동 회부.

### 기각된 대안
- 4-A (a) 분산락이 정합성 보증: Redis 장애·락 리스 만료·클럭 스큐 시 중복 판매.
  one-way door 리스크라 기각.
- 4-C 즉시 outbox 확정: 결제 범위(주제 6) 미정 상태의 선행 투자.

## D-009. 결정 로그 세분화: 1 항목 = 1 원자적 결정 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: 기획 에스컬레이션(escalated-as 본 항목), relates-to D-006
- 결정: 결정 로그 1 항목 = 1 원자적 결정. D-009부터 적용, 기존 묶음 항목(D-001~008)은
  소급 재번호하지 않는다. ID는 접두어별 독립 증가·불변·재사용 금지.
- 이유: 묶음 번호는 "D-004 조건 2" 같은 애매한 참조를 유발. 참조 정밀도 실익이 관리 비용보다 큼.
- 기각: 주제/에스컬레이션 단위 번호 유지 — 크로스롤 참조가 늘어날수록 정밀도 손실 누적.

## D-010. 결정 로그 상태 라벨 도입 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: relates-to D-009
- 결정: 상태 라벨 4종 도입 — PROPOSED / ACCEPTED / ON-HOLD / SUPERSEDED(대체 ID 명시).
  참조 키워드 depends-on / relates-to / supersedes / escalated-as 함께 도입.
- 이유: 4-C(D-008)처럼 뒤집힐 수 있는 결정의 상태 추적 필요가 이미 실재.
- 기각: 미도입 — 보류·대체 이력이 본문 산문에 묻혀 추적 불가.

## D-011. 마스터 인덱스 유지 + ID 보고 규칙 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: relates-to D-009, D-010
- 결정: 총괄이 management/decision-index.md 에 전체 ID 표(ID·제목·상태·소유역할)를 유지한다.
  각 역할은 총괄로 보내는 모든 프롬프트 끝에 "신규 발번 ID" 1줄을 첨부한다.
- 이유: 자율 결정은 총괄을 거치지 않아 인덱스가 불완전해지는 구멍이 있음.
  모든 프롬프트가 총괄을 경유하는 구조를 이용해 보고 규칙으로 봉합.
  내용의 단일 진실은 각 역할 로그, 인덱스는 목차 — 이중 관리 아님.
- 기각: 인덱스 미유지 — 5개 로그 분산 시 크로스롤 현황 파악 불가.
