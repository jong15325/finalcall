# FinalCall 총괄 결정 로그

총괄(PM/아키텍트) 대화에서 내린 프로젝트 수준 결정을 기록한다.
도메인 세부 결정은 docs/design/decision-log.md 에, 확정 스펙은 docs/domain-spec.md · docs/erd.md · docs/api-contract.md 에 남긴다.
전체 ID 현황은 docs/management/decision-index.md 참조.
모든 대화(기획/백엔드/프론트)는 이 문서를 공유 기준으로 삼는다.

---

## D-001. 설계 문서 확정 순서 (2026-07-12, 확정)

### 결정
domain-spec.md → erd.md → api-contract.md 순서로만 확정한다.
앞 문서가 확정되기 전에 뒤 문서를 작성하지 않는다.

### 이유
ERD는 도메인 개념·상태 전이의 산출물이고, API 계약은 그 둘의 산출물이다.
순서를 어기면 계약서가 흔들려 병렬 진행 중인 백엔드/프론트가 재작업하게 된다.

---

## D-002. 도메인 설계를 인증(로그인) 설계보다 우선 (2026-07-12, 확정)

### 결정
경매 도메인 설계를 먼저 진행한다. 인증은 다음 두 지점에서 처리한다.
- 사용자 모델: domain-spec 논의 주제 6(사용자와 거래 범위)에서 도메인이 요구하는 만큼 정의
- auth API(회원가입/로그인/토큰 재발급): api-contract.md 작성 시 맨 앞 섹션으로 우선 확정하여 프론트에 먼저 전달

### 이유
- 의존 방향: 사용자 속성, 역할 구분, 인증 필수 API 목록은 전부 도메인 설계의 출력물이다. 역방향 의존은 "사용자가 식별 가능하다" 정도이며 JWT 스켈레톤이 이미 보장한다.
- 리스크: 로그인은 정형화된 문제라 언제 설계해도 결과가 비슷하지만, 판매 방식·상태 전이·동시성은 결정에 따라 테이블과 API가 통째로 달라지는 고위험 구간이다. 불확실성이 큰 쪽을 먼저 푼다.

### 기각된 대안
- 로그인 우선 설계: 도메인 요구를 모른 채 추측으로 결정하게 되어 재작업 위험. 소셜 로그인 등 과잉 설계 유인.

## D-004. 입찰 규칙 4건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 2)에 대한 총괄 결정. 4건 모두 기획 추천안 채택.

### 결정
1. 최소 입찰 단위: 계단식 테이블(가격 구간별 증분). 검증식 `신규입찰 >= 최고가 + 구간증분`.
   시작은 설정(코드/구성) 기반으로 하고, 운영 중 조정 요구가 실제로 생기면 DB 정책 테이블로 승격.
2. 판매자 자기 경매 입찰 금지, 최고가 보유자의 연속 입찰 금지. proxy(자동)입찰은 이번 범위 밖.
3. 소프트 클로즈 도입: 트리거윈도우 내 입찰 시 마감 연장(기본 T-30초 / +30초), 경매별 설정형.
   총연장상한은 필수 — 상한 없는 연장은 금지.
4. buyNow 상호작용: (b) 최고가 < buyNow인 동안 buyNow 유지. 입찰 상한을 buyNow 미만으로
   제약하여 즉시구매가 항상 유효하도록 한다.

### 이유·조건
- 1: 게임 아이템 가격대가 넓어 단일 증분 부적합. 단, 처음부터 DB 테이블화는 과잉 — 설정으로 시작.
- 3: 마감 시각이 동적이 되어 마감 처리(주제 7)가 "재예약 가능한 지연 처리" 구조여야 한다는
  제약이 생김. 프로젝트 핵심 도전(마감 직전 폭주)과 부합하므로 수용.
- 4: (a)는 buyNowPrice를 경매 속성으로 흡수한 D(주제 1) 결정의 의미를 약화시킴.
  buyNow 근접 구간에서의 입찰 vs 즉시구매 경합은 주제 4(동시성)에서 필수로 다룰 것.

## D-005. 경매 생명주기·상태 전이 5건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 3)에 대한 총괄 결정. 5건 모두 기획 추천안 채택 + 조건 3개.

### 결정
1. (3-1) 예약 시작 지원: Auction에 SCHEDULED 상태 도입. 소프트 클로즈용 지연 인프라에
   얹으므로 한계비용 작음. FixedSale은 SCHEDULED 없음(비대칭 허용, 필요 시 확장).
2. (3-2) 종료 상태: status(SOLD/UNSOLD/CANCELLED) + resultType(BID/BUYNOW) 분리. enum 폭발 방지.
3. (3-3) 취소: 판매자 취소는 "입찰 0건 & 진행 중"일 때만. 입찰 존재 시 불가.
   관리자 강제 취소는 상태 무관 별도 권한.
4. (3-4) 경매 FSM은 SOLD(판매 성립)까지. 결제/정산/배송은 별도 Order 애그리거트로
   핸드오프(SOLD 시 Order 생성). 상세 범위는 주제 6에서 확정.
5. (3-5) FixedSale 기한: 선택적 endAt(있으면 만료 시 EXPIRED, 없으면 무기한).

### 조건 (기획 대화에 부과)
- 취소 vs 첫 입찰 경합(취소 순간 입찰 유입)을 주제 4 동시성 필수 케이스에 추가.
- FixedSale의 SOLD도 동일한 Order 핸드오프로 통일(구매 경로 단일화).
- SOLD 확정과 Order 생성의 원자성(단일 트랜잭션 vs 이벤트 분리)은 주제 4 또는 6에서 명시 결정.

### 범위 절단
- 유찰(UNSOLD) 후 재등록은 별도 플로우 없음 — 신규 등록으로 처리.

## D-006. 협업 체계: 5역할 구성과 결정 위임 (2026-07-12, 확정)

### 결정
- 역할 5개: 총괄 / 기획·설계 / 백엔드 / 프론트엔드 / QA. 상세는 collaboration-guide.md.
- 결정 위임: 에스컬레이션 4기준(범위 변경 / 경계 침범 / 아키텍처·기술 선택 / one-way door)에
  해당하는 것만 총괄로. 나머지는 각 역할 자율 결정 + 자기 결정 로그 기록.
- 계약 변경: api-contract 확정 후 변경은 총괄 경유 필수 (요청 → 총괄 승인 → 기획 수정 → 전파).
- 문서 소유권: 역할별 폴더 분리(design/backend/frontend/qa), 확정 스펙은 docs 루트,
  다른 역할의 작업 폴더 참조 금지. (읽기 규칙은 D-016으로 대체됨)

### 이유
- 전건 승인 방식은 총괄이 병목이 되고 각 역할이 결정권 없는 작성자로 전락.
  위임 기준을 "되돌리기 비용 + 경계 침범"으로 정의하면 통제와 속도를 양립.
- 계약 변경만은 중앙 통제: 병렬 진행 중 한쪽만 아는 계약 변경이 가장 비싼 사고이기 때문.

### 기각된 대안
- 전건 총괄 승인(현행): 병목·피로 누적.
- 계약 변경의 기획 직접 처리: 빠르지만 백/프론트 간 비대칭 정보 위험.

## D-007. 도구 구성과 프론트엔드 저장소 (2026-07-12, 확정)

### 결정
- 도구 구성: 클로드 프로젝트 대화 5개(총괄/기획/백엔드/프론트/QA) + Claude Code 2개(백엔드/프론트 코딩용).
- 대화 vs Claude Code 분업: 대화는 구현 계획·작업 단위 분해·Claude Code 작업 프롬프트 생성·
  설계 수준 리뷰. Claude Code는 그 프롬프트를 받아 실제 코딩만 수행.
- 프론트엔드는 별도 저장소로 분리, 추후 프론트 스켈레톤을 독립 구성.
- api-contract.md 원본은 백엔드 저장소(finalcall)의 docs/. 프론트 저장소에는 복사본을 두고
  문서 헤더에 원본 경로와 버전을 표기. 계약 변경 전파 시(가이드 6절) 총괄이
  "프론트 저장소 복사본 갱신"을 전파 체크리스트에 포함한다.
- 문서 단일 진실은 저장소. 클로드 프로젝트 지식은 스냅샷 업로드(어긋나면 저장소가 우선).

### 이유
- 대화/Claude Code 분업: Claude Code 세션은 컨텍스트가 소진되지만 계획·이력은 대화에 남는다.
  경계 없이 두면 같은 일을 두 군데서 중복 수행.
- 별도 저장소: 이미 구축된 백엔드 스켈레톤(디렉토리 구조·CLAUDE.md·CI 경로)을 건드리지 않고
  프론트 스켈레톤을 독립 구성 가능. 계약서 동기화 비용은 복사본+버전 표기 규칙으로 수용.

### 기각된 대안
- 모노레포: 계약서 동기화 문제는 없으나 백엔드 스켈레톤 구조 재조정 필요, 스켈레톤 재사용성 저하.

## D-008. 동시성 정책 4건 (2026-07-12, 확정)

기획/설계 대화의 결정 요청(주제 4)에 대한 총괄 결정. 4건 모두 기획 추천안 채택 + 조건 2개.
정책 수준 결정이며, 구현 기법(락 종류·Redis 완충 등)은 백엔드 자율.

### 결정
1. (4-A) 정합성 최종 보증은 DB(조건부 원자 갱신 + 유니크 제약). 분산락(Redisson)은
   처리량 최적화 수단이지 정확성 보장 수단이 아니다. 원칙: "정합성은 DB, 처리량은 락".
2. (4-B) 종료성 전이(SOLD/CANCELLED)는 조건부 CAS UPDATE(WHERE status='ACTIVE',
   affected=0이면 이미 종료). 즉시구매·마감낙찰·취소가 단일 승자 패턴 공유.
3. (4-C) SOLD 확정-Order 생성은 기본 단일 트랜잭션. 결제/외부연동이 범위에 들어오면
   outbox 이벤트 분리로 승격.
4. (4-D) 입찰 유효성 검증·최고가 갱신은 경매 단위 직렬화 + DB 최종 정합성.

### 조건
- 4-D: 소프트 클로즈 마감 연장 판단을 입찰 수용과 동일 직렬화 단위에 포함할 것.
  분리 시 "입찰 성공했으나 연장 누락" 틈 발생.
- 4-C: 최종 방식(단일 TX 유지 vs outbox 승격)은 주제 6 종료 직후 재확정 안건으로 자동 회부.

### 기각된 대안
- 4-A (a) 분산락이 정합성 보증: Redis 장애·락 리스 만료·클럭 스큐 시 중복 판매.
  one-way door 리스크라 기각.
- 4-C 즉시 outbox 확정: 결제 범위(주제 6) 미정 상태의 선행 투자.

## D-009. 결정 로그 세분화: 1 항목 = 1 원자적 결정 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: 기획 에스컬레이션(escalated-as 본 항목), relates-to D-006
- 결정: 결정 로그 1 항목 = 1 원자적 결정. D-009부터 적용, 기존 묶음 항목(D-001~008)은
  소급 재번호하지 않는다. ID는 접두어별 독립 증가·불변·재사용 금지.
- 이유: 묶음 번호는 "D-004 조건 2" 같은 애매한 참조를 유발. 참조 정밀도 실익이 관리 비용보다 큼.
- 기각: 주제/에스컬레이션 단위 번호 유지 — 크로스롤 참조가 늘어날수록 정밀도 손실 누적.

## D-010. 결정 로그 상태 라벨 도입 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: relates-to D-009
- 결정: 상태 라벨 4종 도입 — PROPOSED / ACCEPTED / ON-HOLD / SUPERSEDED(대체 ID 명시).
  참조 키워드 depends-on / relates-to / supersedes / escalated-as 함께 도입.
- 이유: 4-C(D-008)처럼 뒤집힐 수 있는 결정의 상태 추적 필요가 이미 실재.
- 기각: 미도입 — 보류·대체 이력이 본문 산문에 묻혀 추적 불가.

## D-011. 마스터 인덱스 유지 + ID 보고 규칙 (2026-07-12) [ACCEPTED]

- 소유: 총괄 / 관련: relates-to D-009, D-010
- 결정: 총괄이 management/decision-index.md 에 전체 ID 표(ID·제목·상태·소유역할)를 유지한다.
  각 역할은 총괄로 보내는 모든 프롬프트 끝에 "신규 발번 ID" 1줄을 첨부한다.
- 이유: 자율 결정은 총괄을 거치지 않아 인덱스가 불완전해지는 구멍이 있음.
  모든 프롬프트가 총괄을 경유하는 구조를 이용해 보고 규칙으로 봉합.
  내용의 단일 진실은 각 역할 로그, 인덱스는 목차 — 이중 관리 아님.
- 기각: 인덱스 미유지 — 5개 로그 분산 시 크로스롤 현황 파악 불가.

- 소유: 총괄 / 관련: escalated-from backend/outbox/028(안건1), relates-to erd 1절 규약·B-024(이중 방어),
  depends-on api-contract v1.4 §2.5(재가입 허용)·domain-spec v0.5 §6.1. 전 도메인 적용 패턴.
- 배경: erd 1절 "soft delete 테이블의 자연키 유니크는 **삭제 식별 컬럼을 포함**(삭제행-신규행 충돌 회피)"의
  구현 해석이 확정되지 않아, V3 `user`가 `UNIQUE(login_id)`·`UNIQUE(nickname)`으로 규약을 위반했다(028 발견).
  이 규약은 user만이 아니라 **soft delete + 자연키를 가진 모든 테이블**에 걸린다. 순진한 해석이 MySQL에서
  함정이라 해석을 결정으로 고정한다.
- 결정: **생성 컬럼(generated column) + 단일 UK** 패턴을 표준으로 채택한다.
  ```sql
  <자연키>_active <TYPE> GENERATED ALWAYS AS (IF(is_deleted, NULL, <자연키>)) STORED,
  UNIQUE KEY uk_<table>_<자연키>_active (<자연키>_active)
  ```
  - 활성 행만 값을 가져 **활성 유일성 보존**, 탈퇴행은 NULL이라 MySQL의 다중 NULL 허용으로 **재탈퇴 무제한**.
  - `deleted_at` 널 허용(erd §4.1) 유지, 센티넬 값 불요. MySQL 8.0 지원.
  - 원본 자연키 컬럼(`login_id` 등)은 그대로 두고 UK만 생성 컬럼에 건다.
  - 적용 대상: soft delete(`is_deleted`) + 자연키 UK를 가진 **전 테이블**. 신규 도메인도 이 패턴을 따른다.
- 이유:
  - **(a) `UNIQUE(자연키, deleted_at)` 기각 — 가장 위험**. MySQL은 UNIQUE 인덱스에서 NULL을 서로 다른 값으로
    취급하므로 `deleted_at=NULL`인 활성 행이 **동일 자연키로 N개 허용된다**. erd 1절의 문자적 해석이지만
    규약 의도(활성 유일성 보존)를 정면으로 깬다. 조용히 뚫리는 유형이라 명시적으로 기각을 남긴다.
  - **(b) `UNIQUE(자연키, is_deleted)` 기각**. 활성 유일성은 지키나 탈퇴행이 자연키당 1개로 제한 →
    가입→탈퇴→재가입→재탈퇴 시 충돌. 이력 보존(domain-spec §6.1)과 상충.
  - **(d) 애플리케이션 레벨 검사만 기각**. DB 이중 방어(B-024 TOCTOU 안전망) 포기.
  - (c)는 위 셋의 결함이 없고 erd 1절 의도(활성 유일성 + 삭제행 충돌 회피)를 동시에 만족한다.
- 동반 필수(순서 주의 — 028 경고): UK 재구성만 하고 리포지토리 파생 쿼리를 두면 **로그인이 깨진다**.
  재가입 성사 시 동일 자연키로 탈퇴행+신규행이 공존해 `findByLoginId`가 다건을 반환한다
  (`IncorrectResultSizeDataAccessException`). UK 변경과 `...AndIsDeletedFalse` 정정은 **같은 작업 단위**로 묶는다.
- 집행: 백엔드 V4 마이그레이션 + UserRepository 정정 + auth 회귀 테스트(별도 선행 단위, 028 안건3 (a)).
  기획이 erd 1절 규약에 본 패턴을 구현 지침으로 명문화 + §4.1 `user` 표 갱신(074).

## D-086. 부재·수량을 근거로 삼을 때 탐색 방법 명시 (D-082 대칭·D-043 일반화) (2026-07-15) [ACCEPTED]

- 소유: 총괄 / 관련: escalated-as C-035(컨설턴트), **generalizes D-043**(마운트 유령 절단 교차검증),

  import 기준 grep의 동일 패키지 미포착(031), 보안 003의 D-08 grep 0건 오탐.
- 결정: 탐색 결과의 **부재("없음")·수량("N건")을 결정·보고의 근거로 삼을 때 탐색 방법을 1구 명시**한다.
  1. 예: "import 기준 grep으로 참조자 5건", "`grep '## D-08' <경로>` → 0건", "호스트 Grep 기준 부재".
  2. **방법을 명시할 수 없으면 근거로 쓸 수 없다.**
  3. D-082 근거 필드의 **대칭 조항**이다 — **근거는 있으면 인용, 없으면 방법.**
  4. 부과 범위는 모든 탐색이 아니라 **부정 결과를 근거로 삼을 때**로 한정한다.
- 이유(부재 증명의 비대칭):
  - **긍정 결과는 자기 증명적이다** — 찾았으면 실재한다. 반면 **부재·수량은 전적으로 도구 커버리지에
    의존**한다. 사각지대는 언제나 거짓 음성으로만 나타나므로, **부정 결과가 정확히 사각지대가 무는 지점**이다.
  - "도구 일반"으로 넓히면 공허한 훈계가 되지만 **"부정 결과"로 좁히면 공허해지지 않는다.**
  - **D-043이 이미 이 규칙의 1호 사례다.** 마운트 stale이라는 한 도구에만 교차검증을 걸어둔 상태라
    일반화하지 않으면 도구가 바뀔 때마다 D를 새로 발번하게 된다(grep용 → 다음 도구용). **개별 규칙의
    누적은 기본값이 틀렸다는 신호이며, 일반화는 규약을 늘리는 쪽이 아니라 증식을 막는 쪽이다**(C-003 논리).
  - 자기 검증: 031에 이 조항이 있었다면 "import 기준 grep"이라 쓰는 순간 동일 패키지 누락이 작성자·독자
    모두에게 드러났다. D-082가 인용으로 실재를 강제하는 것과 같은 장치의 대칭이라 학습 비용이 없다.
- **적용 한계(과장 금지)**: 본 조항은 **기준 커버리지 계열을 잡지 못한다.** QA 검증 기준의 erd 누락은
  부정 결과 문제가 아니라 검증 대상 목록의 결함이며 075로 종결된 별건이다. 이 조항이 사각지대 일반을
  막는다고 주장하지 않는다 — **거짓 안심은 사각지대보다 위험하다.**
- 기각된 대안: 3건(기준 커버리지·환경 결함·질의 방법)을 묶는 일반 규약 — **실패 계열 자체가 다르다.**
  공통점은 "도구를 믿었는데 못 봤다"는 서술 수준일 뿐 메커니즘이 아니며, 메커니즘이 다른 것을 한 규칙으로
  묶으면 검증 불가능한 훈계가 된다.
- 집행: templates 3·4 근거 필드에 대칭 1줄. D-043은 본문 불변(로그 불변 규약) — 본 항목이 일반형이다.

## D-087. 절 참조 표기 — `§` 사용 금지, 대괄호 `[N.M]` 채택 (2026-07-15) [ACCEPTED]

- 소유: 총괄 / 관련: relates-to D-033(문서 파일 네이밍 규약). 사용자 지시.

## D-092. 확정 스펙 상향 전파 시 참조 문서 근거 줄 갱신 (2026-07-15) [ACCEPTED]

  전사본에 신호가 가지 않는 것이다."** 확정 스펙이 상향되면 그것을 참조하는 모든 문서의 근거 줄이 즉시

  1. **델타가 자기 문서에 영향 있는지 검토** → 2. 있으면 **반영** → 3. **근거 줄 갱신**.

- 이유:
  - **2단 마무리(자기 문서 버전 상향 시 grep)로는 구조적으로 못 막는다.** 그 grep은 **자기 문서를 상향할
    때만** 돈다. **남이 상향하면 내 전사본이 낡는데 내 grep은 안 돈다.** 디자인 진단 그대로다.

    누락이 구조적으로 어렵다. 총괄이 이미 전파를 쓰고 있어 **추가 절차 0**이다.
  - 비용 비교: 전파 시점에 각 파트 1분 vs 나중에 정정 라운드(프론트 005 → 기획 028·029·030 → 디자인 013).
    **이미 후자 비용을 치렀고 더 비쌌다.**
- **적용 한계**: 근거 줄 정정만 덮는다. **본문에서 버전을 규범으로 쓴 경우**(skeleton-plan [5] "기준은
  v1.3이다")는 델타 검토 단계에서 걸리지만, 검토를 형식적으로 하면 통과한다. 전사 자체를 없애는 안(근거
  줄에서 버전 삭제)은 QA test-plan처럼 **버전 선언이 규범인 문서**와 충돌해 채택하지 않았다.
- 기각된 대안: 전사 제거(근거 줄에 버전 미표기) — 위 사유. 현행 유지 — 8건+ 재발이 실증.
- 집행: templates [14] 게이트 전파 체크리스트 1줄 추가.

결정

- **"재설계"의 실체는 재정리다. 지금까지의 설계·구현을 전건 동결한다.** `spec/` 3종(domain-spec v0.5 ·

  착수 가능하나 ① 뒤로 배치한다.** 사용자 지시가 순서를 명시했다.
- **각 파트 재정리 산출물** = 자기 레인의 ⓐ 앞으로 할 일 **전수**(탐색 방법 명시) ⓑ 결정 보류로 생략·누락된
  것 회수 ⓒ 사용자 결정 필요분(**추천 필수** — `[5.40]`) ⓓ 자기 지침의 낡은 참조(없으면 "없다").
- **신규 규약·조항·지침 신설 금지.** 이건 목록 작업이지 설계 작업이 아니다.
- **총괄이 7파트 산출물을 하나의 뷰로 조립한다**(`common/status.md`). 사용자는 7문서가 아니라 1문서를 본다.

결과

- 좋아짐: 사용자 결정 큐가 전수로 서고 **보류분이 회수된다**. spec·코드 무변경이라 되돌릴 것이 없고
  `[6]`·`[3.12]`가 발동하지 않아 왕복이 0이다. 백엔드 대기 사유가 "재설계 대상이라 착수 금지"에서
  "순서상 뒤"로 바뀌어 **폐기 위험이 사라진다**(백엔드 handover의 "지금 만들면 그대로 폐기될 수 있다"가 해소).
- 나빠짐: **기능 진입이 재정리 1라운드만큼 더 밀린다.** 사용자 불만이 "진행이 안 된다"인데 진행을 한 번 더
  멈추는 결정이다. **그리고 파트별 재정리가 또 파생을 낳으면 원인을 처방으로 재생산한다** — 컨설턴트가
  C-070에서 자백한 형태("체계 점검을 하루 종일 늘렸다")와 구조가 같다. 이 위험은 실재한다.
- 못 푸는 것: **파생이 많은 것 자체는 못 줄인다.** 목록을 세울 뿐 일을 없애지 않는다. 사용자 파악 부담은
  항목 수에 비례하므로 **전수로 세우면 처음엔 오히려 늘어 보인다** — 줄어드는 것은 "모르는 항목"이지
  "항목"이 아니다. 이 결정이 실패한다면 그 자리다.

기각된 대안

- **`spec/` 3종 재작성**: 사용자가 "설계 및 구현은 유지"라 명시. 그리고 DB가 V4까지 나가 있어 되돌리는 게
  아니라 **V5+로 덮는 것뿐**이라 종이만 고치면 그 순간 스펙과 DB가 갈라진다(기획 handover 진단).
- **회원 3유닛 재정리와 병행**: `[7.10]` 2문상 병행 가능하다(의존 없음 · 쓰기 집합 무충돌 — 코드 대 문서).
  그럼에도 기각 — 사용자 지시가 *"체계 작업을 먼저 진행한 후 기능 작업으로 다시 진입"*으로 **순서를
  명시**했다. 규약이 병행을 허용해도 사용자 지시가 이긴다(`[1.2]`).
- **재정리 없이 기능 재개**: 보류분이 회수되지 않고 사용자 파악 불가가 유지된다. 사용자 진단을 무시하는 안.
- **파트 지침 신설**(기획·총괄은 자기 지침이 없다 — 실측: `<역할>-guide.md` 실재 4종 = qa·security·ux·
  frontend): 기각. C-070 판정(*"지침 없이 이미 기동해 산출물을 냈다"*)이 유효하고 **아무도 막히지 않는다.**
  신설은 사용자 불만("규칙이 너무 까다로워 진행이 안 되고 있다", C-071)의 **재생산**이다.

집행: `management/outbox/_broadcast/002`(전 역할 전파) · `common/status.md`(조립 뷰). **반영 확인 방법** =
각 파트 재정리 보고 수신 수(7파트 중 n) — 호스트 Grep `path=docs, files_with_matches`로 신규 outbox 계수.

맥락

## D-097. 도메인 진행 순서 재정의 — 목업이 코드 앞에, 보안이 QA 앞에

  **지금은 D-097 1-2 착수 직전이다.**

결정

- **D-093 동결선의 사정거리를 확정한다: 재정리 국면 한정.** ② 기능 재진입 후 **도메인 구현이 요구하는
  계약 변경은 `[6]` 정상 절차로 간다.** D-093이 `[6]`을 폐지한 게 아니다.
- **`[6]` 발동. 계약 변경 4건을 `api-contract v1.5` 한 번으로 묶는다.** 넷 다 같은 파일이고,
  네 번 돌리면 **기획이 네 번 열고 전파가 네 번 나간다.**

  | # | 무엇 | 낸 역할 | 판정 |
  |---|---|---|---|
  | 1 | `MEMBER_002` 409에 `details.blockedBy` — enum 3값(`AUCTION`·`BID`·`ORDER`) | 디자인 · 백엔드 지지 | **승인** |
  | 2 | `nickname` 검증 규칙 명시 — **signup에도 없다**(`@NotBlank`+`@Size(max=30)`뿐). **B-016(password)과 같은 뿌리라 같이** | 디자인 → 기획 | **승인** |
  | 3 | `[3.3]` item `element` wire 값 4종 대문자 열거 | 프론트 | **승인** |
  | 4 | `[3.3]` 상태 enum 값 목록 — **복제 아니라 `[3.1]` 참조 형태로** | 프론트 | **승인(조건부)** |

결과

- 좋아짐: **계약이 한 번 바뀐다.** 백엔드 실측대로 미루면 **계약 2회·화면 2회·백엔드 2회**다.
  `blockedBy` 필드가 1-2의 "구조만 두기"에 같이 들어가 **커밋 1건**이 된다.
  `element: string`이 유니온으로 좁아져 **런타임 무성 실패가 컴파일 에러가 된다.**
- 나빠짐: **1-2가 기획 v1.5를 기다리면 밀린다.** → **안 기다린다**(아래 집행). 대신 **기획이 v1.5를
  쓰는 동안 백엔드가 `blockedBy` 없이 짜면 나중에 필드 추가 커밋이 하나 는다.** 그 비용은 감수한다.
  **그리고 `[6]` 4단계 전파가 또 한 바퀴다** — 사용자 손이 한 번 더 든다.
- 못 푸는 것: **`blockedBy`는 지금 항상 `[]`다**(bid/auction/order 미구현 → 검사 대상 공집합).
  **빈 배열을 계약에 박는 것이 맞는지는 auction 구현 때 드러난다.** 디자인 논거(*"빈 배열은 지금
  정직한 값이다"*)를 채택하나 **검증은 그때다.**

기각된 대안

- **목록에만 적고 미룸**(`_broadcast/002` [2] *"고치지 말고 목록에 적어라"* 적용): **그 문장은 재정리
  국면의 것이다.** 지금 적용하면 백엔드 실측(계약 2회·화면 2회·백엔드 2회)이 확정 비용이 된다.
- **`errors` 재사용**(백엔드 (b)): 기각 사유 채택 — *"`errors`는 검증 실패 전용이고 `@Valid` 경로가 쓴다.
  의미가 다른 걸 같은 필드에 넣으면 **프론트가 400과 409를 같은 파서로 읽다가 갈린다.**"*
- **`message` 문자열**(백엔드 (c)): *"화면이 문자열을 파싱해야 한다. 카피가 바뀌면 분기가 깨진다."*
- **안건 4 현행 유지**(프론트 (b)): 프론트가 자진 제시한 반대 근거(*"`[3.3]`에 값을 복제하면 `[3.1]`과
  이중 정본이 된다 — C-073 [2] 형태"*)가 정확하다. **그래서 복제가 아니라 참조 형태로 조건을 달았다.**
  형식은 `[3.4]`상 기획 소관이다.

집행: `management/outbox/CONTRACT/001`(기획 작업 지시 — `[6.1]`-③) · 확정 후 `[6.1]`-④ 전파.
**1-2는 v1.5를 기다리지 않는다**(디자인·백엔드 판단 일치 — 안 막힌다). **반영 확인 방법** =
호스트 Grep `blockedBy|element.*WATER` on `spec/api-contract.md` + 상태줄 `v1.5` 대조.

## D-100. D-097에 프론트 자리를 넣는다 — 디자인 세부 완성 뒤, QA 앞

상태: ACCEPTED · 소유: 총괄 · 관련: 사용자 직접 지시(2026-07-17) · escalated-from `ux/outbox/REFORM/002` [2] ·
**D-097 순서 항 확장**(대체 아님 — 단계 추가) · 2026-07-17

맥락

- **사용자 직접 지시**(2026-07-17, 원문): *"디자인 파트규칙 추가한다. AI티가 나는 디자인은 금지이다.
  디자인 진행할 때 클로드 디자인 스킬을 사용한다. **지금은 목업 디자인이며 디자인이 완성되면 프론트에
  작업이 들어간다.**"*
- **★ 디자인이 실물 공백을 잡았다**(`ux/outbox/REFORM/002` [2]): **D-097 여섯 단계에 프론트가 한 번도
  안 나온다.** 기획 계약 → 디자인 목업 → 백엔드 코드 → 디자인 세부 ∥ 보안 → QA → 판정.
  **프론트가 화면을 만드는 자리가 아무 데도 없다.**
- **디자인 처신이 정확하다** — `[1.4]`상 시퀀싱이 총괄 축이라 **자기 지침에 전사만 하고 넘겼다.**
  그리고 넘긴 이유가 옳다: *"**내 파트 지침은 프론트가 안 읽는다**(`[3]` — 파트 지침은 그 파트 것).
  지금 이 규칙은 디자인 문서에만 있고 프론트는 모른다."*
- **내 결함이다.** D-097을 발번할 때 사용자 지시 3건을 받아 순서를 짰는데 **프론트를 안 넣었다.**
  당시 사용자 지시가 QA·보안·디자인·백엔드만 다뤘고 **나는 지시에 없는 파트를 세지 않았다** —
  "지시된 것만 배치"가 아니라 "레인 전수"가 시퀀싱의 일인데.

결정

- **D-097 순서에 프론트를 넣는다. 「디자인 세부 완성」 뒤, QA 앞이다.**
  ```
  ① 기획 계약 → ② 디자인 목업 → ③ 백엔드 코드
    → ④ 디자인 세부 완성 ∥ 보안 구현 리뷰
    → ⑤ 프론트 화면 구현          ← 신설
    → ⑥ QA 시나리오 실행 → ⑦ 총괄 G4-n 판정
  ```
- **근거**: 사용자 지시(*"디자인이 완성되면 프론트에 작업이 들어간다"*) — **④의 산출이 ⑤의 입력이다.**
  그리고 **③(백엔드 코드)도 ⑤ 앞이라야 프론트가 실 API에 붙는다.** 둘 다 ⑤ 앞에 이미 있다.
- **QA가 프론트 뒤인 이유**: QA 시나리오가 **화면 없이 도는 것과 붙어서 도는 것이 다르다.**
  지금 QA 시나리오(AUTH·GW·MBR)는 API 레벨이라 ⑤ 없이도 돌지만, **화면이 생기면 재실행 대상이 된다.**
  ⑤를 QA 앞에 두면 한 번 돈다.
- **★ 진행 중인 프론트 U-020 토큰 교체는 완주한다**(`[5.45]` — *"진행 중 작업은 완주가 기본값이다.
  중단은 지시가 아니라 합의로 한다"*). **디자인 판단 채택**: *"이건 화면 구현이 아니라 스켈레톤이고
  진행 중이라 사용자 지시가 이걸 중단시키는 뜻이 아니라고 읽었다."* **맞다.** 스켈레톤은 ⑤의 선행 자산이지
  ⑤ 자체가 아니다.

결과

- 좋아짐: **프론트가 레인에 선다.** 지금까지 프론트는 D-097 밖에서 스켈레톤만 하고 있었고
  **도메인이 돌기 시작하면 갈 곳이 없었다.** 그리고 **디자인 세부 → 프론트 순서라 화면을 두 번 안 만든다.**
- 나빠짐: **member G4-2가 한 단계 길어진다.** ⑤가 ⑥ 앞이라 QA가 그만큼 늦게 돈다.
  그리고 **프론트는 코드가 별도 저장소가 아니게 됐어도**(D-098) **총괄이 실물을 검수할 수단이 여전히
  약하다** — 프론트 ⓐ가 "전수 아님"이었던 구조적 이유가 완전히 사라진 건 아니다.
- 못 푸는 것: **⑤와 ④의 경계가 흐리다.** 디자인 "세부 완성"이 어디서 끝나고 프론트 "구현"이 어디서
  시작하는지는 U-013(와이어프레임 경계)이 기능정의/UI레이아웃으로 갈랐을 뿐 **구현 층은 안 갈랐다.**
  첫 도메인(member)에서 부딪히면 그때 본다.

기각된 대안

- **⑤를 QA와 병행**: `[7.10]` 2문상 가능해 보이나(쓰기 집합 다름) **기각.** QA 시나리오가 화면 생기면
  재실행 대상이라 병행하면 두 번 돈다. D-097이 보안↔QA를 직렬화한 것과 같은 논리다.
- **⑤를 ③(백엔드) 직후**: 디자인 세부(④)가 안 끝난 상태로 프론트가 붙으면 **화면을 두 번 만든다.**
  사용자 지시가 *"디자인이 **완성되면**"*이다.
- **D-097 본문 수정**: `[4.2]` 불변. **단계 추가라 대체가 아니고, D-097 상태줄에 확장 주를 단다.**
