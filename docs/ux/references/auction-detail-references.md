## 0. 조사 방법과 신뢰도 표기

레퍼런스마다 다음 태그로 근거 수준을 구분한다. **추측을 관찰로 위장하지 않기 위한 장치다.**

| 태그 | 의미 |
|---|---|
| `[직접 관찰]` | 해당 URL을 실제로 가져와 페이지 구조를 읽었다. 레이아웃 서술은 그 결과다. |
| `[설명 기반]` | 스크린샷·실물 페이지를 보지 못했다. 공식 문서·기사·UX 리서치의 **서술**을 근거로 재구성했다. |
| `[추론]` | 위 두 근거에서 내가 끌어낸 해석·판단. 출처의 주장이 아니다. |

**차단되어 직접 관찰하지 못한 대상**(모두 `[설명 기반]`으로 처리): Goldin Auctions(타임아웃),
Cardmarket(403), TCGplayer(콘텐츠 미노출), 무신사·컬리·29CM 상품 페이지(SPA — 본문 대신 푸터만 반환),
eBay 개별 경매 페이지(타임아웃). 국내 커머스는 **공식 뉴스룸·디자인 케이스 스터디의 서술**로 대체했다.

**ASCII 도식 주의**: 도식은 출처 페이지의 서술을 내가 구조로 옮긴 **재구성**이다. 픽셀 단위 실측이 아니다.

## 1. 경매·입찰 UI — "지금 얼마 · 언제 끝나는가"

### 1-1. Yahoo! Auctions Japan `[직접 관찰]`

- URL: https://auctions.yahoo.co.jp/category/list/2084005207/
- **구조**: 목록 카드마다 4개 값이 **고정 순서로 반복**된다 —
  현재가(`現在 30,000円`) → 배송비(`＋送料980円`) → 입찰수(망치 아이콘 + `入札 0`) →
  잔여시간(시계 아이콘 + `残り 1日`).
- 아이콘이 **레이블을 대체**한다(망치=입찰, 시계=시간). 텍스트 폭을 아이콘이 흡수해
  좁은 카드에서도 4개 값이 한 줄에 들어간다.

```
┌──────────────────────────┐
│      [상품 썸네일]        │
├──────────────────────────┤
│ 제목 2줄 …                │
│ 現在 30,000円             │  ← 가장 큰 활자
│ ＋送料980円               │  ← 회색 보조
│ 🔨 入札 0    🕐 残り 1日   │  ← 아이콘 + 값, 한 줄
│ [未使用] [送料無料]        │  ← 상태 배지
└──────────────────────────┘
```

- **가져올 지점**: ① **현재가·입찰수·잔여시간을 항상 같은 순서로 붙여 하나의 "경매 상태 묶음"으로
  다룬다.** 상세와 목록에서 동일한 묶음을 재사용하면 사용자가 스캔 규칙을 한 번만 배운다.
  ② 잔여시간을 `1日`처럼 **가장 큰 단위 하나로 반올림**해 평시에는 조용히 둔다(임박 구간에서만 초 단위로 승격).
- **안 맞는 지점**: 야후옥션의 밀도는 정보 과다에 가깝고 배지 색이 난잡하다. 우리 라이트 커머스 톤·
  안티-AI 원칙과 충돌한다. 구조만 가져오고 **배지 색은 버린다.**

### 1-2. eBay — 카운트다운의 정직성 문제 `[설명 기반]`

- URL: https://community.ebay.com/t5/Report-eBay-Technical-Issues/Ebays-auction-countdown-timer-out-of-sync-with-reality/td-p/34090217
- URL: https://www.quora.com/How-does-an-eBay-auction-timer-work
- **구조/동작**: 카운트다운은 실시간 스트림이 아니라 **클라이언트 스크립트**다. 주기적으로 서버에
  잔여시간을 물어보고 그 사이는 **기기 로컬 시계로 감산**한다. 그 결과 상품 페이지의 타이머와
  입찰 확인 팝업의 타이머가 **서로 다른 값을 보이는** 버그가 커뮤니티에 반복 보고된다.
- 낙찰 판정은 **eBay 서버가 수신·타임스탬프한 시각** 기준이며 화면 타이머 기준이 아니다.
- **가져올 지점**: **타이머는 UI가 아니라 신뢰의 문제다.** 상세 페이지와 입찰 모달이 **같은 시계
  소스를 공유**해야 한다(서버 시각 1회 동기화 + 클라이언트 오프셋 보정, 화면마다 독립 타이머 금지).
  마감 근처에서는 "서버 수신 시각 기준" 문구를 보조로 노출해 분쟁을 예방한다.
- **안 맞는 지점**: 없음. 이건 **피해야 할 실패 사례**로 가져온다.

### 1-3. Christie's / Sotheby's — 안티스나이프 연장 `[설명 기반]`

- URL: https://theculturalpocalypse.com/how-sothebys-and-christies-adapted-to-the-age-of-virtual-auctions/
- URL: https://help.sothebys.com/en/support/solutions/articles/44002297462-how-can-i-bid-in-an-auction-
- **구조**: 로트는 1분 단위로 순차 마감하되, **마지막 1분 안에 입찰이 들어오면 2분 연장**된다
  (최대 2시간까지). 별도 설명에 따르면 마지막 90초 안에 상위 3인에 드는 입찰이 들어오면
  타이머가 90초로 리셋되는 방식도 쓰인다.
- **가져올 지점**: **카운트다운이 "연장될 수 있다"는 사실 자체가 UI 요소다.** 숫자만 보여주면
  0이 되는 순간 사용자는 배신감을 느낀다. 임박 구간에서 "마감 임박 입찰 시 연장" 규칙을
  **타이머 바로 아래 한 줄로 상시 고지**해야 한다. 연장이 발생하면 타이머를 조용히 갱신하지 말고
  **연장되었음을 명시적으로 표시**한다.
- **안 맞는 지점**: 경매하우스의 "로트 순차 마감"은 우리 모델(아이템 단위 독립 마감)과 다르다.
  연장 규칙만 취한다. (FinalCall이 실제로 연장을 구현할지는 **백엔드 계약 사안 — 게이트2**이며,
  이 문서는 결정하지 않는다.)

### 1-4. Goldin Auctions — 30분 무입찰 규칙 `[설명 기반]`

- URL: https://www.cardsense.app/blog/goldin-auctions-guide
- URL: https://www.auctionreport.com/goldin-2025-weekly-auctions-ends-every-thursday-night/
- **구조**: 예정 마감 후에는 "30분 규칙"으로 전환 — 각 로트는 **30분간 새 입찰이 없어야** 닫힌다.
  새 입찰이 들어오면 30분 카운트다운이 리셋된다.
- **가져올 지점**: 마감 표현이 **두 모드**를 가진다는 점 — "예정 마감까지 D-2일"(절대 시각)과
  "무입찰 30분 남음"(상대 시각). **우리의 임박 3구간도 같은 발상**이다. 평시엔 절대 시각
  (`7월 21일 21:00 마감`)을 우선 노출하고, 임박에서 상대 시간(`04:32`)으로 **표현을 교체**한다.
  둘을 동시에 크게 보여주면 둘 다 안 읽힌다.
- **안 맞는 지점**: 스포츠카드 고액 경매의 여유로운 템포다. 우리는 "마감 직전 입찰 폭주"가
  핵심 도전이므로 임박 구간이 훨씬 짧고 날카로워야 한다.

### 1-5. 긴박함의 윤리 — 진짜 마감 vs 다크패턴 `[설명 기반]`

- URL: https://think.design/blog/responsible-design-part-4-of-14-false-urgency/
- URL: https://www.finance-watch.org/blog/dark-patterns-explained-how-to-spot-and-avoid-deceptive-ux/
- **요지**: 카운트다운 자체는 다크패턴이 아니다. **다크패턴이 되는 조건은 "마감이 실제가 아닐 때"**다.
  판정 기준은 *"완전히 투명한 상태에서도 사용자가 같은 결정을 했겠는가"*. 실제 종료되는 시한 고지는
  정당한 설득이다.
- **가져올 지점 `[추론]`**: **FinalCall의 마감은 진짜다.** 그래서 우리는 대부분의 커머스가 못 쓰는
  강한 긴박 표현을 **떳떳하게 쓸 자격이 있다.** 다만 자격은 정확성에 달려 있다 —
  ① 남은 시간이 실제와 어긋나면(1-2 참조) 정당성이 무너진다.
  ② 마감 후에도 계속 살 수 있는 "즉시구매"와 마감이 걸린 "입찰"의 시한을 섞어 표시하면 거짓 긴박이 된다.
  ③ **긴박 표현은 시간 요소에만 적용하고 가격 블록에는 적용하지 않는다.** 가격까지 빨개지면 세일 광고가 된다.

### 1-6. 임박 3구간의 시각화 `[추론]` — 위 사례들의 종합

우리는 이미 3구간을 쓰기로 했다. 사례에서 끌어낸 **각 구간이 바꿔야 하는 것**은 다음과 같다.
색만 바꾸는 건 약하다. **표현 단위·활자 크기·갱신 주기·CTA 문구까지 함께 움직여야** 긴박이 전달된다.

| 구간 | 시간 표현 | 갱신 주기 | 시각 강도 | CTA |
|---|---|---|---|---|
| 평시 | 절대 시각 우선 (`7월 21일 21:00 마감`) | 분 | 무채색, 본문 크기 | `입찰하기` |
| 주의 | 상대 시간 (`3시간 12분 남음`) | 분 | 퍼플 액센트, 살짝 승격 | `입찰하기` |
| 임박 | 상대 시간 초 단위 (`04:32`) | 초 | 최고 강도, 활자 대폭 승격 + tabular numerals | `지금 입찰` |

- **임박 색 선택 `[추론]`**: 빨강은 커머스에서 "할인·오류"로 이미 소비된 색이고, AI 생성물이 긴박함에
  기본값으로 빨강을 쓴다(안티-AI 위반). **퍼플 액센트를 임박 신호로 승격시키는 쪽**이 우리 시스템에
  정합적이다. 색 대신 **활자 크기·굵기·초 단위 갱신**이 긴박의 주된 운반체가 되게 한다.
- **`tabular-nums` 필수**: 초 단위 카운트다운에서 비례 숫자를 쓰면 자릿수마다 폭이 흔들려
  타이머가 "떨린다". 이게 싸구려로 보이는 대표적 원인이다.
- **`prefers-reduced-motion` 존중**: 깜빡임·펄스 애니메이션은 이 설정에서 반드시 정지시킨다.

## 2. 게임 아이템 거래소 — 작고 세로형인 아트를 다루는 법

### 2-1. Steam 커뮤니티 마켓 `[직접 관찰]` ★ 핵심 레퍼런스

- URL: https://steamcommunity.com/market/listings/730/AK-47%20%7C%20Redline%20%28Field-Tested%29
- URL(2026 개편 설명): https://www.gamermarkt.com/blog/steam-community-market-redesign-new-features/
- **구조**: 상단이 좌우 2단, 하단이 **전폭 매물 테이블**이다.
  - 좌(약 40%): 아이템 이미지 · 이름 + 등급 배지(`Classified Rifle`) · 설명문 ·
    컬렉션 귀속 · **펼침형 속성 목록**(Type / Weapon / Collection / Category / Quality / Exterior)
  - 우(약 60%): **가격 테이블**(Factory New ~ Battle-Scarred 컨디션별 행, StatTrak/Souvenir 토글) ·
    **가격 이력 그래프**(Week/Month/Year/Lifetime 탭) · **구매 액션**(`Place buy order…` + 가격 필터)
  - 하단 전폭: 매물 1,555건 리스트. 각 행에 wear·패턴·부착 스티커·가격.

```
┌───────────────────┬──────────────────────────────────┐
│  [아이템 이미지]   │  가격 테이블 (컨디션별 행)         │
│                   │  ├ Factory New      ₩ ...        │
│  이름 + 등급배지   │  ├ Minimal Wear     ₩ ...        │
│  설명문           │  └ Battle-Scarred   ₩ ...        │
│  컬렉션           ├──────────────────────────────────┤
│  ▼ 속성           │  가격 이력 그래프 [주][월][년][전체]│
│    Type  …        ├──────────────────────────────────┤
│    Quality …      │  [ Place buy order… ]            │
│    Exterior …     │                                  │
└───────────────────┴──────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│  매물 리스트 (전폭) — 1,555건                          │
│  wear · 패턴 · 스티커 · 가격 · [구매]                  │
└──────────────────────────────────────────────────────┘
```

- **가져올 지점 — 이게 우리 안2의 실물이다**:
  ① **아이템 아트가 작아도 성립하는 이유**는, 이미지가 좌단을 **혼자 채우지 않고**
  이름·등급·설명·속성과 **하나의 "정체성 블록"으로 묶여** 좌단을 채우기 때문이다.
  이미지를 억지로 키우지 않고 **텍스트를 이미지의 동반자로 붙여** 좌우 균형을 맞추는 해법.
  ② **속성을 접을 수 있게(collapsible) 둔다** — 밀도는 확보하되 초보 구매자에겐 압박이 안 된다.
  ③ **거래 이력·매물 테이블은 전폭 하단**. 표는 가로 폭을 먹으므로 좁은 컬럼에 밀어넣지 않는다.
  ④ 2026 개편의 방향이 **"더 넓은 레이아웃 + 전폭 그리드"**였다는 점 — 즉 Steam은 좁은 2단에서
  전폭으로 **넓히는 쪽으로 진화**했다.
- **안 맞는 지점**: Steam의 아이템 이미지는 **가로형**(총기 스킨)이라 좌단 폭을 자연스럽게 채운다.
  우리 아트는 **50×93 세로형**이라 확대해도 좌단 폭을 못 채운다 → 좌단에 **텍스트 동반이 Steam보다 더
  절실하다**. 또 Steam은 동일 아이템의 다수 매물이 전제(테이블이 길다)지만, 우리는 **경매 1건 = 페이지 1개**라
  하단 전폭에 들어갈 것은 매물이 아니라 **입찰 이력**이다.

### 2-2. 로스트아크 경매장 `[설명 기반 — 공식 게임 가이드]`

- URL: https://m-lostark.game.onstove.com/GameGuide/Pages/거래소
- **구조**: 목록/검색 화면과 **입찰·구매 팝업**이 분리돼 있다. 팝업에는 "구매하려는 물품에 현재
  진행되고 있는 경매 정보"가 담긴다 — 현재 최고 입찰가 · 즉시구매가 · **최소 입찰가** · 남은 시간 ·
  입찰 현황. 입찰 방식이 둘이다: **[즉시 입찰]**(최소 입찰가로 원클릭) 또는 직접 금액 입력.
  입력 상한은 소지금 또는 즉시구매가.

## 4. ★ 데스크톱과 모바일을 별도로 설계한 사례

> 사용자의 핵심 요구. **열을 접는 게 아니라 정보 구조·상호작용 자체를 다르게** 간 사례.

### 4-1. 모바일 스티키 바이바(Sticky Buy Bar) `[설명 기반]` ★ 핵심 레퍼런스

- URL: https://www.laioutr.com/en/blog/sticky-add-to-cart-mobile-pdp-2026
- URL: https://thegood.com/insights/sticky-add-to-cart/
- URL: https://growthrock.co/sticky-add-to-cart-button-example/
- **문제 정의**: 모바일 PDP는 갤러리 → 제목 → 가격 → 옵션 → 설명 → 배송 → 리뷰 → 교차판매로
  **길다**. 원래 구매 버튼은 상단에 있어 **몇 번 스와이프하면 사라진다.** 리뷰를 읽고 결심한 사용자는
  **위로 되돌아가야** 하고, 그 왕복마다 이탈이 발생한다.
- **해법 구성 — 필수 3요소**: ① 가격(할인 시 취소선 포함) ② 주요 CTA(최소 44×44px 탭 타겟)
  ③ **변형/옵션 상태**(무엇이 담기는지). 썸네일·수량·위시리스트는 선택이며 주요 액션을 밀어내면 안 된다.
- **발동 방식**: **원래 버튼이 뷰포트를 벗어날 때** 나타난다. 픽셀 임계값이 아니라
  **IntersectionObserver로 그 버튼을 관측**한다. 150~200ms 페이드/슬라이드, 깜빡임 방지 버퍼.
- **안티패턴(명시)**: 스크롤 이벤트 리스너 사용 / 하드코딩 픽셀 임계값 / `height`·`top` 애니메이션
  (레이아웃 시프트) / 44px 미만 탭 타겟 / 대비 4.5:1 미만 / **바와 본문의 옵션 상태 불일치**.
- **구현**: `position: fixed`로 문서 흐름 밖에 두고 페이지에 **패딩을 미리 확보**,
  `transform: translateY` + `opacity`로만 애니메이션(CLS 방지).
- **접근성**: 바가 나타날 때 **포커스를 빼앗지 않는다**. 포커스 순서 논리 유지.
- **데스크톱과의 차이(명시)**: **"데스크톱은 이득이 작다 — 폴드 위에 더 많이 들어가기 때문."**
  실제로 모바일에만 스티키 바를 넣고 데스크톱엔 안 넣는 사례가 존재한다(Touchland).
- **성과 주장**: A/B에서 액션 영역을 드로어처럼 올리는 변형이 **주문 +5.2%**(유의도 98%),
  머천트 보고 기준 상품 페이지 전환 **+10~15%**(모바일 편중 스토어는 최대 20%).
  ※ 벤더 블로그 출처다. **수치는 근거가 아니라 방향으로만 취급한다.**
- **가져올 지점 — 우리 맥락에서 이건 옵션이 아니라 필수 `[추론]`**:
  일반 커머스의 스티키 바는 "편의"지만, **경매에서는 "가격이 실시간으로 변한다"**.
  스티키 바가 **현재가 + 잔여시간 + 입찰 CTA**를 상시 노출하지 않으면, 사용자는 스크롤 도중
  **낡은 가격을 기억한 채 결정**하게 된다. 즉 우리 스티키 바는 3요소를 이렇게 치환한다:

  | 커머스 필수 3요소 | FinalCall 치환 |
  |---|---|
  | 가격 | **현재가**(실시간 갱신) |
  | 변형/옵션 상태 | **잔여시간**(임박 시 강조) — 여기서 "무엇이 변하는가"는 시간이다 |
  | 주요 CTA | **[입찰]** (+ 즉시구매가 있으면 보조) |

- **안 맞는 지점**: 커머스 스티키 바는 정적이다. 우리 건 **숫자 2개가 계속 바뀐다** →
  값이 바뀔 때 바 전체가 흔들리지 않도록 **고정폭(`tabular-nums`) + 고정 높이**가 전제다.

### 4-2. 바텀시트 — NN/g의 경고 `[설명 기반]` ★ 반드시 지킬 것

  이동하려 하는데, 시트는 페이지 간 이동 관습을 깨뜨린다.
- **가져올 지점 `[추론]`**: 이 경고가 **우리 모달 설계의 경계선을 정해준다.**
  - 경매 **상세 페이지**는 바텀시트/모달이 아니라 **진짜 페이지**여야 한다. (딥링크·공유·뒤로가기·

### 4-4. 데스크톱 스티키 사이드바 `[설명 기반]`

- URL: https://css-tricks.com/designing-a-product-page-layout-with-flexbox/

  |---|---|---|
  | 구매 액션 상시 노출 | 우측 컬럼 `position: sticky` | 하단 고정 바 (`position: fixed`) |

### 5-1. Baymard — "스펙 중심 상품에는 퀵뷰를 쓰지 마라" `[설명 기반]` ★ 결정적

- URL: https://baymard.com/blog/ecommerce-quick-views
- **주장**: 퀵뷰(목록에서 뜨는 오버레이 미리보기)는 **시각 중심 상품**(의류·인테리어)에는 유용하지만,
  **스펙 중심 상품**(전자제품·공구·가전·산업재)에는 **불필요한 마찰**이다. 속성이 많아 오버레이에
  다 들어가지 않기 때문이다.
- **테스트 결과**: 스펙 중심 사이트에서 사용자들은 **퀵뷰를 대체로 무시**했다.
  실수로 연 사람들은 **정작 필요한 정보가 없어 가치를 못 느꼈다.**
  피험자 인용: *"비교 능력을 잃는다 … 이것들의 차이가 뭔데? 알 방법이 없다."*
- **비율**: 스펙 중심 사이트의 **21%가 퀵뷰를 제공**(= 불필요한 기능) / 52%는 목록 항목에
  카테고리별 정보를 충분히 안 준다 / 17%는 데스크톱 비교 기능이 없다.
- **권고**: 스펙 중심이면 **퀵뷰를 버리고**, 대신 ① 스펙 가시성을 극대화한 **리스트 뷰**
  ② 목록 항목의 **풍부한 정보** ③ **스캔 가능한 비교 도구**에 투자하라.
  시각 중심이면 퀵뷰에 **이미지를 주인공으로** 두고, 반품정책·연관상품 같은 건 상품 페이지로 넘긴다.
  어느 쪽이든 **"상세 보기" 버튼을 눈에 띄게** 둬서 퀵뷰와 전체 페이지를 혼동하지 않게 한다.
- **우리에게 주는 판정 `[추론]` — 냉정하게 봐야 할 대목**:
  FinalCall의 아이템은 **타입·레벨·속성·스킬·골드포스 잔여** — 명백히 **스펙 중심**이다.
  Baymard 기준으로는 **"퀵뷰를 만들지 말라"**에 해당한다. 그런데 우리는 만들었고 실패했다.
  **그러나 우리 모달은 목록의 퀵뷰가 아니라 "아트를 클릭했을 때의 확대 + 정체성 표시"에 가깝다** —
  용도가 다르다. 그래서 결론은 "없애라"가 아니라 **"목적을 하나로 좁혀라"**다:
  - ❌ **하지 말 것**: 모달을 미니 상세 페이지로 만들기(스펙 전량 + 가격 + 입찰까지 우겨넣기).
    Baymard가 실패를 관측한 정확히 그 형태다.
  - ✅ **할 것**: 모달의 역할을 **"아트 확대 + 아이템 정체성(이름·등급·타입) 확인"**으로 좁히고,
    스펙 전량은 **상세 페이지 본문에 펼쳐서** 둔다. 모달 하단에 **[상세 보기]를 명확히** 배치한다.
  - 즉 **모달이 구렸던 이유는 톤 이전에 역할 과부하일 가능성이 높다.** 어두운 남색이 문제이기도 하지만,
    **211×307 창에 스펙을 다 넣으려 한 구조 자체**가 원본의 제약을 그대로 상속한 것이다.

### 6-1. Diablo II: Resurrected — 판단 기준을 명문화한 사례 `[설명 기반]` ★ 핵심

- URL: https://www.gamedeveloper.com/marketing/exploring-modernity-legacy-and-accessibility-in-diablo-ii-resurrected
- URL: https://us.forums.blizzard.com/en/d2r/t/legacy-ui-for-diablo-2-resurrected/169645
- **맥락**: 2001년 원작(우리 참조 원본과 **같은 시기**)의 리마스터.
- **판단 프레임**: 팀은 "합리적 편의 개선"과 "원작 보존" 사이에서 오래 논쟁했고,
  결국 **최소주의**로 갔다 — **"이해도(understandability)와 플레이 가능성(playability)을 높일 때만
  바꾼다. 변화를 위한 변화는 하지 않는다."**
- **거절 사례가 특히 유용하다**: 인벤토리 편의 기능인 '**부적 가방(charm bag)**'은
  **"레거시를 존중하지도 않고, 접근성을 의미 있게 개선하지도 않는다"**는 이유로 **기각**됐다.
  → **개선처럼 보이지만 어느 쪽 기준도 통과 못 하는 변경은 거절**한다는 명시적 규율.
- **보존한 것**: 핵심 게임플레이 메커닉과 "느낌".
- **현대화한 것**: 색맹 토글, 큰 글꼴 / **UI 스케일링**, 자동 골드 획득, 공격 빗나감 표시,
  자막 토글, 오디오 채널 슬라이더 — **전부 접근성 축**이다.
- **핵심 인용**: *"접근성은 곧 커스터마이즈와 최적화다."* 그리고 **레거시 그래픽 토글**을 제공해
  순수주의자에게 변화를 강요하지 않았다.
- **우리에게 주는 기준 `[추론]` — 이 문서에서 가장 실용적인 대목**:
  D2R의 규율을 우리 모달에 그대로 적용하면 판정이 나온다.

  | 원본 요소 | D2R식 판정 | 결론 |
  |---|---|---|
  | 남색 `#001C33` 배경 | 이해도↑? ✗ 접근성↑? ✗ (라이트 커머스 크롬 안에서 **대비 붕괴**) | **답습 — 버린다** |
  | 금색 타이틀 | 이해도↑? ✗ (금색은 우리 시스템에 없는 색, 퍼플과 충돌) | **답습 — 버린다** |
  | 점선 구분선 | 이해도↑? △ (구획 기능은 유효) | **원리만 계승** — 점선 대신 **우리 시스템의 얇은 실선/여백**으로 |
  | 211×307 비율 | 이해도↑? ✗ 접근성↑? ✗ (**모바일에서 깨짐**, 스펙 못 담음) | **답습 — 버린다** |
  | 세로 카드 아트 자체 | 아이템 **정체성 그 자체** | **계승 — 유일하게 지킬 것** |

  → **계승의 대상은 "아트"이지 "창(chrome)"이 아니다.** 우리가 재현한 건 창이었다.
  이것이 CLAUDE 원칙 "게임 요소는 아이템 아트 영역에만 가둔다"와 정확히 같은 결론이며,
  **모달을 만들 때 그 원칙을 스스로 어긴 것**이 실패 원인으로 보인다.

- URL: https://www.denofgeek.com/games/final-fantasy-pixel-remaster-font-controversy-explained/
- URL: https://www.rpgsite.net/feature/11522-how-to-fix-that-awful-font-in-the-final-fantasy-pixel-remaster-games-on-pc

  폰트가 조정됐다.
- **가져올 지점 `[추론]` — 우리에게 직접 적용**:
  ① **레트로 재해석의 성패는 타이포그래피에서 갈린다.** 색보다 폰트다.
  우리 모달의 "금색 타이틀"도 같은 함정 — 향수를 **색으로 흉내 내려는 시도**였다.
  ② **"흔한 산세리프 + 좁은 자간 + 남는 빈 공간"이 정확히 "구리다"의 정체**다.
  이 조합은 AI 생성 UI의 기본 출력물이기도 하다(안티-AI와 같은 문제).
  ③ 해법은 **활자 크기·굵기·자간의 위계를 명확히 세우는 것**. 우리 design-system의 타이포 스케일을
  모달에도 **동일하게** 적용해야 한다(무신사의 "레이아웃·패턴 표준화"와 같은 처방).

### 6-3. 계승 vs 답습 판정 기준 `[추론]` — 6절 종합

D2R의 "이해도 또는 접근성" 이중 관문에, FF PR의 교훈과 우리 원칙을 더해 **4문 체크리스트**를 만든다.
**원본에서 가져오려는 요소마다 통과 여부를 묻는다. 하나라도 ✗면 답습이다.**

```
① 이 요소가 아이템의 정체성을 운반하는가?     (아니면 그냥 옛날 창틀인가)
② 현대 맥락에서 이해도나 접근성을 높이는가?     (D2R 기준 — 대비·가독·조작성)
③ 우리 디자인 시스템의 토큰으로 표현 가능한가?  (불가능하면 그건 이물질이다)
④ 모바일·다크모드·확대에서 살아남는가?         (고정 픽셀 창은 여기서 죽는다)
```

- **계승의 올바른 형태 `[추론]`**: 원본을 **인용**하는 것이지 **복제**하는 게 아니다.
  구체적으로 — 원본의 색을 쓰는 대신, **아트 영역 안쪽에만** 원본을 연상시키는
  **어두운 배경 슬롯**을 두고, 그 바깥(제목·스펙·가격·CTA)은 **전부 우리 커머스 시스템**으로 처리한다.
  이러면 사용자는 아트를 볼 때 향수를 느끼고, 결정할 때는 신뢰할 수 있는 커머스 UI를 본다.
  ※ 프로젝트 결정로그에 이미 "아트 슬롯 딥 글로우" 방향이 있다면 이 결론과 정합적이다 —
  **딥 글로우를 아트 슬롯 안에 가두는 것**이 핵심이다.

## 7. 사용자 제시 두 배치안 — 실제 레퍼런스 짝짓기

### 안1: 좌 = 카드(아트) / 우 = 마감·입찰 정보, **좌우 세로 길이를 맞춤**

```
데스크톱
┌───────────────────────┬───────────────────────────┐
│                       │  아이템명 · 등급           │
│                       │  ───────────────────────  │
│                       │  마감 카운트다운           │
│      [ 카드 아트 ]     │  ───────────────────────  │
│      (확대 표시)       │  시작가 / 현재가 / 즉시구매 │
│                       │  ───────────────────────  │
│                       │  [   입 찰 하 기   ]       │
│                       │  판매자 정보               │
└───────────────────────┴───────────────────────────┘   ← 높이 일치
┌─────────────────────────────────────────────────────┐
│  아이템 스펙 · 입찰 이력 (하단으로 밀림)               │
└─────────────────────────────────────────────────────┘
```

**해당 레퍼런스**

| 사례 | 근거 | 어떻게 쓰는가 |
|---|---|---|
| 무신사 장바구니 좌우 분할 `[설명 기반]` | 뉴스룸 | 좌=대상 나열 / 우=금액·혜택 요약. **"좌 대상 / 우 숫자"의 국내 실물** |
| 일반 커머스 PDP 2단 + 우측 스티키 `[설명 기반]` | Divi/CSS-Tricks | 우측 구매 컬럼을 `sticky`로 고정 |
| OpenSea `[직접 관찰 — 부분]` | opensea.io | 이미지와 가격/액션을 상단에 병치(컬럼 배치 미확인) |

**잘 작동하는 조건**
- 좌측 이미지가 **컬럼 폭을 실제로 채울 때.** 커머스가 이 구조를 쓰는 이유는 사진이 크기 때문이다.
- 우측 정보량이 **좌측 높이와 우연히 비슷할 때.**

**무너지는 지점 `[추론]` — 우리에게 치명적**
1. **"세로 길이를 맞춘다"는 제약이 함정이다.** 50×93 아트를 우측 정보 높이만큼 늘리려면
   **과확대(→ 뭉개짐, 3-4의 전략 A = 최악)** 하거나 **아트 주변에 의미 없는 여백을 억지로 채워야** 한다.
   양쪽 다 "구리다"의 직접 원인이다.
2. **반대로 우측을 좌측에 맞추려면 정보를 줄여야** 한다 → 스펙이 하단으로 밀려나고,
   사용자는 **스펙을 보려고 스크롤 → 가격/마감이 시야에서 사라짐** → 결정이 끊긴다.
3. **`position: sticky`가 무력화된다.** 스티키는 부모 컬럼에 스크롤 여유가 있어야 붙는데,
   높이를 딱 맞추면 여유가 0이다. **데스크톱 상시 노출 수단(4-4)을 스스로 포기하는 셈.**
4. 좌우 높이 일치는 **콘텐츠 길이가 가변인 실서비스에서 유지 불가능**하다
   (스킬 3줄짜리 아이템 vs 8줄짜리 아이템).

### 안2: 카드 + 아이템 스펙을 **가로로 나란히**, 입찰 정보는 **하단 전폭**

```
데스크톱
┌───────────────┬─────────────────────────────────────┐
│               │  아이템명 · 등급 배지                │
│  [ 카드 아트 ] │  타입 / 레벨 / 속성 / 스킬           │
│               │  골드포스 잔여                       │
└───────────────┴─────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│  마감 카운트다운 │ 시작가·현재가·즉시구매가 │ [입찰하기] │  ← 전폭
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│  입찰 이력 (표, 전폭)                                 │
└─────────────────────────────────────────────────────┘
```

**해당 레퍼런스**

| 사례 | 근거 | 어떻게 쓰는가 |
|---|---|---|
| **Steam 커뮤니티 마켓** `[직접 관찰]` ★ | steamcommunity.com | **상단 2단(좌: 이미지+이름+등급+속성 / 우: 가격·그래프·구매) + 하단 전폭 테이블.** 안2의 실물 |
| Steam 2026 개편 방향 `[설명 기반]` | gamermarkt / pcgamer | **더 넓은 레이아웃 + 전폭 그리드**로 진화 — 안2 방향에 대한 진화적 지지 |
| OpenSea Traits/Activity 승격 `[직접 관찰 — 부분]` | opensea.io | 속성과 거래이력을 최상위 단위로 |

**잘 작동하는 조건 `[직접 관찰 근거]`**
- **이미지가 작아도 성립한다.** Steam이 증명한다 — 좌단을 이미지 혼자 채우지 않고
  **이름·등급·설명·속성이 함께 채운다.** 우리 아트가 작다는 약점을 **구조로 상쇄**한다.
- **표가 전폭을 얻는다.** 입찰 이력은 열이 여럿(시각·입찰자·금액)이라 전폭이 맞다.
- **좌우 높이를 맞출 필요가 없다** → 과확대 압력이 사라진다.

**무너지는 지점 `[추론]`**
1. **가격·마감·CTA가 스크롤 아래로 내려간다.** 안1이 상단 우측에서 확보하던
   "폴드 위 결정 정보"를 잃는다. → **전폭 입찰 바를 `position: sticky`로 만들어야 해소된다.**
2. 상단 2단이 **가로로 길어지면** 아트와 스펙이 멀어져 시선 이동이 커진다 → **최대 폭 제한 필요.**
3. Steam은 매물이 많아 하단 테이블이 페이지의 주인공이지만, **우리는 입찰 이력이 0건일 수 있다** →
   빈 상태(empty state)에서 하단이 휑해진다. **빈 상태 설계가 필수.**

## 8. FinalCall 적용 권고

### 8-1. 안1 vs 안2 — 결론: **안2 채택**(단, 하단 입찰 바를 스티키로)

**근거 세 가지.**

1. **관찰된 실물이 안2 편에 있다.** `[직접 관찰]` 등급의 증거는 Steam 하나뿐인데,
   그것이 **"작은 아이템 아트 + 조밀한 스펙 + 거래 데이터"**라는 **우리와 동일한 조건**에서
   실제로 채택한 구조가 안2다. 안1을 지지하는 커머스 사례들은 **모두 큰 사진이 전제**여서
   우리 조건으로 이전되지 않는다.
2. **안1의 "좌우 높이 일치" 제약이 실패의 재생산 장치다.** 50×93 아트로 우측 높이를 채우려면
   과확대(뭉개짐)나 억지 여백밖에 없고(3-4 전략 A), 이는 **이미 두 번 나온 "구리다"의 구조적 원인**과
   일치한다. 안2는 이 제약 자체를 제거한다.
3. **안1은 데스크톱의 상시 노출 수단을 파괴한다.** 높이를 맞추면 `sticky`가 붙을 여유가 사라진다(4-4).
   반면 안2의 전폭 입찰 바는 **`sticky`와 자연스럽게 결합**해, 스크롤 어디서든
   현재가·잔여시간·CTA가 남는다 — **경매에서 이건 편의가 아니라 정확성 요구다**(4-1).

> **안1의 유일한 장점**(폴드 위에 결정 정보가 있다)은 **안2 + 스티키 바로 완전히 흡수된다.**
> 반대로 안2의 장점(높이 자유·전폭 표·스펙 근접)은 안1에서 얻을 수 없다. **비대칭이다.**

**세부 지침**
- **아트 확대는 정수배로만**(2x/3x). 뭉개지면 그 순간 싸구려다(3-4).
- **아트 슬롯은 어둡게, 그 바깥은 전부 라이트 커머스.** 게임색의 경계선은 **슬롯 테두리**다(6-3).
- **스펙은 데스크톱에서 펼친 상태 기본.** 접는 건 모바일. (Steam은 접었지만, 우리는 스펙이
  좌우 균형의 유일한 수단이라 펼쳐야 좌단이 채워진다 — Steam과 다른 판단인 이유는 아트 방향 차이.)
- **스티키 바 3요소**: 현재가 / 잔여시간 / 입찰 CTA (4-1의 치환표).
  `tabular-nums` + 고정 높이로 숫자 변동 시 흔들림 방지.
- **표는 전폭**. 좁은 컬럼에 넣지 않는다.
- **입찰 이력 빈 상태**를 반드시 설계한다("아직 입찰이 없습니다 — 첫 입찰자가 되어보세요" 류).
  안2의 알려진 약점(7절)이다.

### 8-3. 모바일 권고 구조 — **접는 게 아니라 다시 짠다**

```
┌───────────────────────────┐
│ ← 아이템명                 │
├───────────────────────────┤
│      ┌──────────┐         │
│      │ 카드 아트 │  ← 탭하면 
│      │          │     확대 시트
│      └──────────┘         │
│   등급 배지 · 타입 · 레벨   │
├───────────────────────────┤
│ ▾ 아이템 스펙        (접힘) │  ← accordion, 기본 접힘
│ ▾ 입찰 이력 12건     (접힘) │  ← 표 아님. 카드 리스트
│ ▾ 판매자 정보        (접힘) │
├───────────────────────────┤
│         (본문 스크롤)       │
│                           │
└───────────────────────────┘
┌───────────────────────────┐
│ ▣ FIXED BOTTOM BAR         │
│  04:32 남음   1,240,000 G  │
│  [      입찰하기       ]   │  ← 탭 → 바텀시트
└───────────────────────────┘
```

**데스크톱과 다르게 가져가는 것**(단순 열 접기가 아닌 지점)

| 항목 | 데스크톱 | 모바일 | 근거 |
|---|---|---|---|
| 구매 액션 상시 노출 | 전폭 스티키 바 | **하단 고정 바**(`fixed`) | 4-1, 4-4 |
| 입찰 금액 입력 | 인라인 | **바텀시트로 승격** | 4-2, 5-2 |
| 입찰 이력 | **표(table)** | **카드 리스트** — 표를 접으면 가로 스크롤 지옥 | 4-3 |
| 아이템 스펙 | 펼침 | **아코디언 접힘** | 4-4 |
| 아트 | 인라인 확대 | 탭 → **확대 시트** | 5-4 |
| 마감 표현 | 절대 시각 우선 | **상대 시간 우선**(공간 부족) | 1-4 |

**하단 바 구현 규칙**(4-1의 안티패턴 회피 — 그대로 준수)
- `IntersectionObserver`로 본문 CTA 관측 → 벗어나면 표시. **스크롤 리스너·픽셀 임계값 금지.**
- `transform: translateY` + `opacity`만 애니메이션(150~200ms). **`height`/`top` 금지(CLS).**
- 페이지 하단에 **바 높이만큼 패딩 미리 확보**.
- 탭 타겟 **최소 44×44px**, 대비 **4.5:1 이상**.
- 바가 나타날 때 **포커스를 빼앗지 않는다**.
- **본문의 값과 바의 값이 어긋나면 안 된다** — 현재가·잔여시간은 단일 소스에서 구독.

### 8-4. 모달 권고안 — 형태 · 톤 · 모바일

**① 역할을 둘로 쪼갠다 (5-1·5-3의 결론)**

| | **카드 정보 모달**(정보) | **입찰 시트**(액션) |
|---|---|---|
| 목적 | 아트 확대 + 정체성 확인 | 금액 결정 |
| 담는 것 | 확대 아트 · 이름 · 등급 · 타입/레벨 · **핵심 속성 3~4개** | 현재가 · 최소입찰가 · 즉시구매가 · 잔여시간 · 입력 |
| **안 담는 것** | **스펙 전량 · 가격 · 입찰 CTA** | 아이템 스펙 |
| 탈출구 | **[상세 보기]를 명확히** (Baymard 권고) | [취소] |
| 트리거 | 아트 클릭/탭 | 입찰 CTA |

> **핵심**: 기존 모달이 실패한 건 톤 이전에 **역할 과부하**일 가능성이 크다.
> Baymard가 스펙 중심 상품의 퀵뷰에서 관측한 실패 형태와 정확히 일치한다(5-1).
> **"작은 창에 다 넣기"는 원본(211×307)의 제약을 상속한 것이지 우리의 요구가 아니다.**

**② 톤 — 계승은 아트 슬롯 안에서만 (6-3 체크리스트 적용)**

- ❌ **버릴 것**: 남색 `#001C33` 배경 / 금색 타이틀 / 점선 구분선 / 211×307 고정 비율.
  4문 체크리스트를 통과하지 못한다(정체성 운반 ✗, 이해도·접근성 ✗, 토큰화 ✗, 모바일 생존 ✗).
- ✅ **지킬 것**: **세로 카드 아트 그 자체.** 그리고 아트를 담는 **어두운 슬롯**.
- ✅ **모달의 크롬(배경·제목·구분선·버튼)은 100% 우리 커머스 시스템**:
  라이트 배경, 그레이 기반, 블랙 CTA, 퍼플은 액센트만.
- ✅ **타이포 위계를 design-system 스케일로 통일**한다. FF Pixel Remaster의 실패는
  "흔한 산세리프 + 좁은 자간 + 남는 빈 공간"이었다(6-2) — **정확히 "구리다"의 정체**이며
  안티-AI 위반과 같은 증상이다. 크기·굵기·자간의 대비를 분명히 세운다.
- ✅ **여백을 채우려 하지 않는다.** 비어 있음을 견디는 것이 에디토리얼 톤이다(3-4).

**③ 형태 — 디바이스별**

```
데스크톱: 중앙 모달                    모바일: 바텀시트 (가로 배치)
┌────────────────────────────┐        ┌───────────────────────────┐
│                        [X] │        │            ▬▬▬            │ ← 그랩 핸들
│  ┌────────┐  아이템명       │        │                       [X] │
│  │        │  등급 배지       │        │  ┌──────┐  아이템명       │
│  │  아트   │  ──────────    │        │  │      │  등급 배지       │
│  │ (어두운 │  타입 · 레벨    │        │  │ 아트  │  타입 · 레벨    │
│  │  슬롯)  │  핵심 속성 3~4  │        │  │      │  핵심 속성 3~4  │
│  └────────┘                │        │  └──────┘                │
│                            │        │  [    상세 보기    ]      │
│         [   상세 보기   ]   │        └───────────────────────────┘
└────────────────────────────┘         ↑ 아트가 세로형이라 가로 배치가
   ↑ 배경 스크림, ESC/외부클릭 닫기        시트 높이를 낮춘다 (5-4)
```

- **모바일은 중앙 모달이 아니라 바텀시트**(5-4). **그랩 핸들 + 보이는 X 버튼 + 뒤로가기로 닫힘**(4-2 NN/g).
- **바텀시트 안에서 아트를 세로로 스택하지 않는다.** 세로형 아트라 시트가 불필요하게 높아진다 →
  **가로 배치**(안2의 축소판)로 상세 페이지 상단과 **같은 언어**를 쓴다(무신사 "패턴 표준화").
- **시트를 겹쳐 쌓지 않는다**(NN/g). 정보 모달 → 입찰 시트로 **직접 넘어가지 않고**,
  정보 모달은 [상세 보기]로 닫으며 페이지에 위임한다.
- **경매 상세 페이지 자체는 절대 모달/시트로 만들지 않는다.** NN/g가 명시적으로 금지하며,
  딥링크·공유·뒤로가기·새로고침이 성립해야 하는 대상이다(4-2).

### 8-5. 남은 열린 항목 (이 문서가 결정하지 않는 것)

- **마감 임박 입찰 시 연장 규칙**(1-3, 1-4) 도입 여부 — **백엔드 계약·도메인 규칙 사안**이며
  `bid-domain-spec` 및 **게이트2** 영역이다. 다만 도입하든 안 하든 **"연장 여부를 UI에 고지"**는
  프론트 요구사항으로 남는다.
- **실시간 갱신 방식**(폴링 / SSE / WebSocket) — 계약 사안. 단 **"연결 끊김을 사용자에게 보여줘야 한다"**는
  UX 요구는 확정적이다(2-4).
- 임박 3구간의 **정확한 임계값**(예: 24h / 1h / 5m) — 데이터·정책 사안.
- 퍼플을 임박 신호로 승격시키는 안(1-6)은 **디자인 게이트 승인 대상**이다.
