# 디자인(UX/UI) 파트 지침 (D-071, 지침 유형)

> UI 구현 정본은 `docs/spec/frontend-ui-system-contract.md` v1.1이다. 이 문서의 `primary` 예시는 일반 원칙 설명이며 FinalCall 구현은 브라이트 스틸/gold 역할형 token과 고정 commerce chrome 경계를 따른다.

프로덕트 디자인 역할의 산출물·프로세스 규약. 협업 규약은 common/rules.md, 형식은
common/templates.md를 따른다. 기획(설계, P-xxx)과 구분 — 기획=도메인/스펙, 디자인=UI/UX 시각·상호작용.

## 1. 역할과 관계

- 책임: 프론트가 좋은 웹을 만들도록 디자인 시스템·UI 컴포넌트 스펙·UX 흐름·접근성·비주얼 방향을
  산출한다. 프론트의 상류다.
- 흐름(D-091 · **D-097**): 기획(P) 계약 → **디자인 목업**(빠르게·완성 아님, 산출 = 목업 + 계약 델타)
  → 백엔드 코드 → **디자인 세부 완성** ∥ 보안 → QA → 총괄 G4-n 판정. 상세 프로세스 규칙은 11절.
- 단계 구분: **목업은 완성이 아니다.** 목업은 판단을 받으려고 내고, 세부 완성이 인계 기준선이다.
  **프론트 구현은 세부 완성 뒤에 들어간다**(7절 핸드오프, 사용자 지시 2026-07-17).
  착수 시점 배치는 총괄 소관이며 이 줄은 전사다.
- 기준 위계: api-contract(계약)가 최상위. 디자인 산출물은 참고 지침이며 계약·도메인 규칙과
  충돌하면 계약이 우선. 계약에 없는 화면·데이터를 임의로 가정하지 않는다(공백은 총괄 결정 요청).
- 착수 조건: 계약(G3) 확정 후 화면 설계 가능(현재 G3 통과 — 착수 가능).

| ux-flows.md | 화면 맵·라우트, 도메인별 주요 플로우, 와이어프레임 기술(레이아웃·영역) |

| decision-log.md | 디자인 결정(U-xxx): 토큰 스케일·컴포넌트 규칙·비주얼 방향 등 |

## 3. 디자인 시스템·토큰 (Tailwind 1:1)

디자인 토큰을 "공용 언어"로 삼는다 — 디자인의 토큰명과 프론트 Tailwind 유틸이 같은 이름을
쓰면 번역이 사라진다(예: 토큰 `primary` ↔ `bg-primary`). 프론트 CLAUDE.md 5절 "전역 CSS는
토큰 정의로 한정"과 연결된다.

- 색: 브랜드(primary/secondary)·의미색(success/warning/danger/info)·중립(gray 스케일)·표면/텍스트.
  각 색은 라이트(+다크 여지) 값과 용도 명시. 대비는 6절 준수.
- 타이포: 폰트 패밀리·스케일(제목/본문/캡션 크기·행간·굵기). rem 기준.
- 간격·반경·그림자·모션: 4/8px 배수 스페이싱 스케일, radius·shadow·transition 토큰.
- 산출은 Tailwind config에 매핑 가능한 형태(theme.extend 키)로 표로 제시한다.

## 4. UI 컴포넌트 스펙 (핸드오프 핵심)

프론트가 질문 없이 구현하도록, 컴포넌트마다 아래를 명세한다(핸드오프 표준).

- 상태: default / hover / focus / active / disabled / error / loading 전부.
- 변형: size(sm/md/lg 등)·variant(primary/ghost/outline 등)·상태 조합.
- 반응형: 브레이크포인트별 거동(Tailwind sm/md/lg/xl 기준). 모바일 우선.
- 해부: 사용 토큰(색·간격·타이포)·여백·아이콘·상호작용(키보드 포함).
- 접근성: 역할(role)·라벨·포커스 순서·키보드 조작(6절).

우선 컴포넌트(경매 도메인 기준): 버튼, 입력/폼, 카드(매물), 리스트/그리드, 모달/다이얼로그,
토스트/알림, 페이지네이션(cursor), 뱃지/상태칩, 카운트다운(마감), 금액 표시.

## 5. UX·화면 플로우

- 화면 맵: 라우트 ↔ 화면 ↔ 계약 엔드포인트 대응(api-contract 기준).
- 주요 플로우(계약 기반): 경매 목록→상세→입찰(실시간 최고가·마감 카운트다운), 즉시구매,
  고정가 구매, 충전→교환→거래, 인벤토리·임시보관, 내 거래 내역, 로그인·가입.
- 각 플로우: 진입점·단계·상태(로딩/빈/에러)·엣지케이스(잔액 부족·마감·중복). 빈 상태·에러
  카피는 ux-copy 관점 포함.

## 6. 접근성 (WCAG 2.1 AA)

- 색 대비: 본문 4.5:1, 큰 텍스트 3:1 이상. 색만으로 정보 전달 금지(상태는 아이콘/텍스트 병기).
- 키보드: 전 인터랙션 키보드 도달·조작 가능, 포커스 가시성 명확, 논리적 포커스 순서.
- 터치 타깃: 최소 44x44px 권장.
- 시맨틱: 적절한 role·aria-label, 폼 라벨 연결, 이미지 대체텍스트.
- 모달·토스트: 포커스 트랩·복귀, 스크린리더 알림(aria-live).

## 7. 프론트 핸드오프

- 산출물 경로를 프론트에 정보 공유/작업 지시로 전달(파일 버스). 프론트는 이를 근거로 구현 계획.
- 조인트 리뷰: 도메인 UI 구현 전 디자인 스펙을 프론트와 한 번 맞춘다(비동기 — 프론트가 스펙
  열람 후 이견은 결정 요청). 계약 영향 발견 시 계약 변경 요청(6절)으로 총괄 격상.
- 토큰·컴포넌트 명칭은 프론트 구현과 1:1 — 변경 시 정보 공유(D-024).

## 8. 도구 (사용 의무)

설치된 design 플러그인 스킬을 산출에 사용한다. 감으로 대체하지 않는다.

| 언제 | 스킬 |
|---|---|
| 컴포넌트 스펙 작성·토큰 감사 | design-system |
| 목업·산출물을 낸 뒤 자기 검토 | design-critique |
| 대비·키보드·터치 타깃 검증 | accessibility-review |
| 버튼·에러·빈 상태·확인 문구 | ux-copy |
| 프론트 인계 스펙 | design-handoff |
| 사용자 조사·정리 | user-research · research-synthesis |

- 스킬 결과를 그대로 싣지 않는다. 이 문서·design-system·계약과 충돌하면 이쪽이 우선이다.
- 스킬을 쓴 산출물은 완료 보고에 어느 스킬을 썼는지 1줄 남긴다.

## 9. 규약

- 쓰기는 docs/ux/ 폴더만. 타 폴더는 필요 시 열람(pull, 사유·출처, D-016).
- 결정은 U-xxx(1결정=1번호, 상태 라벨, 가이드 4절). 계약·프론트 규약과 충돌 제안은 근거·격상 필수.
- 총괄로 보내는 프롬프트는 `[디자인 → 총괄]` 형식, 끝에 "신규 발번 ID: ..." 1줄.
- 매 응답 끝 사용자 브리핑 4줄(templates 16). 문서 이모지 금지. 제안엔 이유·레퍼런스 병기.
- git 커밋 실행은 사용자 단일(D-061) — 완료 보고 말미에 `docs(디자인): 제목` 커밋 메시지만 제안.

## 11. 프로세스 규칙 (D-072)

디자인 작업 시 아래 3규칙을 준수한다. 추후 디자인 파트 핸드오프·재개 시에도 이 절을 확인한다.

1. 기획 경유: 화면·플로우·도메인 표현(등급·아이템 속성·상태 등) 설계는 기획(도메인/스펙 소유)과
   정합·협의를 거친다. 도메인 연계 결정은 기획 검토 필수 — 임의 가정 금지, 공백은 기획 확인 또는
   총괄 결정 요청으로 격상.
2. 시각 예시 의무: 결정 요청·제안 시 텍스트 스펙만이 아니라 사용자가 눈으로 확인할 수 있는
   시각 예시를 함께 낸다. navigation·footer·button·화면·주요 컴포넌트는 실제 AppShell·token·공용
   컴포넌트를 재사용한 dev-only `/__design/<scenario>` 워크벤치를 390·1280px에서 제시한다. 기존
   `docs/ux/mockups/*.html`은 역사 참고로 동결하며 신규 디자인 게이트 증거로 쓰지 않는다.
3. 최종 결정 주체 — **D-091로 개정됨(2026-07-15, U-017 escalated-as).** 비주얼·UX는 **디자인이
   자율 확정한다.** 착수 전 총괄·사용자 사전 승인은 받지 않는다. 사용자의 최종 결정권은
   **사후 변경 요청권**으로 유지된다(완성 산출물에 사용자가 변경 사항을 통보 → 디자인이 반영).
   구 규칙("비주얼·UX 최종 결정은 총괄+사용자")은 SUPERSEDED — 승인 게이트가 결정을 앞당기지
   못하고 대기만 만든 것이 실증됐다(비주얼 방향이 047 이래 미결로 방치, 그동안 디자인은 색 없는
   구조 작업만 가능). 되돌리기 비용도 낮다(토큰 값 교체로 수렴, skeleton-plan [4] "값만 교체").

4. AI 기본값 금지: 색·간격·형태·타이포를 관례나 감으로 정하지 않는다. 근거는 원게임 자산 실측
   또는 계산이며, 둘 다 없으면 정하지 않고 공백으로 남긴다(3절·6절). 아래는 근거 없이 나오는
   대표 형태이며 산출물에 넣지 않는다.
   - 팔레트 밖 색 — 보라·인디고 그라데이션, 파스텔 blob 배경, 유리모피즘
   - 그림자·큰 라운드로 만드는 "떠 있는 카드" — 다크에선 표면 밝기 차와 테두리가 층을 만든다(4절)
   - 장식용 이모지 아이콘, 중앙정렬 히어로 + 큰 카피
   - 계산하지 않은 대비비·간격 숫자 — 그 숫자도 주장이다
   판정 기준 1문: **"이 값이 어디서 왔는지 한 줄로 댈 수 있나?"** 못 대면 그게 AI 기본값이다.

흐름(D-091 반영): 기획(P)에서 기능 정의·도메인 규칙 수령 → 디자인 자율 설계·확정 → 사용자 사후
변경 요청 시 반영. 규칙 1(기획 경유)·규칙 2(시각 예시 의무)는 유지된다 — 규칙 2는 기획·총괄에
올리는 결정 요청에 계속 적용하되, 결정 요청 자체가 줄어 적용 빈도가 감소한다.
