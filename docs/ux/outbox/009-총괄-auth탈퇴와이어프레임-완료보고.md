# [디자인 → 총괄] 완료 보고: auth 폼 반영 + 탈퇴 확인 UI 4요소 와이어프레임 (072 지시분)

결과: 072 디자인 할당 2건(탈퇴 확인 UI 4요소 표현 / skeleton-plan 토큰 방침 확인)을 완료했다. 함께 기획 회신 024(P-009~011)로 해소된 auth 폼 선행도 와이어프레임에 반영했다. 색 없는 구조 단계이며 비주얼 방향 미확정과 무관하게 진행 가능한 범위다(색값만 잠정, 토큰명·구조 고정).

- `docs/ux/mockups/wireframe-auth.html` (갱신) — 회원가입 4필드화(P-009), 화면 C 가입 성공→로그인 prefill 신설(P-010), legend 미확정 서술 정정

완료 기준 대비:

1. 탈퇴 확인 UI 4요소 — 충족. ① 잔존 잔액(캐시·게임머니 가용·홀드, GET /me/balance, tabular-nums) ② 소멸·복구 불가 경고 ③ 명시 동의 체크(미체크 시 버튼 비활성 + 비활성 사유 문장) ④ MEMBER_002 차단 시 사유 + 다음 행동(경매·입찰·주문 확인 경로). 기능 정의는 screen-spec [3.1-b] 근거, 표현만 디자인 판단(U-012).
2. skeleton-plan [4] 토큰 방침 확인 — 충족. "정본은 docs/ux/design-system.md, 토큰명만 1:1로 옮기고 값은 복제하지 않는다"로 명시돼 있고, element 4색도 design-system [2.3]에 정본 보유(U-010). 값 복제 없음 확인.

디자인 판단 4건(계약·스펙이 요구한 것이 아니라 표현 소관에서 정한 것 — 이견 시 회신):
- 탈퇴 확인을 모달이 아닌 별도 확인 단계 화면으로 둔다. 4요소가 모두 들어가면 모달에 스크롤이 생기고, 파괴적 액션에서 동의 체크가 스크롤 뒤에 숨는 배치는 위험하다.
- 잔액 블록에 홀드(held)를 함께 노출한다. 홀드는 진행 중 입찰을 뜻해 MEMBER_002 차단과 직결되므로 차단을 만나기 전 예고 역할을 한다. 계약 요구사항은 아니다.
- 비활성 버튼 하단에 비활성 사유 문장을 둔다. 비활성 상태만으로는 이유가 전달되지 않는다.
- 차단 카피는 사용자 귀책이 아닌 "사유 + 다음 행동" 톤으로 고정한다(screen-spec [3.1-b] 4의 요구를 카피 규칙으로 승격).

뿌리 점검 (D-085): 이번 처리에서 공백·결함 2건을 발견했고 같은 원인이 다른 층에도 있는지 점검했다.
- 발견 1 — 내 decision-log에서 U-012 헤딩이 유실돼 있었다. 원인은 ee4e07c(U-013 작성)가 U-012 헤딩 줄을 덮어쓴 것. 같은 원인(항목 삽입 시 인접 헤딩 침범)이 다른 층에 있는지 `^## U-0` 헤딩 수를 세어 확인했고 나머지 12건은 정상이다. 본 건은 디자인 폴더 한정이며 타 역할 로그 점검은 소유 역할 소관이라 통지만 남긴다.
- 발견 2 — `docs/ux/design-system.md` 근거 줄이 계약 v1.2로 stale하다(현재 v1.4). 같은 계열의 비동기화가 D-089가 겨냥한 문제와 동일하다. 실질 델타(v1.3 엣지 오류·v1.4 회원 리소스)의 design-system 반영 여부는 별도 판단이 필요해 이번 범위에 넣지 않았다 — 지시 주면 처리한다.
