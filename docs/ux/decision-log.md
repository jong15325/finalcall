## U-004. 아이템 등급(grade)·속성(element)에 색 토큰 체계 부여

상태: SUPERSEDED(→ U-010) · 소유: 디자인 · 관련: relates-to erd(item_template.element), superseded-by U-010(D-073 등급 축 제거) · 2026-07-14

결정(제안)
- 속성(element 4종: 물/불/흙/바람)에 고정 색 매핑(물=info-blue, 불=danger-red, 흙=amber, 바람=success-green). 등급(grade)은 게임 레어리티 관례의 티어 색 스케일(grade-1~5: gray→green→blue→purple→gold)로 확장 가능하게 정의.

이유
- element·grade는 검색 필터·아이템 카드의 핵심 시각 축(erd §7.7 인덱스). 색 코드는 스캔성을 크게 높인다. element는 4종 확정이라 즉시 매핑 가능.

미확정 참고
- erd `grade`는 INT 축으로 값 목록이 스펙에 명시되지 않음. 실제 grade 단계 수·명칭 확정 시 색 매핑을 1:1 고정해야 함(기획 확인 대상). 확정 전까지 5티어는 잠정.

## U-013. 와이어프레임 소유 경계 확정 — 기능 정의=PF, 레이아웃 이후=디자인

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-077·U-011, refines U-012, 사용자 결정 · 2026-07-14

결정
- 화면 와이어프레임을 두 층위로 나눈다: (1) 기능 정의(화면에 담길 요소·필드·플로우·에러) = 프론트 기획(PF, screen-spec.md 소유), (2) UI 레이아웃(요소 배치·반응형·상태) 이후 = 디자인. 디자인은 PF 기능 명세를 근거로 레이아웃 와이어프레임 → 비주얼로 이어간다.

이유
- 와이어프레임은 조직마다 기획/디자인 소유가 갈리는 그레이존. 사용자가 현 프로젝트 지침(디자인=UI/UX)대로 (2)를 디자인에 배정 확정. PF 기능 명세가 선행하므로 중복 없이 레이아웃부터 착수 가능.

기각된 대안
- PF가 레이아웃 와이어프레임까지 소유(국내 웹 기획 관행): 사용자가 현 지침 유지 선택.

## U-012. 디자인 범위 분담 — 게임 자산 차용 vs 웹 레이어 자체 디자인

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to U-010·D-073, 사용자 결정 · 2026-07-14

결정
- 게임 내 비주얼(아이템 카드·인벤토리·아이템 데이터 표현)은 사용자가 게임 디자인을 그대로 차용하고 해당 이미지를 직접 제공한다(디자인이 새로 그리지 않음).
- 디자인이 담당하는 것: (1) 게임 카드 이미지를 감싸는 웹 상거래 카드(이미지 슬롯 + 가격·카운트다운·입찰 등 게임에 없는 웹 정보), (2) 회원가입·로그인·지갑·판매등록 등 게임 외 웹 페이지 전체, (3) 공통 웹 요소(버튼·폼·모달·토스트·네비).
- 기획(PF)과의 정합 범위: 페이지에 담을 필드·플로우(무엇을)만. 레이아웃·색·표현(어떻게 보이는가)은 디자인.

이유
- 게임 자산 차용은 원본 감성 유지·개발 속도에 유리. 단, 게임 카드는 가격·마감·입찰 같은 상거래 정보를 담지 않으므로, "게임 이미지 + 웹 상거래 정보" 결합은 디자인이 설계해야 함(이음새).

미확정 참고
- 차용 게임 카드 아트에 등급(S)·채널링등급 표기가 포함되나, 도메인은 무등급(D-073). 웹 상엔 기능적 등급 필드가 없고 이미지상 표기는 장식으로만 존재 — 기획/총괄에 정보 공유(outbox/006), 문제 시 격상.

## U-014. D-082~085 파생 작업 순서 체계 적용 — 이의 제기를 의무로 전환

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-082·D-083·D-084·D-085, management/outbox/079 · 2026-07-15

결정
- 총괄 지시가 디자인의 진행 중 작업과 충돌하면 **따르기 전에 이의를 제기한다**(D-083). 침묵은 규약 위반으로 취급한다. 부수 적용: 착수된 디자인 작업은 완주가 기본값(중단·선점은 총괄 근거 제시 시에만 성립), 파트 내 유닛 순서(어느 화면·컴포넌트를 먼저)는 디자인 자율(D-084), 근거 인용 없는 착수 지시는 이의 대상(D-082).
- 산출물 형식: 작업 지시 발신 시 `근거(인용)` 필드, 공백·결함 처리 완료 보고 시 `뿌리 점검` 필드를 첨부한다(templates 3·4).

이유
- 종전 "이의 권한"은 쓰이지 않아 실패했다(079 사례: 백엔드가 권한을 갖고도 침묵 → 사용자가 발견). 디자인은 레이아웃·표현의 현장 실측을 쥔 쪽이라, 총괄의 문서 수준 추론과 어긋나는 상황이 구조적으로 발생한다 — 침묵하면 그 정보가 소실된다.

기각된 대안
- 관망 후 문제 발생 시 보고: D-083이 금지하는 침묵 그 자체. 재작업 비용이 이의 비용보다 항상 크다.

## U-015. D-086·D-087·D-089 적용 — 탐색 방법 명시·절 참조 대괄호·결정 로그 `집행` 필드

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-086·D-087·D-089, extends U-014, management/outbox/086·088 · 2026-07-15

결정
- 디자인 산출물에 3건을 적용한다. (1) D-086 — "없음"·"N건" 같은 부재·수량 주장을 근거로 쓸 때 탐색 방법 1구를 함께 적는다(예: 수신 스캔은 패턴 3종 명시). 중대 결론은 호스트 Read/Grep으로 교차검증한다. (2) D-087 — 절 참조에 `§`를 쓰지 않고 대괄호 `[N]`·`[N.M]`으로 적는다. **앞으로만** — 기존 `§` 표기는 유효하며 교체만을 위한 개정은 하지 않는다. (3) D-089 — 신규 결정 로그 항목에 `집행` 필드를 채운다. 공란 금지, 소급 기재 없음.
- D-088(Claude Code 반환 경로)은 **디자인 비대상** — 디자인은 Claude Code를 쓰지 않는다.

이유
- 셋 다 형식에 내장해 점검을 부산물로 강제하는 장치라 디자인 산출물에도 비용 없이 얹힌다. 특히 D-086은 디자인의 수신 스캔에 직결된다 — 실제로 직전 스캔에서 `→ 전역할`(붙여쓰기)만 훑어 `[총괄 → 전 역할]`(띄어쓰기) 헤더를 놓칠 뻔했고, 그때 "신규 수신 없음"이라 보고했다면 패턴 결함이 근거로 둔갑했을 것이다. 부재 주장에 방법을 붙였으면 그 자리에서 드러난다.
- D-089는 design-system.md 근거 줄이 계약 v1.2로 stale하게 방치된 것과 같은 계열의 비동기화를 겨냥한다.

기각된 대안
- 규약 인지만 하고 로그 미발번: U-008·U-014와 불일치. 디자인 산출물 형식이 실제로 바뀌므로 근거가 남아야 한다.

집행

## U-016. 비주얼 방향 = 원게임 UI 스킨 전면 차용 (A/B/C 폐기) — 실행은 이미지 부착이 아니라 토큰 추출·CSS 재현

상태: ACCEPTED · 소유: 디자인 · 관련: supersedes U-009·outbox/004(A/B/C 제시), relates-to U-005·U-012·D-067·D-072, 사용자 결정 · 2026-07-15

결정
- 웹 전체의 비주얼 방향을 **원게임(SurvivalProject) UI 스킨 전면 차용**으로 확정한다(사용자 직접 결정, D-072 "비주얼 최종은 총괄+사용자"). 기존 A/B/C 제시(Dark Arena 등, outbox/004·U-009)는 폐기한다.
- **실행 방식은 게임 UI 이미지를 그대로 부착하는 것이 아니라, 게임의 색·형태 언어를 design-system 토큰으로 추출해 웹 컴포넌트로 CSS 재현하는 것**으로 한다. 차용 대상은 시각 언어(팔레트·테두리·패널 형태·타이포 위계)이지 비트맵 자산이 아니다.
- 예외 — 실제 비트맵으로 차용하는 것은 **아이템 아트 스프라이트 한정**(U-012 이미지 슬롯). 크롬(패널·탭·버튼)은 CSS 재현.

이유
- 제공된 게임 버튼 자산은 **텍스트가 이미지에 구워져 있다**(`상점에 팔기`·`포스충전`·`기본특징`·`합성조건`). 웹에는 게임에 없는 카피가 필요하다(`로그인`·`입찰하기`·`회원 탈퇴`·`충전하기`·`동의합니다`) — 이 자산으로는 만들 수 없고, 카피마다 새 이미지를 요구하면 확장이 막힌다.
- 텍스트가 이미지에 박히면 스크린리더가 읽지 못한다(accessibility.md 위반). 게임 UI는 고정 해상도 전제라 360px 모바일 우선(와이어프레임 기준)에 그대로 늘어나지 않는다.
- CSS 재현이면 원본 감성을 유지하면서 웹 카피·반응형·접근성·다국어를 모두 살린다. 차용의 목적(원본 감성·개발 속도, U-012 이유)은 시각 언어에서 오지 비트맵에서 오지 않는다.

기각된 대안
- 게임 UI 비트맵을 9-slice로 부착: 버튼 카피 문제를 해결 못 하고(텍스트 구움), 접근성·반응형이 무너진다.
- A/B/C 중 택1 유지(U-009): 사용자가 게임 스킨을 선택해 전제가 소멸.

미확정 참고
- 게임 팔레트 값은 현재 **스크린샷 육안 추정(잠정)**이다 — 원본 자산이 세션에 없어 픽셀 샘플링을 하지 못했다. 정확한 hex는 원본 UI 자산(또는 색상값) 수령 후 확정한다. 토큰명·구조는 이 확정과 무관하게 먼저 고정할 수 있다(skeleton-plan [4] "값만 교체" 설계와 정합).
- U-005(라이트/다크 양립 토큰 구조)의 유효성은 게임 스킨이 단일 다크 계열이라 재검토 대상 — 구조는 유지하되 라이트 테마를 노출할지는 별건. 본 항목에서 결정하지 않는다.

집행
- `docs/ux/design-system.md` [2] 색 토큰 — 게임 팔레트로 재정의 필요, **미반영**(원본 자산 대기). 반영 전까지 A안 잠정값 유지.
- `docs/ux/mockups/visual-directions.html` — A/B/C 제시물이라 U-016으로 무효화됨, **미반영**(게임 스킨 목업으로 대체 예정).
- `docs/frontend-planning/skeleton-plan.md` [4] — "색값은 잠정 A안, 확정 시 값만 교체" 설계라 구조 변경 불요. 값 교체 시점에 기획 통지 필요(outbox/011로 총괄 통지 완료).
- `docs/ux/outbox/004` — 상태 SUPERSEDED 갱신(반영 완료).

## U-017. 디자인 운영 모드 전환 — 사용자 사전 승인 대기 폐지, 자율 설계 + 사후 변경 요청

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-072(규칙 3 실질 변경 — 총괄 D 발번 필요), D-071, 사용자 결정 · 2026-07-15

결정
- 디자인은 **사용자에게 사전 승인을 묻지 않고 자율 설계**한다. 완성 산출물에 대해 **사용자가 사후 변경 사항을 통보**하는 방식으로 전환한다(사용자 직접 결정, 2026-07-15).
- 상류 입력은 **기획(P)에서 받는다** — 필요한 기능 정의·도메인 규칙을 기획에게 요청해 받고, 그 위에서 표현은 디자인이 자율 결정한다(U-013 경계 유지).
- D-072 규칙 2(결정 요청 시 시각 예시 의무)는 **결정 요청 자체가 줄어들어 적용 빈도가 감소**하나 폐기하지 않는다 — 기획·총괄에 올리는 결정 요청에는 계속 적용한다.

이유
- 사용자 지시: "이제 나한테 물어보지말고 알아서 디자인해줘. 완성이 되면 내가 변경사항을 알려주는게 맞는 것 같아. 이제 디자인은 기획에게 필요한 것을 받아서 알아서 디자인하는 것으로 한다."
- D-072 규칙 3("비주얼·UX 최종은 총괄+사용자")이 실제로는 병목이었다. 비주얼 방향은 047 이래 미결로 남아 있다가 U-016에서야 닫혔고, 그동안 디자인은 색 없는 구조 작업만 가능했다. 사후 리뷰로 바꾸면 진행이 막히지 않으면서 사용자의 최종 결정권은 유지된다(변경 요청 = 거부권).

기각된 대안
- 사전 승인 유지: 사용자가 명시적으로 폐지를 지시했고, 실측상 병목이 증명됐다.

집행
- `docs/ux/design-guide.md` [11](D-072 3규칙 명문화) — **미반영.** D-072는 총괄 소유라 디자인이 개정할 수 없다. **총괄에 D-072 개정(규칙 3) 요청 발신 = ux/outbox/013.** 총괄 D 발번 후 design-guide 반영이 정합.
- 본 항목이 그때까지의 잠정 근거다. 총괄 D 발번 시 상태 줄에 escalated-as 추가.

## U-018. D-090 적용 — 저장소 파일 판단은 호스트 도구 전용, bash 마운트 뷰 판단 금지

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-090·D-086·D-043, extends U-015, management/outbox/092 · 2026-07-15

결정
- 저장소 파일의 **목록·내용·존재·형상·위치·수량 판단은 호스트 도구(Read·Grep·Glob·Edit)로만** 한다. bash 마운트 뷰(`/sessions/.../mnt/...`) 조회 결과를 판단 근거로 쓰지 않는다. bash는 `git`·해시·이미지 디코딩 등 마운트 뷰 형상과 무관한 실행에만 쓴다.
- 부득이 bash 조회를 인용하면 호스트 교차검증 결과를 병기한다(D-086 결합).

이유
- 이번 세션에서 디자인만 **2회** 당했다. (1) `ux/inbox-log.md`의 072·086·088 행이 bash grep에 안 잡혀 미기록으로 보였다 → 호스트 Grep은 17·20·21행에 정상 존재. (2) `wireframe-auth.html`의 `prefill`·`자동 로그인 없음`·`GATEWAY_429`가 bash에 "누락"으로 나왔다 → 호스트 Grep은 전부 존재. 두 번 다 **에러 없이 낡은 내용을 서빙**했다 — 실패 신호가 없어 의심 트리거가 안 걸린다.
- 총괄 관측 5건(실피해 2건: 보안 에러코드 오등재, 기획 erd 구조 파손)과 같은 병이다.

기각된 대안
- D-043(교차검증)으로 충분: stale은 의심 트리거를 주지 않아 "의심했을 때 발동"하는 규칙이 발동하지 않는다. 실제로 디자인의 2건 모두 우연히 결과가 이상해서 잡힌 것이지 규칙이 잡은 게 아니다.

집행
- `docs/ux/inbox-log.md` 수신 스캔 방법 주 — 호스트 Grep 기준으로 갱신(반영 완료).
- `docs/ux/notes/handover.md` 재개 절차 — 호스트 도구 전용 명시(반영 완료).
- 본 결정 이후 디자인의 전 산출물에 적용. 별도 실행 문서 불요(결정 자체가 정본).
