## U-001. 디자인 토큰 명칭을 프론트 Tailwind 유틸과 1:1로 고정

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to F(screen-route-map), frontend/CLAUDE.md 5절 · 2026-07-14

결정
- 토큰명(색·간격·타이포·반경 등)을 Tailwind theme.extend 키와 동일 문자열로 정의한다. 예: 토큰 `primary` ↔ 유틸 `bg-primary`, `surface` ↔ `bg-surface`.

이유
- 디자인-프론트 사이 "번역 레이어"를 없앤다. 프론트 CLAUDE.md 5절(전역 CSS는 토큰 정의로 한정)과 정합. 명칭 변경은 정보 공유(D-024)로 통지.

기각된 대안
- 디자인 전용 명칭 후 프론트 재매핑: 매핑 표 유지 비용·불일치 위험.

## U-003. 본문 폰트 Pretendard + 금액·시간 tabular-nums

상태: ACCEPTED · 소유: 디자인 · 2026-07-14

결정

이유

## U-004. 아이템 등급(grade)·속성(element)에 색 토큰 체계 부여

상태: SUPERSEDED(→ U-010) · 소유: 디자인 · 관련: relates-to erd(item_template.element), superseded-by U-010(D-073 등급 축 제거) · 2026-07-14

결정(제안)
- 속성(element 4종: 물/불/흙/바람)에 고정 색 매핑(물=info-blue, 불=danger-red, 흙=amber, 바람=success-green). 등급(grade)은 게임 레어리티 관례의 티어 색 스케일(grade-1~5: gray→green→blue→purple→gold)로 확장 가능하게 정의.

이유
- element·grade는 검색 필터·아이템 카드의 핵심 시각 축(erd §7.7 인덱스). 색 코드는 스캔성을 크게 높인다. element는 4종 확정이라 즉시 매핑 가능.

미확정 참고
- erd `grade`는 INT 축으로 값 목록이 스펙에 명시되지 않음. 실제 grade 단계 수·명칭 확정 시 색 매핑을 1:1 고정해야 함(기획 확인 대상). 확정 전까지 5티어는 잠정.

## U-005. 라이트/다크 양립 토큰 구조 채택(기본 테마는 총괄 결정 요청)

상태: ACCEPTED · 소유: 디자인 · 관련: escalated-as (기본 테마는 outbox/001 안건 2) · 2026-07-14

결정
- surface/text/border 등 의미 토큰을 라이트·다크 두 값으로 정의해 테마 전환이 토큰 교체만으로 되게 한다. 어느 테마를 기본으로 노출할지는 비주얼 방향과 함께 총괄/사용자 결정.

이유
- 게임·거래 사용자층은 다크 선호가 강하나 자금 신뢰감은 라이트가 유리 — 구조로 양립시키고 기본값만 결정 대상으로 남긴다(되돌리기 저비용).

## U-006. 실시간(최고가·카운트다운) UI를 폴링 전제로 설계

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to F-001(폴링) · 2026-07-14

결정
- 경매 상세의 최고가·남은시간·마감 연장(소프트클로즈)을 폴링 갱신 전제로 설계한다. 갱신 시 낙관적 표시 + 서버 확정 반영, 종료 시 폴링 중지·상태 전환.

이유
- 계약에 실시간 푸시 채널(SSE/WS) 부재, 프론트 F-001이 폴링 채택. 디자인이 푸시를 전제하면 계약·프론트와 어긋남. 채널 도입 시 카운트다운·입찰 피드 컴포넌트는 소스만 교체 가능하게 분리.

## U-013. 와이어프레임 소유 경계 확정 — 기능 정의=PF, 레이아웃 이후=디자인

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-077·U-011, refines U-012, 사용자 결정 · 2026-07-14

결정
- 화면 와이어프레임을 두 층위로 나눈다: (1) 기능 정의(화면에 담길 요소·필드·플로우·에러) = 프론트 기획(PF, screen-spec.md 소유), (2) UI 레이아웃(요소 배치·반응형·상태) 이후 = 디자인. 디자인은 PF 기능 명세를 근거로 레이아웃 와이어프레임 → 비주얼로 이어간다.

이유
- 와이어프레임은 조직마다 기획/디자인 소유가 갈리는 그레이존. 사용자가 현 프로젝트 지침(디자인=UI/UX)대로 (2)를 디자인에 배정 확정. PF 기능 명세가 선행하므로 중복 없이 레이아웃부터 착수 가능.

기각된 대안
- PF가 레이아웃 와이어프레임까지 소유(국내 웹 기획 관행): 사용자가 현 지침 유지 선택.

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to U-010·D-073, 사용자 결정 · 2026-07-14

결정
- 게임 내 비주얼(아이템 카드·인벤토리·아이템 데이터 표현)은 사용자가 게임 디자인을 그대로 차용하고 해당 이미지를 직접 제공한다(디자인이 새로 그리지 않음).
- 디자인이 담당하는 것: (1) 게임 카드 이미지를 감싸는 웹 상거래 카드(이미지 슬롯 + 가격·카운트다운·입찰 등 게임에 없는 웹 정보), (2) 회원가입·로그인·지갑·판매등록 등 게임 외 웹 페이지 전체, (3) 공통 웹 요소(버튼·폼·모달·토스트·네비).
- 기획(PF)과의 정합 범위: 페이지에 담을 필드·플로우(무엇을)만. 레이아웃·색·표현(어떻게 보이는가)은 디자인.

이유
- 게임 자산 차용은 원본 감성 유지·개발 속도에 유리. 단, 게임 카드는 가격·마감·입찰 같은 상거래 정보를 담지 않으므로, "게임 이미지 + 웹 상거래 정보" 결합은 디자인이 설계해야 함(이음새).

미확정 참고
- 차용 게임 카드 아트에 등급(S)·채널링등급 표기가 포함되나, 도메인은 무등급(D-073). 웹 상엔 기능적 등급 필드가 없고 이미지상 표기는 장식으로만 존재 — 기획/총괄에 정보 공유(outbox/006), 문제 시 격상.

## U-010. 아이템 시각 축 = 속성(4색)·레벨·골드포스·스킬 (등급/희귀도 폐기)

상태: ACCEPTED · 소유: 디자인 · 관련: supersedes U-004, relates-to D-073·api-contract v1.2 §3.3 · 2026-07-14

결정
- 등급(grade) 색 티어를 폐기(D-073, 원게임 무등급)하고, 아이템 카드·상세의 시각 축을 속성(element 4색 매핑)·레벨(강조 숫자)·골드포스(잔여시간 칩)·스킬(태그+skillPercent)로 재조정한다. 레어리티/등급 색 위계 없음.

이유
- 계약 §3.3 item 블록에 grade 없음, 필터에서도 제거(D-073). 색으로 "희귀함"을 표현하면 도메인과 어긋남. element만 색 코드, 나머지는 정보 표현.

기각된 대안
- 등급 색을 다른 축(레벨 구간)에 재활용: 도메인에 없는 위계를 시각이 발명 — 오해 유발.

## U-011. 상류 조율 파트너 = 프론트 기획(PF) 반영 (D-077)

상태: SUPERSEDED(→ D-079) · 소유: 디자인 · 관련: relates-to D-077, superseded-by D-079(PF→P 재통합, 상류 조율=기획 P) · 2026-07-14

결정
- D-077(기획 파트 분리)에 따라 D-072 '기획 경유'의 기획을 프론트 기획(PF, docs/frontend-planning/)으로 해석한다. 도메인 표현 정합·조율은 PF 경유, 서버 도메인/계약 소유는 백엔드 기획(P) 불변. 시각 최종은 총괄+사용자(D-072 불변).

이유
- 단일 기획이 백엔드 기획(P)/프론트 기획(PF)로 분리됨. 디자인의 화면·표현 상류 파트너는 PF가 적합.

## U-008. D-072 프로세스 3규칙 적용 (기획 경유·시각 예시 의무·최종 총괄+사용자)

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-072 · 2026-07-14

결정
- 총괄 D-072를 디자인 파트에 적용한다: (1) 도메인 표현 설계는 기획 경유, (2) 결정 요청·제안은 렌더된 시각 예시(docs/ux/mockups/) 동반(텍스트만 불가), (3) 비주얼·UX 최종은 총괄+사용자.

이유

## U-007. 우선 컴포넌트 세트와 핸드오프 스펙 범위 확정
