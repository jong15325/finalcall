- focus 선택 원값 `#C78300`은 steel chrome에서 유지한다. 밝은 surface/canvas에는 같은 계열을 2% 어둡힌

  `control-focus`와 `control-focus-on-dark`로 분리했다.

## U-022. 프론트 UI 시스템 정본 통합 — navy/gold/orange와 고정 commerce chrome

상태: DECIDED · 소유: 사용자/architect · 관련: EPIC-FRONTEND-UI-SYSTEM, supersedes U-021의 브랜드 값·CTA 매핑 및 route chrome 재색 조항 · 2026-08-12

## U-004. 아이템 등급(grade)·속성(element)에 색 토큰 체계 부여

상태: SUPERSEDED(→ U-010) · 소유: 디자인 · 관련: relates-to erd(item_template.element), superseded-by U-010(D-073 등급 축 제거) · 2026-07-14

결정(제안)
- 속성(element 4종: 물/불/흙/바람)에 고정 색 매핑(물=info-blue, 불=danger-red, 흙=amber, 바람=success-green). 등급(grade)은 게임 레어리티 관례의 티어 색 스케일(grade-1~5: gray→green→blue→purple→gold)로 확장 가능하게 정의.

이유
- element·grade는 검색 필터·아이템 카드의 핵심 시각 축(erd §7.7 인덱스). 색 코드는 스캔성을 크게 높인다. element는 4종 확정이라 즉시 매핑 가능.

미확정 참고
- erd `grade`는 INT 축으로 값 목록이 스펙에 명시되지 않음. 실제 grade 단계 수·명칭 확정 시 색 매핑을 1:1 고정해야 함(기획 확인 대상). 확정 전까지 5티어는 잠정.

## U-013. 와이어프레임 소유 경계 확정 — 기능 정의=PF, 레이아웃 이후=디자인

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-077·U-011, refines U-012, 사용자 결정 · 2026-07-14

결정
- 화면 와이어프레임을 두 층위로 나눈다: (1) 기능 정의(화면에 담길 요소·필드·플로우·에러) = 프론트 기획(PF, screen-spec.md 소유), (2) UI 레이아웃(요소 배치·반응형·상태) 이후 = 디자인. 디자인은 PF 기능 명세를 근거로 레이아웃 와이어프레임 → 비주얼로 이어간다.

기각된 대안
- PF가 레이아웃 와이어프레임까지 소유(국내 웹 기획 관행): 사용자가 현 지침 유지 선택.

## U-012. 디자인 범위 분담 — 게임 자산 차용 vs 웹 레이어 자체 디자인

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to U-010·D-073, 사용자 결정 · 2026-07-14

결정
- 게임 내 비주얼(아이템 카드·인벤토리·아이템 데이터 표현)은 사용자가 게임 디자인을 그대로 차용하고 해당 이미지를 직접 제공한다(디자인이 새로 그리지 않음).
- 디자인이 담당하는 것: (1) 게임 카드 이미지를 감싸는 웹 상거래 카드(이미지 슬롯 + 가격·카운트다운·입찰 등 게임에 없는 웹 정보), (2) 회원가입·로그인·지갑·판매등록 등 게임 외 웹 페이지 전체, (3) 공통 웹 요소(버튼·폼·모달·토스트·네비).
- 기획(PF)과의 정합 범위: 페이지에 담을 필드·플로우(무엇을)만. 레이아웃·색·표현(어떻게 보이는가)은 디자인.

이유
- 게임 자산 차용은 원본 감성 유지·개발 속도에 유리. 단, 게임 카드는 가격·마감·입찰 같은 상거래 정보를 담지 않으므로, "게임 이미지 + 웹 상거래 정보" 결합은 디자인이 설계해야 함(이음새).

미확정 참고
- 차용 게임 카드 아트에 등급(S)·채널링등급 표기가 포함되나, 도메인은 무등급(D-073). 웹 상엔 기능적 등급 필드가 없고 이미지상 표기는 장식으로만 존재 — 기획/총괄에 정보 공유(outbox/006), 문제 시 격상.

## U-014. D-082~085 파생 작업 순서 체계 적용 — 이의 제기를 의무로 전환

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-082·D-083·D-084·D-085, management/outbox/079 · 2026-07-15

결정
- 총괄 지시가 디자인의 진행 중 작업과 충돌하면 **따르기 전에 이의를 제기한다**(D-083). 침묵은 규약 위반으로 취급한다. 부수 적용: 착수된 디자인 작업은 완주가 기본값(중단·선점은 총괄 근거 제시 시에만 성립), 파트 내 유닛 순서(어느 화면·컴포넌트를 먼저)는 디자인 자율(D-084), 근거 인용 없는 착수 지시는 이의 대상(D-082).
- 산출물 형식: 작업 지시 발신 시 `근거(인용)` 필드, 공백·결함 처리 완료 보고 시 `뿌리 점검` 필드를 첨부한다(templates 3·4).

이유
- 종전 "이의 권한"은 쓰이지 않아 실패했다(079 사례: 백엔드가 권한을 갖고도 침묵 → 사용자가 발견). 디자인은 레이아웃·표현의 현장 실측을 쥔 쪽이라, 총괄의 문서 수준 추론과 어긋나는 상황이 구조적으로 발생한다 — 침묵하면 그 정보가 소실된다.

기각된 대안
- 관망 후 문제 발생 시 보고: D-083이 금지하는 침묵 그 자체. 재작업 비용이 이의 비용보다 항상 크다.

## U-016. 비주얼 방향 = 원게임 UI 스킨 전면 차용 (A/B/C 폐기) — 실행은 이미지 부착이 아니라 토큰 추출·CSS 재현

결정

이유

기각된 대안

미확정 참고
- 게임 팔레트 값은 현재 **스크린샷 육안 추정(잠정)**이다 — 원본 자산이 세션에 없어 픽셀 샘플링을 하지 못했다. 정확한 hex는 원본 UI 자산(또는 색상값) 수령 후 확정한다. 토큰명·구조는 이 확정과 무관하게 먼저 고정할 수 있다(skeleton-plan [4] "값만 교체" 설계와 정합).

## U-019. D-092 적용 — 확정 스펙 상향 전파 시 3단(델타 검토 → 반영 → 근거 줄 갱신)을 디자인 문서에 집행

상태: ACCEPTED · 소유: 디자인 · 관련: relates-to D-092·D-091, extends U-015·U-018, management/outbox/095 · 2026-07-15

결정
- 확정 스펙(api-contract·erd·domain-spec) 상향 전파를 수신하면 디자인은 **순서대로 3단**을 실행한다. ① 델타가 디자인 산출물(`design-system.md`·`ux-flows.md`·`accessibility.md`·`design-guide.md`·`mockups/`)에 미치는 영향 검토 → ② 반영 → ③ 각 문서 `근거:` 줄의 버전 전사 갱신. **①을 건너뛴 ③ 단독 갱신은 금지** — 델타를 안 보고 근거 줄만 올리면 "v1.4 근거"가 거짓 진술이 된다.
- 완료 보고에 3단 실행 여부를 1줄로 적는다(D-085 뿌리 점검 필드와 병기 가능).
- 적용 한계를 인지한다: D-092는 **근거 줄만** 덮는다. 본문에서 버전을 규범으로 쓴 서술(예: "계약 [3.3](v1.2)로 확정")은 ① 검토 단계에서만 걸리므로, 형식적으로 훑으면 통과한다 — 검토는 grep이 아니라 델타 대조로 한다.

이유
- 디자인의 근거 줄 stale은 이번 세션에 4층 재귀로 드러났다(프론트 육안 1 → 기획 grep 3 → 총괄 1 → 디자인 1: `decision-log` 머리말 `api-contract v1.1`). 뿌리는 **참조 버전을 손으로 전사하는데 참조 대상이 갱신돼도 전사본에 신호가 가지 않는 것**이다.
- 자기 문서 상향 시 도는 2단 마무리 grep으로는 못 막는다 — **남이 상향하면 내 전사본이 낡는데 내 grep은 돌지 않는다.** 신호가 오는 유일한 지점이 전파이므로 거기에 건다. 디자인은 계약·erd 양쪽을 근거로 다는 문서가 3개라 노출이 크다.
- D-089 `집행` 필드로도 못 막는다: 집행 필드는 실행 문서를 지목할 뿐 전사본의 낡음을 감지하지 않는다.

기각된 대안
- 전사 자체를 제거하고 "최신 정본 참조"로 통일: 총괄이 기각(095 [4절]). QA `test-plan`처럼 버전 선언이 규범인 문서와 충돌한다 — 전사가 정보를 담는 경우가 있어 일괄 제거가 성립하지 않는다. 디자인 문서에 한정 적용하는 것도 전 역할 규약과 어긋나 채택하지 않는다.

집행

## U-020. 색 토큰 = 게임 자산 실측값으로 전면 재정의 + 색 사용 3계층 규칙 (U-016 집행 완료)

상태: SUPERSEDED(→ U-021) · 소유: 디자인 · 관련: implements U-016, superseded-by U-021(라이트 커머스 색 토큰 전면 재정의 — 남색 게임 팔레트 폐기, element 아트 실측값·3계층 규칙 구조는 U-021이 계승), relates-to U-001·U-005·U-010·U-012·D-091(자율 확정 근거), supersedes(값) U-002 색 부분·U-007 컴포넌트 세트 일부 · 2026-07-15

결정
- `design-system.md` [2] 색 토큰을 **원본 자산 픽셀 실측값**으로 전면 교체한다(v0.2). 크롬 = `bg`#001C33 · `primary`#0667BD · `border`#3394DE · `text`#FAF7D5 · 슬롯 #000000. 조작 상태 = 기본 파랑 / 눌림 #E25706 / 활성 #E2B206.
- **element 4색을 아트 픽셀 실측으로 교체한다**: water #19B2FF(200°) · fire #FF5500(20°) · earth #95B259(80°) · wind #66CCCC(180°). 속성별 `l` 81파일 전 픽셀 HSV 히스토그램(투명 키 컬러 `#0000FF`·검정 슬롯·무채색 제외, PNG 청크 CRC 전건 검증).
- **색 사용 3계층 규칙을 신설한다**([1.2]): ① 조작 = 게임 상태 언어만 / ② 정보 = 의미색만 / ③ 아이템 = element 실측색만(색 단독 금지, 아이콘+라벨 필수). 세 계층은 한 컴포넌트 안에서 색으로 섞이지 않는다. **element 칩은 `bg` 위에만 배치**한다.
- 전경색 보정: 주황·황금 위 텍스트는 크림이 아니라 **남색 `#001C33`** 으로 반전한다.
- 폐기: `primary-50/100/300/500/600/700` 6단 스케일 · `accent-500/600` · 의미색 `-soft`/`-strong` 토큰 · Button `accent` variant. 신설: `primary.pressed`·`primary.selected`·`on-accent-fg` · Field `Checkbox`.
- 라이트 테마 값은 **정의하지 않는다**(구조만 유지). U-005는 총괄이 ON-HOLD·후순위 등재(095 [6절]).

이유
- **U-016의 마지막 미확정("게임 팔레트 값은 육안 추정")이 실측으로 닫혔다.** 자산 경로가 확보돼 픽셀 샘플링이 가능해졌으므로 추정값을 정본에 남길 이유가 없다.
- **아트 실측이 관례 추정을 2건 반증했다**: earth는 amber가 아니라 올리브(80°), wind는 green이 아니라 청록(180°)이다. 칩 색과 카드 아트가 어긋나면 사용자는 같은 속성을 두 색으로 배운다 — 아트가 정본이다.
- **3계층 규칙은 게임 팔레트가 좁다는 사실의 귀결이다.** 실측이 드러낸 hue 충돌: element-water(200°) ↔ 크롬 파랑(208°) 8° 차 · element-fire(20°) ↔ 눌림 주황(22°) 2° 차. 색을 재배치해 피하면 아트와 어긋나므로, 양보 가능한 쪽(웹의 배치 규칙)을 양보시켰다.
- **전경 반전은 게임을 그대로 베끼면 깨지는 지점이다.** 주황 위 크림 3.45:1, 황금 위 크림 **1.82:1** — 게임은 버튼 텍스트가 이미지에 구워져 있어(U-016) 이 문제를 겪지 않지만 웹은 겪는다.
- 전 토큰을 WCAG 2.1 상대휘도 공식으로 계산 검증했다(20쌍, 미달 0). 검증 과정에서 **내가 파생한 hover 값(#1E7FD4)이 크림 전경 3.83:1로 AA 미달임을 잡았다** — 실측값이 아닌 파생값이 위험 지점이라는 증거다.

기각된 대안
- element 색을 크롬과 안 겹치는 hue로 재배치: 칩과 카드 아트가 어긋난다. 아트는 648개 비트맵이라 바꿀 수 없고, 크롬은 CSS라 바꿀 수 있으나 그러면 U-016(게임 스킨 차용) 자체가 무너진다. 충돌은 색이 아니라 배치 규칙으로 푼다.
- 관례색 유지(물=파랑·불=빨강·흙=amber·바람=green): 실측이 흙·바람을 반증했다. 관례를 지키면 아트와 어긋난다.
- 라이트 테마 값을 지금 정의: 게임 스킨은 단일 다크이고 U-005는 후순위다. 근거 없는 색이 정본에 박힌다.
- `accent`(amber)를 즉시구매 CTA에 유지: 조작 계층에서 활성 황금과 충돌한다. 강조는 크기·배치로 만든다.

## U-021. 비주얼 방향 = 라이트 커머스로 전환 (무신사+마켓컬리 참조) — 남색 게임스킨(U-016/U-020) 폐기

상태: ACCEPTED · 소유: 디자인 · 관련: supersedes U-016·U-020(비주얼 방향·색 토큰), relates-to U-005·U-010·U-012·D-091(자율 확정 근거), 사용자 결정(2026-07-17) · 2026-07-17

결정
- 웹 전체의 비주얼 방향을 **라이트 커머스**로 전환한다(사용자 직접 정정, D-072 "비주얼 최종은 총괄+사용자"). **무신사(미니멀 에디토리얼: near-black·얇은 그레이 선·낮은 반경·강한 타입 위계·넉넉한 여백)** + **마켓컬리(화이트 베이스 + 프리미엄 퍼플 무드)**를 **참조**하되 자산·실hex를 복제하지 않고 고유값을 창작한다.
- **베이스 = 순백 `#FFFFFF`**(페이지·카드 동색, 카드는 border·shadow로 분리). `surface`#FFFFFF · `surface-sunken`#F4F4F5 · `slot`#000000.
- **조작 계층 개정**: **주 CTA = 블랙(`ink`#18181B, 흰 글자 17.72:1)**. **퍼플 `#6E2A9F`는 브랜드 액센트**(링크·포커스·선택 상태·소소한 포인트) — CTA 채움이 아니다. `primary-hover`#5C2185 · `pressed`#491A6C · `soft`/`selected`#F1EAF5 · `disabled`#E4E4E7 · `primary-fg`#FFFFFF. 게임식 hue 전환 상태 언어(주황/황금)를 폐기하고 명도 램프로 돌아간다.
- **의미색 라이트 재검증**: `success`#14742F(5.88) · `warning`#A0510A(5.71) · `danger`#C81E1E(5.74) · `info`#1D4ED8(6.70). `-soft`는 해당 색 8% 알파를 흰 위에 합성(칩 텍스트 base 전건 ≥ 4.5:1 계산 확인).
- **element 4색 아트 hex 불변, 라이트에서 역할 반전**: 라이트 배경에선 텍스트/선 대비가 무너진다(water 2.37 · fire 3.21 · earth 2.39 · wind 1.90 — 전건 미달) → **소프트 틴트 배경 + near-black(`#18181B`) 라벨 + solid 도트**로 뒤집는다(전경만 반전, hex 불변). 배치는 **아이템 카드·속성 배지·아이템 필터 칩에만**(Game-Color Containment).
- **테마 전제 역전**: 구 "단일 다크·라이트값 0개"를 **라이트 기본으로 역전**. `:root`에 라이트값, `[data-theme="dark"]`는 U-005 대기 미래 오버레이(지금 다크값 미창작). 그림자가 라이트에서 실제 부양에 쓰인다.
- 신설: `ink`·`primary-soft`·`border-strong`(#8A8A8F, 1.4.11 컨트롤 경계 3.44)·`surface-sunken` 4토큰 · OAuth(카카오·네이버 브랜드 규격) 컴포넌트 자리(기능은 미래 에픽). 반경 낮춤(sm4/md6/lg8, 무신사 각진 감성).

이유
- **사용자가 U-016/U-020을 오류로 정정했다.** 게임 아이템 정보창의 남색#001C33 단일 다크 스킨을 자금 거래 커머스 전체 팔레트로 채택한 것이 문제였다 — 실제 돈에 준하는 캐시·게임머니를 다루는 UI는 "게임"이 아니라 "믿을 수 있는 거래처"로 읽혀야 한다. 게임 감성은 아이템에만 국한한다.
- **이원 구조가 핵심이다**: 깨끗한 커머스 셸(화이트·그레이·퍼플) 안에 아이템 카드 한 장만 게임이 드러나는 "창"(검정 슬롯 + element색)이다. 로그인·가입·마이페이지·탈퇴 등 계정/거래 크롬엔 element색·검정 슬롯이 전무하다.
- **element 역할 반전은 다크→라이트의 정확한 역전 현상이다**: 남색 위에서 빛나던 4색(7.29~9.12)이 흰 배경에서 텍스트로 전건 무너진다(1.90~3.21). 아트 hex는 정본이라 불변, 전경만 뒤집어 채움+near-black 라벨(5.5~9.3:1)로 우회한다.
- **`border-strong` 신설 근거**: 라이트 순백 위에서 단일 border 값으로는 무신사식 whisper-thin 카드 선(≈1.3:1)과 인풋 컨트롤 경계 3:1(1.4.11)을 동시에 만족할 수 없다. 구 시스템은 남색 위 밝은 파랑(#3394DE 5.3)이 우연히 둘 다 충족했으나 라이트에선 갈린다.
- 전 토큰을 라이트 베이스(#FFFFFF)에서 sRGB 상대휘도로 계산 검증했다(redesign-commerce-proposal.md 계산 출처, AA 전건 통과).

기각된 대안
- 남색 게임스킨 유지(U-016/U-020): 사용자가 명시적으로 정정했고, 자금 거래 신뢰감과 상충한다.
- 퍼플을 주 CTA 채움으로: 사용자가 무신사식 블랙 CTA를 확정(퍼플은 액센트만). CTA 강조는 색이 아니라 블랙+크기·배치.
- 의미색 `-soft`를 12% 알파로: proposal이 8%로 계산 검증했고 목업 렌더값(#FBEDED 등)이 8%와 정확히 일치한다. 12%는 칩 텍스트 대비를 4.5:1 미만으로 떨어뜨려 계산 인용과 어긋난다.
- 지금 다크 테마값 정의: U-005 후순위. 근거 없는 색이 정본에 박힌다 — 구 문서가 라이트를 미룬 규율을 방향만 반대로 계승.
- element 색을 라이트 대비용으로 재조정: 아트가 정본이라 hex 불변. 역할(전경/배경)만 반전한다.

## U-007. 우선 컴포넌트 세트와 핸드오프 스펙 범위 확정

상태: ACCEPTED · 소유: 디자인 · 2026-07-14

결정
- v0 우선 컴포넌트: Button, Field(Input/Select), ItemCard, ListGrid, Modal, Toast, Pagination(cursor/offset), Badge/StatusChip(+Grade/Element), Countdown, MoneyAmount. 각 컴포넌트는 상태·변형·토큰·반응형·접근성을 명세한다(design-guide 4절).
