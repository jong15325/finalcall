# 영역 2 설계안: 협업 진행 형식

상태: PROPOSED (사용자 피드백 대기)
소유: 컨설턴트 · 2026-07-12
결정 항목: C-006 ~ C-009 (consulting/decision-log.md 정본)

---

## 1. 진단

현행 가이드 5절(전달 프로토콜)·7절(진행 순서)이 골격은 갖췄으나 3개 공백이 있다.

| # | 공백 | 실물 근거 |
|---|---|---|
| 1 | 게이트에 진입·통과 기준 없음 | 7절은 순서("api-contract 확정 시점에 동시 시작")만 정의. "확정"이 무엇으로 성립하는지(누가 승인, 어디에 기록) 미정의. D-001도 순서만 규정 |
| 2 | 메시지 유형이 결정 요청 1종뿐 | 5절 형식은 결정 요청 전제(선택지+추천 필수). 그러나 실제로는 작업 지시(킥오프), 완료 보고, 정보 공유가 이미 오가는 중 — 전부 즉흥 형식 |
| 3 | 동기화 리추얼 부재 | 진행 현황을 모으는 시점·형식 규약 없음. 대화가 늘수록(7개+) 사용자만이 전체 상태를 아는 구조가 됨 |

복붙 부담 관찰: 전달 1건당 프롬프트 1회 복사 + 회신 1회 복사. 병렬 구현 시작 후
역할 7개면 왕복이 폭증한다. 부담을 줄이는 지점은 (a) 전달 횟수 자체 축소(묶음),
(b) 프롬프트 길이 축소(본문 대신 경로 참조), (c) 회신 대기 상태의 가시화(outbox 상태 줄, D-017)다.

## 2. 제안 요약

### 2.1 단계 게이트: 진입·통과 기준 명문화 (C-006)

기존 순서(D-001, 가이드 7절)를 게이트 표로 형식화한다. 새 절차 추가가 아니라 기존 절차의 기준 명시다.

| 게이트 | 통과 기준 (exit criteria) | 통과 시 후속 |
|---|---|---|
| G1 domain-spec 확정 | 기획 초안 + 총괄 검수 + 사용자 승인. 미해결 ON-HOLD는 인덱스에 등재되어 있을 것 | ERD 착수 |
| G2 erd 확정 | 위와 동일 + domain-spec과의 정합 확인 | api-contract 착수 |
| G3 api-contract 확정 | 총괄 검수 + 보안 게이트 1(S 검토, D-013) 통과 + 사용자 승인 | 백/프론트/QA 대화 동시 기동(G0 킥오프), 프론트 repo 복사본 생성 |
| G4-n 도메인 n 구현 완료 | 구현 DoD: 계약 준수 + CLAUDE.md 컨벤션 + 테스트 통과. QA 시나리오 실행 + defects 처리. 도메인 전체 완료 시 보안 게이트 2 | 다음 도메인 착수 |

- 게이트 통과는 총괄이 decision-index.md의 게이트 표에 1줄 기록(날짜·근거 프롬프트).
  D 발번은 하지 않는다 — 게이트 통과는 결정이 아니라 상태 전이이므로.
- 덜어낸 것: 스테이지 게이트 위원회·게이트 문서 양식(Phase-gate process의 원형) —
  승인자가 총괄+사용자로 고정된 1인 구조에서는 체크리스트 1표로 충분.

### 2.2 메시지 유형 4종 표준 (C-007, 가이드 5절 확장)

공통 헤더: `[발신 → 수신] <유형>: 제목` + 말미 `회신: 필요(무엇을) / 불요`.

| 유형 | 필수 요소 | 비고 |
|---|---|---|
| 결정 요청 | 배경 1~3줄, 안건별 선택지+추천+이유, 신규 발번 ID | 현행 5절과 동일 |
| 작업 지시 | 목표, 완료 기준, 범위 제한(하지 말 것), 관련 문서 경로 | 킥오프·Claude Code 작업 프롬프트 포함 |
| 완료 보고 | 산출물 경로, 완료 기준 충족 여부, 신규 발번 ID, 다음 단계 제안 | 게이트 통과 요청 겸용 |
| 정보 공유 | 요지 3줄 이내 + 상세는 경로 참조 | 회신 불요 명시. 계약 영향 시 이 유형 사용 금지(결정 요청으로) |

- 근거: 아마존 서면 문화의 원리(서면 강제 + 추천안 선행)는 현행 5절이 이미 구현.
  확장분은 GitLab 비동기 규약의 "회신 기대치 명시" 차용 — 수신 대화가 회신 프롬프트를
  만들지 말지 스스로 판단하게 하여 불필요한 왕복 제거.
- 덜어낸 것: 6-pager 분량 규범, silent reading — 대화는 어차피 전문을 읽는다.

### 2.3 복붙 부담 최소화 3규칙 (C-008)

1. 묶음 전달: 같은 수신자로 가는 독립 안건은 1프롬프트에 번호 매겨 묶는다(기획의 D-004
   4건 묶음 방식을 규약으로 승격). 안건별 부분 회신 허용.
2. 게이트 = 지식 동기화 앵커: 게이트 통과 전파 프롬프트에 동기화 대상 파일 목록을 포함,
   사용자가 그 시점에 각 대화의 프로젝트 지식을 일괄 갱신한다. 동기화된 문서는 경로 참조,
   게이트 이후 변경분만 발췌 첨부(원본 경로·기준 게이트 병기).
   현행 관행(동기화 거의 없음, 프롬프트 본문 의존)은 낡은 사본을 증식시키고, 상시 동기화는
   복붙보다 무거우므로 동기화를 게이트 이벤트에 묶는다.
3. 왕복 1회 완결 설계: 발신자는 "이 회신만 오면 내가 진행 가능한가"를 자문하고,
   부족하면 안건을 묶어 보낸다. 열린 질문 금지(현행)에 더해 후속 질문 유발 문구도 금지.

### 2.4 동기화: 이벤트 기반 리추얼 (C-009)

시간 기반(데일리 스탠드업)을 도입하지 않고 이벤트 기반 3종으로 경량화한다.

| 이벤트 | 행동 | 형식 |
|---|---|---|
| 게이트 통과 | 총괄이 전 역할에 전파 1프롬프트(변경점 + 각 역할이 할 일) | 정보 공유 유형 |
| 역할 작업 블록 종료 | 해당 역할이 완료 보고 → 총괄 | 완료 보고 유형 |
| 사용자 세션 재개 | 총괄이 현황 브리핑 생성(인덱스 + 보류 안건 + 대기 중 SENT 목록 기반) | 신규 문서 없음 — 기존 트래킹 문서(유형 6)에서 즉석 생성 |

- 근거: GitLab 비동기 문화 — 동기 리추얼 대신 문서 기반 상태 공유. 1인 구조에서는
  사용자가 유일한 클록이므로 "매일"이 아니라 "세션 재개 시"가 자연스러운 주기다.
- 덜어낸 것: 스크럼의 스프린트·데일리(시간 박스) — 대화는 세션 간 시간이 흐르지 않아
  시간 박스가 무의미. 회고는 영역 3(보고 체계)에서 다룬다.
