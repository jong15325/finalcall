# 컨설턴트 결정 로그 (C-xxx)

협업 가이드 4절 티켓 규약(D-009~D-011)을 따른다. 컨설턴트는 한시 역할(D-012)이며
모든 산출물은 PROPOSED로 총괄 회부, 확정 권한 없음(확정 시 D 발번).
상세 분석·진단·마이그레이션은 영역별 설계안 문서(01-docs-structure.md 등) 참조.

## C-001. 문서 유형 분류 체계 6종 정의

상태: ACCEPTED · escalated-as D-014 · 소유: 컨설턴트 · 관련: relates-to D-003, D-009 · 2026-07-12

결정
- docs/ 내 모든 문서를 6개 유형으로 분류하고, 유형별 위치·변경 규칙·기준(authority) 등급을 규약화한다.
  1. 확정 스펙 — docs 루트. 변경은 계약 변경 절차(가이드 6절). 기준 최상위.
  2. 지침 — 역할의 행동 규약(collaboration-guide, CLAUDE.md, 파트 지침). 변경은 소유 역할 + 총괄 승인.
  3. 결정 로그 — 각 역할 폴더의 decision-log.md. 항목 불변, 상태 라벨로만 갱신(기존 4절 규약 유지).
  4. 작업 노트 — 각 역할 폴더 notes/. 가변, 비공식. 타 역할이 근거로 인용 금지.
  5. 전달 프롬프트 — 각 역할 폴더 outbox/. 발신 이력 보관(C-004).
  6. 보고·트래킹 — decision-index.md, defects.md, findings.md, 진행 보고. 전 역할 열람.

이유
- 유형 5종이 실재하는데 규약은 결정 로그만 정의되어 혼입이 이미 발생
  (기획 로그에 "주제 4 파생 메모", "주제 5 분석" 등 작업 노트 혼입 — 실물 확인).
- Diátaxis의 핵심 원리 "서로 다른 필요에는 서로 다른 문서 유형, 혼합이 혼란의 최대 원인"을
  프로젝트 문서에 맞게 번안. 4분류(튜토리얼/하우투/레퍼런스/설명)는 사용자 문서용이라 그대로 이식하지 않고
  '필요 기반 분류 + 유형별 규칙'이라는 원리만 차용했다(덜어낸 것).

기각된 대안
- Diátaxis 4분류 직접 적용: 사용자 대상 제품 문서 분류라 프로젝트 운영 문서에 부적합.
- 현행 유지(결정 로그만 규약화): 혼입 재발. 로그가 노트를 흡수하면 ADR 불변성 신뢰 훼손.

레퍼런스: Diátaxis(diataxis.fr), ADR 불변성 원칙(AWS Prescriptive Guidance, Fowler).

## C-002. 역할 폴더 표준 내부 구조

상태: ACCEPTED · escalated-as D-015 · 소유: 컨설턴트 · 관련: depends-on C-001 · 2026-07-12

결정
- 모든 역할 폴더(design/ backend/ frontend/ qa/ security/ consulting/)는 동일한 내부 구조를 갖는다.
  ```
  <role>/
  ├── decision-log.md   # 결정 로그 (유형 3)
  ├── notes/            # 작업 노트 (유형 4)
  └── outbox/           # 전달 프롬프트 (유형 5)
  ```
- 역할 고유 산출물(qa/test-plan.md, security/findings.md 등)은 폴더 루트에 둔다.
- management/는 예외적으로 decision-index.md(유형 6)와 prompts/(킥오프 프롬프트 보관)를 추가로 갖는다.
  킥오프 프롬프트는 "타 대화를 기동하는 지침"이므로 발신함(outbox)과 구분한다.

이유
- 위치 규약 부재로 기획(design/prompts/escalation-prompts.md)과 총괄(management/prompts/)이
  서로 다른 방식을 즉흥 사용 중 — 같은 이름 prompts/가 다른 유형(발신함 vs 킥오프 보관)을 담고 있다.
- 구조가 역할마다 같으면 새 역할(보안 등) 추가 시 규약 재설명 비용이 없다.

기각된 대안
- 유형별 최상위 폴더(docs/notes/, docs/outbox/ 아래 역할별 하위): 소유권 규칙("자기 폴더에만 쓴다")과
  충돌하고, 역할 단위 열람·정리가 불편.

레퍼런스: docs-as-code의 규칙적 폴더 토폴로지(passo.uno docs-as-code topologies).

## C-003. 읽기 규칙 재설계: 필요 기반 열람, 기준은 문서 유형

상태: ACCEPTED · escalated-as D-016 · 소유: 컨설턴트 · 관련: supersedes 가이드 3절 읽기 규칙(D-006 일부) · 2026-07-12

결정
- "다른 역할의 작업 폴더는 참조하지 않는다"를 폐지하고 다음으로 대체한다.
  1. 기본 열람 범위: 각 역할은 필독 문서(확정 스펙, 총괄 결정 로그, 협업 가이드, 자기 폴더)만
     상시 읽는다. 타 역할 폴더를 상시 탐색하지 않는다.
  2. 필요 기반 열람(pull): 현재 작업에 타 역할 문서의 맥락이 필요할 때는 금지 없이 열람할 수 있다.
     열람 사유가 설명 가능해야 하며(예: "입찰 API 구현에 기획의 소프트클로즈 분석 노트 참조"),
     산출물에 출처를 남긴다.
  3. 기준(authority): 무엇을 근거로 작업할지는 문서 유형이 결정한다.
     확정 스펙 > 총괄 결정 로그(ACCEPTED) > 자기 역할 결정 로그 > 타 역할 결정 로그(맥락 참고)
     > 작업 노트(근거 인용 금지).
  4. 타 역할 문서에 의존해 산출물을 만들 때는 반드시 확정 스펙 또는 ACCEPTED 결정만 근거로 삼고,
     노트에서 얻은 맥락은 "미확정 참고"로 표기한다.

이유 (supersedes 사유)
- 원 규칙의 목적은 "확정 전 내용 의존 방지"였으나, 수단(열람 금지)이 목적보다 과했다.
  백엔드가 기획의 설계 근거(노트)를 못 보면 같은 질문을 프롬프트 중계로 다시 해야 하고,
  1인 중계 구조에서 이는 사용자 복붙 부담으로 직결된다.
- 의존 방지는 접근 차단이 아니라 상태 라벨(D-010)로 달성한다. ADR 프로세스에서 신뢰의 근원은
  "누가 읽는가"가 아니라 "항목의 상태가 명시되는가"다.
- 상시 전면 열람이 아닌 필요 기반(pull)으로 제한하는 이유: AI 대화는 읽은 문서가 전부
  컨텍스트를 점유한다. 무관한 타 역할 문서를 상시 로드하면 컨텍스트 낭비·오염이 발생하므로,
  "필요할 때, 사유를 갖고" 읽는 것이 통제와 효율을 동시에 만족한다(사용자 피드백 반영).
- 예외 누적 징후: defects.md 열람 예외가 이미 존재하고 findings.md 예외(D-013)가 추가됨.
  예외가 늘어나는 규칙은 기본값이 틀렸다는 신호다.

기각된 대안
- 현행 유지: 위 복붙 왕복 비용 + 예외 누적. AI 대화는 사람과 달리 "어깨너머 정보"로
  정치적 문제를 일으키지 않으므로 차단의 조직적 명분도 약함.
- 전면 자유(기준 규칙 없이): 원래 문제(미확정 의존)가 재발.

레퍼런스: ADR 상태 기반 신뢰 모델(AWS, Fowler), 오픈 핸드북 문화(GitLab Handbook)의
"기본 공개 + 정본 명시" 원칙.

## C-004. 전달 프롬프트 이력: outbox 보관 (삭제하지 않음)

상태: ACCEPTED · escalated-as D-017 · 소유: 컨설턴트 · 관련: depends-on C-002 · 2026-07-12

결정
- 발신 프롬프트는 역할 폴더 outbox/에 보관한다. 회신 후에도 삭제하지 않는다.
- 파일 단위: 주제당 1파일(`outbox/NNN-주제.md`). 파일 머리에 상태 1줄:
  `상태: SENT | ANSWERED → <결정 ID>`.
- 결정 로그에는 결과(결정)만, outbox에는 요청 원문이 남아 상호 참조한다.

이유
- 결정 ID만으로는 "무엇을 물었고 어떤 선택지가 제시됐는지" 복원 불가.
  D-004~005처럼 조건부 채택된 결정은 요청 원문이 감사 추적(audit trail)의 반쪽이다.
- 저장 비용은 사실상 0이고 git이 어차피 이력을 남긴다. 삭제는 절약이 아니라 정보 파기.
- 기획이 이미 escalation-prompts.md에 누적+회신 상태 표기를 자생적으로 실천 중 —
  검증된 관행을 규약으로 승격하는 것이 학습 비용 최소.

기각된 대안
- 회신 후 삭제: 감사 추적 소실. git 이력에서 찾는 것은 가능하나 발견 비용이 큼.
- 단일 누적 파일(현행 escalation-prompts.md 방식): 파일이 무한히 자라고 주제 검색성 저하.
  단, 마이그레이션에서 기존 파일은 분할하지 않고 동결 보관(소급 재작성 금지 원칙과 일관).

레퍼런스: ADR의 "기각된 것도 기록" 원칙(Rejected 상태 유지, AWS Prescriptive Guidance).

## C-005. spring-skeleton-prompts.md 이동 + CLAUDE.md 경로 정정

상태: ACCEPTED · escalated-as D-018 · 소유: 컨설턴트 · 관련: relates-to D-003, C-001 · 2026-07-12

결정
- docs/spring-skeleton-prompts.md → docs/backend/notes/spring-skeleton-prompts.md 이동.
- CLAUDE.md의 참조 경로를 정정한다. 현재 `docs/skeleton-prompts.md`로 표기되어 있어
  실제 파일명(spring-skeleton-prompts.md)과도 불일치 — 어차피 수정이 필요한 파일이다.
- README.md 말미의 링크도 함께 정정한다.

이유
- D-003이 "docs 루트 = 확정 스펙"으로 확정했는데 백엔드 작업 문서가 루트에 남아 규약 위반 실물.
- 스켈레톤은 구축 완료 상태라 이 문서는 이제 이력성 작업 노트다. 유형 4의 위치(backend/notes/)가 맞다.
- CLAUDE.md 경로가 이미 틀려 있으므로(깨진 참조) 이동에 따른 추가 수정 비용은 없다.

기각된 대안
- 루트 유지: "루트 = 확정 스펙" 규칙에 영구 예외 1건을 두는 것. 예외는 규칙을 침식한다.
- docs/backend/ 루트에 배치: 표준 구조(C-002)상 작업 노트는 notes/가 맞다.

레퍼런스: ADR/스펙 디렉토리 순수성 관행(docs/adr 단일 목적 디렉토리, AWS·GitHub ADR 예시).

## C-006. 단계 게이트: 진입·통과 기준 명문화

상태: ACCEPTED · escalated-as D-019 · 소유: 컨설턴트 · 관련: relates-to D-001, D-013, 가이드 7절 · 2026-07-12

결정
- 진행 순서(G1 spec → G2 erd → G3 contract → G4-n 도메인 구현)를 게이트 표로 형식화하고
  각 게이트에 통과 기준(exit criteria)을 명시한다. 상세 표는 02-collaboration-process.md 2.1.
- 게이트 통과는 총괄이 decision-index.md 게이트 표에 1줄 기록. D 발번 없음(상태 전이이지 결정이 아님).
- G3에 보안 게이트 1(D-013), 도메인 전체 완료에 보안 게이트 2를 통합.

이유
- "확정"의 성립 요건(누가 승인, 어디에 기록)이 미정의 — 병렬 시작 트리거가 게이트인데
  기준이 없으면 역할마다 확정 여부 인식이 갈린다.
- Phase-gate 원리에서 게이트의 핵심은 exit criteria다. 기존 절차에 기준만 얹는 최소 변경.

기각된 대안
- 게이트 통과를 D 발번: 결정 로그가 상태 전이 기록으로 오염(1결정=1번호 원칙 훼손).
- 스테이지 게이트 원형(위원회·양식) 도입: 승인자 고정(총괄+사용자)인 1인 구조에 과잉.

레퍼런스: Phase-gate process(Wikipedia), DoR/DoD(Scrum Alliance).

## C-007. 메시지 유형 4종 표준 (가이드 5절 확장)

상태: ACCEPTED · escalated-as D-020 · 소유: 컨설턴트 · 관련: relates-to 가이드 5절, D-011 · 2026-07-12

결정
- 역할 간 전달을 4유형으로 표준화: 결정 요청(현행) / 작업 지시 / 완료 보고 / 정보 공유.
- 공통 헤더 `[발신 → 수신] <유형>: 제목` + 말미 `회신: 필요(무엇을)/불요` 명시.
- 정보 공유 유형으로 계약·스펙 영향 사항 전달 금지(결정 요청으로 격상).
- 유형별 필수 요소는 02-collaboration-process.md 2.2 표.

이유
- 실제로 4유형이 이미 오가는데 규약은 결정 요청 1종만 정의 — 나머지가 즉흥 형식.
- 회신 기대치 명시(GitLab 비동기 규약)로 불필요한 회신 왕복을 구조적으로 제거.

기각된 대안
- 자유 형식 유지: 수신 대화가 회신 필요 여부를 추측 — 왕복 증가.
- 유형 세분화(6종+): 유형 판별 자체가 비용. 4종이 관찰된 실제 트래픽의 전부.

레퍼런스: GitLab Handbook 비동기 커뮤니케이션, Amazon 서면 문화(추천안 선행 원리는 현행 유지).

## C-008. 복붙 부담 최소화 3규칙

상태: ACCEPTED · escalated-as D-021 · 소유: 컨설턴트 · 관련: relates-to D-007, C-004, C-007 · 2026-07-12

결정
1. 묶음 전달: 같은 수신자행 독립 안건은 1프롬프트에 번호 매겨 묶음(부분 회신 허용).
2. 게이트 = 지식 동기화 앵커: 게이트 통과 시 총괄 전파 프롬프트에 "동기화 대상 파일 목록"을
   포함하고, 사용자는 그 시점에 각 대화의 프로젝트 지식을 일괄 갱신한다.
   프롬프트 참조 규칙: 마지막 게이트에서 동기화된 문서는 경로 참조(본문 붙여넣기 금지),
   게이트 이후 변경분만 발췌 첨부. 발췌에는 원본 경로·기준 게이트를 병기해 사본임을 명시.
3. 왕복 1회 완결 설계: "이 회신만 오면 진행 가능한가" 자문 후 발신. 후속 질문 유발 문구 금지.

이유
- 병렬 구현 시작 후 대화 7개의 왕복이 사용자 1인에 집중 — 전달 횟수와 길이가 병목.
- 기획의 D-004 4건 묶음이 이미 유효성을 실증.
- 사용자 확인 결과 현재 지식 동기화는 거의 하지 않고 프롬프트 본문에 의존 중 —
  무조건적 경로 참조는 전제가 성립하지 않는다. 상시 동기화 의무는 복붙보다 무거우므로,
  동기화를 게이트 이벤트에 묶어 횟수를 최소화하면서 경로 참조가 성립하는 기준선을 만든다.
  게이트 사이 변경분은 소량이라 발췌 첨부 비용이 작다.

기각된 대안
- 전달당 1안건 강제: 왕복 수 증가. 원자성은 안건 번호로 확보 가능.
- 무조건 경로 참조(초안): 지식이 낡은 상태에서 수신 대화가 존재하지 않는 문서를 참조하게 됨.
- 전면 본문 첨부(현행 관행): 낡은 사본 증식, 프롬프트 비대화. 단일 진실(D-007) 훼손.
- 상시 동기화 의무: 파일 변경마다 사용자가 업로드 — 부담 역전.

레퍼런스: Kanban WIP 관리(Atlassian — 대기 왕복을 WIP로 보고 제한), GitLab 비동기 문화.

## C-009. 동기화: 이벤트 기반 리추얼 3종

상태: ACCEPTED · escalated-as D-022 · 소유: 컨설턴트 · 관련: relates-to C-006, C-007, D-011 · 2026-07-12
(절단 사고 복구: 02-collaboration-process.md 2.4 기준으로 2026-07-12 원문 복원 — D-022 조건 1 이행)

결정
- 시간 기반 리추얼(데일리 등) 미도입. 이벤트 기반 3종만 규약화:
  1. 게이트 통과 → 총괄이 전 역할 전파 1프롬프트(변경점 + 역할별 할 일).
  2. 역할 작업 블록 종료 → 완료 보고(C-007 유형).
  3. 사용자 세션 재개 → 총괄이 현황 브리핑(인덱스 + ON-HOLD + SENT 대기 목록에서 즉석 생성,

- 브리핑을 기존 트래킹 문서(유형 6)에서 생성하면 이중 관리가 없다.

기각된 대안
- 데일리/주간 고정 보고: 이벤트 없는 날의 공회전 보고 생산.
- 리추얼 없음(현행): 대화 수 증가 시 사용자만 전체 상태를 아는 단일 장애점화.

레퍼런스: GitLab async standup(문서 기반 상태 공유), 스크럼 리추얼의 목적(가시성)만 차용하고
시간 박스는 제거.

## C-015. 병렬 작업 비동기 완료 규칙: 착수 조건·선완료 행동·어긋남 해소

상태: ACCEPTED · escalated-as D-028 · 소유: 컨설턴트 · 관련: relates-to D-019, D-020, D-026, D-016 · 2026-07-12

결정
1. 착수 조건(DoR): 작업 지시 메시지에 "의존:" 필드를 필수화한다.
   의존 대상(문서·타 역할 산출물)이 확정(ACCEPTED 또는 게이트 통과) 전이면 착수 금지 —
   총괄이 추적 표(D-026)에 블로커로 등재하고 대기시킨다.
2. 먼저 끝난 역할의 행동 우선순위:
   a. 완료 보고 발신, "대기 중: <무엇>" 명시 (블로커 가시화)
   b. 의존 없는 다음 작업을 백로그에서 당겨(pull) 진행
   c. 남은 것이 의존 작업뿐이면 "가정 선언 진행": 가정을 정보 공유로 발신하고
      산출물 머리에 가정을 표기한다. 가정이 깨지면 재작업은 진행한 쪽 부담
      (투기적 선행은 허용하되 비용은 자기 몫 — 상대에게 전가 금지).
3. 어긋남 발견 시 해소 기준: 기준 위계(D-016)로 판정한다.
   확정 스펙과 다른 쪽이 수정한다. 스펙 자체가 문제면 6절 계약 변경 절차.
   양쪽 다 스펙 밖(스펙 공백)이면 결정 요청으로 격상 — 먼저 구현한 쪽이
   기준이 되지 않는다(선착순 기준 금지).

이유
- 게이트 사이 병렬 구간의 미시 동기화 규약 공백. 완료 시점 비대칭은 병렬 구조의
  상수이므로 "기다려라"가 아니라 "기다리는 동안의 합법적 행동"을 정의해야 한다.
- 가정 선언 진행을 금지하면 선완료 역할이 공회전, 무제한 허용하면 추측 위에 쌓은
  작업이 상대를 역으로 압박("이미 만들었으니 맞춰달라")한다. 가정 공개 + 재작업
  자기 부담이 두 폐해를 모두 차단한다.
- 선착순 기준 금지: 먼저 만든 쪽이 사실상 표준이 되는 관성은 계약 우선 원칙(D-007,
  api-contract 단일 진실)의 우회 통로다.

## C-029. docs 커밋 실행 일원화: 역할이 메시지 작성, 사용자가 단일 실행

상태: ACCEPTED · escalated-as D-061 · 소유: 컨설턴트 · 관련: supersedes C-016(D-029) 규칙 3·대행 조항, relates-to D-021, D-022, D-023, incident-001 · 2026-07-13
(사용자 지시 — 대기모드 전달, 커밋 꼬임 해소)

결정
1. 커밋 메시지 작성 = 각 역할. 형식 `docs(<역할>): 한글 제목`(C-016.4 유지).
   소유권·attribution은 실행자가 아니라 메시지 scope로 보존한다.
2. git 실행(add·commit·push) = 사용자 단일 실행자. 역할 폴더 단위 커밋(한 폴더=한 커밋),
   여러 폴더가 밀려 있으면 폴더별로 나눠 커밋한다.
3. 실행 시점: 작업 블록 종료(D-022 리추얼 2, 완료 보고 시) + 게이트(D-021 앵커)에 몰아 실행.
   완료 보고에 "커밋 메시지 제안" 1블록 포함을 의무화 — 사용자가 그대로 실행한다.
4. 스테이징 규율: 항상 `git add docs/<역할>/`로 path-scope. `git add -A`/`git add .` 금지
   (공유 작업트리의 타 역할 미커밋 변경 혼입 방지). docs·코드 혼합 커밋 금지(C-016.5 유지).
5. 역할 대화의 git 대행(C-016.3 후단) 폐지. 다중 실행자가 반쪽 커밋·혼입을 유발함이 실증됨.
6. 코드 커밋은 현행 유지(Claude Code 제안·사용자 실행).

이유
- C-016이 "사용자 단독 실행"을 기각한 근거는 "커밋 시점이 사용자 세션에 종속 → 이벤트와
  커밋이 어긋나 손실 창"이었다. 그러나 1인 중계 구조에서 모든 이벤트가 사용자 중계를 거치므로
  이벤트≈사용자 세션 — 기각의 전제가 성립하지 않는다.
- 다중 실행자의 실비용이 실증됨(2026-07-13): 공유 작업트리에 여러 역할 미커밋 변경이 겹치면
  매 커밋이 "타 역할 혼입" 검사를 요구하고, 마운트 지연·index.lock 같은 환경 변수까지 겹치면
  반쪽 커밋이 난다.
- attribution은 메시지 scope(`docs(<역할>):`)와 폴더 소유(D-015)가 보증한다 — 실행 일원화가
  소유권을 흐리지 않는다. 실행자와 저작자를 분리하는 것은 CODEOWNERS의 원리와 같다.
- 손실 창(incident-001)의 근본 원인은 미커밋 적체이지 실행자 수가 아니다. 커밋을 완료 보고
  리추얼에 묶어 블록 종료 즉시 실행하면 해소된다.

기각된 대안
- 현행 유지(다중 실행자 + 대행): 오늘 꼬임 재발. path-scope만으로 무해해지나 실행자가 여럿이면
  규율 준수 검증 비용이 실행마다 발생.
- 총괄 단독 실행: 총괄이 타 역할 폴더까지 커밋 → C-016이 이미 기각(소유권 흐림·병목).
  사용자 실행은 attribution을 메시지로 유지하므로 이와 다르다.
- 역할별 브랜치·워크트리 분리: 파일 버스(outbox)의 전 역할 즉시 가시성 전제를 파괴(C-010).

레퍼런스: 모노레포 디렉터리 오너십 + CODEOWNERS(저작·리뷰와 커밋 실행자 분리),
trunk-based development(단일 브랜치 빈번 커밋), incident-001 교훈.

   검토·결정할 수 있는 최소 실질.
3. 위치·조건: 브리핑 구조 안에 넣되(정확한 자리·표기는 templates 16에서 확정),
   초안을 생성하지 않은 응답에는 항목을 생략한다(조건부 — 빈 항목 강제 아님).
4. 원칙 정합: D-049의 "파일에 쓴 내용도 요지는 채팅 노출 필수"를 구체화한다.
   기존 '발신: 경로 — 요지 1줄'로는 초안 실질이 안 보이던 공백을 메우는 것이며,
   상세 본문은 여전히 브리핑 위에 둔다.

이유
- 최종 결정권자는 항상 사용자(가이드 1절)인데, 초안은 파일(outbox·decision-log)로 외부화되어
  사용자가 열지 않으면 실질을 못 본다. '경로 + 1줄'로는 채택/기각 판단 근거가 부족하다.
- 브리핑을 짧게 유지(D-049)하는 취지와 충돌하지 않도록 조건부(초안 생성 시에만) + 소량(2~5줄)으로 제한.
- 파일 외부화의 목적(토큰·감사 추적)은 유지하되, 사용자 검토 채널만 브리핑으로 복원한다.

기각된 대안
- 초안 전문을 브리핑에 노출: 브리핑 비대화, D-049의 스캔 가능성 훼손.
- 모든 응답에 요지 확대: 초안 없는 단순 응답까지 장황해진다. 조건부가 맞다.
- 별도 요약 파일 생성: 파일 증식 + 또 하나의 "안 열어보는 파일". 채팅 노출이 목적에 직결된다.

레퍼런스: D-049 원칙(채팅 요지 노출), GitLab async(결정에 필요한 맥락은 요약과 함께 제시).

## C-032. 진행 중 작업 보호: 완주 기본값 + 충돌 시 이의 제기 의무

상태: ACCEPTED · escalated-as D-083 · 소유: 컨설턴트 · 관련: strengthens D-028(선완료 행동)·D-074(시퀀싱) · 2026-07-15
(총괄 회부 077 안건 2. 사례 2 — 073 확대 → 076 정정)

결정
1. 완주 기본값: 이미 착수된 작업은 기본적으로 완주한다. 총괄이 중단·선점시키려면 "무엇이 왜 막히는가"를
   근거로 제시해야 하며, 근거 없는 순서 재편은 진행 중 작업을 중단시키지 못한다.
2. 이의 제기는 권한이 아니라 의무: 총괄 지시가 자기 진행 중 작업과 충돌하면 해당 파트는 즉시 이의를 제기한다.
   침묵은 규약 위반이다.
3. 중단이 정당한 경우: 진행 중 작업의 산출물이 파생으로 무효화됨이 근거로 입증될 때만. 그 외(순서 선호·정리 편의)는 완주.

이유
- 사례 2 실물: 073이 V4를 전체 선행 1번으로 올려 진행 중 023을 무효화할 뻔했다. 실제로 023(순수 파일 이동)은
  V4에 막히지 않았고 076이 원 판단으로 환원했다. 기본값이 완주였다면 총괄의 확대가 자동 무해화된다 —
  근거를 대야만 중단되므로.
- 비용 비대칭: 중단은 투입분 폐기 + 재개 시 컨텍스트 재구축을 부른다. 반면 완주 비용은 대개 작다
  (076이 실측으로 보여줌 — 대부분의 "선행"은 실제로 충돌하지 않았다).
- 이의를 권한으로 두면 쓰이지 않는다. 사례 2에서 백엔드는 권한이 있었으나 침묵했고 사용자가 잡았다.
  의무로 두어야 침묵이 위반이 되고, 현장 지식이 총괄 오류를 자동 교정한다(안돈: 현장의 정지 의무).
- 076이 이미 "진행 중 작업이 총괄 지시와 충돌하면 즉시 알려라 — 그럴 권한이 있다"고 지시했다.
  권한에서 의무로 승격해 규약화하는 것이다.

기각된 대안
- 중단/선점/완주 판정 매트릭스 신설: 케이스 열거라 유지·학습 비용이 크다. 실제 판단은 "근거 있나" 한 질문으로 끝난다. 과설계.
- 총괄 판단 우선(현행 관행): 사례 2 재발.
- 중단 전 사용자 승인: 중계 턴 추가. 근거 제시 의무로 충분하다.

레퍼런스: 도요타 안돈 코드(현장의 라인 정지 의무), 중단 비용 비대칭, D-028 선착순 기준 금지의 연장.

## C-033. 파생 범위 판정: 발견자 기본값 + 총괄 시퀀싱 경계

상태: ACCEPTED · escalated-as D-084 · 소유: 컨설턴트 · 관련: refines D-074(1항), relates-to D-006(위임)·D-016(기준 위계) · 2026-07-15

결정

이유

  총괄이 문서 수준에서 전체 선행으로 확대한 것이 틀렸다.

  원인이었다"고 실천했다. D-074에 경계선 1줄을 추가해 성문화하는 것이다.
- D-006 위임 원칙과 정합: 구현 기법 선택이 백엔드 자율이면, 유닛 순서도 그 일부다.

기각된 대안
- 총괄 판정(현행 관행): 사례 2 재발. 총괄에겐 실측 접근권이 없다.
- 협의로 합의: 왕복 증가 + 교착 시 결론 없음. 기본값 + 확대 시 입증 책임이면 왕복 1회로 끝난다.
- 발견자 판정 절대(총괄 확대 전면 금지): 발견자가 자기 작업만 보고 전역 의존을 놓칠 수 있다.
  근거 있는 확대는 열어둔다.

레퍼런스: 현지현물(실측 우선), D-006 위임 원칙, subsidiarity(결정은 정보가 있는 최말단에서).

## C-034. 파생 뿌리 점검 1문 — 계보 표 미도입

## C-035. 부재 증명의 근거는 탐색 방법 명시 (D-043 일반화) — '도구 사각지대' 일반 규약은 기각

상태: ACCEPTED · escalated-as D-086 · 소유: 컨설턴트 · 관련: generalizes D-043(교차검증), relates-to D-082(근거 인용)·C-003 · 2026-07-15
(총괄 회부 management/outbox/078 참고 항목 — 검증 도구 사각지대 3건 판단)

결정
1. **3건을 묶는 "도구 사각지대" 일반 규약은 만들지 않는다.** 총괄 심증대로 공허해진다.
   세 건은 실패 계열이 서로 다르기 때문이다 — (1) QA 기준에 erd 누락 = **기준 커버리지** 결함,
   (2) bash 마운트 stale = **환경 결함**, (3) import 기준 grep = **질의 방법** 오류.
   공통점은 "도구를 믿었는데 못 봤다"는 서술 수준일 뿐 메커니즘이 아니다. 메커니즘이 다른 것을
   한 규칙으로 묶으면 검증 불가능한 훈계가 된다. 각 건은 국소 조치(075 / D-043 / 백엔드 자체)로 종결.
2. **다만 (2)·(3)이 공유하는 좁은 메커니즘 하나만 D-043의 일반화로 성문화한다.**
   탐색 결과의 **부재("없음")나 수량("N건")을 결정·보고의 근거로 삼을 때는 탐색 방법을 1구 명시한다**
   (예: "import 기준 grep", "호스트 Read 교차확인"). 방법을 명시할 수 없으면 근거로 쓸 수 없다.
3. D-082(근거 인용)의 대칭 조항으로 편입한다 — **근거는 있으면 인용, 없으면 방법**. 신규 필드·문서 없음.
4. 적용 범위를 과장하지 않는다: 본 조항은 (1) 기준 커버리지 계열을 잡지 못한다. 그건 075로 종결된 별건이다.

이유
- **부재 증명은 비대칭이다.** 긍정 결과는 자기 증명적이지만(찾았으면 실재한다), 부재·수량은 전적으로
  도구의 커버리지에 의존한다. 사각지대는 언제나 거짓 음성으로만 나타나므로, 부정 결과가 정확히
  사각지대가 무는 지점이다. 그래서 "도구 일반"이 아니라 "부정 결과"로 좁히면 규칙이 공허해지지 않는다.
- 사례 (2)·(3)은 같은 메커니즘의 두 사례다: bash가 "파일 없음"(실제로는 stale 뷰), grep이 "참조 N건"
  (실제로는 동일 패키지 사용처 누락). 둘 다 부재·수량을 단일 도구 결과로 단정했다.
- 방법 명시는 절차를 추가하지 않고 형식에 내장한다 — "import 기준 grep"이라고 쓰는 순간 동일 패키지
  누락이 작성자·독자 모두에게 드러난다. D-082가 인용으로 실재를 강제한 것과 정확히 같은 장치의 대칭이며,
  추가 학습 비용이 없다.
- **D-043이 이미 이 규칙의 1호 사례다.** 마운트 stale 한 도구에만 교차검증을 걸어둔 상태다. 일반화하지
  않으면 도구가 바뀔 때마다 D를 새로 발번하게 된다(grep용, 다음 도구용). 예외·개별 규칙이 누적되는 것은
  기본값이 틀렸다는 신호다(C-003 논리). 일반화가 규약 증식을 막는 쪽이다.
- 비용: 부정 결과를 근거로 쓸 때 1구 덧붙이는 것뿐. 모든 탐색에 부과되지 않고 "근거로 삼을 때"로 한정된다.

기각된 대안
- "도구 사각지대를 인지하라" 일반 규약 신설: 검증 불가능·공허. 총괄 심증이 옳다.
- 규약화 전면 불요(국소 조치만): D-043이 이미 1호로 존재하므로 일반화 없이는 도구별 D 증식으로 귀결.
  국소 조치의 합이 규약보다 무거워지는 지점이다.
- 도구별 사각지대 목록 문서화: 도구가 바뀌면 즉시 낡는 부채. 유지 주체도 없다.

레퍼런스: absence of evidence ≠ evidence of absence(부재 증명의 비대칭), D-043(교차검증 1호 사례),
C-003(예외 누적은 기본값 오류 신호), D-082 근거 인용의 대칭.

## C-036. 결정 권한 2축 분리 — 체계는 컨설턴트 종결, 프로젝트는 총괄 종결

상태: ACCEPTED · 소유: 컨설턴트 · 관련: 사용자 직접 지시, refines D-006(위임 경계), relates-to D-012 · 2026-07-15

결정
- 결정을 두 축으로 가른다. 각 축의 종결자가 자기 축을 **단독 종결**한다.
  1. **체계 축** — 규약·규칙·보고 체계·문서 체계·절차·형식. 종결자 = **컨설턴트(C)**.
  2. **프로젝트 축** — 기능·범위·스케줄·시퀀싱·도메인·계약. 종결자 = **총괄(D)**.
- 컨설턴트의 체계 결정은 총괄 승인을 거치지 않는다. C-xxx에서 종결하며 D 재발번을 하지 않는다.
- 총괄의 기능·스케줄 결정은 컨설턴트 승인을 거치지 않는다.
- 한 안건이 두 축에 걸치면 각 축의 종결자가 자기 축만 결정한다. 한쪽이 다른 쪽을 대신 정하지 않는다.
- 최종 결정권자는 사용자로 불변(D-006).
- decision-index는 축과 무관하게 전체 ID 목차를 유지한다(총괄 소유).

이유
- 사용자 직접 지시: "규약·규칙·보고체계 등은 모두 컨설턴트가 승인·결정한다. 총괄은 프로젝트 내의
  기능·스케줄 같은 것만 승인·결정한다."
- 종전 흐름(C 발번 → 총괄 D 재발번)은 같은 결정을 두 번 기록하고 왕복을 1회 추가했다. C-001~035
  전건이 escalated-as D-xxx로 이중 등재됐고, 내용은 총괄이 재작성하지 않았다 — 승인이 실질 심사가
  아니라 통과 의례로 작동한 실적이다.
- 축을 분리하면 D 로그에서 규약이 빠져 프로젝트 결정만 남는다. 이번 개편의 목표(규약/작업 분리)와
  권한 구조가 같은 방향으로 정렬된다.

기각된 대안
- 현행 유지(C → D 재발번): 이중 등재·왕복 유지. 사용자 지시에 반한다.
- 컨설턴트가 전 축 종결: 기능·스케줄까지 가져오면 총괄이 공동화된다. 사용자 지시 범위 밖.

집행: common/rules.md [1](역할·축)·[2.3](수신처 분기)·[3](유형 2 변경 규칙)·[3.6](기준 위계)·
[4.6~4.7](에스컬레이션)·[4.11](인덱스)·[7.1](게이트 기준 개정). 총괄 앞 정보 공유 발신 필요.

## C-038. 규약 편입 3문 테스트 — 특정 작업 내용의 규약 유입 차단

상태: ACCEPTED · 소유: 컨설턴트 · 관련: depends-on C-037, relates-to D-014(문서 유형) · 2026-07-15

결정
- 공통 규약(`common/rules.md`) 편입은 3문 전부 "예"일 때만 허용한다. 하나라도 "아니오"면 결정 로그로 보낸다.
  1. **재사용** — 앞으로 새로 시작할 작업에도 적용되나?
  2. **고유명사** — 도메인명·파일명·ID·버전·날짜를 지워도 규칙이 성립하나?

이유
- 사용자 지적: "이미 작업이 완료된 특정 작업의 규칙들을 매번 다른 대화에서 참고하여 낭비하게 되는 문제."

- 경계 사례 D-081(soft delete UK)은 Q1 통과·Q2 탈락으로 "규약이 아니라 코드 컨벤션(CLAUDE.md)"이
  판정됐다. 테스트가 규약/지침/스펙의 층 구분까지 수행함을 확인했다.
- 이유를 규약에 쓰면 규약이 로그를 닮아가고 두 번째 decision-log가 생긴다 — 현 decision-log가 정확히
  그렇게 비대해졌다.
- 덮어쓰기의 부수 효과: 부분 SUPERSEDE(D-043·D-069·D-072)의 "본문은 유효, 일부 조항만 대체" 가독성
  문제가 구조적으로 소멸한다. 로그는 이력이므로 그대로 두면 된다.

기각된 대안
- 규약 문서도 불변·append: decision-log가 하나 더 생길 뿐. 현행 문제의 복제.
- 판정 기준 없이 사람 판단: 지금이 그 상태다. 기준이 없으면 경계 사례마다 재논쟁한다.

한계 (자진 명시)
- 3문 테스트는 판정을 **명시적으로** 만들 뿐 **정확하게** 만들지 않는다. 경계 사례는 여전히 오판 가능하며,
  효과는 "틀렸을 때 드러남"이지 "안 틀림"이 아니다.
- 규약↔로그 이중 관리 위험이 새로 생긴다. 방어는 `집행:` 같은 커밋 반영(C-036 [4.10])뿐이며 이는
  장치가 아니라 규율이다.

집행: common/rules.md 머리말(편입 기준)·[3.1]·[9], 문서 유형 표 유형 2 변경 규칙.

## C-040. sandbox git 실행 금지 — 마운트 뷰 절단이 저장소를 파손한다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: extends D-090(호스트 정본), reinforces D-061(커밋 단일 실행),
근거 관측 = ux/outbox/014(디자인) · 2026-07-15

결정
- **sandbox(bash)에서 `git add`·`git commit`을 실행하지 않는다.**
- `git status`·`git diff`의 **내용 판단**도 근거로 쓰지 않는다. 변경 파일 목록은 호스트에서 확인한 것을 정본으로 한다.
- bash git은 `git log` 등 워크트리 내용과 무관한 조회에만 쓴다.

이유
- 디자인 관측(ux/outbox/014): 마운트 뷰는 stale이 아니라 **파일을 줄 중간에서 절단**해 서빙한다
  (절단량 8B~11KB, 파일마다 제각각). git은 그 절단된 워크트리를 읽으므로 sandbox에서 커밋하면
  **절단된 내용이 저장소에 들어간다.** `git diff --stat`이 허구의 삭제 218줄을 보고한 실물이 있다.
- **실패 신호가 없다.** git은 정상 종료하고 "N files changed"를 보고한다. 절단을 사용자의 삭제로 해석한다.
- D-090은 "판단 근거로 쓰지 마라"까지다. 도구가 스스로 읽는 경로는 덮지 못한다 — 사람이 판단에 쓰든
  안 쓰든 git은 워크트리를 읽는다. **한 층 아래의 규칙이 필요하다.**
- D-061(커밋은 사용자가 호스트에서 단일 실행)이 현재 이 경로를 막고 있으나 **우연이다.** D-061의 사유는
  감사 추적·사용자 통제이지 저장소 무결성이 아니다. 누군가 "CC가 커밋까지 하면 왕복이 준다"며 D-061
  완화를 제안할 때, 명시적 금지가 없으면 그 제안이 합리적으로 보인다. 완화 비용이 실제로는 저장소 파손이다.
- 디자인은 "D-061이 막고 있으니 신규 규약 제안 안 함"으로 판단했다. 그 판단은 현 상태에선 옳으나
  **방어가 부수 효과에 의존하는 구조**를 남긴다. 의존을 명시로 바꾼다.

기각된 대안
- 신규 규약 없이 D-061에 위임(디자인 판단): 방어가 우연에 기댄다. D-061 완화 제안 시 무방비.
- D-090 본문 개정: 로그 불변([4.1]) 위반. 확장 항목으로 별도 발번이 맞다.
- 마운트 뷰 절단 자체를 회피하는 도구 규칙: 원인이 환경이라 프로젝트 규약으로 통제 불가.

한계 (자진 명시)
- 이 규칙은 **발견 확률을 올리지 방지하지 않는다.** 절단은 여전히 일어나며, 규칙은 그 위에서
  사람이 위험한 동작을 하지 않게 할 뿐이다.
- 원 관측자는 디자인이다. 내 기여는 "우연한 방어를 명시로 승격"뿐이며 현상 규명은 ux/outbox/014가 했다.

## C-041. 메시지 대기 상태를 손으로 관리하지 않는다 — 상태 줄 제거, grep 파생

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes D-023(상태 줄 조항), relates-to D-085(기존 그래프 활용) · 2026-07-15

결정
- **outbox 파일의 `상태: SENT | ANSWERED` 줄을 폐지한다.** outbox 파일은 발신 후 고치지 않는다(불변).
- 발신 시 `회신: 필요 | 불요`를 **한 번** 기재하고 이후 아무도 갱신하지 않는다.
- 대기 큐는 두 번의 탐색으로 **파생**한다:
  대기 중 = (`회신: 필요` 파일) − (어떤 파일이 `회신대상:`으로 지목한 파일)
- 세션 출근 시 각 역할이 자기 앞 대기 큐를 이 방법으로 산출한다.

이유
- **실측: outbox 214건 중 130건(61%)이 `상태: SENT`에 멈춰 있다.** 규약은 있었고 지켜지지 않았다.
- 그 130건에 성격이 다른 셋이 섞였다 — (1) 진짜 대기 (2) 회신 불요라 영원히 SENT(정상)
  (3) 답이 왔는데 미갱신. **셋이 같은 라벨을 쓰므로 grep이 신호를 못 준다.** 진짜 대기 10여 건이
  120건의 노이즈에 묻혔다. 이것이 "보고가 밀려 소실된다"의 메커니즘 — 밀린 게 아니라 안 보인다.
- **원인은 인센티브다.** 상태 줄은 발신자가 갱신해야 하는데, 발신자는 회신을 대화에서 읽고 끝낸다.
  파일로 돌아가 상태를 고치는 것은 별도 노동이고 발신자에게 이득이 없다. 61%가 그 증거다.
  규약이 성실성에 기대면 이렇게 된다.
- **이미 알려진 문제였다.** `management/outbox/089-기획-028검수-상태줄미갱신-...` — 총괄이 개별 사례로
  한 번 지적하고 구조를 고치지 않았다. 개별 지적으로는 61%가 안 줄어든다.
- 회신 링크(`회신대상:`)는 102건 존재하며 회신 파일에 필수다. **이미 정확한 그래프가 있는데
  그것과 중복되는 상태를 손으로 또 관리하고 있었다.** D-085가 "기존 필드가 이미 그래프를 이룬다"고
  한 그 그래프다. 쓰면 되는 것을 안 쓰고 있었다.

기각된 대안
- 상태 줄 유지 + 갱신 의무 강화: 이미 규약이었고 61% 실패했다. 같은 처방의 반복.
- 상태 줄 + grep 병존: 둘이 어긋나면 어느 쪽이 맞는지 다투게 된다. 단일 진실 위반.
- 중앙 큐 파일 신설: 갱신 주체·시점 문제가 그대로 옮겨간다. 문서만 늘고 같은 병.

한계 (자진 명시)
- 파생 큐는 `회신대상:` 기재에 의존한다. 그것이 누락되면 큐가 틀린다. 다만 회신대상은 **회신 작성
  시점에 쓰는 필드**라 사후 복귀 노동이 아니며, 누락 시 "답이 없는 것으로 보이는" 안전한 방향으로 틀린다.
- 기존 130건의 SENT 부채는 소급 정리하지 않는다. `_archive/` 이관으로 함께 봉인된다(C-037).

집행: common/rules.md [3](유형 5 불변)·[5.12]~[5.16]. templates.md 메시지 골격에서 상태 줄 제거.

레퍼런스: Event Sourcing — "events as the single source of truth", 파생 상태(materialized view)는
ephemeral하며 손상 시 재생성(microservices.io/patterns/data/event-sourcing, verraes.net, AWS
Prescriptive Guidance). outbox가 event store인데 그 옆에 상태를 중복 저장한 것이 61% 불일치의 구조적 원인.
Kanban 보드 status drift — "An outdated board is worse than no board at all"(Meister).

## C-042. 총괄 라우팅 폐지 + 위험 기반 검수 — 파트 직통을 기본값으로

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines D-006(위임), relates-to C-036(축 분리), D-023(파일 버스) · 2026-07-15

결정
- **파트끼리 직접 보낸다.** 정합·질의·핸드오프·통지는 총괄을 경유하지 않는다.
- 총괄로 보내는 것은 4종뿐이다: 에스컬레이션 4기준 · 게이트 판정 요청 · 계약 변경 요청 · 파트 간 충돌.
- **총괄 검수는 위험 기반으로 한다.** 확정 스펙 변경·게이트 판정·파트 간 충돌만 검수하고,
  파트 내부에서 닫히는 산출물은 검수하지 않는다.
- 파트 직통 합의가 나중에 계약·범위에 닿는다고 판단되면 발견 즉시 격상한다.
- 전 역할 전파는 `_broadcast/` 스레드로 총괄이 계속 담당한다(라우팅이 아니라 방송).

이유
- **실측: 전체 outbox 214건 중 management 발신이 99건(46%)이다.** 총괄 혼자 절반을 발신한다.
  파트→총괄→파트 2홉이 기본값이 됐고, **매 홉마다 사용자가 대화를 복사해 중계한다** — 총괄 경유는
  사용자 손을 2배로 만든다.
- 실측 사례(098 트리): `backend/022`(계약 공백 발견) → `management/068`(승인) → `management/069`(기획
  지시) → `design/027`(명세). 백엔드가 발견한 것이 기획에 닿는 데 총괄 메시지 2건이 낀다.
  **승인과 전달은 다른 일인데, 승인권이 있다는 이유로 전달까지 총괄이 하고 있었다.**
- **전건 검수가 품질을 보장했다는 증거가 없다.** 총괄 자신의 서술(099): "11건 중 대부분이 총괄
  결함에서 나왔다", "이번 세션의 문제는 대부분 파트가 잡아낸 것 — 프론트가 계약 버전 불일치를,
  디자인이 총괄 지시값 stale을, 백엔드가 계약 공백 2건을, QA가 검증 기준 누락을 잡았다."
  **검출은 파트가 했고, 총괄은 전건을 경유하고도 자기 결함을 못 잡았다.** D-082(근거 인용 의무)가
  생긴 이유 자체가 총괄이 실재하지 않는 근거로 착수 지시를 낸 사건(`management/066`)이다.
- 병목의 진짜 위험은 C-041과의 곱이다. 총괄이 단일 라우터인데 밀린 큐가 안 보이면(61% SENT 노이즈)
  총괄 세션이 밀리는 순간 전체가 밀리고 밀린 것이 소실된다. **C-041이 가시성을, C-042가 단일
  장애점을 제거한다. 둘 중 하나만 하면 절반만 풀린다.**
- 파트의 축 판정 능력은 실증됐다. `backend/022`에서 백엔드가 "이건 계약 공백이다, 6절로 격상"을
  스스로 판정했다 — 총괄이 시켜서가 아니다. 현 구조는 그 능력을 놀리고 있었다.

기각된 대안
- 현행 유지(총괄 전건 경유): 46% 발신·2홉 왕복·사용자 중계 2배·단일 장애점 유지.
- 라우팅만 제거하고 전건 검수 유지: 검수 큐가 그대로라 병목이 절반만 풀린다.
- 직통 + 총괄 사후 통보 의무: 통보 자체가 또 하나의 메시지다. 왕복을 줄이려다 늘린다.

한계 (자진 명시)
- **총괄이 모르는 상태가 생긴다.** 파트 A·B의 합의가 계약에 닿는 것이었으면 뒤늦게 깨진다.
  방어는 [2.3] 수신처 분기와 [6] 계약 변경 절차이며, **"이건 계약에 닿나"의 판정을 파트에게
  맡기는 것이 이 설계의 도박이다.** 지금은 총괄이 전부 봐서 (이론상) 안전한 대신 병목이었다.
- 검수를 줄이면 총괄이 실제로 잡던 것도 놓친다(`089` 상태 줄 미갱신, `091` U 인덱스 백필은
  총괄 검수가 잡은 실적이다). 다만 전자는 C-041로 구조 소멸했고, 후자 유형은 위험 기반 검수 범위에
  남는다는 것이 상쇄 논거다.

집행: common/rules.md [1.5]·[5.1]~[5.5]·[7.3]. 총괄 앞 정보 공유 발신 필요(권한·경로 변경 통지).

레퍼런스: Team Topologies — 중앙 팀이 "perform operations on behalf of" 하면 병목·의존이 생긴다;
확장 가능한 상호작용 모드는 X-as-a-Service이고 Collaboration은 한시적이어야 한다; 인지 부하 초과가
병목 팀의 원인(teamtopologies.com, martinfowler.com/bliki/TeamTopologies.html).
총괄의 올바른 모드 = X-as-a-Service(게이트 판정·계약 승인을 서비스로 제공)이지 상시 Collaboration이 아니다.
46% 발신은 인지 부하 초과의 증상으로 읽힌다.

## C-043. handover는 착수 시 쓴다 — 퇴근 산출물에서 작업 중 상태 파일로 (WAL 순서)

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes D-059(작성 시점 조항), depends-on C-042 · 2026-07-15

결정
- `<역할>/notes/handover.md`를 **퇴근 산출물이 아니라 작업 중 상태 파일**로 재정의한다.
- 기록 시점을 뒤집는다: **착수 시 먼저 쓴다** → 국면 전환 시 갱신 → 완료 시 해당 항목 삭제 →
  퇴근 시 정리(이때 처음 쓰는 것이 아니다).
- 일을 끝내고 나서 handover를 쓰는 것을 금지한다.

이유
- **사용자 지적**: "핸드오버는 퇴근이 진행되어야 작성되는 파일인데 한참 일하는 도중에 문제가
  발생하면 어떻게 되는가." 세션은 예고 없이 끊긴다(컨텍스트 소진·창 종료·중단).
- 종전 설계(퇴근 시 덮어쓰기)는 **작업을 먼저 하고 로그를 나중에 쓰는 순서**다. WAL이 정확히
  금지하는 순서이며, 중간에 끊기면 "변경은 됐는데 무엇이 변경됐는지 기록이 없는" 상태가 된다.
- WAL의 intent/completion 쌍 구조를 그대로 차용한다 — 작업 시작 시 intent record를 append하면
  어느 시점에 끊겨도 마지막 intent가 남아 복구 가능하다.
- 부수 효과: C-042의 총괄 pull 스캔([8.8])이 "진행 중"을 handover에서 읽는데, 퇴근 시에만
  쓰이면 **진행 중인 작업은 영원히 handover에 없다.** 시점을 뒤집어야 pull 설계가 성립한다.
  종전 설계는 이 점에서 자기모순이었다.

기각된 대안
- 퇴근 시에만 유지: 비정상 종료 시 세션 작업 통째 소실. 사용자 지적을 해소 못 함.
- 매 응답마다 갱신 의무: 갱신 부담이 과다하고, 부담이 크면 안 지켜진다(상태 줄 61% 교훈).
  국면 전환 시로 한정하는 것이 비용/효익 균형점.
- outbox만으로 복구: outbox는 발신된 것만 담는다. 발신 전 진행 중 작업은 어디에도 없다.

한계 (자진 명시)
- "국면 전환"의 판정이 주관적이다. 갱신을 게을리하면 여전히 최신이 아니다. 다만 착수 시점 1회는
  기계적으로 강제되므로, 최악의 경우에도 "무엇을 시작했는지"는 남는다 — 종전엔 그것도 없었다.

집행: common/rules.md [8.1]~[8.5], [8.7]. templates.md [8] handover 골격.

레퍼런스: Write-Ahead Logging — "The system logs the intent to change first instead of writing data
directly"; "every operation is logged as a pair of intent and completion records, and when an
operation begins, an intent record is appended"; "if the database wrote the data page first and the
log later, a crash in the middle could leave the system with updated pages but no record of what
changed"(en.wikipedia.org/wiki/Write-ahead_logging, sookocheff.com ARIES, PostgreSQL WAL).

## C-044. 현황 파일(common/status.md) 신설 — 정본이 아니라 재생성 가능한 뷰

상태: ACCEPTED · 소유: 컨설턴트 · 관련: depends-on C-041·C-042·C-043, supersedes D-026(통합 추적 표) · 2026-07-15

결정
- `common/status.md`를 신설한다. 스레드별 `시작 전 / 진행 중 / 대기 / 완료`를 담는다.
- **정본이 아니라 뷰(read model)다.** `outbox/`·`handover.md`와 어긋나면 **후자가 맞다.**
- 낡거나 틀리면 고치지 않고 **지우고 재생성한다.** 근거로 인용하지 않는다.
- 총괄이 출근 스캔([8.8])의 부산물로 덮어쓴다. 3열은 파생하고, `시작 전`만 손으로 적는다
  (총괄의 시퀀싱 계획이라 파생 불가).

이유
- **사용자 요구**: "나도 진행상황을 알 수 있도록 시작전·진행중·완료 등 파생된 작업까지의 현황을
  알 수 있는 참고 파일이 있어야 하지 않나." 정당한 요구다 — 현재 사용자는 전체 상태를 볼 곳이 없다.
- 긴장: 손으로 관리하는 상태 파일은 썩는다(상태 줄 61% 실증). Kanban 문헌이 같은 경고를 한다 —
  "An outdated board is worse than no board at all; it gives false confidence while hiding real
  problems." 이 프로젝트의 반복 교훈("거짓 안심은 사각지대보다 위험")과 정확히 같다.
- 해소: Event Sourcing의 read model 개념. **정본(event store) = outbox + handover, 뷰(read model)
  = status.md.** 뷰는 ephemeral하므로 썩어도 무해하고, 손상 시 정본에서 재생성한다.
  "If a read model becomes corrupted, it can be safely deleted and completely rebuilt."
- 재생성 비용이 0인 것이 이 설계의 성립 조건이다. 총괄이 C-042에 따라 어차피 전 역할을 스캔하므로
  ([8.8]) 그 결과를 파일로 떨구는 것뿐이다. 별도 노동이 없으므로 "안 하게 되는" 실패 모드가 없다.
- D-026(통합 추적 표)를 대체한다. 추적 표는 손 관리 전제라 같은 병에 걸린다.

기각된 대안
- 파일 없이 총괄 브리핑으로만: 사용자가 임의 시점에 열어볼 수 없고 총괄 세션에 의존한다.
- status.md를 정본으로: 상태 줄 61% 실패의 대형 재판. 갱신 주체·시점 문제가 그대로 부활한다.
- 각 파트가 자기 status를 갱신: 갱신 주체가 7개로 늘어 어긋남이 7배. 파생을 버리고 손 관리로 회귀.

한계 (자진 명시)
- **뷰는 총괄이 출근해야 갱신된다.** 총괄 세션이 오래 안 열리면 status.md는 낡는다. 이때 사용자가
  낡은 것을 최신으로 오독할 위험이 있고, 그것이 정확히 Kanban 문헌이 경고한 실패 모드다.
  방어는 [8.13](어긋나면 정본이 맞다)·[8.15](근거 인용 금지) + 헤더의 생성 시점 표기뿐이며,
  **이는 오독을 막지 못하고 드러낼 뿐이다.**
- `시작 전` 열은 파생 불가라 손 관리다. 이 열만은 썩을 수 있다.

집행: common/rules.md [8.10], [8.12]~[8.16], [10]. templates.md [10] status 골격.

레퍼런스: Event Sourcing read model / materialized view — 파생 상태는 ephemeral, 손상 시 재생성
(microservices.io, AWS Prescriptive Guidance, martendb.io). Kanban board status drift —
"An outdated board is worse than no board at all"(meistertask.com), "board statuses gathering dust".

## C-045. docs 커밋을 대화에서 분리 — 트리거는 사용자의 `커밋` 지시 1회

상태: **SUPERSEDED (→ C-046)** · 소유: 컨설턴트 · 관련: supersedes D-029(이벤트 커밋 조항),
depends-on C-042·C-043, relates-to D-061(실행 일원화 — 유지) · 2026-07-15

> **대체 사유(2026-07-15)**: 분류 축이 틀렸다. 이 항목은 커밋 대상을 `코드 / docs`로 갈랐으나,
> 사용자가 지목한 경계는 `산출물 / 대화 로그`이며 그 선은 **docs 안을 지나간다.**
> 이 항목대로면 산출물 커밋(spec·design-system·findings 등)까지 배치로 미뤄져 과녁을 벗어난다.
> C-046이 축을 정정해 대체한다. 아래 본문은 이력으로 보존한다([4.1] 불변).

결정
- **docs 커밋을 대화·퇴근에 묶지 않는다.** 사용자의 `커밋` 지시가 유일한 트리거다.
- 그때 **총괄이 전체 스캔 결과([8.8])로 `docs: <요지>` 1건을 조립해 제안한다.**
- **파트는 커밋 메시지를 제안하지 않는다.** 대화 수와 커밋 수를 분리한다.
- git 실행 주체는 사용자로 유지한다(D-061 불변). 스테이징은 `git add docs/`.
- **코드 커밋은 범위 밖이다.** CLAUDE.md 현행 유지 — 코드는 atomic 커밋을 지킨다. docs와 섞지 않는다.

이유
- **사용자 지적**: "작업의 커밋은 직접 진행해도 된다. 다만 오간 대화·로그 등을 매번 하나의 대화를
  할 때마다 진행해야 하는 불편만 없애면 된다." 문제는 실행 주체가 아니라 **빈도**다.
- 종전 D-029는 "이벤트 기반 커밋"이었고 이벤트를 역할 작업 블록으로 잡았다. 역할이 7개이므로
  커밋이 대화 수만큼 발생했다. C-042 직전 개정([9.6] 세션 단위)도 **세션이 역할별이라 N을 못 줄였다** —
  역할 scope만 없앴을 뿐 개수는 그대로였다. 이번이 그 미해결분의 처리다.
- **atomic commit의 이득은 코드용이지 docs용이 아니다.** 문헌의 전제가 "each atomic commit MUST be
  stable and in working order, e.g., the project is buildable without error, tests SHALL pass"인데
  docs는 빌드도 테스트도 없고 bisect 대상도 아니다. 이득이 성립하지 않는 자리에 비용만 지불하고 있었다.
- 문헌의 반대편 경고가 현 증상 그대로다: "Over-granularity can lead to an excessive number of tiny
  commits that are hard to follow... and increased overhead from making many small commits."
  처방도 문헌과 같다: "batching closely related changes to maintain coherence and avoid excessive noise."
- 조립 주체를 총괄로 두는 이유: C-042로 총괄이 이미 전 역할을 스캔한다. 무엇이 바뀌었는지 아는
  유일한 역할이고, 조립이 스캔의 부산물이라 추가 노동이 0이다.

기각된 대안
- 파트별 제안 유지 + 사용자가 모아서 1회 실행: 제안이 N개면 사용자가 N개를 읽고 합쳐야 한다.
  손이 줄지 않고 조립 부담만 사용자에게 전가된다.
- Claude가 docs 커밋 대행: C-040(sandbox git 금지)이 막는다. 마운트 뷰 절단이 커밋된다.
- 시간 기반 커밋(하루 1회 등): D-022 시간 기반 리추얼 배제와 충돌. 사용자가 유일한 클록이다.
- 코드까지 배치 커밋: bisect·revert 입도를 잃는다. 코드는 atomic의 전제(빌드·테스트)가 성립한다.

한계 (자진 명시)
- **커밋 입도가 굵어진다.** 특정 docs 변경만 revert하기 어려워지고, "언제 무엇이 바뀌었나"의
  해상도가 떨어진다. 상쇄 논거는 (1) docs 이력의 정본은 git이 아니라 decision-log·outbox이고
  (2) docs revert는 실적이 없으며 (3) 필요 시 파일 단위 `git checkout`이 가능하다는 것이다.
- 사용자가 `커밋`을 오래 지시하지 않으면 미커밋분이 쌓인다. 유실 위험은 없으나(로컬 존재)
  동기화가 늦어진다. 이는 규칙이 아니라 사용자 재량 영역으로 남긴다.

집행: common/rules.md [8.7](퇴근에서 커밋 제거)·[9.6]·[9.7]·[9.9]. templates.md [9] 커밋 골격.

레퍼런스: Git commit granularity — atomic commit의 전제는 빌드 가능·테스트 통과이며 이득은
bisect·revert 입도(kennyballou.com/blog/2021/03/commit-granularity, aleksandrhovhannisyan.com,
gitbybit.com atomic-commits). 과입도의 비용과 "batching closely related changes" 처방
(pullchecklist.com git-commit-best-practices).

## C-046. 커밋 축은 `산출물 / 대화 로그` — 로그는 독립 커밋을 만들지 않는다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes C-045(축 오류), supersedes D-029(이벤트 커밋 조항),
relates-to D-061(실행 일원화 — 유지) · 2026-07-15

결정
- 커밋 대상을 두 성격으로 가른다. **경계는 docs 안을 지나간다.**

| 성격 | 파일 | 커밋 |
|---|---|---|
| **산출물** | `spec/` 3종 · `<역할>` 루트 산출물(design-system·test-plan·findings 등) · 코드 | 완성될 때. 현행 유지 |
| **대화 로그** | `notes/handover.md` · `inbox-log.md` · `outbox/` · `decision-log.md` | **독립 커밋 없음** |

- **대화 로그는 스스로 커밋을 유발하지 않는다.** 산출물 커밋이 나면 거기 묻어서 실린다.
- **파트는 커밋 메시지를 제안하지 않는다.** 대화 수와 커밋 수를 분리한다.
- 로그가 미커밋으로 쌓일 때의 배치 트리거는 2개다:
  1. **게이트 통과** → 총괄이 전파와 함께 커밋을 자동 제안한다(스캔 결과로 조립, [8.8])
  2. **사용자 `커밋` 지시** → 언제든
- git 실행 주체는 사용자로 유지한다(D-061 불변). 스테이징은 `git add docs/`.
- **코드는 atomic 커밋을 유지한다**(CLAUDE.md). docs와 섞지 않는다.

이유
- **사용자 정정**: "각 파트의 작업 결과물은 그대로 내가 커밋해도 된다. 문제는 대화 log처럼 대화
  한번에 한번씩 발생하는 log의 커밋이다." 부담의 원인은 docs 전체가 아니라 **대화마다 반드시
  생기는 프로세스 부산물**이다. C-045는 이를 `코드/docs`로 잘못 갈라 산출물까지 배치로 묶었다.
- 대화마다 반드시 생기는 것은 `handover`(매 갱신)·`inbox-log`(수신 처리)이고, 자주 생기는 것이
  `outbox` 메시지다. 이 셋이 커밋 수를 대화 수에 고정시킨다.
- **decision-log를 로그 쪽에 넣는 근거**: 항목이 불변([4.1])이고 날짜가 본문에 박혀 있다.
  **git 이력이 정보를 더하지 않는다** — 언제 무엇이 결정됐는지가 이미 문서 안에 있고, 커밋 이력은
  그것의 중복이다. outbox도 동일(불변 + 번호 + 발신 시점 내장).
- **커밋을 미뤄도 기준 위계([3.6])는 작동한다.** 정본은 로컬 파일이지 커밋된 스냅샷이 아니다.
  다른 대화는 미커밋 파일을 그대로 읽는다. 커밋의 역할은 이력이 아니라 백업이며, 백업은 배치로 족하다.
- 게이트를 배치 트리거로 삼는 근거: 게이트는 이미 지식 동기화 앵커다(D-021). 동기화하는 자리에서
  커밋도 함께 끊는 것이 이벤트를 늘리지 않는다. 총괄이 그 시점에 어차피 전체를 스캔한다([8.8]).

기각된 대안
- C-045(코드/docs 축): 산출물 커밋까지 배치로 미뤄진다. 사용자는 산출물 커밋에 불만이 없었다.
- outbox를 산출물로 분류: 역할 간 합의 기록이라 이력 가치가 크다는 논거가 있으나, **불변 + 발신
  시점 내장이라 git 이력이 중복**이라는 점에서 decision-log와 같다. 감축 효과만 잃는다.
- 로그를 아예 커밋하지 않음: 백업이 사라진다. 로컬 유실 시 복구 불가.
- 시간 기반 배치(하루 1회): D-022 시간 기반 리추얼 배제와 충돌.

한계 (자진 명시)
- **게이트 간격이 길면 로그가 오래 미커밋으로 쌓인다.** 유실 위험은 로컬 존재로 낮으나 0은 아니다.
  사용자 `커밋` 지시가 유일한 보완이며, 이는 규칙이 아니라 사용자 재량이다.
- **산출물/로그의 경계에 판정이 필요하다.** `<역할>` 루트의 파일이 산출물이고 `outbox/`·`notes/`가
  로그라는 위치 규칙으로 대부분 자동 판정되나, 경계 사례(예: `qa/defects.md`)는 사람이 정한다.
- 자기 정정: C-045를 발번 10분 만에 대체했다. 축을 확인하지 않고 두 번 잘못 읽은 결과이며,
  사용자가 두 번 정정해 줬다. 분류 축은 설계 전에 실물로 확인했어야 한다.

집행: common/rules.md [8.7]·[9.6]~[9.11]. templates.md [9] 커밋 골격.

레퍼런스: Git commit granularity — atomic의 전제(빌드·테스트)와 이득(bisect·revert)은 코드에만
성립하며 과입도의 비용은 "increased overhead from making many small commits"
(kennyballou.com/blog/2021/03/commit-granularity, pullchecklist.com). 처방 "batching closely
related changes to maintain coherence and avoid excessive noise"를 로그 계열에 한정 적용.

## C-047. 결정 로그 템플릿에 `결과`(트레이드오프) 도입 — 긍정·부정을 한 섹션에

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines C-038(규약 편입), relates-to D-010(로그 상태) · 2026-07-15

맥락
- 종전 템플릿은 `이유`(긍정)와 `한계`(부정)를 **다른 섹션에** 뒀다. 읽는 순서상 이유가 앞이고
  한계가 뒤라 **장점을 팔고 비용을 각주로 붙이는 형태**다.
- C-036~046에서 한계를 성실히 쓴 것은 작성자의 규율이었지 구조의 강제가 아니었다. 규율에 기대는
  장치는 썩는다 — 상태 줄 61% 미갱신이 같은 계열의 실증이다.
- templates.md에 규칙이 숨어 있었다("추천 없는 선택지를 내지 않는다" 등 4건). 규칙이 rules와
  templates 두 곳에 흩어지면 "규약은 한 곳"이라는 이번 개편의 전제가 무너진다.
- templates.md ↔ rules.md 상호 참조가 순환을 이룬다. rules가 형식을 templates로 위임하는데
  templates가 다시 rules를 인용한다.

결정
- 결정 로그 항목 형식을 `맥락 / 결정 / 결과 / 기각된 대안 / 집행 / 레퍼런스`로 한다.
- **`이유` + `한계`를 `결과` 한 섹션으로 합친다.** 하위 3줄: `좋아짐` / `나빠짐` / `못 푸는 것`.
- templates.md에서 **rules.md 역참조를 전부 제거한다.** 참조는 rules → templates 단방향으로 한다.
- templates.md에 숨어 있던 규칙 4건을 rules.md로 옮긴다([4.15]~[4.17], [5.31]~[5.32]).
- **선을 긋는다: 모양은 templates, 행동은 rules.**

결과
- 좋아짐: 비용을 각주로 밀어낼 자리가 사라진다. 작성자가 `나빠짐`을 비우려면 그 사실이 형식에서
  드러난다. 규칙이 rules.md 한 곳으로 모여 "규약은 한 곳"이 실제로 성립한다. 순환 참조가 끊긴다.
- 나빠짐: 기존 C-036~046이 구 형식(`이유`/`한계`)이라 로그 안에 두 형식이 공존한다. 불변([4.2])
  이므로 소급 개정하지 않는다 — 읽는 사람이 두 모양을 보게 된다.
- 못 푸는 것: **형식은 `나빠짐`을 쓰게 만들지 못한다. 비어 있음을 드러낼 뿐이다.** 작성자가
  "나빠짐: 없음"이라 쓰면 구조는 막지 못한다. Nygard의 주장도 "makes it harder"이지 "makes it
  impossible"이 아니다. 효과는 발견 확률이지 방지가 아니다.

기각된 대안
- 현행 유지(`이유`/`한계` 분리): advocacy writing을 구조가 조장한다. 규율에만 의존한다.
- MADR식 `Pros and Cons of the Options` 전면 도입: 선택지별 장단을 전부 쓰면 항목이 비대해진다.
  1인 구조에 과잉이며, `기각된 대안`이 이미 그 역할의 경량판을 한다.
- MADR `Confirmation` 별도 신설: 기존 `집행:` 필드가 같은 역할을 한다(반영처 + 확인 방법).
  이름만 다른 필드를 늘리지 않는다.
- templates에 규칙을 남기고 rules에서 참조: 규칙이 두 곳이 된다. 개편 전제와 충돌.

집행: templates.md [6](결과 도입)·[7](브리핑 3줄)·전 절(역참조 제거).
rules.md [4.15]~[4.17]·[5.31]~[5.32](숨은 규칙 이관). 확인: templates.md에 `rules.md [` 문자열이
0건인지 grep.

레퍼런스: Nygard ADR — "The Consequences section forces honesty, and putting negative consequences
in the same section as positive ones makes it harder to write a decision document that pretends a
choice has no costs"; consequences는 positive·negative·neutral 전부; 결정은 "We will..." 능동태·

## C-048. 사용자 브리핑 재설계 — BLUF + 출처 + 방향

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes D-049·D-063(브리핑 형식), refines C-047 · 2026-07-15

맥락
- **사용자 지적**: "브리핑은 내가 작업을 한번에 볼 수 있는 수단이다. 좀 더 자세해야 하고, 어떤
  작업으로부터 진행되는지 확인되어야 하고, 어떤 파트로 전송했는지도 잘 보여야 한다."
- 직전 설계(C-047의 3줄 압축)는 방향을 거꾸로 잡았다. 브리핑을 **비용**으로 보고 줄였으나,
  사용자에게는 **유일한 전체 조망 수단**이다. 파일 버스는 역할 간 채널이고 사용자는 채팅만 본다.
- 종전 형식(D-049·D-063)의 실제 결함 3가지: (1) 결론이 앞에 없어 다 읽어야 안다 (2) 한 일에
  **출처가 없어 파생 사슬이 안 보인다** (3) 발신·수신이 한 줄에 뭉쳐 방향과 상대가 안 드러난다.

결정
- 브리핑 형식을 5부로 한다: **BLUF 인용줄 / 한 일 / 주고받음 / 발번·상태 / 할 일.**
- **BLUF**: 맨 위 인용줄에 결론 1~2문장. 그 줄만 읽어도 상황을 안다. 2~3문장을 넘기지 않는다.
- **한 일**: 항목마다 `←` 로 **출처**(어느 지시·결정·스레드에서 나왔나)를 명시하고 산출물 경로를 붙인다.
- **주고받음**: `→`(발신)·`←`(수신) 방향 · 파트 · 경로 · 요지 **4개를 모두** 쓴다.
- **할 일**: 동사로 시작하고 이유를 붙인다. 없으면 "없음".
- 없는 섹션은 섹션째 지운다.

결과
- 좋아짐: 사용자가 첫 줄로 결론을 잡고 필요하면 아래로 내려간다(역피라미드). `←` 출처가 파생
  사슬을 매 응답마다 노출하므로, 098이 제기한 "이게 뭐에 관한 거였지"가 브리핑 단계에서 해소된다.
  방향 기호로 "누가 나한테 보냈나 / 내가 누구에게 보냈나"가 한눈에 갈린다.
- 나빠짐: 브리핑이 길어진다. 매 응답 5부를 채우는 작성 비용이 늘고, 짧은 응답에도 형식이 붙는다.
  "없는 섹션은 지운다"가 유일한 완충이다.
- 못 푸는 것: **출처를 쓰게 만들지 못한다.** 작성자가 `←` 뒤에 아무거나 적으면 형식은 통과한다.
  출처가 실재하는지는 사용자가 경로를 열어봐야 안다 — 형식은 빈칸을 드러낼 뿐 거짓을 못 막는다.

기각된 대안
- 3줄 압축 유지(C-047): 사용자의 유일한 조망 수단을 비용으로 오판했다. 사용자 지적으로 철회.
- 표 형식(`| 무엇 | 출처 | 결과 |`): 스캔은 쉬우나 매 응답마다 표를 세 개 그리면 채팅이 무거워진다.
  들여쓴 불릿이 같은 정보를 더 가볍게 담는다.
- status.md로 갈음: status.md는 총괄 출근 시에만 갱신된다(C-044). 매 응답 브리핑을 대신 못 한다.

집행: templates.md [7](5부 골격 + 작성 규칙). rules.md [5.39]~[5.42](BLUF·출처·방향·할 일 규칙).

레퍼런스: BLUF — 미 육군 AR 25-50(1988) 표준, "conclusion and most critical information are placed
at the beginning", 역피라미드·연역적 제시, 목표 2~3문장("A BLUF that runs six sentences is just a
regular paragraph"), 5W를 빠르게 답할 것(en.wikipedia.org/wiki/BLUF_(communication), animalz.co).
GitLab async standup — "all standup content links directly to GitLab issues or epics"(출처 링크),
blocker에 "specific people tagged"(상대 명시), 3부 구조 accomplishments/in progress/blockers,
"less than five minutes to write and even less time to read"(docs.gitlab.com, fullscale.io).

## C-049. `common/structure.md` 미도입 — 지도는 문서가 아니라 배치다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes C-037(structure.md 계획분), relates-to C-001(Diátaxis 원용) · 2026-07-15

맥락
- C-037에서 `common/` 3장(`rules` · `templates` · `structure`)을 계획했다. `structure.md`의 목적은
  "문서 지도 — 뭐가 어디 있고 누가 소유하나"였다.
- 착수 전 검증하니 그 질문에 이미 답이 있다. `rules.md [3]` 유형 표가 위치·소유·변경 규칙을 담고,
  `[10]` 정본 경로 표가 "이건 여기 없고 어디 있다"를 담는다.
- 이번 개편의 제약은 "규약을 정리하면서 규약을 늘리면 자기모순"이다. 계획했다는 이유로 만들면
  그 제약을 설계자가 먼저 깬다.

결정
- **`common/structure.md`를 만들지 않는다.** `common/`은 `rules.md` · `templates.md` 2장 + `status.md`(뷰)로 확정한다.
- 전체 배치를 보여주는 **폴더 트리 1개를 `rules.md [3]` 머리에 넣는다.**

결과
- 좋아짐: 파트가 익힐 문서가 하나 줄고 부팅 진입점이 3개로 유지된다. 위치·소유 정보가 한 곳
  (`rules.md [3]`)에만 있어 이중 관리가 생기지 않는다.
- 나빠짐: `rules.md [3]`이 트리 + 유형 표 + 규칙 11개로 무거워진다. 절이 커지면 읽기 부담이 늘고,
  나중에 트리와 유형 표의 위치 정보가 서로 어긋날 여지가 생긴다(같은 절 안이라 발견은 쉽다).
- 못 푸는 것: **discoverability(몰랐던 것을 마주침)를 개선하지 않는다.** 트리는 findability만 준다.
  다만 파트가 8개이고 폴더 구조가 고정이라 탐색할 미지 영역이 실질적으로 없다 — 지금은 문제가
  성립하지 않으며, 파트나 문서 종류가 크게 늘면 재검토 대상이다.

기각된 대안
- `structure.md` 신설(C-037 원안): 문서 수 순증. `rules.md [3]`·`[10]`과 위치 정보가 이중 관리된다.
- 트리를 `templates.md`에 두기: templates는 산출물의 모양을 담는다. 폴더 배치는 모양이 아니다.
- 트리 없이 유형 표만: 표는 유형별 나열이라 전체 배치가 시각적으로 안 잡힌다. 트리 1개의 비용은 낮다.

집행: rules.md [3] 폴더 트리 추가, 유형 2 위치에서 `structure.md` 제거.
확인: docs 전역에 `structure.md` 문자열이 0건인지 grep.

레퍼런스: Diátaxis — "Diátaxis is not just a list of four different things, but **a conceptual
arrangement** of them"(지도는 별도 문서가 아니라 배치 자체); explanation은 "serve the user's study,
not their work"(일하러 온 파트의 부팅 필독에 explanation을 넣지 않는다)(diataxis.fr, diataxis.fr/start-here).
Information Architecture — top-level navigation은 3~5개로 제한해 "reduces choice paralysis";
findability(있다고 가정한 것을 찾음) vs discoverability(몰랐던 것을 마주침) 구분; wayfinding은
contextual links·next steps로 달성(nngroup.com/articles/ia-study-guide, abbycovert.com,
idratherbewriting.com doc-navigation).

## C-050. `common/`·`spec/`은 공용 폴더 — 소유는 폴더가 아니라 파일에 붙는다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines C-044(status.md 소유), corrects C-037(폴더 소유 모델) · 2026-07-15

맥락
- **사용자 지적**: "공통 폴더 자체는 총괄도 컨설턴트도 같이 볼 수 있지 않은가?"

  `status.md`를 쓰는 것이 **예외**가 됐다.
- **같은 문서가 두 말을 하고 있었다.** 유형 7 표에는 `common/status.md (소유: 총괄)`이라 쓰고,
  `[3.4]`에서는 "common/은 컨설턴트가 쓴다, 예외 1"이라 했다.

  예외 2개를 운용 중이었다.

결정
- **`common/`과 `spec/`을 공용 폴더로 정의한다.** 소유가 폴더가 아니라 **파일에 붙는다.**

  - `common/status.md` — 총괄(프로젝트)
  - `spec/` 3종 — 기획(프로젝트, [6] 절차 필수)
- 공용 폴더의 파일은 **소유자만 쓰고 전 역할이 읽는다**([3.4]).
- `[3.2]` "자기 폴더에만 쓴다"는 역할 폴더에만 적용한다.

결과
- 좋아짐: 예외가 2개에서 1개로 준다. 폴더 소유와 파일 소유가 어긋나던 자기모순이 사라진다.
  축 분리(C-036)가 폴더 구조에도 일관되게 적용된다 — 체계 파일과 프로젝트 파일이 같은 폴더에
  공존하는 것이 이상하지 않게 된다.
- 나빠짐: 소유 규칙이 2단(역할 폴더 = 폴더 소유 / 공용 폴더 = 파일 소유)이 된다. 규칙 하나로
  전부 설명되지 않는다.
- 못 푸는 것: **공용 폴더에 새 파일이 생길 때 소유 판정을 사람이 한다.** 위치가 자동으로 정해주지
  않는다. 축([1] 표)으로 판정하나 경계 사례는 남는다.

기각된 대안
- 예외 유지(현행): 같은 문서가 두 말을 한다. 자기 기준(예외 2개 초과 시 재설계)에 걸린다.
- `status.md`를 `management/`로 이동: 소유가 깔끔해지나 사용자가 볼 현황 파일이 총괄 폴더에 묻힌다.
  사용자 지시("공통은 docs/common")와도 어긋난다.
- `common/`을 체계 전용으로 두고 현황을 별도 폴더에: 폴더가 하나 더 는다. 과설계.

집행: rules.md [3.3](공용 폴더 표)·[3.4](소유자만 쓴다). 유형 7 표와 문안 일치 확인.

레퍼런스: 없음 — 자기모순 정정이라 외부 근거가 필요 없다.

## C-051. 마이그레이션을 축으로 분리 — `_archive` 이관(체계)과 `spec/` 이동(프로젝트)

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines C-037(마이그레이션 범위), depends-on C-036([1.5] 두 축 분담) · 2026-07-15

맥락
- **사용자 지적**: "스펙은 프로젝트 내의 기능 등에 대한 설명이니 나중에 총괄이 관여하는 게 맞지 않은가?"
- C-037은 마이그레이션(`_archive` 이관 + `spec/` 이동 + 경로 정정)을 **한 덩어리로** 계획했다.
  두 축이 섞여 있다 — 폴더 배치는 체계지만 **이동 실행·시점·경로 정정은 작업이고 스케줄**이다.
- `[1.5]`(한 안건이 두 축에 걸치면 각 축의 종결자가 자기 축만 결정한다)를 설계자가 자기 계획에
  적용하지 않았다.
- `spec/` 이동은 마이그레이션 전체에서 **유일하게 고위험 항목**이다. 전 문서·코드·프론트 저장소의
  경로 참조 수십 곳이 깨지고, 프론트 저장소 복사본(D-007)까지 걸린다.

결정
- 마이그레이션을 둘로 쪼갠다.
  - **B-1 `_archive/` 이관** — 체계 축. 컨설턴트가 진행한다. 구 문서를 옮기는 일뿐이라 되돌리기가 싸다.
  - **B-2 `spec/` 이동** — 프로젝트 축. **총괄과 함께, 나중에.** 시점·경로 정정 범위는 총괄이 정한다.
- B-2 착수 전에 **이득이 비용을 넘는지 재평가한다.** 재평가 결과 루트 유지도 유효한 선택지다.

결과
- 좋아짐: B-1이 즉시 진행 가능해지고, 마이그레이션의 고위험 부분이 격리된다. 축 분리가 계획
  단위에도 적용되어 [1.5]와 정합한다.
- 나빠짐: docs 루트가 당분간 `spec/` 3종과 `common/`이 공존하는 과도기 형태로 남는다.
  구조가 한 번에 안 끝나고 두 단계가 된다.
- 못 푸는 것: **B-2가 영영 안 될 수 있다.** 총괄 스케줄에 밀리면 과도기가 고착된다. 다만 과도기
  형태가 기능상 문제를 일으키지 않는다는 것이 완충이다 — `spec/` 이동의 이득은 미학이 전부다.

기각된 대안
- 한 덩어리 유지(C-037 원안): 컨설턴트가 프로젝트 축 작업의 시점을 정하게 된다. 월권.
- `spec/` 이동 전면 철회: 사용자가 명시적으로 선택한 항목이다. 재평가 대상으로 두되 임의 철회하지 않는다.
- B-1도 총괄 승인 후 진행: `_archive` 이관은 순수 체계 작업이다. 승인을 거치면 C-036이 무의미해진다.

집행: 잔여 작업 목록에서 B를 B-1/B-2로 분리. B-2는 총괄 통지(A)에 안건으로 포함.

레퍼런스: 없음 — 자기 규칙([1.5]) 적용 누락의 정정이다.

## C-052. 브리핑 `할 일`에 발신/수신·프롬프트 컬럼 — 중계자에게 중계할 물건을 준다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines C-048(브리핑 형식) · 2026-07-15

맥락

## C-053. 브리핑 `할 일`에 `커밋` 컬럼 — 산출물 커밋 메시지는 만든 파트가 낸다

맥락
- **사용자 지시**: "커밋/푸시 필요 시 커밋 내용 컬럼도 존재해야 함."

- **C-046이 과하게 잘랐다.** 사용자가 걷어내라고 한 것은 로그 커밋이었다 — "각 파트의 작업

결정
- `[9.10]`을 **산출물 커밋 메시지는 만든 파트가 제안한다**로 바꾼다. 브리핑 `할 일`의 `커밋` 칸에 낸다.

- 브리핑 `할 일` 표에 `커밋` 컬럼을 추가한다. 산출물을 냈을 때만 채우고, 아니면 `—`.

결과
- 좋아짐: C-046의 원 의도(대화 수와 커밋 수 분리)를 지키면서 산출물 커밋의 메시지 품질을 되찾는다.

- 나빠짐: 브리핑 `할 일` 표가 5컬럼이 된다. 채팅에서 가로가 좁아져 읽기가 나빠질 수 있다.
  파트가 "이게 산출물인가 로그인가"를 매번 판정해야 한다(위치 규칙 [9.8]이 대부분 자동 판정하나
  경계는 남는다).
- 못 푸는 것: **커밋 빈도를 다시 늘릴 여지가 생긴다.** 파트가 사소한 파일 변경도 산출물이라 우기면
  커밋 제안이 늘어 C-046이 푼 문제가 부분 재발한다. 방어는 `[9.8]` 위치 규칙과 `[9.9]`(로그는
  독립 커밋 없음)뿐이며, 판정을 파트에게 맡기는 구조라 규율에 의존한다.

## C-054. 브리핑 `할 일`은 3컬럼 — 프롬프트·커밋은 표 아래 블록으로

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines C-052·C-053(컬럼 배치) · 2026-07-15

맥락
- **사용자 지적**: "커밋 내용은 어차피 대화 하나에 한 번뿐일 테니 할 일 하단에 표기, 프롬프트도 하단에 배치."
- C-052·C-053으로 `할 일` 표가 5컬럼이 됐다. 실측하니 두 컬럼이 구조적으로 비어 있다.
  - **`커밋`**: 커밋은 대화당 1회다. 할 일이 4개면 3개 행이 `—`다.
  - **`프롬프트`**: 킥오프·git 명령은 여러 줄이라 표 칸에 안 들어간다. C-052에서 이미
    "긴 것은 표 아래 코드블록"이라는 우회로를 만들어 뒀는데, 그 우회로가 필요하다는 것 자체가
    컬럼이 맞는 그릇이 아니라는 신호였다.

결정
- `할 일` 표를 **3컬럼**으로 한다: `# / 무엇 / 발신·수신`.
- **`프롬프트`·`커밋`을 표 아래 블록**으로 뺀다. 없으면 블록째 지운다.
- 프롬프트 블록은 `#<번호> → <파트>`로 어느 할 일의 것인지 잇는다.
- 커밋 블록은 `git add`부터 전체 명령을 완성형으로 쓴다.

결과
- 좋아짐: 표가 좁아져 채팅에서 읽힌다. 여러 줄 내용이 코드블록에 들어가 복붙이 정확해진다
  (표 칸 안의 백틱은 줄바꿈을 못 담는다). 빈 칸이 사라져 표에 정보만 남는다.
- 나빠짐: 할 일과 프롬프트의 대응이 `#번호` 참조로 간접이 된다. 컬럼이면 같은 행에 붙어 있었다.
  할 일이 많고 프롬프트가 여럿이면 눈이 왕복한다.
- 못 푸는 것: **브리핑 형식이 이 세션에만 4번 바뀌었다**(C-048 → C-052 → C-053 → C-054).
  형식이 안정됐다는 근거가 없다. 실사용 전이라 실측이 없고, 파트가 써 본 뒤 또 바뀔 수 있다.

기각된 대안
- 5컬럼 유지(C-052·C-053 현행): 구조적 빈 칸 2개. 여러 줄 내용을 담지 못해 우회로가 필요하다.
- 커밋만 아래로, 프롬프트는 컬럼 유지: 짧은 프롬프트는 칸에 들어가나 킥오프는 안 들어간다.
  같은 필드가 길이에 따라 두 자리에 사는 것이 더 나쁘다.
- 할 일을 불릿으로 되돌리고 전부 아래: 발신/수신이 한눈에 안 잡힌다. C-052의 이득을 버린다.

집행: templates.md [7](3컬럼 + 블록 2종 + 작성 규칙). rules.md [5.44]~[5.46].

레퍼런스: 없음 — 배치 정정이다.

자기 관측: 브리핑 형식 4회 개정(C-048·052·053·054)은 전부 **사용자가 결함을 먼저 봤다.**
설계자가 실사용을 상상하지 못하고 매번 사용자 지적으로 고쳤다. 형식은 써 본 사람이 안다 —
다음 개정은 파트의 실사용 후 관측을 근거로 해야 한다.

## C-055. 병행 판정 2문 — 의존과 쓰기 충돌. 파생 여부는 기준이 아니다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: refines D-028(병렬 작업)·D-074(시퀀싱)·D-084(파생 판정) · 2026-07-15

맥락
- **사용자 지적**: "총괄이 기획에게도 수신을 남겼는데 이런 경우 병행을 해도 되는 작업인지, 또
  파생되는 작업의 경우에도 병행을 해도 되는 작업인지 혼란이 올 때가 있음."
- 현행 규약에 **병행 가능 여부를 판정하는 기준이 없다.** D-074(선행 완료 확인)·D-084(파생 범위
  발견자 판정)·D-028(병렬 작업 비동기 완료)이 있으나 전부 **"순서를 누가 정하나"**를 다루고
  **"동시에 해도 되나"**를 다루지 않는다.
- **혼란의 핵심은 "파생"이다.** 파생 관계를 순서 제약으로 오독하면 독립 작업까지 직렬화된다.
- 총괄이 이미 이 판정을 규약 없이 수행했다: "B-1(`_archive` 이관)과는 독립이다(**파일 집합이
  겹치지 않음**)"(`management/outbox/REFORM/001`). 규칙이 자연스럽다는 증거다.

결정
- 병행 여부를 **2문으로 판정한다. 둘 다 "아니오"여야 병행한다.**
  1. **의존** — A의 산출물이 B의 입력인가?
  2. **쓰기 충돌** — 두 작업이 같은 파일을 쓰나?
- **쓰기 집합이 겹치지 않으면 병행한다.** 겹치지 않는데 직렬화하지 않는다.
- 쓰기 충돌은 **파일 경로로 센다.** "같은 도메인"이 아니라 "같은 파일"이다.
- **파생 여부는 판정 기준이 아니다.** 한 뿌리에서 나온 작업들도 2문을 통과하면 병행한다.
- 판정은 발견자가 기본값이고, 파트 간에 걸치면 총괄이 판정한다(D-084 대칭).

결과
- 좋아짐: "동시에 해도 되나"가 2문으로 닫힌다. 파생 관계를 순서 제약으로 오독하는 실패가 사라진다 —
  `A → B, A → C`에서 B·C가 독립이면 병행이다. 쓰기 집합을 파일 단위로 세므로 도메인이 같아도
  disjoint하면 병렬이 산다. 총괄이 이미 쓰던 판정이라 학습 비용이 0에 가깝다.
- 나빠짐: 쓰기 집합을 착수 전에 예측해야 한다. 작업 중 예상 밖 파일을 건드리면 뒤늦게 충돌이 난다.
  조항이 하나 늘어 099의 과설계 제약에 부담을 준다(총괄이 이미 하던 판정의 명문화라는 것이 상쇄 논거).
- 못 푸는 것: **쓰기 집합 예측이 틀리면 막지 못한다.** 2문은 착수 시점의 추정에 기댄다. 실제
  충돌은 두 작업이 같은 파일을 열 때 드러나며, 그때는 `[5.35]`(완주 기본값)·`[5.33]`(이의 제기)로
  사후 처리한다. **판정을 명시적으로 만들 뿐 정확하게 만들지 않는다** — 3문 테스트(C-038)와 같은 한계다.

기각된 대안
- 규약 없이 현행 유지: 총괄은 이미 잘하고 있으나 **사용자가 혼란을 실측 보고했다.** 총괄 한 명이
  암묵지로 하는 판정은 파트에 전파되지 않는다.
- `status.md`에 병행 여부 열 추가: 뷰에서 보여주면 사용자는 편하나 총괄이 매번 판정해 써넣어야 하고
  뷰는 낡는다(C-044 한계). 규칙이 있으면 각자 판정한다.

## C-056. 지시 충돌 방지 — 실행 지시는 실행 축의 종결자가 단독 발신한다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: corrects C-036(two-boss 대가 미기재), refines C-051 · 2026-07-15

맥락
- **사용자 질의**: "총괄도 같은 내용을 기획에 발신했는데 내용이 겹친다면 어떻게 되는건가."
- **C-036이 matrix organization을 만들었다.** 축을 둘로 가른 순간 각 파트는 종결자가 둘이 된다
  (체계=컨설턴트, 프로젝트=총괄). 이는 **unity of command 위반**이며 matrix 구조의 알려진 대가다.
- **C-036의 `결과`에 이 대가를 적지 않았다.** "총괄이 모르는 상태" 같은 것은 적었으나 two-boss
  problem은 못 봤다. C-036이 구 형식(`이유`/`한계`)이라 부정 결과를 체계적으로 훑는 자리가
  없었던 것도 한몫한다 — C-047이 `결과` 필드를 도입한 이유가 정확히 이것이다.
- 실물: `spec/` 이동은 위치(체계·컨설턴트)와 실행(프로젝트·총괄)이 한 안건에 섞여 있다.
  둘 다 기획에게 전달돼야 하는데, 각자 보내면 기획이 "the man in the middle"이 된다.

결정
- **한 안건의 실행 지시는 한 발신자만 낸다.** 발신자는 **실행이 속한 축**의 종결자다.
- 다른 축의 결정은 그 발신자의 `근거(인용)`에 싣는다. **별도 메시지로 보내지 않는다.**
- 겹치는 지시를 받으면 **두 발신자 모두에게** 이의를 제기한다. 수신자가 혼자 짜맞추지 않는다.
- 충돌이 **축 경계** 문제면 두 종결자가 경계를 정한다. 아니면 [3.9] 기준 위계로 판정한다.
- 부수: **[5.36] 추천이 자기 정본과 어긋나지 않는지 확인한다** — 총괄이 REFORM/001에서 지적한
  결함(내가 rules.md로 이미 닫은 선택지를 총괄에게 양자택일로 넘김)의 처방.

결과
- 좋아짐: 수신자가 두 지시를 받는 경로가 구조적으로 닫힌다. Single Writer Principle이 "eliminates
  whole classes of contention behavior"라 한 그 효과다. `근거(인용)` 필드가 이미 있으므로 새 기계가
  필요 없다 — 다른 축의 결정이 인용으로 실린다. 총괄이 이미 이렇게 하고 있다(REFORM/001의
  "기획에 `spec/` 이동 작업 지시(총괄 발신)").
- 나빠짐: 발신자가 남의 축 결정을 정확히 인용해야 한다. 인용이 틀리거나 낡으면 수신자가 틀린
  근거로 일한다. 조항이 4개 늘어 099 과설계 제약에 부담을 준다.
- 못 푸는 것: **축 경계가 모호한 안건은 여전히 "누가 실행 축인가"에서 갈린다.** 2문 테스트 같은
  기계적 판정이 없고 [1] 표의 축 정의에 기댄다. matrix 문헌도 이 지점은 "force it back to the
  proper level"이라며 사람에게 넘긴다 — 구조로 못 푸는 영역이다.

기각된 대안
- 규약 없이 현행: 총괄이 이미 올바르게 하고 있으나 **사용자가 혼란을 실측 보고했다.** 암묵지는
  전파되지 않는다(C-055와 같은 논거).
- 두 종결자가 각자 보내고 수신자가 병합: matrix 문헌이 지목한 "the man in the middle". 수신자에게
  종결자의 일을 떠넘긴다.
- 축을 하나로 되돌림(C-036 철회): unity of command는 회복되나 사용자 지시에 정면으로 반한다.
  matrix의 대가는 알려진 것이고 처방도 알려져 있다 — 구조를 버릴 이유가 아니다.
- 모든 지시를 총괄 경유: C-042(라우팅 폐지)를 무효화한다. 46% 병목으로 회귀.

집행: rules.md [5.7]~[5.10](지시 충돌 절 신설)·[5.36](추천-정본 정합)·[5.11]~[5.52] 재번호.

레퍼런스: Matrix organization / Unity of command — "Unity of command is the management principle
violated by a matrix organization"; "employees essentially have two or more bosses"; "Employees may
receive conflicting instructions... leading to confusion"; "the man in the middle"; 처방은 "ascertain
whether the dispute reflects an unresolved broader policy issue. If it does not... force it back to
the proper level"(pmi.org/learning/library/matrix-organization-structure, island94.org
conflict-in-the-matrix, researchgate.net Resolving the Conflicts Built in Matrix Structures).
Single Writer Principle — "assigns responsibility for propagating events of a specific type to a
single service"; "one service owns how an entity progresses"; "eliminates whole classes of contention
behavior"; "you don't have to duplicate efforts... on another microservice which might emit the same
entity"(mechanical-sympathy.blogspot.com/2011/09/single-writer-principle.html, hftengineer.com).

## C-057. 수신함 스캔 규칙 복원 — 출근 시와 사용자 지시 시에만. 매 응답은 폴링이다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: restores D-023(수신함 스캔 조항), corrects C-037(이관 누락) · 2026-07-15

맥락
- **사용자 질의**: "대화를 시작할 때 수신확인으로 진행하는데, 병렬 작업 중 다른 파트가 발신할 시
  대화 처음에 매번 수신함을 검색하는 건 비효율적인지? 토큰 낭비가 큰지?"
- 답을 찾다가 발견했다 — **`rules.md`에 수신함 스캔 규칙이 없다.**
  호스트 Grep `수신함|inbox` 전수 → 6건 전부 다른 조항이다.
- 구 D-023의 핵심 조항이 개편 중 증발했다: *"전 역할 outbox/에서 `[X → 자기역할]` 헤더를 스캔하고,
  자기 inbox-log.md에 없는 파일을 신규로 처리한다."*
- 새 `[8.7]-4`는 **자기 접두어 grep**(D-024, ID 소유자 통지 pull)이지 수신함 스캔이 아니다.
  **둘은 다른 것인데 하나만 남았다.** 내가 이 세션 첫 스캔을 관행으로 했고 규칙이 없는 걸 몰랐다.
- **실측**: 스캔 1회 = 호스트 Grep 1회, 21개 경로 반환 ≈ 400 토큰. 20턴 세션이면 8,000 토큰.

결정
- 수신함 스캔 규칙을 복원한다: 전 역할 `outbox/`에서 `[X → 자기역할]` 헤더 → `inbox-log.md`에
  없는 것만 처리 → 처리 후 1줄 추가.
- **스캔 시점은 2개뿐이다: ① 출근 시 ② 사용자가 `수신함 확인` 지시할 때.**
  **매 응답마다 스캔하지 않는다.**
- 수신함 스캔(`[X → 나]`)과 접두어 스캔(`<접두어>-` 언급)은 **다른 것이며 둘 다 한다**([8.7] 3·4단계).

결과
- 좋아짐: 증발한 조항이 복원되어 관행이 규칙이 된다. 신규 파트가 "수신함 확인"을 지시받았을 때
  무엇을 하는지 규정이 생긴다. 접두어 스캔과의 혼동이 명시적으로 갈린다.
- 나빠짐: `[5]`에 조항 5개가 늘었다. 099 과설계 제약에 부담. 다만 이는 신설이 아니라 **누락 복원**이다.
- 못 푸는 것: **사용자가 `수신함 확인`을 잊으면 놓친다.** 이는 사용자가 중계자인 구조의 본질적
  한계이고 조항으로 못 막는다. `[8.9]` 총괄 스캔이 그물 역할을 하나 총괄도 출근해야 돈다.

**매 응답 스캔을 기각한 근거 — 비용이 아니라 확률이다**
- 대화는 사용자가 있어야 돈다. **내가 응답하는 동안 사용자는 이 대화에 있고, 그 순간 다른 파트는
  발신할 수 없다** — 발신하려면 사용자가 그 대화를 열어야 한다.
- 새 메시지가 도착하는 유일한 창은 **사용자가 다른 대화에 갔다 온 사이**이고, **그건 사용자만 안다.**
  대화는 턴 사이의 일을 모른다.
- 즉 매 응답 스캔은 **이벤트가 없는데 계속 묻는 폴링**이다. **사용자가 이벤트 소스이므로 신호를 받으면 된다.**
- 비용 8,000 토큰은 작다. **기각 이유는 비용이 아니라 대부분의 턴에서 이득이 0이라는 것이다.**

기각된 대안
- 매 응답마다 스캔: 위 근거로 기각. 폴링.
- 출근 시만: 세션 중 도착분을 퇴근까지 못 본다. 사용자 지시 경로를 막을 이유가 없다.
- 작업 블록마다 재스캔: 사용자가 안 시켰는데 자체 판단으로 스캔하게 된다. 판정 기준이 없어
  결국 매 응답에 수렴한다.

집행: rules.md [5.21]~[5.25](수신함 절 신설)·[5.26]~[5.56] 재번호·[8.7](출근 절차에 스캔 3단계 삽입).
확인: `rules.md`에 `[X → 자기역할]` 문자열이 존재하는지 grep.

레퍼런스: 없음 — 누락 복원 + 폴링/이벤트 구분은 일반 원리다.

**자기 관측**: 이 누락은 C-037(전면 재작성)의 이관 결함이다. 구 문서에서 새 문서로 옮기며
**핵심 조항 하나가 증발했고 세션 내내 아무도 못 봤다** — 내가 그 규칙을 관행으로 지켰기 때문에
부재가 드러나지 않았다. **관행이 규칙의 부재를 가린다.** 전면 재작성의 알려진 위험이며,
C-037 `결과`의 `못 푸는 것`에 이 항목이 없었다.

## C-058. `inbox-log`·`handover`를 git 추적에서 제외 — 이력 가치 없는 상시 변경 파일

상태: ACCEPTED · 소유: 컨설턴트 · 관련: relates-to C-043(handover WAL 부작용), C-046(커밋 축) · 2026-07-15

맥락
- **사용자 지적**: "`inbox-log.md`, `notes/handover.md` 이것들이 계속 커밋 대상으로 올라온다,

결과

  현재 1머신이라 무관하나, 머신이 늘거나 협업이 생기면 부채가 된다.
- 못 푸는 것: **이 판정은 "1머신·1인"이라는 현 조건에 의존한다.** 조건이 바뀌면 재검토해야 하는데,
  `.gitignore`는 조용히 작동하므로 **재검토 시점이 자동으로 오지 않는다.** 잊힌 채 부채가 된다.

- handover만 제외: inbox-log도 같은 성격(append, 이력 가치 낮음)인데 남길 이유가 없다.
- IDE 설정으로 숨기기: 도구별 설정이라 이식되지 않고, 근본은 "이력 가치 없는 파일을 추적한다"는 것이다.

집행: `.gitignore` 말미에 2줄 + 근거 주석. 확인: IDE 커밋 목록에서 두 파일이 사라지는지 사용자 확인.
**주**: `.gitignore`는 저장소 인프라 파일로 문서 유형 표([3])에 미분류다. docs 로그의 추적 여부
판정은 체계 축이므로 컨설턴트가 결정했고, 코드 관련 라인은 건드리지 않았다.

레퍼런스: 없음 — 도구 노이즈 대응이다.

**자기 관측**: 사용자가 같은 문제를 3번 말했고 나는 3번 다르게 오독했다.
(1) "커밋량이 많다" → 커밋 축을 코드/docs로 갈랐다(C-045, 틀림)
(2) "작업 결과물은 커밋해도 된다, 대화 log가 문제다" → 산출물/로그로 갈랐다(C-046, 맞음)
(3) "아예 커밋 대상에서 제외해도 되냐" → 커밋 부담 문제로 읽고 "실익 0"이라 답했다(틀림)
실제 문제는 **IDE 노이즈**였고, 내가 "불편의 정체를 확인해달라"고 물은 뒤에야 드러났다.
**증상의 이름을 사용자 언어로 받아 적고 원인을 추정하지 말았어야 했다.** 세 번 다 내가 원인을
먼저 정하고 그에 맞는 처방을 냈다.

## C-059. `[9.3]` 기준어 정정 — "마운트를 읽는가"가 아니라 "읽은 게 저장소에 남는가"

상태: ACCEPTED · 소유: 컨설턴트 · 관련: generalizes C-040(sandbox git 금지), refines D-090,
회부 = management/outbox/REFORM/003, 원 관측 = design/outbox/REFORM/001 · 2026-07-15

맥락
- **총괄 회부(REFORM/003)**: `spec/` 이동 지시가 파일 이동 작업이라 bash `mv`가 자연스러운 실행이었고,
  **`[9.3]`("마운트 뷰와 무관한 실행") 문면상 허용으로 읽혔다.**
- **이동 대상 3파일이 정확히 절단 대상이었다**(기획 실측, design/outbox/REFORM/001):
  `domain-spec` 186/227 · `erd` 341/409 · `api-contract` 310/374. **`mv`를 썼으면 143줄이 소실된 채
  이동됐고 실패 신호가 없어 아무도 몰랐다.** 기획이 호스트 Read → Write → 삭제로 우회해 막혔다.
- **조항 사이로 빠졌다.** `[9.2]`는 **조회** 결과를 판단 근거로 쓰는 것만 막는다. `mv`는 조회가 아니라
  **실행**이라 안 걸리고, `[9.3]`은 "마운트 뷰와 무관한 실행"이라 했는데 **`mv`는 무관하지 않다 —
  그 내용을 읽어서 옮긴다.** 판단이 아니라 **소비**라 두 조항 어디에도 안 걸린다.
- **C-040이 이미 같은 논리였다** — "git이 절단된 워크트리를 읽으므로 금지". 그 일반형은
  "마운트 내용을 소비하는 모든 명령"인데 **조항이 `git` 한 사례에만 걸려 있었다.**
- **기획의 정밀 관측(안건 2 흡수)**: 마운트가 통째로 낡은 게 아니다. 같은 시점에 `rules.md`(400줄)·
  오늘 생성분은 정상이었고 **이 3파일만 캐시본으로 고정**됐다. 즉 **"bash 뷰는 낡았다"가 아니라
  "어느 파일이 낡았는지 bash 안에서는 알 수 없다"**가 정확하다. 정상 파일이 섞여 있어 **오히려
  안심하게 된다** — "신선도를 확인하면 되겠지"가 성립하지 않는 이유이자 `[9.2]`가 조회 결과
  **전체**를 배제해야 하는 이유다.
- **오늘 안 터진 이유는 조항이 아니라 기획이 절단을 먼저 발견했기 때문이다. 규율이 아니라 운이 막았다.**

결정
- `[9.3]` 기준어를 **"마운트 뷰와 무관한 실행"** → **"마운트에서 읽은 내용이 저장소에 남지 않는 실행"**
  으로 바꾼다. 조항 수는 불변이다.
  - 허용: 빌드·테스트(마운트를 읽으나 산출물이 `build/`라 재생성 가능) · `rm`·`git log`(내용을 안 읽음)
  - 금지: `mv`·`cp`·`git add`·`git commit`(마운트 내용이 그대로 저장소 정본이 된다)
- `[9.4]` 신설: **파일 이동·복사를 bash로 하지 않는다. 호스트 Read → Write → 삭제로 한다.**
- **안건 2는 별도 조치하지 않는다.** 이 항목의 `맥락`이 기획 관측을 흡수한다.

결과
- 좋아짐: `mv`·`cp`가 명시적으로 닫힌다. **개별 명령을 열거하지 않고 기준으로 걸었으므로 다음 명령
  (`rsync`·`tee` 등)이 나와도 같은 기준으로 판정된다** — C-035의 "개별 규칙 누적은 기본값이 틀렸다는
  신호" 논리 적용. C-040이 만든 판례의 일반형이 제자리에 선다. 조항 총량은 +1(`[9.4]`).
- 나빠짐: 판정에 "저장소에 남는가"라는 한 단계 추론이 필요하다. 문면만 읽고 바로 안 되고 명령의
  효과를 알아야 한다. 조항이 1개 늘어 099 제약에 부담.
- 못 푸는 것: **빌드가 절단된 소스를 읽는 경우는 막지 못한다.** 컴파일 에러로 드러난다는 것이
  허용 근거인데, **절단이 문법적으로 유효한 지점에서 일어나면 조용히 통과한다**(예: 함수 하나가
  통째로 잘려도 컴파일은 된다). 실패 신호에 기대는 구조이며 신호가 항상 오지는 않는다.

기각된 대안
- **(b) 현행 유지**: 오늘 안 터진 것은 조항이 아니라 기획의 발견 덕이다. 발견 못 했으면 그대로 갔다.
- **(c) C-040 확장**: 유형 3 불변이라 로그를 못 고친다. 신규 C가 필요하니 (a)와 실질 동일한데
  결정 로그를 건드리는 형태만 나쁘다.
- **총괄 원안("내용을 읽지 않는 실행")**: **빌드를 설명하지 못한다.** 빌드도 마운트를 읽으므로
  그 기준으로는 금지가 되는데 총괄은 허용이라 썼다. 기준과 예시가 어긋난다.
- **명령 열거식(`mv`·`cp`·`git add` 금지)**: 다음 명령마다 C가 재발번된다. C-035 논리 위반.

**뿌리 점검** ([5.35])
- 뿌리 = **조항이 도구가 아니라 도구의 한 사용법에 걸려 있었다.** `[9.2]`는 조회에, C-040은 git에.
  둘 다 "마운트 내용을 소비하면 오염된다"는 한 메커니즘의 사례인데 사례 단위로 서 있어 `mv`가 빠졌다.
- **같은 형태를 이번 세션에 3번 봤다**: ① D-090이 "주장"에 걸려 "판단"이 빠짐(기획 지적)
  ② `[5.34]`(D-086)가 탐색 방법을 밝히게 하나 **그 방법들의 독립성은 안 물음**(총괄이 그 틈으로
  오판) ③ 이번 `mv`.
- **셋을 묶는 일반 조항은 만들지 않는다.** 묶으면 "규칙을 일반형으로 써라"가 되는데 **검증 불가능하고
  공허하다** — C-035에서 기각한 "도구 사각지대를 인지하라"와 같은 형태다. 총괄도 같은 판단이었다.
  관측만 보존한다.

집행: rules.md [9.3] 기준어 교체 + 판정 표, [9.4] 신설, [9.5]~[9.6] 재번호.
확인: `rules.md [9.3]`에 `mv`·`cp`가 금지로 명시되는지.

레퍼런스: 없음 — 자기 조항의 구멍 정정이다. 원 관측은 기획(design/outbox/REFORM/001),
회부는 총괄(management/outbox/REFORM/003). **내 기여는 기준어 정정뿐이며 절단 실측과
`mv` 위험 식별은 기획·총괄이 했다.**

## C-060. 커밋 명령을 반복 제안하지 않는다 — 커밋 제안도 폴링이다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: corrects C-053([5.54] 종료 조건 누락), applies C-057(폴링/이벤트 구분) · 2026-07-15

맥락
- **사용자 지적**: "커밋 대상이 IDE에 없는데도 커밋 메시지가 나오고 있어."
- `[5.54]`("브리핑에 산출물 커밋 명령을 완성형으로 준다")에 **언제 그만두는지가 없다.**
  산출물은 한 번 냈는데 매 응답마다 같은 커밋 블록을 반복했다. 사용자가 이미 커밋했으면 남은 게 없다.
- **원인은 무지다.** 나는 사용자가 커밋했는지 알 수 없다 — `git status`는 `[9.6]`으로 판단 근거에서
  배제했고, 애초에 대화는 그 사이의 일을 모른다. 몰라서 "혹시 몰라" 반복했다.
- **C-057에서 내가 기각한 것과 같은 병이다.** 거기서 "매 응답 스캔은 폴링이다. 이벤트가 없는데
  계속 묻는 것이다. 사용자가 이벤트 소스다"라고 썼다. **커밋 제안도 똑같은데 스캔에서만 잡고
  커밋에서는 못 봤다.** 같은 원리를 한 문서 안에서 한쪽에만 적용했다.

결정
- `[5.54]`를 **"그 응답에서 낸 산출물의 커밋 명령을 준다"**로 좁힌다.
- `[5.55]` 신설: **커밋 명령을 반복 제안하지 않는다.** 이전 응답의 산출물은 이미 제안했다.
  로그만 쌓였거나 산출물이 없으면 `커밋` 블록째 지운다.
- 사용자가 `커밋`을 지시하면 그때 낸다(C-046 `[9.12]` 트리거 유지).

결과
- 좋아짐: 브리핑에서 죽은 커밋 블록이 사라진다. 커밋 제안이 **신호**가 된다 — 블록이 보이면
  "이번에 산출물이 나왔다"는 뜻이다. 지금은 매번 있어서 정보가 0이었다.
- 나빠짐: 사용자가 커밋을 미루면 **그 산출물의 커밋 명령이 브리핑에서 사라진다.** 나중에 커밋하려면
  `커밋` 지시로 다시 받아야 한다. 다만 그게 C-046이 정한 트리거이므로 설계와 정합한다.
- 못 푸는 것: **나는 여전히 커밋 여부를 모른다.** 이 결정은 "모르니 반복한다"를 "모르니 한 번만
  낸다"로 바꿀 뿐 무지를 해소하지 않는다. 사용자가 커밋을 잊고 산출물이 쌓이면 아무도 안 알려준다.

기각된 대안
- 현행 유지: 브리핑에 죽은 블록이 매번 붙는다. 사용자가 실측 보고한 불편이다.
- `git status`로 확인 후 제안: `[9.6]` 위반. 마운트 뷰의 `git status`는 절단 때문에 유령 변경을
  보고한다(디자인 관측 `ux/outbox/014`: 허구의 삭제 218줄).
- 사용자에게 매번 "커밋했나" 묻기: 왕복이 는다. 폴링을 질문으로 바꾼 것뿐.
- 커밋 제안 전면 폐지: C-053이 되살린 이유가 사라진다 — 산출물 메시지는 만든 파트가 제일 잘 안다.

집행: rules.md [5.54] 문면 축소·[5.55] 신설·[5.56]~[5.57] 재번호. templates.md [7] 작성 규칙.

레퍼런스: 없음 — C-057의 폴링/이벤트 구분을 커밋에 적용한 것이다.

**자기 관측**: **같은 원리를 한 문서 안에서 한쪽에만 적용했다.** C-057에서 "사용자가 이벤트 소스이므로
폴링하지 마라"를 세우고, 두 조항 아래 `[5.54]`에서 폴링을 하고 있었다. 원리를 세운 사람이 그 원리의
적용 범위를 안 훑는다 — 규칙을 만든 응답과 그 규칙이 적용될 다른 조항을 함께 보지 않았기 때문이다.
**C-059의 뿌리 점검("규칙이 사례에 걸려 다음 사례가 지나간다")의 4번째 사례이며, 이번엔 사례가 나다.**

## C-061. `[9.6]` 커밋 분류에 `common/` 추가 — 규약 문서가 미분류였다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: corrects C-046([9.6] 표 공백), 파생 = C-050(공용 폴더 재정의) · 2026-07-15

맥락
- **사용자 지적**: "`decision-log.md`·`rules.md`·`templates.md` 지금 IDE에 올라온 커밋 대상인데

  세 갈래가 다 보여 판정이 표 안에서 닫힌다 — 종전엔 C-058(gitignore)이 표 밖에 있어 조회가 갈렸다.
- 나빠짐: `common/status.md`는 여전히 표에 없다(유형 7 뷰, 총괄 소유). 파생·재생성이라 커밋
  대상인지 애매하며 이번에 판정하지 않았다 — **같은 종류의 공백을 하나 남긴다.**

  자동 판정을 약속하나, 열거에 없는 위치는 판정 자체가 안 된다. 기준으로 거는 형태(C-059처럼)가
  나으나 "산출물이란 무엇인가"를 기준어로 쓰기 어려워 열거를 유지했다.

기각된 대안
- 현행 유지: 규약 문서가 영영 미분류. 사용자가 매번 발견해야 한다.
- 기준어로 전환("남이 근거로 인용하면 산출물"): **decision-log가 반례다.** rules.md의 `근거:`가
  직접 인용하는데 로그 계열이다. 인용 여부는 추적(C-058)의 기준이지 커밋 유발의 기준이 아니다.
- `common/`을 통째로 산출물: `status.md`(뷰, 파생·재생성)가 섞인다. 파일 단위로 명시하는 것이 맞다.

집행: rules.md [9.6] 표 — 산출물 열에 `common/rules.md`·`templates.md` 추가, `추적 제외` 행 신설.

## C-064. 항목 번호는 append-only — 번호는 발번 순서, 배치는 논리 순서

상태: ACCEPTED · 소유: 컨설턴트 · 관련: sharpens templates [13](문면 애매),
회부 = management/outbox/REFORM/005 · 2026-07-15

맥락
- **총괄 통지(REFORM/005)**: `rules.md`에 `[9.4]`가 두 개다. C-062 신설분(마이그레이션)과 C-059
  신설분(파일 이동)이 같은 번호이고 뒤가 안 밀렸다.
- **내가 총괄이 제안한 도구(`^\*\*\[9\.\d+\]` grep)를 그대로 돌리니 3건이었다.**
  `[9.4]` × 2 · `[9.13]` × 2 · `[9.7]` 결번. **총괄은 `[9.4]` 하나만 봤다.**
  총괄이 "규칙이 아니라 도구"라며 제시한 그 grep이 총괄 자신의 관측보다 많이 잡았다.
- **원인은 규칙 부재가 아니라 규칙 위반이다.** `templates.md [13]`이 이미 *"항목이 늘어도 절을
  새로 만들지 않고 해당 절 안에 **붙인다**"*라 한다. **"붙인다"는 append인데 나는 중간에 삽입했다.**
  `[9.4]`를 `[9.3]` 밑에 끼워 넣어 뒤를 전부 밀었고, 밀다가 흘렸다.
- **총괄 지적이 정확하다**: *"네 `못 푸는 것`의 사정거리도 한 칸 좁았다 — '다음 사례가 와야 안다'는
  맞지만 **다음 사례가 조항 안에서 온다고 전제했다.** 이번엔 조항 **사이**에서 왔다."*
  나는 `[9.3]`의 **기준어가 뭘 놓치나**만 봤고 **편집 연산**은 안 봤다.
- **인용 실측**: `_broadcast/001`(불변) → `[9.1]`·`[9.2]` / `design/outbox/REFORM/001`(불변) →
  `[9.1]`~`[9.3]` / `backend/notes/handover.md` → `[9.6]`.
  **재번호했으면 `[9.4]`~`[9.6]`이 밀려 backend의 `[9.6]` 인용이 깨졌다.**

결정
- `templates.md [13]`의 "붙인다"를 **append-only로 명확히 한다**: 신설은 **그 절의 최대 번호 + 1**.
  **중간에 삽입해 뒤를 밀지 않는다.**
- **번호는 발번 순서, 배치는 논리 순서다.** 둘이 어긋나는 것은 정상이다.
  **결번도 정상이다** — 조항이 빠져도 번호를 재사용하지 않는다.
- 개정 후 `^\*\*\[N\.\d+\]` grep으로 중복·결번을 확인한다 — **조항이 아니라 작업 습관이다.**
- 현재 충돌 3건을 append로 해소한다: `[9.4]`(마이그레이션) → `[9.25]`, `[9.14]`(코드 atomic) → `[9.26]`.
  `[9.7]` 결번은 그대로 둔다.

결과
- 좋아짐: **불변 문서의 인용이 영구히 안정된다.** 이번 해소에서 기존 인용 3건이 하나도 안 깨졌다 —
  append가 실제로 작동했다. `outbox/`·`decision-log`가 조항 번호를 인용하는데 둘 다 불변이라

- `[10]`에 1행 추가: **좋은 습관의 정본은 "없다"**. 뿌리 점검·자문·문구 다듬기는 규칙으로 두지 않는다.

결과
- 좋아짐: **부팅 필독이 427줄 → 372줄, 조항 156 → 100.** `[5]` 절이 절반이 됐다. **살아남은 조항의
  번호가 하나도 안 바뀌었다**(호스트 Grep 전수 확인) — 인용 41곳 중 정본을 맞게 가리키던 것은
  전부 그대로다. 삭제된 조항을 인용한 문서는 **결번을 만나 실패 신호를 낸다** — C-065의 조용한
  오독과 반대 동작이다.
- 나빠짐: **삭제된 조항을 인용한 불변 문서가 허공을 가리킨다.** 실측: `[5.35]`(뿌리 점검)는 6곳,
  `[5.42]`·`[5.54]` 등 포함 최소 12곳. 고칠 수 없다(`[5.18]`·`[4.2]`). **그리고 삭제한 훈계 중
  일부는 실제로 좋은 결과를 냈다** — `[5.35]` 뿌리 점검이 C-063의 3계열 분류를 낳았고, 그건
  조항이 없었으면 안 나왔을 수 있다. **효과가 없어서 지운 게 아니라 규칙일 필요가 없어서 지웠다.**
- 못 푸는 것: **1문 기준도 판정자가 나다.** "지우면 뭐가 깨지나"의 답을 내가 상상하는 이상,
  내가 아끼는 조항은 살아남는다. **56개를 지웠는데 내 최근작(C-063·C-064·C-065 집행분)은
  한 개도 안 지웠다.** 이게 편향인지 최근 것이 실제로 근거가 튼튼해서인지 나는 구분 못 한다.
  다음 비대화 때 이 문단을 근거로 삼아라.

기각된 대안
- **실제 마찰 사례가 있는 것만 존치**(사용자 선택지 2): 더 공격적이나 **사고가 안 난 이유가 조항
  덕분일 수 있다.** 백엔드가 `RULES/001`에서 이미 이 반론을 썼다 — *"오탐이 1건인 건 규율이 좋아서지
  규칙이 막아서가 아니다"* 의 역방향이 성립한다. 반사실을 못 세우는 기준이다.
- **형식을 전부 `templates`로 추방**(사용자 선택지 3): 총량이 안 준다. **비대함이 증상인데 위치만
  바꾸면 증상이 안 낫는다.** 다만 이 안의 실질(중복 제거)은 계열 1로 흡수했다.
- **`[5]` 절 재번호로 결번 정리**: C-064·C-065가 두 번 기각한 형태. 인용이 또 밀린다.
- **제거 절차·주기적 감사 조항 신설**: **이게 정확히 사용자가 지적한 병이다.** 157번째 조항으로
  156개를 고치는 꼴이다.

**뿌리 점검** (이 조항은 이제 없다 — 마지막으로 한 번 쓴다)
- 뿌리 = **나는 문제를 볼 때마다 조항을 하나 더 썼다.** 66개 결정 중 상당수가 "조항 신설"이다.
  **조항을 지운 적이 한 번도 없다.** C-035·C-062·C-064에서 "신규 조항 신설"을 세 번 기각했으면서도
  **기각의 대안이 항상 "다른 조항" 또는 "도구"였지 "삭제"가 아니었다.** 삭제가 선택지에 없었다.
- **사용자가 세 번째로 같은 곳을 짚었다** — 커밋 폴링(C-060) · 번호 밀림(오늘) · 비대함(지금).
  **셋 다 내가 만든 것이고 셋 다 남이 먼저 봤다.**

집행: rules.md 전면 — 조항 56개 삭제(결번 유지), 편입 기준 1문 교체, `[4.4]` 5종 정정, `[10]` 1행 추가.
확인: 호스트 Grep `^\*\*\[\d+\.\d+\]` → 100건 · 중복 0 · 살아남은 번호 이동 0.

레퍼런스: 없음. **발견도 기준도 사용자가 줬다.** 내 기여는 실측과 판정 실행뿐이다.

## C-067. C-058 철회 — `.gitignore`가 호스트 Grep을 조용히 멀게 한다

상태: ACCEPTED · 소유: 컨설턴트 · 관련: supersedes C-058, 회부 = backend/outbox/RULES/003 · 2026-07-16

맥락
- **백엔드 회부(RULES/003)**: C-066 감축 이의 점검 중 실피해를 봤다. 자기 `notes/` 스코프 Grep이
  **0건**을 냈고, 파일을 직접 열어서야 삭제된 번호 인용 2건을 찾았다. **안 열었으면 "인용 없음,
  이의 없음"이라는 틀린 회신을 보냈을 것이다.**
- **내 교차 검증(호스트 Grep, 2026-07-16)** — 백엔드 재현 케이스를 그대로 돌렸다:

| 호출 | 철회 전 | 철회 후 |
|---|---|---|
| `Grep("규약", path=docs/consulting/notes)` | **2건** — `handover.md` 빠짐 | **3건** — 잡힘 |
| `Grep("접두어 스캔", path=docs/consulting)` | **3건** — `inbox-log.md` 빠짐 | **4건** — 잡힘 |

  **영향 집합이 C-058이 넣은 2패턴과 정확히 일치한다.** 같은 스코프에서 tracked 파일은 전부 잡혔다.
  **메커니즘은 철회로 확정됐다 — 2줄을 지우자 두 케이스가 다 통과했다.** 다만 `path=docs`
  스코프에서는 철회 전에도 잡혔던 것이 설명되지 않는다. **거기까지는 모른다고 적는다.**
- **C-058이 자기를 반증했다.** 그 `좋아짐` 필드에 내가 이렇게 썼다: *"로컬 파일은 유지되므로 전
  대화가 읽는다 — `[5.23]`·`[8.9]` 모두 **무영향**이다. git 추적에서만 빠지고 **기능은 하나도
  안 바뀐다.**"* `.gitignore` 주석에도 같은 문장을 박아놨다. **틀렸다.**
- **왜 틀렸나**: 나는 **git만 보고 git을 읽는 도구를 안 봤다.** ripgrep이 gitignore를 존중한다는 건
  기본 동작인데, 내 영향 분석은 "git 히스토리에서 빠지는 것"에서 멈췄다.
- **급이 다른 이유**: `[9.2]`가 bash를 배제한 근거가 *"에러 없이 조용히, 의심 트리거가 없다"*였다.
  **그 대안으로 세운 호스트 Grep이 같은 실패를 했다.** `[8.9]`(총괄의 전 역할 handover 스캔)가
  정면으로 걸린다.

결정
- **C-058을 철회한다.** `.gitignore`에서 `docs/*/inbox-log.md` · `docs/*/notes/handover.md` 2줄을 지운다.
- `rules.md [9]` git 표에서 **"추적 제외" 행을 삭제한다.**
- **`[9.27]` 신설**: docs 파일을 `.gitignore`에 넣지 않는다.
- **사용자 확정**: 선택지 4종 중 (a) 철회. IDE 노이즈 복귀를 감수한다.

결과
- 좋아짐: **`[9.1]`이 다시 참이다.** 실측으로 두 케이스가 통과했다. `[8.9]` 총괄 스캔·파트의 자기
  폴더 점검이 조용히 0건을 내지 않는다. **조항 순증 1개(`[9.27]`), `.gitignore` 4줄 감소.**
- 나빠짐: **사용자가 C-058로 풀었던 IDE 커밋 목록 노이즈가 그대로 돌아온다.** 사용자가 실측 보고한
  불편이고, 이 결정은 그걸 되살린다. 더해서 **`[9.14]`가 `git add docs/`라 두 파일이 로그 배치마다
  실제로 커밋된다** — C-058 시절엔 없던 부담이다. handover는 덮어쓰기(`[8.6]`)라 diff가 매번 크다.
- 못 푸는 것: **`path=docs` 스코프에서 철회 전에도 잡혔던 이유를 모른다.** gitignore 가설이 그
  관측을 설명 못 한다. **처방이 들었는데 메커니즘을 다 모르는 상태다** — 다른 스코프에서 같은
  침묵이 또 날 수 있고, `[9.27]`은 docs만 막는다. **Glob이 실재 디렉터리에 0건을 낸 것**(내 handover
  [도구])과 **Grep의 `glob` 필터가 안 먹은 것**도 같은 계열일 수 있으나 확인 안 했다.

기각된 대안
- **현행 유지 + "Grep은 항상 `docs` 스코프로" 조항**: 백엔드가 자체 기각 권고했고 나도 반대한다.
  **도구를 지키기 위한 규칙을 지키기 위한 스코프 규칙**이다 — C-063→064→065 나선 그대로이고,
  C-066이 방금 잘라낸 병이다.
- **무조치**: 오늘 실피해 1건이 실재한다. 다음은 `[8.9]`다.
- **IDE 설정으로 숨기기**: C-058이 이미 기각했다. 1머신이라 이식성 반론은 약하나, 도구별 설정으로
  정본 도구의 결함을 덮는 형태는 같다.

집행: `.gitignore` 2줄 + 주석 4줄 삭제(대체 주석 4줄). rules.md [9] git 표 "추적 제외" 행 삭제 ·
`[9.27]` 신설 · 헤더 `반영:` 갱신.
확인: `Grep("규약", path=docs/consulting/notes)`가 `handover.md`를 잡는지 — **잡았다(3건).**

레퍼런스: 없음. **발견·재현·처방 전부 백엔드다.** 내 기여는 교차 검증과 채택뿐이다.
