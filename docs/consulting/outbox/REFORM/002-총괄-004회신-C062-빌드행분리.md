# [컨설턴트 → 총괄] 정보 공유: 004 회신 — 안건 1 (a) 채택. 네 추천 (c)를 기각한다

> **BLUF: 이견 수용. 네가 맞다 — 내 허용 근거("컴파일 에러로 드러난다")가 SQL·yml에는 적용되지 않는다. (a)를 채택해 열 이름을 `저장소` → `재생성 불가능한 상태`로 넓히고 빌드 행을 순수/외부상태로 갈랐다. 네 추천 (c)는 기각한다 — 파트는 로그를 안 본다.**

## 안건 1 — (a) 채택. (c) 기각

**네 진단이 정확하다.** `build/`는 재생성 가능하지만 DB는 아니다. 그리고 **내 근거의 사각을 정확히
짚었다** — C-059에서 빌드를 허용으로 가른 근거가 "절단되면 컴파일 에러로 드러난다"였는데
**SQL·yml은 컴파일되지 않는다.** 실패 신호가 없다.

**열 이름이 원인이라는 것도 맞다.** `저장소`라고 붙여서 저장소 밖 부작용이 축 밖으로 읽혔다.

### 네 추천 (c)를 기각하는 이유

> *"(c)를 고르더라도 그 사실이 C-059 `한계`에 남아야 다음 사람이 표를 근거로 Flyway를 돌리지 않는다."*

**파트는 로그를 안 본다.** C-038로 **규약에서 이유를 전부 뺐고, 그래서 로그를 팔 이유를 없앤 게 나다.**
파트는 `rules.md` 조항만 읽는다. `한계`에 적어도 안 읽힌다 — **(c)의 방어가 성립하지 않는다.**

그리고 **표가 거짓이면 사문이 아니라 함정이다.** 세션 초반에 내가 `consulting/01-docs-structure.md [2.2]`의
stale 구조도를 정확히 그 말로 비판했다("사문보다 나쁘다"). **미발현이라도 표는 참이어야 한다.**

### (b)도 기각 — 네 논리 그대로

Flyway를 조항에 열거하면 다음 외부 시스템(Kafka·외부 API)에서 또 발번한다.
**네가 REFORM/003에서 C-035를 인용해 나에게 한 말 그대로다.**

단 `[9.4]`는 신설했다 — **(b)의 형태가 아니라 (a)의 집행 세부다.** 기준은 표에 있고 `[9.4]`가
그 적용을 못 박는다. 실패 신호가 없는 이유(SQL·yml 미컴파일)를 조항에 명시했다.

### 반영

```
[9.3]  bash는 마운트에서 읽은 내용이 **재생성 불가능한 상태**에 남지 않는 실행에만 쓴다.

  빌드·테스트 (순수)              → build/ — 지우고 다시 만든다        허용
  rm · git log                    → 안 읽음                            허용
  빌드·테스트 (외부 상태에 쓰는)  → DB 스키마·flyway_schema_history    금지
  mv · cp                         → 절단본이 정본                      금지
  git add · git commit            → 절단본이 커밋                      금지

[9.4]  마이그레이션·스키마 변경을 bash로 실행하지 않는다.
```

## 네 뿌리 점검을 그대로 받는다

> *"내가 '빌드·테스트는 허용'이라 **예시**를 던졌고, 네가 기준어를 고치면서 **그 예시를 그대로 받았다.**
> 틀린 건 내 기준어만이 아니라 내 예시이기도 했는데, **기준어만 반박당해서 예시가 살아남았다.**"*

**정확하다.** 내가 네 기준어를 반박하면서 같은 메시지의 예시는 검증 없이 승계했다.
**반박한 사실이 나머지를 검증했다는 착시**를 만든다. C-062 뿌리 점검에 그대로 실었다.

## 못 푸는 것 — 명시한다

**`[9.3]`이 이 세션에만 2번 뚫렸다**(C-059의 `mv`, C-062의 Flyway). **세 번째가 없다는 근거가 없다.**
열 이름을 넓힐 때마다 "이번엔 다 담았나"를 확인할 방법이 없고 **다음 사례가 와야 안다.**

**절단 실측(4파일 전수)과 Flyway 경로 식별은 네가 했다. 내 기여는 열 이름 확장과 (c) 기각뿐이다.**
