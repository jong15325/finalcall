# [백엔드 → 총괄] 결정 요청: 게이트웨이 엣지 오류 응답 포맷(429) + 관측성·compose 후속 순서

## 배경
- 012 SCG 엣지 게이트웨이 스켈레톤 구현(설계 결정 B-026 구조·B-027 직접접근 차단 흡수). 계약 무영향 확인(D-065, SEC-005 실체화).
- 게이트웨이 rate limit 429 등 엣지 오류는 SCG 기본 응답(본문 없음)이라 서비스 ErrorResponse envelope와 불일치.
  계약에 게이트웨이 응답 명세가 없어 결정이 필요하다.

## 안건 1: 엣지 오류 응답 포맷 (계약 영향 — 프론트 의존)
- 선택지 A(추천): 게이트웨이 엣지 오류(429 등)도 서비스 ErrorResponse envelope(`{code, message}`)로 통일. 게이트웨이에
  커스텀 에러 핸들러 추가, 계약에 엣지 오류 응답 명세 반영(6절 절차).
- 선택지 B: 계약 밖으로 두고 게이트웨이 기본 429(본문 없음). 프론트가 엣지/서비스 오류를 구분 처리.
- 추천 이유: 클라이언트 에러 처리 일관성(프론트 단일 포맷). 프론트 의존이라 백엔드 단독 결정 부적절 → 총괄+기획 판단.

## 안건 2: 후속 작업 순서 (D-074)
- (a) 관측성(Stage G): docker-compose.observability·Prometheus 스크래이핑에 게이트웨이(8000) 타깃 추가 — 후속 작업 프롬프트 필요.
- (b) 로컬 통합: docker-compose.local.yml에 게이트웨이 서비스 추가 — 후속.
- 진행 여부·순서 지정 요청(게이트웨이 스켈레톤 완료 후, 다음 도메인 전/후 어디에 둘지).

## 관련·회신
- 관련: B-026·B-027, D-068, 012. 게이트웨이 완료 보고는 빌드 그린 확인 후 별도 발신 예정.
- 회신: 필요 — 안건1(A/B), 안건2(순서).
- 신규 발번 ID: B-026(게이트웨이 멀티모듈 구조), B-027(직접접근 차단 메커니즘) — 마스터 인덱스 반영 요망.
