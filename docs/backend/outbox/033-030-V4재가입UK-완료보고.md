## 산출물·실물 (기획 erd 동기화용 — 074 [2] 반영 대상)

**Flyway 채번: `V4__user_natural_key_uk.sql`** (V3까지 소비 → V4. 탐색 방법: `db/migration` 디렉터리 목록 확인)

```sql
-- 1) 기존 단일 컬럼 UK 제거
ALTER TABLE user DROP INDEX uk_user_login_id;
ALTER TABLE user DROP INDEX uk_user_nickname;

-- 2) 활성 값만 담는 생성 컬럼
ALTER TABLE user
    ADD COLUMN login_id_active VARCHAR(50) GENERATED ALWAYS AS (IF(is_deleted, NULL, login_id)) STORED,
    ADD COLUMN nickname_active VARCHAR(30) GENERATED ALWAYS AS (IF(is_deleted, NULL, nickname)) STORED;

-- 3) 생성 컬럼에 UK
ALTER TABLE user
    ADD UNIQUE KEY uk_user_login_id_active (login_id_active),
    ADD UNIQUE KEY uk_user_nickname_active (nickname_active);
```
- 원본 `login_id`·`nickname` 컬럼 존치(UK만 이전). 타입·길이 원본 일치.
- **`public_id` 과적용 없음**(083 조건 2 준수) — 탐색 방법: V4 전문에 `public_id_active|publicIdActive` grep → 0건.
  V4 주석에 배제 사유(ULID 대리키라 삭제행 충돌 구조적 부재) 명기.

**리포지토리 정정**(D-081 동반 필수): `domain/member/UserRepository`
`existsByLoginIdAndIsDeletedFalse` · `existsByNicknameAndIsDeletedFalse` · `findByLoginIdAndIsDeletedFalse`.

**auth 정합**: `AuthService`가 B-024 이중 방어의 **제약명 파싱을 `uk_user_login_id_active`/`uk_user_nickname_active`
로 갱신**(80·83행). 이 갱신을 빠뜨렸으면 경쟁 케이스 409 매핑이 깨져 500이 났다 — 030 프롬프트 경고분이 유효했다.

**신규 테스트**: `test/integration/ReSignupIntegrationTest.java` — 재가입 성공 / 재가입 후 로그인 성공(다건 파손 부재).

## 신규 발번 — B-030 (UserRepository 소유 도메인 = member)
**B-028 의 열거 공백을 보정했다.** B-028 은 이동 대상 3건(`User`·`UserBalance`·`UserBalanceRepository`)과
존치 3건(`AuthService`·`TokenBundle`·`AuthErrorCode`)을 열거하면서 **`UserRepository` 를 어느 목록에도 넣지
않았다.** 그 결과 023 은 존치로 처리했고(023 완료 보고에 "auth 존치" 명시), 030 프롬프트는 내가
"`domain/member/UserRepository`(023 이동 후 위치)"로 **이동을 전제**해 써서 서로 어긋났다. Claude Code 가
현장에서 이동을 수행해 해소했다.

- 결과는 정합하다 — 리포지토리는 자기 엔티티와 동거해야 하고(`notice` 참조 구현 동일), `User` 만 member 로
  가고 `UserRepository` 가 auth 에 남으면 B-028 이 차단하려던 역방향 의존이 리포지토리 계층에서 재현된다.
- **다만 범위 처리로는 매끄럽지 않다** — 본래 023 몫이 030(V4) 커밋에 섞였다. 되돌릴 사유는 없어 그대로 둔다.
- 원인은 **B-028 발번 시 내가 대상 목록을 열거하며 `UserRepository` 를 빠뜨린 것**이다. 031 에서 자진 신고한
  참조자 수치 오류(import 기준 grep 한계)와 **같은 뿌리** — 열거·수량을 근거로 삼으면서 탐색 방법을 검증하지
  않은 것. D-086 이 이 유형을 정확히 겨눈다.

## 뿌리 점검 (D-085)
같은 원인이 다른 층에도 공백을 만들었나 — **그렇다. 다만 이미 조치됐다.**
이번 건의 원인은 "erd [1] 규약이 erd [4.1] 표에 미반영 → 표만 보고 구현하면 V3 가 나온다"(083 QA 뿌리 점검)

담당한다. **추가 공백 관측: 없음** — 탐색 방법: `user` 외 soft delete + 자연키 UK 테이블 존재 여부는
