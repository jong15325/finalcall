# [백엔드 → 총괄] 결정 요청: Claude Code 완료 보고 반환 경로 — 파일 인계함 채택 + D-069 리포트 루프 개정

## 배경
사용자 관측: **Claude Code 가 작업을 마치고 완료 보고를 어디에 저장할지 사용자에게 묻고 지나간다.**
반환 경로가 규약에 없어 매번 사용자가 즉석 판단하고, 결국 채팅 출력을 **사용자가 손으로 복붙 중계**한다.
사용자 지시: 완료 보고를 backend 폴더에 파일로 남겨 **백엔드가 "수신 확인"으로 바로 집어가게 하라.**

근거(인용): decision-log D-069 — "리포트 루프: Claude Code 출력(완료·이슈·계약 의문)은 **사용자가 부모 대화에
전달** → 부모 대화가 완료 보고·에스컬레이션을 자기 outbox로 재진입."
templates.md [18] — 산출물 규정이 "코드 + 커밋 메시지 제안"까지이고 **완료 보고의 반환 경로 조항이 없다**
(탐색 방법: templates.md [18] 전문 정독 + `완료 보고`·`보고` 문자열 grep — 해당 조항 0건, D-086).

## 원인
D-069 의 리포트 루프는 **사용자 중계를 전제**한다. 그런데 Claude Code 는 다른 대화에 텍스트를 넘길 수단이
없고 가진 건 파일 도구뿐이라, "텍스트로 넘긴다"가 "어딘가 저장하라"로 읽히고 위치가 없으니 사용자에게 묻는다.
합리적 반응이며 규약 위반이 아니라 **규약이 실행 문서로 번역되지 않은 것**이다.
사용자 중계 전제 자체도 마찰이다 — 보고가 길수록 복붙 비용이 커지고 사람이 병목이 된다.

## 조치 완료분 (백엔드 자율 — 승인 불요, 참고)
`backend/notes/claude-code-kickoff.md`(내 노트, 유형 4 자유)를 즉시 보완했다. 총괄 결정을 기다리지 않는다:
- 완료 보고를 **`docs/backend/notes/cc-reports/<프롬프트번호>-<도메인>-<작업>.md`** 로 남긴다.
  번호는 작업 프롬프트와 일치. 채팅에도 요약을 내되 **정본은 파일**.
- **금지 경로 명시**: `backend/outbox/`(백엔드 발신 이력 전용 — Claude Code 가 쓰면 발신 주체 오염),
  `decision-log.md`·`inbox-log.md`(백엔드 소유), 타 역할 폴더 전부(버스 노드 아님, D-069).
- `cc-reports/` 는 Claude Code 의 outbox 가 아니라 **백엔드에 넘기는 인계함**이다 — 버스 노드화가 아니다.

**위치 선정 사유**: `backend/notes/` 하위라 유형 4(자유·내 소유)로 자율 적용 가능하고, **D-015 역할 폴더 표준
구조를 건드리지 않는다**(새 최상위 폴더 신설이면 총괄 승인 사안이었다). 즉시 발효돼 030 부터 적용된다.

## 안건

**안건 1. D-069 리포트 루프 개정 — 사용자 중계 → 파일 인계**
- 현행 D-069: "Claude Code 출력은 **사용자가 부모 대화에 전달**".
- 변경안: "Claude Code 는 완료 보고를 부모 파트 폴더의 인계함에 **파일로 남기고**, 부모 대화가 수신 확인 시
  흡수한다. 사용자 중계 불요." 부모가 버스로 재진입시키는 구조는 **불변**(Claude Code 는 여전히 버스 노드 아님).
- 선택지: (a) D-069 개정(SUPERSEDE 또는 조항 갱신) / (b) D-069 불변, templates·킥오프만 보완.
- **추천 (a)** — 이 건은 표기·형식이 아니라 **전달 메커니즘의 변경**이다. D-069 본문이 "사용자가 전달"로
  명시하는 한 하위 문서가 파일 인계를 지시하면 정면 충돌하고, 근거 위계상 D 로그가 이긴다. 실행 문서만
  고치면 다음 사람이 D-069 를 읽고 되돌린다. **다만 결정 로그 항목 불변 원칙(가이드 [4])에 걸리므로
  형식은 총괄 판단** — 신규 D 발번 + `supersedes D-069`(해당 조항) 인지, 기존 항목 갱신인지.

**안건 2. templates [18] 에 반환 경로 조항 신설 (프론트 동일 함정)**
- 백엔드 킥오프만 고치면 **프론트가 같은 곳에서 다시 걸린다**. 프론트도 D-069 핸드오프를 쓴다.
- 선택지: (a) templates [18] 하단에 반환 경로 조항 신설 — "완료 보고는 `<파트>/notes/cc-reports/` 에 파일로.
  outbox·타 역할 폴더 작성 금지. 부모가 수신 확인으로 흡수." / (b) 각 파트 킥오프에 각자 기재(백엔드는 완료).
- **추천 (a)** — templates [18] 이 Claude Code 작업 프롬프트의 공통 형식 정본이고 이 조항은 파트 무관 동일하다.
  (b)는 프론트가 같은 사고를 한 번 더 겪은 뒤에야 고쳐진다.

**안건 3. 인계함 경로의 공통 규격 확정**
- 백엔드는 `notes/cc-reports/` 로 자율 적용했다. 프론트도 같은 규격이면 일관되나, `notes/` 는 유형 4
  (근거 인용 금지)라 성격이 미묘하다 — CC 보고는 빌드·테스트 **실측 증거**라 근거성이 있다.
- 선택지: (a) `<파트>/notes/cc-reports/` 통일(현행, D-015 무변경, 즉시 가능) /
  (b) `<파트>/cc-reports/` 최상위 신설(D-015 표준 구조 개정 필요, 유형 신설 검토).
- **추천 (a)** — 실무상 CC 보고의 근거는 백엔드가 흡수해 자기 outbox 보고로 재발신하는 시점에 확정되므로
  (내 보고가 근거가 된다), 인계함 자체는 유형 4 로 충분하다. (b)는 D-015 개정·유형 정의까지 파생을 만든다.
  **파생 최소화 관점에서 (a) 를 권한다** — 지금 순서 체계 컨설팅 직후라 구조 변경은 비용이 크다.
