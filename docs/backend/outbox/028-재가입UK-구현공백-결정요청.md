# [백엔드 → 총괄] 결정 요청: 재가입 UK 구현 공백 — V3 스키마가 erd 1절 규약 위반 (탈퇴·수정 유닛 선행)

## 요지
계약 v1.4 §2.5 "재가입: login_id·nickname 재사용 허용"은 **현재 구현으로 동작하지 않는다**. 스펙 공백이 아니라
**구현이 erd 규약을 못 지킨 상태**다. 탈퇴·프로필 수정 두 유닛의 공통 선행이라 착수 전 올린다.

## 현행 (근거 위계상 erd = 확정 스펙)
erd 1절 규약:
> soft delete: `is_deleted`(bool) + `deleted_at`. **soft delete 테이블의 자연키 유니크는 삭제 식별 컬럼을 포함**(삭제행-신규행 충돌 회피).

domain-spec §6.1·api-contract §2.5의 재가입 허용은 **이 규약이 지켜졌다는 전제** 위에 서 있다
(§6.1 인용: "자연키 유니크가 삭제 식별 컬럼을 포함해(erd 1절 규약) 탈퇴행이 신규 가입을 막지 않으며").

그러나 V3 실물(`V3__user_and_balance.sql`):
```
UNIQUE KEY uk_user_login_id (login_id),
UNIQUE KEY uk_user_nickname (nickname)
```
삭제 식별 컬럼이 없다. **erd 1절 위반**이다. auth 구현 시점엔 탈퇴 스펙이 아예 없었으므로(022가 발견한 그 공백)
누락 경위는 자연스럽다 — 비난 사안이 아니라 스펙 공백의 2차 파생이다.

## 파급 3건 (실측)
1. **재가입 차단**: 탈퇴자 login_id로 신규 가입 → UK 위반 → `AUTH_001`. 계약 §2.5 재가입 허용 위반.
2. **중복 오판정**: `UserRepository.existsByLoginId`·`existsByNickname`이 탈퇴행까지 센다(필터 없음).
   → 탈퇴자가 점유한 nickname을 `PATCH /me`에서 `MEMBER_001`(409)로 잘못 거부. **프로필 수정 유닛도 영향**.
3. **로그인 파손(재가입 성사 시)**: `findByLoginId`가 `Optional<User>` 반환인데, 재가입이 허용되면 동일 login_id에
   탈퇴행 + 신규행이 공존 → 다건 결과 → `IncorrectResultSizeDataAccessException`. 현재는 1번이 재가입을
   막고 있어 잠복 상태다. **UK만 고치고 리포지토리를 안 고치면 로그인이 깨진다** — 순서 주의.

즉 auth(G4-1 PASS)에 **잠복 결함**이 있다. 지금은 재가입 경로가 막혀 있어 발현하지 않는다.

## 변경안 — UK 재구성 방식 (추천: c)
MySQL UNIQUE의 NULL 취급 때문에 "삭제 식별 컬럼을 포함"의 순진한 해석이 함정이다.

- (a) `UNIQUE (login_id, deleted_at)`, active는 `deleted_at=NULL` — **채택 불가**. MySQL은 NULL을 서로 다른 값으로
  취급해 **활성 중복이 뚫린다**(같은 login_id 활성 행 N개 허용). erd 1절의 문자적 해석이지만 규약 의도(활성 유일성
  보존)를 정면으로 깬다. 가장 위험한 선택지라 명시적으로 기각한다.
- (b) `UNIQUE (login_id, is_deleted)` — 활성 유일성은 지키나 **탈퇴행이 login_id당 1개로 제한**된다.
  가입→탈퇴→재가입→재탈퇴 시 충돌. 이력 보존(§6.1)과 상충.
- (c) **생성 컬럼 + UK** — 추천:
  ```sql
  login_id_active VARCHAR(50) GENERATED ALWAYS AS (IF(is_deleted, NULL, login_id)) STORED,
  UNIQUE KEY uk_user_login_id_active (login_id_active)
  ```
  활성 행만 값을 갖고(유일성 보존), 탈퇴행은 NULL(다건 허용 → 재탈퇴 무제한). nickname 동일 적용.
  `deleted_at` 널 허용(erd §4.1 표) 유지, 센티넬 값 불요. MySQL 8.0 지원 확인됨.
- (d) 애플리케이션 레벨 검사만(UK 제거) — B-024 이중 방어(TOCTOU 안전망) 포기라 기각.

## 영향 범위
- **백엔드**: V4 마이그레이션 + `UserRepository` 파생 쿼리 정정(`existsBy...AndIsDeletedFalse`,
  `findByLoginIdAndIsDeletedFalse`) + auth 회귀 테스트. 탈퇴·수정 유닛의 **선행**.
- **기획(erd 소유)**: (c) 채택 시 erd §4.1 `user` 표에 `login_id_active`·`nickname_active` 생성 컬럼과
  UK 구성이 드러나야 정합(B-012 erd §6 정정 선례처럼 동기화 필요). **erd 변경이라 내 자율 범위를 넘는다.**
- **QA**: auth 재가입·중복 시나리오 신규(현재 미커버 — G4-1 PASS 범위에 재가입이 없었다).
- **계약**: 변경 불요. §2.5 재가입 조항은 그대로 옳고, 구현이 따라가는 것이다.

## 안건
1. **UK 재구성 방식**: (c) 생성 컬럼 채택 승인? — 추천 (c). 근거는 위 (a) 활성 중복 관통·(b) 재탈퇴 충돌.
2. **erd §4.1 정합 주체**: (c)는 컬럼 추가라 erd 표 갱신이 필요하다. 기획 지시 요망(B-012 선례 = 백엔드
   실물 → 기획 반영). 백엔드가 V4 채번 후 정보 공유로 동기화하는 방식이면 그대로 진행하겠다.
3. **처리 순서**: 이 선행(V4+리포지토리)을 (a) 별도 단위로 먼저 실행 후 탈퇴·수정 착수 / (b) 탈퇴 유닛에 포함.
   추천 (a) — auth 잠복 결함 수정이라 member 유닛과 성격·리스크가 다르고, 단독 커밋·회귀 테스트가 명확하다.
4. **auth 잠복 결함 취급**: G4-1 PASS 후 발견이다. QA 결함(defects) 등재 대상인지, 아니면 계약 v1.4로 비로소
   요구가 생긴 것이니 신규 작업으로 볼지 총괄 판단 요망. (내 견해: 후자 — v1.3까지는 재가입 요구 자체가
   없었으므로 당시 구현은 결함이 아니었다. 다만 erd 1절 규약 위반은 v1.3 시점에도 성립하므로 애매하다.)
