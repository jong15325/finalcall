# [백엔드 → 총괄] 결정 요청(계약 변경): §2 말미 전방 참조 미이행 — 회원 리소스 엔드포인트 공백

## 현행
api-contract v1.3 §2(인증) 말미 line 96:

> 주: 회원 프로필·잔액 조회 등 user 리소스 엔드포인트는 3절(후속)에서 기술.

그러나 §3은 "경매·고정가·입찰"이다. 전방 참조가 이행되지 않았다. 계약 전수 확인 결과:
- 명세 있음: `GET /api/v1/me/balance` (§4.4 화폐) — 응답 `{cashBalance, gameMoneyBalance, gameMoneyHeld, gameMoneyAvailable}`
- 명세 없음: 회원 프로필 조회 / 프로필 수정 / 탈퇴(soft delete) — URL·요청·응답·에러코드 전부 미정
- `/users` 는 §1.1 URL 규칙에 리소스명만 등장(엔드포인트 정의 없음)

## 변경안
§2 이후에 회원 리소스 절을 신설(가칭 §2.5 또는 §4.x 편입 — 위치는 기획 판단)하고 아래를 명세한다.
백엔드는 임의 설계하지 않고 확정 명세를 기다린다.

명세 필요 항목:
1. 프로필 조회 — URL(`GET /api/v1/me` vs `/users/{publicId}` 타인 조회 포함 여부), 응답 필드(nickname·publicId·createdAt·isAdmin 노출 범위)
2. 프로필 수정 — 수정 가능 필드(nickname 한정 여부, 비밀번호 변경 포함 여부), 메서드(PATCH/PUT), 중복 nickname 409 코드
3. 탈퇴 — URL·메서드(`DELETE /api/v1/me`), 응답(204 예상), refresh 세션 폐기 동반 여부(B-018 연계), 재가입·식별자 정책
4. 에러코드 — `MEMBER_NNN` 신설 여부(§5 표 등재)

## 사유
066이 지정한 착수 범위("프로필 조회·수정, 탈퇴 등 계약 §2 이후 회원 관련 조항")가 계약에 실재하지 않아
착수 근거가 없다. 발견 경위 = 066 착수 지시 후 확정 스펙 정독 중.

백엔드가 임의 설계하면 (a) 확정 스펙 아닌 코드가 사실상 계약이 되고(D-028 "먼저 구현한 쪽이 기준이 되지
않는다" 위반), (b) 프론트·QA가 같은 계약을 병렬 의존하는 전제가 깨진다. 6절 절차로 올린다.

## 영향 범위
- 백엔드: member 도메인 중 프로필·탈퇴 유닛 착수 불가(대기). 잔액 조회(§4.4 명세분)·게이트웨이 핸들러(065)는 영향 없이 병행 진행.
- 프론트: 마이페이지 계열 화면의 API 계약 부재(screen-spec 정합 확인 필요) — 기획(P) 조율 대상.
- QA: member 시나리오 설계는 계약 확정 후.

## 부수 확인 요청 (계약 아님, 참고)
066 "balance 엔티티·리포지토리 착수"는 이미 실재한다 — auth 도메인이 V3(`user_and_balance`)와 함께
`domain/auth/User.java`·`UserBalance.java`·`UserBalanceRepository.java`를 생성 완료. 따라서 실작업은 신규
생성이 아니라 member 도메인 재배치 + 조회 API 추가다(구현 기법이라 백엔드 자율, B 발번 예정).
또한 `money_hold`는 erd상 `bid_id UK FK→bid`라 bid 테이블 선행이 필요 → 066의 "홀드/차감 구조적 골격"은
`user_balance.game_money_held` 기반 가용 계산·원자적 갱신 골격으로 한정 해석했다. 이견 있으면 회신 바람.
